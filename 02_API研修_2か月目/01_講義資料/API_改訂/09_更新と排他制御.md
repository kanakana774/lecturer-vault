# 更新と排他制御

> [!abstract] この章が終わったら
> - `version`（更新回数）が**何のためにあるのか**を説明できる
> - 同じデータを 2 人が同時に更新すると**何が困るのか**を説明できる
> - **楽観ロック**を実装できる
> - 「確認してから実行する」書き方に潜む**隙**に、自分で気づけるようになる

この章は更新（PUT）を扱います。削除（DELETE）も考え方は同じです（§9）。

---

## 1. 作るもの

```
PUT http://localhost:8080/sports/1
```

```json
{
  "name": "フットサル",
  "playerCount": 5,
  "version": 0
}
```

| 場合 | ステータス |
| :--- | :--- |
| 更新できた | **204 No Content**（ボディなし） |
| 入力に誤りがある（`version` が無い、など） | 400 |
| その ID が無い | 404 |
| **ほかの人が先に更新していた** | **409 Conflict** |

tag の更新（`PUT /tags/{tagId}`）も、API 設計書ではこの 4 つです。
最後の **409** が、この章の中心です。

---

## 2. `version` の正体

POST から毎回入れてきた `version` は、**そのデータが何回更新されたか**を数えるカラムです。

- 登録したときは **0**
- 更新するたびに **1 増える**
- 更新するときは、**クライアントが「自分が見たときの `version`」を一緒に送ってくる**

```
GET /sports/1   → {"sportId":1, "name":"サッカー", ..., "version":0}   ← この 0 を覚えておく
PUT /sports/1   ← {"name":"フットサル", ..., "version":0}              ← 覚えておいた 0 を送る
```

なぜ送らせるのか。それが次の節です。

---

## 3. 同時に更新されると、何が困るか

A さんと B さんが、同じスポーツ（`version` 0）をほぼ同時に編集します。

| # | A さん | B さん | DB |
| :--- | :--- | :--- | :--- |
| 1 | 画面を開く（サッカー／11 人） | | サッカー／11 人 |
| 2 | | 画面を開く（サッカー／11 人） | |
| 3 | 名前を「サッカーA」にして保存 | | サッカーA／11 人 |
| 4 | | **A さんの変更を知らないまま**、人数を 7 にして保存 | **サッカー／7 人** |

B さんが保存した時点で、**A さんの変更が消えました。** B さんは古い画面を見たまま、全部を上書きしたからです。
これを**更新消失**（Lost Update）と言います。

![[98_作図_楽観ロックの具体例.excalidraw|700]]

B さんに「**先に A さんが更新しました。最新を読み込み直してください**」と伝えられれば、この事故は防げます。
そのための仕組みを**排他制御**と言います。

---

## 4. 排他制御の 2 つの考え方

| | 悲観ロック | 楽観ロック |
| :--- | :--- | :--- |
| 考え方 | 「どうせ誰かとぶつかる」と考え、**読んだ時点で鍵をかける**。他の人は待たされる | 「めったにぶつからない」と考え、鍵はかけない。**更新するときに、誰かが先に更新していないかを確かめる** |
| 向いている場面 | ぶつかることが多く、絶対に失敗できない処理（座席予約など） | 画面を開いてから保存するまで時間がかかる処理（編集画面など） |

この課題では**楽観ロック**を使います。確かめるために使うのが `version` です。

- クライアントが送ってきた `version` が、**DB の今の `version` と同じ** → 誰も更新していない → 更新してよい
- **違う** → 誰かが先に更新した → 409 を返す

§3 の例なら、A さんの保存で DB は `version` 1 になります。B さんが送ってくるのは 0 なので、B さんは 409 になります。

## 5. まず、素直に書いてみる

§4 の説明をそのままコードにすると、こうなります。

```java
public void update(SportEntity sportEntity) {
    // ① 今のデータを取ってくる
    SportEntity latest = sportMapper.selectById(sportEntity.getSportId());
    if (Objects.isNull(latest)) {
        throw new NotFoundException(ErrorCodes.NOT_FOUND_RESOURCE);
    }

    // ② version を比べる
    if (!Objects.equals(latest.getVersion(), sportEntity.getVersion())) {
        throw new OptimisticLockException(ErrorCodes.OPTIMISTIC_LOCK);
    }

    // ③ 更新する
    sportMapper.update(sportEntity);
}
```

```xml
<update id="update" parameterType="jp.aevic.todo.entity.sport.SportEntity">
    UPDATE SPORT
    SET
        NAME = #{name},
        PLAYER_COUNT = #{playerCount},
        VERSION = VERSION + 1
    WHERE
        SPORT_ID = #{sportId}
</update>
```

§3 の手順で試すと、B さんにはちゃんと 409 が返ります。

> [!question] このコードで、更新消失は本当に防げているでしょうか
> §3 では、A さんが保存してから B さんが保存しました。
> **2 人がまったく同じタイミングで保存したら**、どうなるでしょう。

## 6. 2 つのリクエストを、同じところで止めてみる

講義では、デバッガで実際に確かめます。

### 6-1. 手順

1. ③ の `sportMapper.update(...)` の行に**ブレークポイント**を置き、デバッグモードで起動する
2. Postman で **A** のリクエスト（`version` 0、名前を「サッカーA」）を送る → ③ で止まる
3. 止めたまま、別のタブから **B** のリクエスト（`version` 0、名前を「サッカーB」、人数を 7）を送る → B も ③ で止まる
4. A を進める → B を進める

### 6-2. 結果

| | ステータス |
| :--- | :--- |
| A | **204** |
| B | **204** |

```
 sport_id |   name    | player_count | version
----------+-----------+--------------+---------
        1 | サッカーB |            7 |       2
```

**2 人とも成功しました。** A さんの「サッカーA」は残っていません。**更新消失が起きています。**

### 6-3. 何が起きたのか

| 時点 | A | B | DB の `version` |
| :--- | :--- | :--- | :--- |
| ① ② | 取ってきて比べる：0 = 0 で**通過** | | 0 |
| ① ② | | 取ってきて比べる：0 = 0 で**通過** | 0 |
| ③ | 更新する | | 1 |
| ③ | | 更新する（**A の変更を上書き**） | 2 |

B が ② で比べたときは、まだ A は更新していませんでした。だから B は通過できました。
**確かめた時点では正しかった。でも、使う時点ではもう古かった。**

この隙を **TOCTOU**（Time Of Check to Time Of Use：確かめた時と使う時のズレ）と言います。
「**確かめてから、実行する**」という形の処理には、いつもこの隙が付いて回ります。

> [!question] 考えてみよう
> ② と ③ の間に、ほかのリクエストが割り込めてしまうのが原因でした。
> - 割り込ませないには、どうすればいいでしょう
> - 「確かめる」と「更新する」を、**別々にやらずに済む**方法はないでしょうか

## 7. 確かめるのと更新するのを、1 つの SQL でやる

答えの 1 つは、**`version` の比較を UPDATE 文の条件に入れる**ことです。

```xml
<update id="update" parameterType="jp.aevic.todo.entity.sport.SportEntity">
    UPDATE SPORT
    SET
        NAME = #{name},
        PLAYER_COUNT = #{playerCount},
        VERSION = VERSION + 1
    WHERE
        SPORT_ID = #{sportId}
        AND VERSION = #{version}
</update>
```

Mapper の戻り値を `int` にすると、**更新した件数**が返ります。

```java
/**
 * 更新回数が一致するときだけ更新する
 *
 * @param sportEntity 更新する内容
 * @return 更新した件数
 */
int update(SportEntity sportEntity);
```

```java
public void update(SportEntity sportEntity) {
    // その ID が無ければ 404
    if (Objects.isNull(sportMapper.selectById(sportEntity.getSportId()))) {
        throw new NotFoundException(ErrorCodes.NOT_FOUND_RESOURCE);
    }

    // version が一致したときだけ更新される。0 件なら、誰かが先に更新していた
    int updatedCount = sportMapper.update(sportEntity);
    if (updatedCount == 0) {
        throw new OptimisticLockException(ErrorCodes.OPTIMISTIC_LOCK);
    }
}
```

「比べる」と「更新する」を DB に**まとめて**頼むので、間に割り込まれる隙がありません。
同じ行を 2 つの UPDATE が同時に更新しようとすると、DB は片方を待たせます。
待たされた側は、先の更新が終わってから `WHERE` をもう一度確かめます。そのときには `version` がもう 1 なので、0 件になります。

§6 と同じ手順で、2 つのリクエストを止めて進めると、こうなります。

| | ステータス |
| :--- | :--- |
| A | **204** |
| B | **409** |

```
 sport_id |   name    | player_count | version
----------+-----------+--------------+---------
        1 | サッカーA |           11 |       1
```

> [!note]- 409 のときに返るボディ
> ```json
> {"title":"CONFLICT","status":409,"code":"conflict.optimistic","message":"The request could not be processed because of conflict in the request."}
> ```

## 8. Controller と Form

### 8-1. Controller

```java
/**
 * スポーツの更新
 *
 * @param sportId 更新するスポーツのID
 * @param sportUpdateForm 更新内容を詰めたForm
 * @return 204 No Content
 */
@PutMapping(path = "/{sportId}")
public ResponseEntity<Void> update(@PathVariable Integer sportId,
                                   @RequestBody @Validated SportUpdateForm sportUpdateForm) {
    SportEntity sportEntity = new SportEntity();
    sportEntity.setSportId(sportId);
    sportEntity.setName(sportUpdateForm.getName());
    sportEntity.setPlayerCount(sportUpdateForm.getPlayerCount());
    sportEntity.setVersion(sportUpdateForm.getVersion());

    sportService.update(sportEntity);
    return ResponseEntity.noContent().build();
}
```

- パスパラメータ（どれを更新するか）と、リクエストボディ（どう更新するか）を**両方**受け取ります
- 返すのは **204**。更新後のデータは返しません

### 8-2. Form

```java
public class SportUpdateForm {
    @NotBlank
    @Size(max = 20)
    private String name;

    @NotNull
    private Integer playerCount;

    // 更新回数
    @NotNull
    private Integer version;

    // getter / setter は省略
}
```

> ⚠️ **`version` は必ず `Integer` で受ける**
> `int` だと、`version` を送ってこなかったリクエストが **0 として通ります**（`07_POST処理を作ってみよう` §3）。
> まだ 1 度も更新されていないデータは `version` が 0 なので、**`version` を付けずに送るだけで誰でも上書きできる**ことになります。
> 楽観ロックそのものが効かなくなります。

---

## 9. 削除も同じ

削除（`DELETE /sports/{sportId}`）も、ボディで `version` を受け取ります。

```xml
<delete id="delete">
    DELETE FROM SPORT
    WHERE
        SPORT_ID = #{sportId}
        AND VERSION = #{version}
</delete>
```

**消した件数が 0 件なら 409** です。

## 10. それでも残る隙

§7 の Service は、最初に「その ID があるか」を確かめています（なければ 404）。
これも「**確かめてから、実行する**」形です。

> [!question] 考えてみよう
> 存在を確かめたあと、UPDATE を実行するまでの間に、**別のリクエストがそのデータを削除した**としたら？
> - UPDATE は何件になるでしょう
> - クライアントに返るのは 404 と 409 のどちらでしょう。それは正しいでしょうか
> - 正しく返すには、どう書けばいいでしょう。完全に塞ぐことはできるでしょうか
>
> 答えは 1 つではありません。考えたことを講師に話してみてください。

## 11. まとめ

| | 書くこと |
| :--- | :--- |
| Form | `version` を **`Integer`** で受け取る。`@NotNull` |
| Controller | パスパラメータとボディの両方を受け取り、**204** を返す |
| Service | 存在しなければ 404。**更新件数が 0 件なら 409** |
| Mapper | `WHERE ... AND VERSION = #{version}` で**確かめると同時に更新する**。`VERSION = VERSION + 1` で増やす。戻り値は `int` |

**「確かめてから、実行する」には、間に隙がある。** 処理を書くときは、確かめた内容が実行する時点でもまだ正しいかを疑ってください。
