#### 2. 起動する

DBを作成したら、クローンしたbatchプロジェクトで `mvn spring-boot:run` を実行してください。

- DBには、API研修で作った `todo` ユーザー（パスワード `todo`）で接続します（`application.properties`）
- **起動するたびにジョブが1回実行され、終わるとアプリも終了します。** API のように起動したまま待ち受けるわけではありません
- ログの最後のほうに次の行が出れば成功です。まだ何も編集していない状態でも `COMPLETED` になります（Writer が何も書かないだけです）

```
Job: [SimpleJob: [name=aggregateJob]] completed with the following parameters: [...] and the following status: [COMPLETED]
```

#### 3. 自動で作られるものを確認する

初回起動時に、`batch` DB に次のテーブルが作られます。

| テーブル | 中身 |
| :--- | :--- |
| `T_SCORE` | ゲームのプレイ履歴。1回遊ぶと1件 |
| `T_GAME_HISTORY` | プレイ履歴の日ごとの集計。**このテーブルに書き込むのが課題** |
| `BATCH_` で始まるテーブル | Spring Batch が実行の記録を書き込むテーブル（講義資料 2-2 の JobRepository） |

**`T_SCORE` のテストデータ（6,000件）は、初回起動時に1回だけ作られます。** 中身は、起動した日の**前後1か月（前後30日）**のプレイ履歴です。

- 2回目以降の起動では、データは変わりません。何度起動しても同じデータで確認できます
- 未来の日付の履歴も入っていますが、集計するのは「前日」と「前日まで」なので影響はありません
- ⚠️ 作成から1か月ほど経つと「前日」のデータが無くなります。そのときやデータを作り直したいときは、`batch` DB を削除して作り直し、もう一度起動してください

**`T_GAME_HISTORY` のうち、処理日が本日の行は、起動のたびに消えます。** 同じ日に何度流しても、前回の結果に足し込まれることはありません。

### テーブルの確認

課題で使う列は次のとおりです。pgAdmin で中身も見ておいてください。

**T_SCORE（プレイ履歴）**

| 列 | 意味 |
| :--- | :--- |
| `SCORE_ID` | 成績ID（主キー） |
| `USER_ID` | 遊んだユーザー |
| `INSERT_DATE` | 登録日時＝**プレイした日時**（日付と時刻） |
| `DELETE_FLG` | `'1'` なら論理削除済み、`'0'` なら有効 |

**T_GAME_HISTORY（日ごとの集計）**

| 列 | 意味 | NOT NULL |
| :--- | :--- | :--- |
| `PROCESSED_DAY` | 処理日（主キー）。1日1行 | ○ |
| `TODAY_PLAY_NUMBERS` | 前日のプレイ数（**Step1 で書く**） | ○ |
| `TOTAL_PLAY_NUMBERS` | 前日までの累計のプレイ数（Step2 で書く） | ○ |
| `INSERT_USER_ID` / `INSERT_DATE` | 登録したユーザー・日時 | ○ |
| `UPDATE_USER_ID` / `UPDATE_DATE` | 更新したユーザー・日時 | |
| `DELETE_FLG` | 削除フラグ（既定値 `'0'`） | ○ |
| `UPDATE_COUNT` | 更新回数 | ○ |

### 課題で作成するプログラムの内容
下記のプログラムが上記テーブルをどのように操作すれば作れそうか考えてみてください。

**前日のゲームのプレイ数と、前日までの累計のプレイ数を記録するjobの作成**

- **プレイ数**は `T_SCORE` の件数（1回遊ぶと1件）です。同じユーザーが2回遊べば2と数えます（ユーザーの重複は除きません）
- 集計の対象は**バッチを起動した日の前日**です。0時を過ぎてから起動し、前日分を集計する想定です（講義資料 2-6 落とし穴1）
- 結果は `T_GAME_HISTORY` の、`PROCESSED_DAY`（処理日）が**起動した日**の行に書きます

ジョブは2つの Step でできています（`config/BatchConfig.java`）。

- step1（chunk）
	- **Reader**で、`T_SCOREテーブル`（ゲームのプレイ履歴）を読み込む。←作成済み
	- **Processor**で、論理削除されておらず、かつ前日にプレイされた履歴だけに絞り込む。←**要編集**
		- 絞り込みの条件は Reader のSQLに書くほうが効率的ですが、この課題では Processor の練習のため、全件を読んで Processor で絞ります（対象外の件は `null` を返すと捨てられます）
	- **Writer**で、`T_GAME_HISTORYテーブル`（日ごとの集計）に、前日のプレイ数を `TODAY_PLAY_NUMBERS` として書き込む。←**要編集**
		- SQLを呼ぶ必要があるので、`mapperインタフェース`と`mapper.xml`の記述が必要。←**要編集**
- step2（tasklet）←作成済み
	- 前日までの累計のプレイ数を `TOTAL_PLAY_NUMBERS` として `T_GAME_HISTORYテーブル`に書き込む

#### 編集するファイル

Java は `src/main/java/com/example/batch/` の下、XML は `src/main/resources/` の下にあります。

| ファイル | やること |
| :--- | :--- |
| `chunk/CustomItemProcesser.java` | 対象外の件に `null` を返す |
| `chunk/CustomItemWriter.java` | 受け取った件数を `T_GAME_HISTORY` に書く |
| `mapper/TGameHistoryMapper.java` | Writer から呼ぶメソッドを追加する |
| `META-INF/mapper/TGameHistoryMapper.xml` | 上のメソッドに対応するSQLを書く |

それ以外のファイル（Reader・Tasklet・`BatchConfig` など）は編集しません。
ファイルに書いてあるコメントが処理の流れです。コメントの下に処理を書いていってください。

#### 取り組むときのポイント

**Processor**
- `INSERT_DATE` は日時（`Timestamp`）です。「前日かどうか」を比べるには、日付（`LocalDate`）にそろえてから比べます
- 前日は「バッチを起動した日の前日」です。データの中の日付ではなく、実行した日を基準にします

**Writer**
- ⚠️ **Writer はチャンク（100件）ごとに何回も呼ばれます。** 1回の呼び出しで前日分の全件が来るわけではありません（講義資料 4章）。1回目の呼び出しと2回目以降でやることが違います
	- 当日の行がまだ無ければ → 行を登録する（`INSERT`）
	- 既にあれば → 今回のチャンクの件数を、前回までの件数に**足す**（`UPDATE`）。上書きすると最後のチャンクの件数しか残りません
- 登録するときは、NOT NULL の列（上の表の ○）にすべて値を入れる必要があります。`TOTAL_PLAY_NUMBERS` は Step2 で書くので、登録の時点では仮の値（0）で構いません
- Step2 は当日の行を `UPDATE` するだけなので、Step1 で行が作られていないと累計も書かれません

### 動作確認（答え合わせ）

起動して `COMPLETED` になったら、次の3つを確かめてください。

1. **`T_GAME_HISTORY` に処理日が本日の行ができているか**
2. **その数値が正しいか。** 同じ条件（論理削除されていない・前日にプレイされた）で `T_SCORE` を数える SQL を自分で書き、`TODAY_PLAY_NUMBERS` と比べます。`TOTAL_PLAY_NUMBERS` も同じように確かめます
3. **`BATCH_STEP_EXECUTION` の件数**（講義資料 4章）
	- `READ_COUNT` が 6000（全件読んでいる）
	- `FILTER_COUNT` が Processor で捨てた件数、`WRITE_COUNT` が Writer に渡った件数。`WRITE_COUNT` は `TODAY_PLAY_NUMBERS` と一致するはずです
	- `COMMIT_COUNT` が 61（チャンクサイズ100で6,000件）

数値が合わないときは、ログを見てください。MyBatis が実行した SQL とパラメータが `==>  Preparing:` `==> Parameters:` の行に出ています。
