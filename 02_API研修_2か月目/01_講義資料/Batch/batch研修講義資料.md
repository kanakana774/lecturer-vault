# 1. バッチ処理の基礎知識

## 1-1. バッチ処理とは
バッチ処理とは、一言で言えば「**あらかじめ定めた一定量のデータを、人の手を介さずに一括（Batch）で処理する方式**」のことです。

Web API が「ユーザーのリクエストにその場で応答する」のに対し、バッチ処理は「決まったタイミングで、溜まったデータを後からまとめて処理する」という違いがあります。
郵便に例えると、Web API は電話（その場でやり取りが完結）、バッチ処理はポストの集荷（決まった時刻にまとめて回収し、まとめて配る）です。

### Web API（オンライン処理）との比較

| 特徴 | Web API（オンライン処理） | バッチ処理 |
| :--- | :--- | :--- |
| **開始のきっかけ** | ユーザーの操作（リクエスト） | スケジュール（時間）や特定条件 |
| **処理単位** | 1リクエスト（少量のデータ） | 大量データ（数万〜数百万件など） |
| **応答性** | リアルタイム（即時性が必要） | 非リアルタイム（完了まで時間がかかる） |
| **ユーザーとの対話** | あり（UIがある） | なし（バックグラウンドで完結） |

## 1-2. 特徴とメリット・デメリット

### 特徴とメリット
1.  **まとめて処理するので効率がよい**
    *   1件ごとにその都度処理するより、DBへの往復やコミットの回数を減らせます。どう「まとめる」かは 2-3 のチャンクで扱います。
2.  **決まったタイミングで自動実行される**
    *   「毎日24時」「毎月月末」「特定のファイルが置かれた時」など、決められたルールに従って起動します。手動操作が要らないので、集計やバックアップのような定型業務を人的ミスなく実行できます。
3.  **負荷の高い処理を空いている時間に回せる**
    *   即時性が求められない代わりに、利用者が少ない夜間にリソースを集中させて重い処理を実行できます。日中のレスポンスへの影響を抑えられます。

### デメリット
*   **データの鮮度（タイムラグ）**
    *   処理が完了するまで結果が反映されないため、「今現在の最新状態」が見られない期間が生じます。
*   **障害時の影響範囲が広い**
    *   大量のデータを扱うため、途中でエラーが起きると「どこまで終わったか」の把握や、やり直しに手間がかかります。そのため、失敗したところから**再開（リスタート）**できる仕組みが重視されます。

## 1-3. 主な利用シーン

Web API開発でも、以下のような機能が必要になったら「バッチ処理」の導入検討タイミングです。

*   **データ集計**: 前日の売上データを計算し、集計テーブルに保存する。
*   **レポート作成**: 月末にPDFの請求書を数万件一括で生成する。
*   **外部システム連携**: 外部サービスからCSVデータを取り込んだり、逆にデータを転送したりする（ETL処理）。
*   **一括通知**: 期限が近いユーザーに対して、プッシュ通知やメールを一斉送信する。
*   **クリーニング**: 保存期間を過ぎた古いログデータや一時ファイルを削除する。

# 2. 実装の話（Spring Batchとスケジューラ）

## 2-1. Spring Batchとは
Spring Batchは、Spring Frameworkの系譜でバッチ処理を開発するためのフレームワークです。
Web API開発で使う Dependency Injection (DI) といった Spring Boot の恩恵を、そのままバッチ開発に持ち込めます。

## 2-2. 主要な構成要素

[公式ドキュメント](https://spring.pleiades.io/spring-batch/reference/domain.html)
![[Pasted image 20260528160256.png]]

| コンポーネント | 役割 |
| :--- | :--- |
| **JobLauncher** | Jobを起動する役。Spring Batch 6 からは **JobOperator** に統合された。 |
| **Job** | バッチ処理の「全体」を定義するコンテナ。 |
| **Step** | Jobを構成する個々の「工程」。1つのJobに複数のStepを持てる。 |
| **JobRepository** | JobやStepの実行状態（成功・失敗・開始時刻・どこまで処理したか）を、DBのメタデータテーブルに読み書きする部品。 |

### 構造のイメージ
1. **JobLauncher**が「このJobを動かして」と命令する。
2. **Job**が実行され、その中の**Step**が順番に動く。
3. その経過や結果を **JobRepository** がDBに記録し続ける。これが「失敗したところから再開（リスタート）」の土台になります（2-6）。

## 2-3. Stepの2つの実装モデル
Spring Batchには、処理内容に応じて使い分ける2つのモデルがあります。

### 1. Chunk（チャンク）モデル【大量データ用】
大量のデータを一定の件数ごとに区切って処理するモデルです。この区切りを**チャンク**、1チャンクの件数を**チャンクサイズ**と呼びます（以下、チャンクサイズ100で説明します）。

*   **構成要素**:
    *   **ItemReader**: データを1件ずつ読み込む（DB、CSVファイルなど）。
    *   **ItemProcessor**: 読み込んだデータを1件ずつ加工する。**`null` を返すと、その件は捨てられて Writer に渡りません**（フィルタリングはこれで行います）。
    *   **ItemWriter**: チャンクサイズ分たまった件をまとめて受け取り、DB等に一括で書き込む。
*   **流れ**: Read と Process を100件分繰り返す → Write で100件まとめて書く → コミット。これを読むデータが無くなるまで繰り返します。
*   **特徴**:
    *   **メモリに優しい**: 100万件あっても、手元に持つのは100件分だけです。ただし Reader がDBから少しずつ取り出す作り（カーソルやページング）であることが前提で、最初に全件を List に読み込む Reader では効果がありません。
    *   **途中までを確定できる**: 100件ごとにコミットするため、途中でエラーが起きても、それまでにコミットしたチャンクは完了済みとして残ります。
*   **用途**: 大規模なDB更新、ファイル取り込みなど。

下の図は TERASOLUNA のサンプルを描き直したものなので、部品名（`MyBatisCursorItemReader` など）とテーブル名はそのサンプルのものです。1回の Write とコミットが1つのトランザクション（Framework Transaction）に入っていることを確認してください。

![[チャンクモデルの流れ.excalidraw]]


### 2. Tasklet（タスクレット）モデル【単発処理用】
「1つのメソッド（`execute()`）の中に処理を書く」シンプルなモデルです。

*   **特徴**:
    *   自由度が高い。
    *   `execute()` を1回呼ぶごとに1トランザクション。`RepeatStatus.FINISHED` を返せば終わり、`CONTINUABLE` を返すと再度呼ばれます。単発の処理なら、結果として処理全体が1トランザクションになります。
*   **用途**: ファイルの削除、シェルスクリプトの実行、SQLを1つ発行するだけの処理など。


## 2-4. どちらのモデルを使うべきか？

| 比較項目 | Chunkモデル | Taskletモデル |
| :--- | :--- | :--- |
| **得意なこと** | 大量データの繰り返し処理 | シンプルな1回限りの処理 |
| **メモリ効率** | 良い（小分けにするため） | 実装次第（一気に読み込むと危ない） |
| **実装の複雑さ** | やや高い（3つの部品を作るため） | 低い（1つのクラスで完結） |
| **リスタート** | 途中から再開できる | 途中の位置を自分で保存しない限り、最初からやり直し |
| **例** | 会員全員へのポイント付与、全商品の在庫同期、大量のログ解析 | 中間テーブルの削除（TRUNCATE）、ファイル1つの転送、完了通知 |

**選定基準：**
- 処理対象が「大量のリスト」で、1件ごとに独立した処理（計算や変換）があるなら **Chunkモデル**。
- SQLを1発発行して終わり、ファイルを1つ動かして終わり、のように途中で止まっても最初からやり直せば済む処理なら **Taskletモデル**。


## 2-5. JobParameters（ジョブ・パラメータ）
APIの「クエリパラメータ」や「リクエストボディ」に相当します。
「何月何日のデータを処理するか」といった実行ごとの変数を、外部（起動引数）から渡す仕組みです。

JobParameters は、**「どの実行か」を見分ける鍵**でもあります。Spring Batch は「Job ＋ JobParameters」の組を1つの実行単位（JobInstance）として扱います。

| 同じ JobParameters で再度起動したとき | 結果 |
| :--- | :--- |
| 前回が**失敗**している | 前回の続きから再開する（リスタート） |
| 前回が**成功**している | 「完了済み」としてエラーになり、実行されない |

同じジョブを2回目に動かしたらエラーになった、というときはこれが原因です。実行ごとに日付などのパラメータを変えて起動します。

課題のプロジェクトでは、`JobStartupRunner` が起動した時刻（`time`）を JobParameters に入れています。起動するたびに別の実行になるので、何度でも流せます。その代わり、**失敗しても続きからの再開にはならず、毎回最初から**実行されます。


## 2-6. リスタートの仕組みと、やり直すときの落とし穴

APIは「失敗したらエラーを返して終わり」ですが、バッチは「失敗したところからやり直す」ことが求められます。

### 仕組み
Chunkモデルでは、チャンクをコミットするときに、同じトランザクションで **JobRepository にも「何件目まで読んだか」が記録されます**。
再実行すると、Reader は記録された件数を読み飛ばして続きから読みます。これが「前回の続きから再開できる」理由です。

件数を記録するのは Reader 自身です。Reader が `ItemStream` の3つのメソッドを持ち、Spring Batch がそれを呼び出します。

| メソッド | 呼ばれるとき | やること |
| :--- | :--- | :--- |
| `open` | Step の開始時 | 検索を実行する。再開時は、記録された件数を読み飛ばす |
| `update` | チャンクをコミットするとき | 「何件目まで読んだか」を記録する |
| `close` | Step の終了時 | カーソルなどを閉じる |

Spring Batch 付属の Reader（`JdbcCursorItemReader` など）は、3つとも実装済みです。課題の `CustomItemReader` のように付属の Reader を包んで自作するときは、⚠️ **3つとも中の Reader に委譲します。** `update` を委譲し忘れると件数が記録されず、再開しても最初から読み直します。

なお、再開できるのは**前回と同じ JobParameters で起動したとき**だけです（2-5）。

たとえばチャンクサイズ100で10万件を処理中、9万件目でエラーが起きた場合：
- **Chunkモデル**: 9万件目を含むチャンク（89,901〜90,000件目）はロールバックされます。JobRepository には「89,900件目までコミット完了」と記録されているため、エラー原因を除去して再実行すれば **89,901件目から再開**します。
- **Taskletモデルや自作のループ**: どこまで終わったかを自分で記録しない限り分かりません。最初からやり直すと、データが二重登録されるおそれがあります。

> [!note]- retry と restart は別の機能
> Spring Batch の **retry** は「失敗した1件をその場でもう一度試す」機能、**restart** は「失敗したジョブを後から続きで再開する」機能です。この資料で扱っているのは restart です。

### 落とし穴1：再検索しても同じ並びが返るとは限らない
Reader は再開時に**検索をやり直し**、前回の件数分を読み飛ばします。
そのため、初回と再開時で検索結果の中身や並び順が変わると、読み飛ばす位置がずれて、処理漏れや二重処理が起きます。

- ⚠️ **Reader のSQLには必ず `ORDER BY`（一意になる列まで含める）を付ける。** 付けないと、DBは毎回同じ順で返す保証がありません。
- 処理中に対象データが増減しないよう、取得条件で範囲を固定します。たとえば「0時を過ぎてから起動し、前日分だけを取得する」のように条件を付けるのが一般的です。
- 処理済みフラグを更新しながら「未処理のもの」を検索する作りも、再開時に件数がずれる原因になります。

### 落とし穴2：取り消せない処理を Writer に書かない
ロールバックで取り消せるのは**DBへの書き込みだけ**です。

⚠️ Writer の中でカード決済APIの呼び出しやメール送信のような外部への処理を行うと、コミット前に落ちたとき、DBは巻き戻っても外部への処理は済んだままになります。そのチャンクは再開時にもう一度処理されるので、**二重課金・二重送信**になります。
外部への処理は、DBに「依頼」を書くところまでをバッチで行い、実際の送信は別の仕組みに任せる（同じ依頼を2回受けても1回しか実行しないようにする）のが基本です。

### 落とし穴3：もう一度流すと二重に計上される
リスタートではなく、成功したジョブを**パラメータを変えてもう一度流す**こともあります。「データを直したので今日の集計をやり直したい」などです。
Writer はチャンクごとに呼ばれるので、集計値はチャンクごとに足し込んでいくことになります。ここで**前回の実行が残した値にまで足してしまう**と、同じ件数がもう一度足されて集計が倍になります。

何度流しても同じ結果になるように作ります。たとえば、ジョブの最初に集計の行を0に戻し（または消し）、そこから足し込みます。


## 2-7. スケジューラと役割分担

ジョブを「いつ起動するか」は Spring Batch ではなく、**スケジューラ**が担当します。JP1 / Airflow / Cron / Quartz などがあります。

具体的には下記のような役割があります。
- 毎晩 23:00 にジョブを起動する
- 前段階（注文締め処理など）が終わってから起動するよう、依存関係を設定する
- エラー発生時は Slack/メールに通知して運用者にエスカレーションする
- 再実行時は同じ Spring Batch ジョブを同じ JobParameters で起動し直す（リスタート機能の活用）

| フェーズ | 使うツール | 内容 |
| :--- | :--- | :--- |
| **ロジック実装** | **Spring Batch** | 「どう処理するか」を書く。ChunkやTaskletの実装。 |
| **実行管理** | **JP1 / Airflow / Cron / Quartz** | 「いつ・どの順番で実行するか」を決める。前工程（バックアップ等）との順番制御。 |

# 3. 実例で学ぶ：Spring Batchのジョブ構成

ここまでの部品を、1つの業務に当てはめてみます。

## 業務例：月額会員の請求データ作成と継続ボーナス付与ジョブ

**【要件】**
- 毎月1日の深夜に実行。
- 月額会員（サブスク）ユーザー全員について、今月分の請求データを作成し、継続特典のポイントを付与する。
- 完了後、今回のジョブで計上した売上の合計をCSV出力し、完了通知を送る。
- 実際のカード決済は、決済システムが請求データを見て行う（このジョブでは決済APIを呼ばない）。

## ジョブの全体像（Step構成）

ひとつの「Job」の中に、役割の異なる「Step」を組み合わせて構築します。

### Step1：請求データの作成とポイント付与（Chunkモデル）
**なぜChunkか？**：ユーザー数は数万人〜数百万人になる可能性があるため、一定人数ごとに確定させていくのが安全だからです。
- **ItemReader**: DBから「有効な月額会員」を、会員IDの順（`ORDER BY`）に1件ずつ読み込む。
- **ItemProcessor**: 
    - 会員プラン（ライト/プレミアム）に応じた料金を計算する。
    - 継続月数に応じた「ボーナスポイント」を計算する。
- **ItemWriter**: 
    - 請求データを請求テーブルに登録し、ユーザーのポイント残高を更新する。
    - 100件まとめてDBに書き込み、コミットする。

**なぜ Writer でカード決済をしないか？**：決済はロールバックで取り消せないため、途中で落ちて再開すると二重課金になるからです（2-6 落とし穴2）。

### Step2：売上集計CSVの作成（Taskletモデル）
**なぜTaskletか？**：DBの集計関数（`SUM`）で合計を出し、ファイルを1つ作るだけの「単発処理」だからです。
- 処理内容：今回のジョブで作成した請求データの合計金額をDBから集計し、管理用のCSVファイルに書き出す。

### Step3：運営への完了通知（Taskletモデル）
**なぜTaskletか？**：ループ処理ではなく、「メッセージを1回送る」という単一のアクションだからです。
- 処理内容：Slackやメール等で「○件の請求データを作成しました」と通知を送る。

**外部への送信なのに、ここでは送ってよいのはなぜか？**：落とし穴2で問題にしたのは、チャンクごとに何度も送られ、再開時に二重に送られることでした。完了通知はジョブの最後に1回送るだけで、万一2回届いても害がありません。決済のように2回実行されると困る処理とは違います。

# 4. 課題のコードの読み方

2章の部品が、課題のプロジェクトのどこにあるかを対応させます。

| 2章の部品 | 課題のコード | 見るところ |
| :--- | :--- | :--- |
| Job / Step の定義 | `config/BatchConfig.java` | `.start(Step1).next(Step2)` が Step の順番。`chunk(100, ...)` の100がチャンクサイズ |
| 起動役と JobParameters | `JobStartupRunner.java` | 起動時刻を JobParameters に入れて、毎回別の実行にしている（2-5） |
| ItemReader | `chunk/CustomItemReader.java` | `JdbcCursorItemReader`（カーソルで少しずつ読む Reader）を包んでいる。`open` / `update` / `close` は 2-6 の表のとおり |
| ItemProcessor | `chunk/CustomItemProcesser.java` | 対象外の件は `null` を返して捨てる（2-3） |
| ItemWriter | `chunk/CustomItemWriter.java` | 受け取るのは `Chunk`（Processor を通った件のまとまり）。**チャンクごとに呼ばれる**ので、1回の呼び出しで全件が来るわけではない |
| Tasklet | `tasklet/AggregateTasklet.java` | 件数は `COUNT(*)` でDBに数えさせている（全件をJavaに持ってこない） |
| JobRepository のメタデータ | `BATCH_` で始まるテーブル | 下記 |

## 動かしたら、メタデータテーブルを見る

JobRepository が記録した内容は、`BATCH_` で始まるテーブルで見られます。特に `BATCH_STEP_EXECUTION` を見ると、チャンクの動きを数字で確かめられます。

```sql
SELECT STEP_NAME, STATUS, READ_COUNT, FILTER_COUNT, WRITE_COUNT, COMMIT_COUNT
FROM BATCH_STEP_EXECUTION
ORDER BY STEP_EXECUTION_ID;
```

| 列 | 意味 |
| :--- | :--- |
| `READ_COUNT` | Reader が読んだ件数 |
| `FILTER_COUNT` | Processor が `null` を返して捨てた件数 |
| `WRITE_COUNT` | Writer に渡った件数（＝読んだ件数 − 捨てた件数） |
| `COMMIT_COUNT` | コミットした回数。チャンク1つにつき1回で、最後に「もう読むものが無い」と確かめた回も1回と数える（課題の6,000件・チャンクサイズ100なら61回） |

絞り込んだ後の件数は `WRITE_COUNT` に出ます。Processor の絞り込みが正しいかは、`WRITE_COUNT` と、同じ条件で数えたSQLの結果を比べれば確かめられます。
