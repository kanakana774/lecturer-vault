# トリガーと動的 SQL
## 〜勝手に動く仕組みと、実行時に組み立てる SQL〜

12章の最後の章です。ここまでは「自分が呼んだものが動く」話でした。この章では毛色の違う 2 つを扱います。

- **トリガー** … 誰も呼んでいないのに、`INSERT` / `UPDATE` / `DELETE` に反応して**勝手に動く**仕組み
- **動的 SQL** … テーブル名や列名が実行時に決まる場合に、**SQL を文字列として組み立てて実行する**仕組み

どちらも強力ですが、**どちらも「後から読む人を混乱させる」道具**です。使いどころと危険を合わせて押さえてください。

> **この資料の前提**
> - PostgreSQL 17 で動作確認しています。掲載しているエラーメッセージ・出力は**すべて実測**です。
> - 使用するテーブルは [[00_SQL研修/02_問題/08_結合から使用するテーブル|08_結合から使用するテーブル]] で作成したもの（8章以降と同じ）です。**この章だけ、変更履歴を残すための `inventory_logs` テーブルを新しく作ります**（§3）。
> - [[12-4_関数とプロシージャと例外処理|12-4]] の関数定義・`RAISE EXCEPTION`・`EXCEPTION` 句を前提にします。

---

## 1. トリガーとは何か

**トリガー**は、あるテーブルに対する `INSERT` / `UPDATE` / `DELETE` を検知して、**自動的に指定した関数を実行する**仕組みです。

用途は主に 3 つです。

1. **検証**（変な値が入らないようにする）
2. **補正**（値を自動で整える。空白の除去、更新日時の自動設定など）
3. **履歴**（誰がいつ何を変えたかを記録する）

作るものは 2 つあります。

| 作るもの | 役割 |
|:---|:---|
| **トリガー関数** | 実際の処理。戻り値の型は `trigger` |
| **トリガー** | 「どのテーブルの、どの操作の、いつ」その関数を呼ぶかの設定 |

### 1-1. トリガー関数の中で使える特別な変数

| 変数 | 中身 |
|:---|:---|
| `NEW` | これから書き込まれる行。`INSERT` と `UPDATE` で使える（`DELETE` では NULL） |
| `OLD` | 変更前の行。`UPDATE` と `DELETE` で使える（`INSERT` では NULL） |
| `TG_OP` | 何の操作か。`'INSERT'` / `'UPDATE'` / `'DELETE'` |

`NEW` と `OLD` は `%ROWTYPE` の変数と同じように **`NEW.列名`** で使えます（[[12-2_変数とSQLの実行|12-2]] §6）。

### 1-2. `BEFORE` と `AFTER`

トリガーを仕掛けるタイミングは 2 つあります。

| タイミング | 使いどころ | 戻り値 |
|:---|:---|:---|
| `BEFORE` | **書き込む前**。検証と補正 | `RETURN NEW` で書き込む。`RETURN NULL` にすると**その行の書き込みが取り消される** |
| `AFTER` | **書き込んだ後**。履歴の記録 | 無視されるので `RETURN NULL` でよい |

**値を変えたいなら `BEFORE`、記録したいなら `AFTER`** と覚えてください。

## 2. `BEFORE` トリガー：検証と補正

`reviews` テーブルに、次の 2 つを仕掛けます。

1. `rating` が 1〜5 の範囲外なら**エラーにする**
2. `comment` の前後の空白を**自動で取り除く**

```sql
CREATE OR REPLACE FUNCTION reviews_validate()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    -- ① 検証：範囲外ならエラー
    IF NEW.rating < 1 OR NEW.rating > 5 THEN
        RAISE EXCEPTION '評価は 1〜5 で指定してください（指定値: %）', NEW.rating
            USING HINT = '1 以上 5 以下の整数を指定してください。';
    END IF;

    -- ② 補正：前後の空白を除去
    NEW.comment := trim(NEW.comment);

    RETURN NEW;   -- ★ NEW を返すと、この内容で書き込まれる
END;
$$;

CREATE OR REPLACE TRIGGER reviews_before_save
    BEFORE INSERT OR UPDATE ON reviews
    FOR EACH ROW
    EXECUTE FUNCTION reviews_validate();
```

`FOR EACH ROW` は「**1 行ごとに呼ぶ**」という指定です。10 行を `UPDATE` すれば 10 回呼ばれます。

### 2-1. 【手を動かす】検証が効くか

範囲外の `rating = 7` を入れてみます。

```sql
BEGIN;
INSERT INTO reviews (review_id, product_id, customer_id, rating, comment, review_date)
VALUES (101, 5, 2, 7, 'すごい', CURRENT_DATE);
ROLLBACK;
```

```
BEGIN
ERROR:  評価は 1〜5 で指定してください（指定値: 7）
HINT:  1 以上 5 以下の整数を指定してください。
CONTEXT:  PL/pgSQL function reviews_validate() line 4 at RAISE
ROLLBACK
```

**`INSERT` 文しか書いていないのに、トリガー関数の中でエラーが起きています。** `CONTEXT:` に `reviews_validate()` と出ているので、原因がトリガーだと分かります。

### 2-2. 【手を動かす】補正が効くか

前後に空白を付けたコメントで入れてみます。

```sql
BEGIN;
INSERT INTO reviews (review_id, product_id, customer_id, rating, comment, review_date)
VALUES (101, 5, 2, 4, '   前後に空白があるコメント   ', CURRENT_DATE);

SELECT review_id, rating, '[' || comment || ']' AS comment_with_brackets
  FROM reviews WHERE review_id = 101;
ROLLBACK;
```

```
BEGIN
INSERT 0 1
 review_id | rating |   comment_with_brackets    
-----------+--------+----------------------------
       101 |      4 | [前後に空白があるコメント]
(1 row)
```

**空白が消えています。** 角かっこで囲んで表示しているのは、空白が残っているかを目で確かめるためです。

`NEW.comment := trim(NEW.comment);` のように **`BEFORE` トリガーで `NEW` を書き換えると、書き換えた内容が保存されます**。これが `BEFORE` の使い方です。

## 3. `AFTER` トリガー：変更履歴を残す

在庫が変わった記録を残します。**この章だけで使う追加テーブルです。**

```sql
DROP TABLE IF EXISTS inventory_logs;

CREATE TABLE inventory_logs (
    log_id       serial PRIMARY KEY,
    changed_at   timestamptz DEFAULT now(),
    operation    text,
    product_id   integer,
    warehouse_id integer,
    old_quantity integer,
    new_quantity integer
);
```

```sql
CREATE OR REPLACE FUNCTION inventory_log()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO inventory_logs (
        operation, product_id, warehouse_id, old_quantity, new_quantity
    ) VALUES (
        TG_OP,
        COALESCE(NEW.product_id,   OLD.product_id),
        COALESCE(NEW.warehouse_id, OLD.warehouse_id),
        OLD.stock_quantity,
        NEW.stock_quantity
    );

    RETURN NULL;   -- AFTER トリガーの戻り値は無視される
END;
$$;

CREATE OR REPLACE TRIGGER inventory_after_change
    AFTER INSERT OR UPDATE OR DELETE ON inventory
    FOR EACH ROW
    EXECUTE FUNCTION inventory_log();
```

`INSERT` のときは `OLD` が、`DELETE` のときは `NEW` が使えません。**そのまま `OLD.列名` と書くと NULL になります**（エラーにはなりません）。`product_id` のように「どちらの操作でも必要な値」は `COALESCE(NEW.…, OLD.…)` で拾います。

### 3-1. 【手を動かす】3 種類の操作を記録する

```sql
BEGIN;
UPDATE inventory SET stock_quantity = stock_quantity - 5 WHERE product_id = 1 AND warehouse_id = 1;
INSERT INTO inventory (product_id, warehouse_id, stock_quantity) VALUES (6, 2, 12);
DELETE FROM inventory WHERE product_id = 6 AND warehouse_id = 2;

SELECT operation, product_id, warehouse_id, old_quantity, new_quantity
  FROM inventory_logs ORDER BY log_id;
ROLLBACK;
```

```
BEGIN
UPDATE 1
INSERT 0 1
DELETE 1
 operation | product_id | warehouse_id | old_quantity | new_quantity 
-----------+------------+--------------+--------------+--------------
 UPDATE    |          1 |            1 |           50 |           45
 INSERT    |          6 |            2 |              |           12
 DELETE    |          6 |            2 |           12 |             
(3 rows)
```

**`INSERT` では `old_quantity` が空、`DELETE` では `new_quantity` が空**になっています。`TG_OP` で操作の種類も残っています。

`ROLLBACK` しているので、**ログも一緒に消えます**。トリガーの中の `INSERT` も同じトランザクションの中の変更なので、当然そうなります（[[12-4_関数とプロシージャと例外処理|12-4]] §9-2 と同じ理屈）。

## 4. 無駄な発火を抑える：`WHEN` 句

`FOR EACH ROW` は 1 行ごとに関数を呼びます。**「値が変わっていないのに `UPDATE` された」場合まで記録すると、ログが無意味に膨らみます。**

`WHEN` 句で条件を書くと、条件を満たす行だけトリガーが動きます。

```sql
CREATE OR REPLACE TRIGGER inventory_after_change
    AFTER UPDATE ON inventory
    FOR EACH ROW
    WHEN (OLD.stock_quantity IS DISTINCT FROM NEW.stock_quantity)
    EXECUTE FUNCTION inventory_log();
```

```sql
BEGIN;
-- 在庫数を変える更新（トリガーが動く）
UPDATE inventory SET stock_quantity = 45 WHERE product_id = 1 AND warehouse_id = 1;
-- 同じ値で更新（在庫数は変わらない＝トリガーは動かない）
UPDATE inventory SET stock_quantity = 45 WHERE product_id = 1 AND warehouse_id = 1;

SELECT count(*) AS log_count FROM inventory_logs;
ROLLBACK;
```

```
BEGIN
UPDATE 1
UPDATE 1
 log_count 
-----------
         1
(1 row)
```

**`UPDATE` は 2 回実行されたのに、ログは 1 件だけです。**

`IS DISTINCT FROM` は「値が違う」を NULL も含めて正しく判定する演算子です。`<>` だと、どちらかが NULL のときに結果が NULL になって条件を満たさなくなります。**トリガーの `WHEN` 句ではほぼ常に `IS DISTINCT FROM` を使います。**

## 5. トリガーの怖さ

便利ですが、**トリガーは実務でトラブルの原因になりやすい**仕組みです。理由を押さえておいてください。

1. **呼び出しがコードに現れない。**
   `INSERT INTO reviews …` と書いた人は、トリガーが動いていることを知りません。「なぜかコメントの空白が消える」「なぜかエラーになる」と悩むことになります。**エラーの `CONTEXT:` 行を見る習慣**が身についていないと、原因にたどり着けません。

2. **性能に影響する。**
   `FOR EACH ROW` は 1 行ごとに関数を呼びます。10 万行を更新すれば 10 万回です。

3. **連鎖する。**
   トリガーの中で別のテーブルを更新すれば、そのテーブルのトリガーも動きます。追いかけるのが難しくなります。

4. **調べる方法を知らないと存在に気づけない。**
   どのテーブルにどんなトリガーが付いているかは、psql なら `\d テーブル名` で確認できます（[[00_SQL研修/01_講義資料/99_補足_psqlコマンドチートシート|99_補足_psqlコマンドチートシート]]）。pgAdmin ならテーブルの下の Triggers を見ます。

**「アプリ側で書けることは、トリガーにしない」**が無難な判断です。トリガーが向いているのは、**アプリを経由しない更新まで確実に押さえたい**場合（監査ログ、更新日時の自動設定など）です。

## 6. 動的 SQL：SQL を組み立てて実行する

ここまで書いてきた SQL は、**書いた時点で形が決まっていました**。しかし「テーブル名を引数で受け取りたい」という場合、こう書くことはできません。

```sql
-- これは動かない（テーブル名は変数にできない）
SELECT count(*) FROM p_table_name;
```

テーブル名や列名を実行時に決めたいときは、**SQL を文字列として組み立てて `EXECUTE` で実行**します。

```sql
CREATE OR REPLACE FUNCTION table_row_count(p_table_name text)
RETURNS bigint
LANGUAGE plpgsql
AS $$
DECLARE
    v_count bigint;
BEGIN
    EXECUTE format('SELECT count(*) FROM %I', p_table_name) INTO v_count;
    RETURN v_count;
END;
$$;
```

```sql
SELECT table_row_count('customers') AS customers,
       table_row_count('products')  AS products,
       table_row_count('orders')    AS orders;
```

```
 customers | products | orders 
-----------+----------+--------
         9 |       13 |     13
(1 row)
```

- **`EXECUTE 文字列`** で、組み立てた SQL を実行します。
- 結果を受け取りたいときは **`EXECUTE … INTO 変数`** と書きます（`SELECT … INTO` と同じ形）。

存在しないテーブル名を渡すと、当然エラーになります。

```sql
SELECT table_row_count('no_such_table');
```

```
ERROR:  relation "no_such_table" does not exist
QUERY:  SELECT count(*) FROM no_such_table
CONTEXT:  PL/pgSQL function table_row_count(text) line 5 at EXECUTE
```

**`QUERY:` の行に、実際に組み立てられた SQL が出ます。** 動的 SQL のデバッグでは、ここを見るのが一番早いです。

### 6-1. `format()` の `%I` と `%L`

上の例で使った `format()` は、テンプレートに値を差し込む関数です。**差し込み方が 3 種類あり、使い分けが極めて重要**です。

| 指定子 | 意味 | 用途 |
|:---|:---|:---|
| `%I` | **識別子**（Identifier）として引用する | テーブル名・列名 |
| `%L` | **リテラル**（Literal）として引用する | 値 |
| `%s` | そのまま文字列として入れる | メッセージ組み立てのみ |

```sql
DO $$
DECLARE
    v_sql text;
BEGIN
    v_sql := format('SELECT count(*) FROM %I WHERE %I > %L', 'products', 'price', 500);
    RAISE NOTICE '組み立てたSQL: %', v_sql;
END;
$$;
```

```
NOTICE:  組み立てたSQL: SELECT count(*) FROM products WHERE price > '500'
```

`%L` が値を `'500'` と引用符で囲んでいることに注目してください。**`%L` は、値の中にシングルクォートが含まれていても正しくエスケープします。** これが次節の防御になります。

## 7. 【手を動かす】文字列連結は危険：SQL インジェクション

動的 SQL を `||` で連結して組み立てると、**引数に細工をされたときに、意図しない SQL が実行されます**。実際にやってみます。

### 7-1. 危険な書き方

```sql
CREATE OR REPLACE FUNCTION find_customer_unsafe(p_name text)
RETURNS TABLE (customer_id integer, name text)
LANGUAGE plpgsql
AS $$
BEGIN
    RETURN QUERY EXECUTE
        'SELECT customer_id, name::text FROM customers WHERE name = ''' || p_name || '''';
END;
$$;
```

普通に呼べば、期待どおり 1 件だけ返ります。

```sql
SELECT * FROM find_customer_unsafe('Alice');
```

```
 customer_id | name  
-------------+-------
           1 | Alice
(1 row)
```

では、引数にこう渡すとどうなるか。

```sql
SELECT * FROM find_customer_unsafe($x$Alice' OR '1'='1$x$);
```

```
 customer_id |  name   
-------------+---------
           1 | Alice
           2 | Bob
           3 | Charlie
           4 | Diana
           5 | Ellen
           6 | Grace
           7 | Hank
           8 | Ivy
           9 | Jack
(9 rows)
```

**全員のデータが出てしまいました。**

組み立てられた SQL はこうなっています。

```sql
SELECT customer_id, name::text FROM customers WHERE name = 'Alice' OR '1'='1'
```

引数に含めたシングルクォートが**文字列を途中で閉じてしまい**、その後ろが SQL として解釈されました。`'1'='1'` は常に真なので、`WHERE` が実質的に無効になっています。

これが **SQL インジェクション**です。今回は「見えてはいけないデータが見えた」だけですが、同じ仕組みで `DELETE` を差し込むこともできます。

> 💡 `$x$ … $x$` は [[12-1_PLpgSQLの基礎とDOブロック|12-1]] §3-2 のドル引用符です。シングルクォートを含む文字列をそのまま書くために使っています。

### 7-2. 安全な書き方：`USING` でバインドする

`EXECUTE` には **`USING`** を付けられます。SQL の中には `$1`, `$2` … と書いておき、値は `USING` で渡します。

```sql
CREATE OR REPLACE FUNCTION find_customer_safe(p_name text)
RETURNS TABLE (customer_id integer, name text)
LANGUAGE plpgsql
AS $$
BEGIN
    RETURN QUERY EXECUTE
        'SELECT customer_id, name::text FROM customers WHERE name = $1'
        USING p_name;
END;
$$;
```

普通に呼んだとき：

```sql
SELECT * FROM find_customer_safe('Alice');
```

```
 customer_id | name  
-------------+-------
           1 | Alice
(1 row)
```

**同じ細工をした引数**で呼んだとき：

```sql
SELECT * FROM find_customer_safe($x$Alice' OR '1'='1$x$);
```

```
 customer_id | name 
-------------+------
(0 rows)
```

**0 件です。** 細工した文字列は「そういう名前の顧客を探す値」として扱われ、SQL としては解釈されませんでした。該当者がいないので 0 件、というのが正しい結果です。

### 7-3. 使い分けのルール

| 差し込むもの | 書き方 |
|:---|:---|
| **値** | **`USING` を第一候補**。使えない場面では `format` の `%L` |
| **テーブル名・列名** | `format` の `%I`（`USING` では渡せない） |
| どちらでもない | そもそも動的 SQL が必要か考え直す |

**`||` で値を連結するのは、理由があっても書かないでください。** 例外はありません。

なお、`%I` と同じ働きをする `quote_ident()` という関数もあります。8章のテーブル作成資料にある、全テーブルを `TRUNCATE` するスクリプトで実際に使われています（[[00_SQL研修/02_問題/08_結合から使用するテーブル|08_結合から使用するテーブル]] の冒頭）。あのスクリプトが**まさに動的 SQL の実例**です。今なら読めるはずなので、戻って読んでみてください。

## 8. この章で作ったものの片付け

```sql
DROP TRIGGER  IF EXISTS reviews_before_save ON reviews;
DROP FUNCTION IF EXISTS reviews_validate();

DROP TRIGGER  IF EXISTS inventory_after_change ON inventory;
DROP FUNCTION IF EXISTS inventory_log();
DROP TABLE    IF EXISTS inventory_logs;

DROP FUNCTION IF EXISTS table_row_count(text);
DROP FUNCTION IF EXISTS find_customer_unsafe(text);
DROP FUNCTION IF EXISTS find_customer_safe(text);
```

**トリガーは「テーブル名を指定して」消します**（`DROP TRIGGER 名前 ON テーブル名`）。トリガー関数は別オブジェクトなので、別に `DROP FUNCTION` が必要です。

> ⚠️ **トリガーを消し忘れると、後の演習で「原因不明のエラー」になります。**
> この章の実験が終わったら、必ず片付けてください。

## この章のまとめ

- **トリガーはトリガー関数（`RETURNS trigger`）とトリガー設定の 2 つで作る**
- **`NEW` / `OLD` / `TG_OP`** が使える。`INSERT` では `OLD`、`DELETE` では `NEW` が NULL になる
- **値を変えるなら `BEFORE` + `RETURN NEW`、記録するなら `AFTER` + `RETURN NULL`**
- **`WHEN` 句で無駄な発火を抑える。** 条件は `IS DISTINCT FROM` で書く
- **トリガーは呼び出しがコードに現れない。** エラーの `CONTEXT:` 行と `\d テーブル名` で存在を確認する
- **テーブル名・列名が実行時に決まるときは `EXECUTE`** で動的 SQL を組み立てる。結果は `EXECUTE … INTO`
- **`format()` の `%I` は識別子、`%L` は値。`%s` は SQL の組み立てに使わない**
- **値の差し込みは `USING` でバインドする。`||` で値を連結すると SQL インジェクションになる**（実測で全件漏洩を再現）
- **エラーの `QUERY:` 行に、組み立てられた SQL が出る**
