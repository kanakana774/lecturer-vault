# 変数と SQL の実行
## 〜クエリの結果を受け取り、「取れなかったとき」に備える〜

前章で、変数を宣言して `SELECT ... INTO` で値を受け取る形を見ました。この章では、その `INTO` を正しく使うために必要なことを詰めます。

**実務でバグの温床になるのは、正常系ではなく「1 件あるはずが 0 件だった」「1 件のはずが複数件あった」というケースです。** PL/pgSQL はこれを黙って通してしまう仕様なので、先に挙動を知り、対策を身につけます。

> **この資料の前提**
> - PostgreSQL 17 で動作確認しています。掲載しているエラーメッセージ・出力は**すべて実測**です。
> - 使用するテーブルは [[00_SQL研修/02_問題/08_結合から使用するテーブル|08_結合から使用するテーブル]] で作成したもの（8章以降と同じ）です。新しく作るものはありません。
> - [[12-1_PLpgSQLの基礎とDOブロック|12-1]] の `DO` ブロック・`DECLARE`・`RAISE NOTICE`・命名規約（`v_` / `p_`）を前提にします。

---

## 1. `SELECT ... INTO` で 1 行を受け取る

`SELECT` の結果を変数に入れるには、列のリストの直後に `INTO 変数` を書きます。**複数の列を複数の変数に、順番どおりに受け取れます。**

```sql
DO $$
DECLARE
    v_name text;
    v_rank text;
BEGIN
    SELECT c.name, m.rank_name
      INTO v_name, v_rank
      FROM customers c
      LEFT JOIN memberships m ON c.membership_id = m.membership_id
     WHERE c.customer_id = 1;

    RAISE NOTICE '氏名=% ランク=%', v_name, v_rank;
END;
$$;
```

```
NOTICE:  氏名=Alice ランク=Silver
```

- `INTO` に並べる変数の**個数と順番**は、`SELECT` の列と一致させます。
- 書く位置は `SELECT 列リスト INTO 変数リスト FROM …` です（`FROM` の後ろではありません）。

## 2. 【手を動かす】「取れなかったとき」に何が起きるか

ここがこの章の山場です。**`SELECT ... INTO` は、行が取れなくてもエラーになりません。**

### 2-1. 0 件のとき：変数に NULL が入る

存在しない `customer_id = 999` を引いてみます。

```sql
DO $$
DECLARE
    v_name text := '(初期値)';
BEGIN
    SELECT name INTO v_name FROM customers WHERE customer_id = 999;

    RAISE NOTICE '0件のとき: v_name = %', v_name;
    RAISE NOTICE 'NULL かどうか: %', (v_name IS NULL);
END;
$$;
```

```
NOTICE:  0件のとき: v_name = <NULL>
NOTICE:  NULL かどうか: t
```

**エラーは出ません。** しかも、代入前に入れていた `'(初期値)'` は**上書きされて NULL になります**。「取れなかったら初期値が残るだろう」という期待は外れます。

これが厄介なのは、**この後の処理が NULL のまま進む**ことです。`v_name` を使って文字列を組み立てれば結果は NULL、`WHERE name = v_name` で検索すれば 1 件もヒットしません（NULL との比較は真になりません）。**エラーが出ないので、原因から遠い場所で症状が出ます。**

### 2-2. 複数件のとき：先頭の 1 行だけが入る

今度は `WHERE` を付けずに、9 件ある `customers` を丸ごと引いてみます。

```sql
DO $$
DECLARE
    v_name text;
BEGIN
    SELECT name INTO v_name FROM customers;

    RAISE NOTICE '複数件のとき: v_name = %', v_name;
END;
$$;
```

```
NOTICE:  複数件のとき: v_name = Alice
```

**これもエラーになりません。** 最初に返ってきた 1 行が代入され、**残りは黙って捨てられます**。

> ⚠️ **どの行が「最初」になるかは保証されません。**
> 上の実測では Alice が入りましたが、これは `ORDER BY` を書いていないので**たまたま**です。データが増えたり、実行計画が変わったりすると、別の行になり得ます。「1 件に絞ったつもりのクエリが実は複数件返していて、たまたま期待どおりの行が入っていた」——これは実務で本当に起きます。

### 2-3. だからどうするか

対策は 2 つあります。この章では 1 つ目、**「取れたかどうかを自分で確かめる」**を扱います。

2 つ目は「1 件でなければエラーにする」という方法（`STRICT`）ですが、これはエラーの仕組みを学んでから使う必要があるので [[12-4_関数とプロシージャと例外処理|12-4]] §10 で扱います。

## 3. 取れたかどうかを確かめる：`FOUND`

`FOUND` は PL/pgSQL が自動で用意している論理型（boolean）の変数で、**直前の SQL が 1 行以上に影響したか**を保持します。

```sql
DO $$
DECLARE
    v_name text;
BEGIN
    SELECT name INTO v_name FROM customers WHERE customer_id = 999;
    IF NOT FOUND THEN
        RAISE NOTICE '顧客ID 999 は存在しません';
    END IF;

    SELECT name INTO v_name FROM customers WHERE customer_id = 1;
    IF FOUND THEN
        RAISE NOTICE '顧客ID 1 は存在します（% さん）', v_name;
    END IF;
END;
$$;
```

```
NOTICE:  顧客ID 999 は存在しません
NOTICE:  顧客ID 1 は存在します（Alice さん）
```

- `FOUND` は `SELECT INTO` だけでなく、`INSERT` / `UPDATE` / `DELETE` の後にも更新されます（1 行以上処理されたか）。
- **`FOUND` は SQL を実行するたびに上書きされます。** 判定は「その SQL の直後」に書いてください。間に別の SQL を挟むと、見ているのは別の文の結果になります。
- `IF` 文の詳しい書き方は次章（[[12-3_制御構造|12-3]] §1）で扱いますが、ここでは「条件が真なら中を実行する」というだけ押さえれば読めます。

## 4. 値がいらないなら `EXISTS` で聞く

「値は要らない、**あるかないかだけ**知りたい」場合は、変数に受け取る必要がありません。既習の `EXISTS`（[[00_SQL研修/01_講義資料/10_サブクエリ|10 サブクエリ]]）をそのまま `IF` の条件に書けます。

```sql
DO $$
BEGIN
    IF EXISTS (SELECT 1 FROM orders WHERE customer_id = 6) THEN
        RAISE NOTICE '顧客ID 6 には注文履歴があります';
    ELSE
        RAISE NOTICE '顧客ID 6 には注文履歴がありません';
    END IF;

    IF EXISTS (SELECT 1 FROM orders WHERE customer_id = 1) THEN
        RAISE NOTICE '顧客ID 1 には注文履歴があります';
    END IF;
END;
$$;
```

```
NOTICE:  顧客ID 6 には注文履歴がありません
NOTICE:  顧客ID 1 には注文履歴があります
```

### 4-1. `FOUND` と `EXISTS` の使い分け

| 状況 | 書き方 |
|:---|:---|
| **値も欲しい**（取ったうえで、取れたか確かめたい） | `SELECT ... INTO` → `IF NOT FOUND` |
| **あるかないかだけ知りたい** | `IF EXISTS (SELECT 1 FROM …)` |

`EXISTS` の方が「何を判定しているか」が 1 行で読めます。**存在チェックだけなら `EXISTS` を第一候補にしてください。**

## 5. 結果を捨てる：`PERFORM`

PL/pgSQL では、**結果の行き先がない裸の `SELECT` は書けません。** 書くとこうなります。

```sql
DO $$
BEGIN
    SELECT name FROM customers WHERE customer_id = 1;
END;
$$;
```

```
ERROR:  query has no destination for result data
HINT:  If you want to discard the results of a SELECT, use PERFORM instead.
CONTEXT:  PL/pgSQL function inline_code_block line 3 at SQL statement
```

`HINT` が答えを言っています。**結果を捨てたいなら `SELECT` の代わりに `PERFORM` と書きます。**

```sql
DO $$
BEGIN
    PERFORM 1 FROM orders WHERE customer_id = 6;

    IF NOT FOUND THEN
        RAISE NOTICE '顧客ID 6 の注文は見つかりませんでした';
    END IF;
END;
$$;
```

```
NOTICE:  顧客ID 6 の注文は見つかりませんでした
```

`PERFORM` を使う場面は 2 つです。

1. **結果はいらないが、その SQL を実行したい**（値を返す関数を、戻り値を捨てて呼ぶときなど）
2. 上のように `FOUND` だけを見たいとき

ただし 2 の用途は、§4 の `IF EXISTS` の方が読みやすいことが多いです。**`PERFORM` は「結果を捨てるという意思表示」**だと理解しておいてください。

## 6. テーブル定義に合わせた型：`%TYPE` と `%ROWTYPE`

変数の型を `text` や `numeric` と直接書くと、**テーブル側の型が変わったときにコードが合わなくなります**。そこで、テーブル定義から型を借りる書き方があります。

| 書き方 | 意味 |
|:---|:---|
| `テーブル名.列名%TYPE` | その列と同じ型 |
| `テーブル名%ROWTYPE` | その表の 1 行分をまとめて入れられる型 |

```sql
DO $$
DECLARE
    v_name    customers.name%TYPE;   -- customers.name と同じ型
    r_product products%ROWTYPE;      -- products の 1 行分
BEGIN
    SELECT name INTO v_name FROM customers WHERE customer_id = 1;
    RAISE NOTICE '%%TYPE で受けた氏名: %', v_name;

    SELECT * INTO r_product FROM products WHERE product_id = 1;

    RAISE NOTICE 'ID=% 商品名=% 価格=%',
        r_product.product_id, r_product.product_name, r_product.price;
END;
$$;
```

```
NOTICE:  %TYPE で受けた氏名: Alice
NOTICE:  ID=1 商品名=Laptop 価格=1200.00
```

- `%ROWTYPE` の変数には `SELECT * INTO` で行ごと入れられます。
- 中の値は **`変数名.列名`**（ドット）で取り出します。
- 行データを入れる変数なので、命名規約どおり **`r_`** を付けています。

> 💡 **`%TYPE` は「型を書き写さない」ための道具です。**
> `varchar(100)` と書いてしまうと、テーブル側を `varchar(200)` に広げたときに切り詰めが起きます。`%TYPE` にしておけば、テーブルに追従します。

## 7. 構造が決まっていない行を受ける：`RECORD`

`%ROWTYPE` は「どのテーブルの 1 行か」が決まっている場合に使えます。では **JOIN した結果**のように、どのテーブルにも対応しない形はどう受け取るか。そのための型が `RECORD` です。

```sql
DO $$
DECLARE
    r_row RECORD;   -- 構造を決めずに宣言する
BEGIN
    SELECT p.product_name, c.category_name, p.price
      INTO r_row
      FROM products p
      JOIN categories c ON p.category_id = c.category_id
     WHERE p.product_id = 1;

    RAISE NOTICE '商品=% カテゴリ=% 価格=%',
        r_row.product_name, r_row.category_name, r_row.price;
END;
$$;
```

```
NOTICE:  商品=Laptop カテゴリ=Electronics 価格=1200.00
```

`RECORD` は**代入されるまで構造が決まりません**。代入したクエリの列がそのままフィールドになります。

### 7-1. `%ROWTYPE` と `RECORD` の使い分け

| | 使う場面 |
|:---|:---|
| `%ROWTYPE` | 1 つのテーブルの行をそのまま受ける。列名が定義から決まるので読み手に分かりやすい |
| `RECORD` | JOIN 結果や、必要な列だけ選んだ結果を受ける |

**どちらでも書けるなら `%ROWTYPE` を選んでください。** 「どのテーブルの行か」がコードに書いてある方が、読む人に伝わります。

`RECORD` は次章のループでも主役になります（[[12-3_制御構造|12-3]] §4）。

## 8. 何件処理したか：`GET DIAGNOSTICS`

`FOUND` は「1 行以上あったか」しか教えてくれません。**具体的な件数**が必要なら `GET DIAGNOSTICS` で `ROW_COUNT` を受け取ります。

```sql
BEGIN;

DO $$
DECLARE
    v_count integer;
BEGIN
    UPDATE products SET price = price * 1.1 WHERE category_id = 1;
    GET DIAGNOSTICS v_count = ROW_COUNT;
    RAISE NOTICE 'Electronics の % 件を更新しました', v_count;

    UPDATE products SET price = price * 1.1 WHERE category_id = 99;
    GET DIAGNOSTICS v_count = ROW_COUNT;
    RAISE NOTICE '存在しないカテゴリ: % 件', v_count;
END;
$$;

ROLLBACK;
```

```
BEGIN
NOTICE:  Electronics の 4 件を更新しました
NOTICE:  存在しないカテゴリ: 0 件
DO
ROLLBACK
```

> 💡 **`BEGIN;` … `ROLLBACK;` で囲んでいる理由。**
> この例は `products` の価格を書き換えます。囲んでおけば実行後にデータが元に戻るので、**何度でも試せます**（[[15-1_導入_トランザクションとACID|15-1]] §1-3）。以降、データを変更する例はこの形で書きます。

`ROW_COUNT` は業務ロジックの判断材料として使います。「1 件だけ更新されるはずが 0 件だった」「1 件のはずが 3 件更新された」は、どちらも異常です。**件数を確かめる癖をつけると、壊れたデータを作る前に気づけます。**

## 9. 更新した値をその場で受け取る：`RETURNING ... INTO`

`INSERT` や `UPDATE` の後で「今入れた行はどうなったか」を知りたいとき、もう一度 `SELECT` するのは無駄です。`RETURNING` を使うと、**その場で変数に受け取れます**。

この研修で使うテーブルは主キーが自動採番ではないので、**登録の前に自分で ID を決める**必要があります。`COALESCE(MAX(id), 0) + 1` が定番の形です。

```sql
BEGIN;

DO $$
DECLARE
    v_new_id    integer;
    v_new_price numeric;
BEGIN
    -- ① 次の review_id を決める（1件もなければ 1 になる）
    SELECT COALESCE(MAX(review_id), 0) + 1 INTO v_new_id FROM reviews;

    -- ② 登録し、確定した review_id を受け取る
    INSERT INTO reviews (review_id, product_id, customer_id, rating, comment, review_date)
    VALUES (v_new_id, 6, 1, 4, 'モニタは十分な品質', CURRENT_DATE)
    RETURNING review_id INTO v_new_id;

    RAISE NOTICE '採番して登録した review_id = %', v_new_id;

    -- ③ UPDATE でも使える
    UPDATE products SET price = price + 50 WHERE product_id = 6
    RETURNING price INTO v_new_price;

    RAISE NOTICE '更新後の価格 = %', v_new_price;
END;
$$;

ROLLBACK;
```

```
BEGIN
NOTICE:  採番して登録した review_id = 7
NOTICE:  更新後の価格 = 350.00
DO
ROLLBACK
```

- `COALESCE(MAX(review_id), 0) + 1` の `COALESCE` は、**テーブルが空のとき `MAX` が NULL になる**のを 0 に読み替えるためです。これがないと `NULL + 1` = NULL になり、登録に失敗します。
- **`RETURNING` が返すのは「変更後」の値だけです。** 「変更前の値も一緒に取りたい」はできません。前の値が必要なら、変更する前に `SELECT ... INTO` で退避しておきます。

> ⚠️ **`MAX(id) + 1` は学習用の書き方です。**
> 実務では、複数の処理が同時に走ると**同じ ID を 2 つの処理が同時に取ってしまう**ため、主キーの重複エラーになります。本来は連番を発行する仕組み（シーケンス）を使います（[[00_SQL研修/01_講義資料/99_補足_sequenceについて|99_補足_sequenceについて]]）。この研修のテーブルは手動採番なので、まずこの形で「テーブルの現在の状態を見て次を決める」ロジックに慣れてください。

## この章のまとめ

- **`SELECT ... INTO` は 0 件でも複数件でもエラーにならない。** 0 件なら NULL で上書き、複数件なら先頭 1 行だけ入って残りは捨てられる
- **どの行が「先頭」かは `ORDER BY` がなければ保証されない**
- **取れたかどうかは `FOUND` で確かめる。** ただし SQL を実行するたびに上書きされるので、判定は直後に書く
- **あるかないかだけなら `IF EXISTS (SELECT 1 …)`** が読みやすい
- **裸の `SELECT` は書けない**（`query has no destination for result data`）。結果を捨てるなら `PERFORM`
- **型はテーブルから借りる。** 列は `%TYPE`、1 行は `%ROWTYPE`、JOIN 結果は `RECORD`
- **件数が必要なら `GET DIAGNOSTICS v_count = ROW_COUNT`**
- **`RETURNING ... INTO` で更新後の値をその場で受け取れる。** 返るのは変更後の値だけ
- **データを変える例は `BEGIN;` … `ROLLBACK;` で囲めば何度でも試せる**

次は、ここまで断片的に使ってきた `IF` を正面から扱い、**繰り返し（ループ）**に進みます。
