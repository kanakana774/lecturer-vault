# 関数とプロシージャと例外処理
## 〜コードに名前を付けて残し、失敗に備える〜

ここまで書いてきたコードは、すべて `DO` ブロックでした。`DO` は**その場で 1 回実行して消える**ので、同じ処理をもう一度やりたければ、また全部書くことになります。

この章の前半では、コードに**名前を付けてデータベースに残す**方法（関数とプロシージャ）を扱います。後半では、**失敗したときに何が起きるか、どう扱うか**（例外処理）を扱います。

この 2 つを 1 つの章にしているのは理由があります。**名前を付けて他の人に呼ばれるコードになった瞬間、「変な値を渡されたらどうするか」を決める責任が生まれる**からです。関数とエラー処理はセットで学ぶのが自然です。

> **この資料の前提**
> - PostgreSQL 17 で動作確認しています。掲載しているエラーメッセージ・出力は**すべて実測**です。
> - 使用するテーブルは [[00_SQL研修/02_問題/08_結合から使用するテーブル|08_結合から使用するテーブル]] で作成したもの（8章以降と同じ）です。§11 の実験だけ、ログ用のテーブルを作って最後に削除します。
> - [[12-2_変数とSQLの実行|12-2]]・[[12-3_制御構造|12-3]] の内容（`SELECT INTO`・`FOUND`・`RETURNING INTO`・`IF`・ループ）を前提にします。
> - [[15-1_導入_トランザクションとACID|15-1]] の原子性（§1・§3）を前提にします。

## 1. 関数（FUNCTION）を作る

### 1-1. 値を 1 つ返す関数

`CREATE FUNCTION` で、名前・引数・戻り値の型を決めて登録します。

```sql
CREATE OR REPLACE FUNCTION 関数名(引数名 型, …)
RETURNS 戻り値の型
LANGUAGE plpgsql
AS $$
DECLARE
    …
BEGIN
    …
    RETURN 値;
END;
$$;
```

`DO` ブロックとの違いは 3 点だけです。

1. **名前と引数がある**
2. **`RETURNS` で戻り値の型を宣言し、`RETURN` で値を返す**
3. **登録すると残る**（消したいときは `DROP FUNCTION`）

会員ランクの割引率を適用した価格を返す関数を作ります。

```sql
CREATE OR REPLACE FUNCTION discounted_price(p_product_id integer, p_customer_id integer)
RETURNS numeric
LANGUAGE plpgsql
AS $$
DECLARE
    v_price numeric;
    v_rate  numeric;
BEGIN
    SELECT price INTO v_price FROM products WHERE product_id = p_product_id;

    -- 会員ランクがない顧客（membership_id が NULL）は割引率 0 とみなす
    SELECT COALESCE(m.discount_rate, 0) INTO v_rate
      FROM customers c
      LEFT JOIN memberships m ON c.membership_id = m.membership_id
     WHERE c.customer_id = p_customer_id;

    RETURN round(v_price * (1 - v_rate / 100), 2);
END;
$$;
```

**引数には `p_` を付けます**（[[12-1_PLpgSQLの基礎とDOブロック|12-1]] §5）。引数名も列名と衝突するので、変数と同じ理由です。

### 1-2. 関数は SQL の中で呼べる

ここが関数の強みです。**`SELECT` の列として、普通の関数と同じように使えます。**

```sql
SELECT c.name,
       p.product_name,
       p.price,
       discounted_price(p.product_id, c.customer_id) AS discounted
  FROM customers c
  CROSS JOIN products p
 WHERE c.customer_id IN (1, 3, 4) AND p.product_id = 1
 ORDER BY c.customer_id;
```

```
  name   | product_name |  price  | discounted 
---------+--------------+---------+------------
 Alice   | Laptop       | 1200.00 |    1080.00
 Charlie | Laptop       | 1200.00 |    1200.00
 Diana   | Laptop       | 1200.00 |    1020.00
(3 rows)
```

Alice は Silver（10%引き）、Diana は Gold（15%引き）、Charlie は会員ランクなしなので割引なし。`COALESCE` が効いています。

> ⚠️ **SQL の中で呼べるということは、行数ぶん呼ばれるということです。**
> 上の関数は中で `SELECT` を 2 回実行しています。100 万行に対してこの関数を使えば、200 万回クエリが走ります。**[[12-3_制御構造|12-3]] §7 の N+1 と同じ構造**です。「関数にまとめたから速い」わけではないことに注意してください。

### 1-3. 表を返す関数（`RETURNS TABLE`）

集計結果のような**複数行・複数列**を返したいときは `RETURNS TABLE` を使い、`RETURN QUERY` でクエリの結果をそのまま返します。

```sql
CREATE OR REPLACE FUNCTION category_sales()
RETURNS TABLE (category_name text, order_count bigint, total_amount numeric)
LANGUAGE plpgsql
AS $$
BEGIN
    RETURN QUERY
    SELECT c.category_name::text,
           count(DISTINCT o.order_id),
           COALESCE(sum(oi.quantity * p.price), 0)
      FROM categories c
      LEFT JOIN products p    ON p.category_id = c.category_id
      LEFT JOIN orderitems oi ON oi.product_id = p.product_id
      LEFT JOIN orders o      ON o.order_id = oi.order_id AND o.status <> 'Cancelled'
     GROUP BY c.category_name
     ORDER BY c.category_name;
END;
$$;
```

呼び出しは **`FROM` に書きます**。表と同じように扱えるので、`WHERE` で絞り込めます。

```sql
SELECT * FROM category_sales();
```

```
  category_name  | order_count | total_amount 
-----------------+-------------+--------------
 Books           |           2 |        90.00
 Clothing        |           4 |       195.00
 Electronics     |           6 |      6550.00
 Furniture       |           2 |       900.00
 Office Supplies |           0 |            0
(5 rows)
```

```sql
SELECT * FROM category_sales() WHERE total_amount > 1000;
```

```
 category_name | order_count | total_amount 
---------------+-------------+--------------
 Electronics   |           6 |      6550.00
(1 row)
```

- `RETURNS TABLE (…)` に書いた**列名と型が、返る表の定義**になります。
- `category_name::text` とキャストしているのは、テーブル側が `varchar(50)` で、宣言した `text` と型を合わせる必要があるためです。ここがずれると登録時にエラーになります。
- ビューと似ていますが、**引数を取れる**のが違いです。「カテゴリを引数で受け取って、その分だけ集計する」ようなことができます。

## 2. プロシージャ（PROCEDURE）を作る

**値を返さず、一連の処理を実行するだけ**のものはプロシージャで書きます。呼び出しは `CALL` です。

```sql
CREATE OR REPLACE PROCEDURE add_stock(
    p_product_id   integer,
    p_warehouse_id integer,
    p_quantity     integer
)
LANGUAGE plpgsql
AS $$
DECLARE
    v_after integer;
BEGIN
    UPDATE inventory
       SET stock_quantity = stock_quantity + p_quantity
     WHERE product_id = p_product_id AND warehouse_id = p_warehouse_id
    RETURNING stock_quantity INTO v_after;

    IF NOT FOUND THEN
        RAISE NOTICE '商品% / 倉庫% の在庫行がありません', p_product_id, p_warehouse_id;
    ELSE
        RAISE NOTICE '商品% / 倉庫% の在庫を % 個追加しました（現在 % 個）',
            p_product_id, p_warehouse_id, p_quantity, v_after;
    END IF;
END;
$$;
```

呼んでみます（データが戻るように `BEGIN;` … `ROLLBACK;` で囲みます）。

```sql
BEGIN;
CALL add_stock(1, 1, 10);
CALL add_stock(1, 99, 10);
ROLLBACK;
```

```
BEGIN
NOTICE:  商品1 / 倉庫1 の在庫を 10 個追加しました（現在 60 個）
CALL
NOTICE:  商品1 / 倉庫99 の在庫行がありません
CALL
ROLLBACK
```

- **`RETURNS` を書きません。** `RETURN` で値を返すこともできません。
- `UPDATE ... RETURNING ... INTO` と `IF NOT FOUND` の組み合わせで、「更新できたか」を判定しています（[[12-2_変数とSQLの実行|12-2]] §3, §9）。

### 2-1. 値を返したいなら `OUT` 引数

プロシージャは戻り値を持てませんが、**`OUT` を付けた引数**を使えば呼び出し元に値を渡せます。

```sql
CREATE OR REPLACE PROCEDURE customer_summary(
    p_customer_id  IN  integer,
    p_name         OUT text,
    p_order_count  OUT bigint
)
LANGUAGE plpgsql
AS $$
BEGIN
    SELECT c.name, count(o.order_id)
      INTO p_name, p_order_count
      FROM customers c
      LEFT JOIN orders o ON o.customer_id = c.customer_id
     WHERE c.customer_id = p_customer_id
     GROUP BY c.name;
END;
$$;
```

`CALL` するときは、受け取る変数を並べます。

```sql
DO $$
DECLARE
    v_name  text;
    v_count bigint;
BEGIN
    CALL customer_summary(1, v_name, v_count);
    RAISE NOTICE '% さんの注文は % 件です', v_name, v_count;
END;
$$;
```

```
NOTICE:  Alice さんの注文は 4 件です
```

- 引数モードは **`IN`（既定）／`OUT`（返す）／`INOUT`（受け取って返す）** の 3 つです。`IN` は省略できます。
- `OUT` 引数が複数あるなら、**そもそも関数にして表を返した方が扱いやすい**ことも多いです。使い分けは次節の表で整理します。

## 3. 関数とプロシージャの使い分け

| 項目 | 関数（FUNCTION） | プロシージャ（PROCEDURE） |
|:---|:---|:---|
| 主な用途 | 計算・値の取得・変換 | 一連の業務処理の実行 |
| 戻り値 | **必要**（`RETURNS`） | なし（`OUT` 引数で代替） |
| 呼び出し方 | `SELECT f(…)` / `FROM f(…)` | `CALL p(…)` |
| SQL の一部として使えるか | **使える** | 使えない |
| `COMMIT` / `ROLLBACK` | **書けない** | **条件付きで書ける** |

判断はほぼこれだけです。

- **`SELECT` の中で使いたいなら関数**
- **更新処理を一括で実行したいならプロシージャ**

> ⚠️ **プロシージャの `COMMIT` / `ROLLBACK` には条件があります。**
> 「プロシージャならトランザクションを制御できる」と単純に覚えると、**手元では動いたのにアプリから呼んだら `invalid transaction termination` で落ちる**という事故になります。条件は 2 つあり、`EXCEPTION` 句との関係も絡みます。
> この章では、**関数の中では書けない**ということだけ覚えてください。関数は `SELECT f() FROM …` のように SQL 文の一部として動くので、その途中で勝手に確定されると呼び出し元の SQL が成立しなくなるためです。

## 4. エラーを起こす：`RAISE`

ここから後半、エラーの扱いです。

`RAISE` は [[12-1_PLpgSQLの基礎とDOブロック|12-1]] からずっと `RAISE NOTICE` として使ってきましたが、**レベルを変えると意味が変わります**。

| レベル | 動き |
|:---|:---|
| `NOTICE` | メッセージを出して**続行** |
| `WARNING` | メッセージを出して**続行**（NOTICE より強い警告の意図） |
| `EXCEPTION` | **エラーにして中断する** |

```sql
DO $$
BEGIN
    RAISE NOTICE  'これは NOTICE：処理は続く';
    RAISE WARNING 'これは WARNING：処理は続く';
    RAISE NOTICE  'WARNING の後も続いています';
    RAISE EXCEPTION 'これは EXCEPTION：ここで中断される';
    RAISE NOTICE  'この行は実行されない';
END;
$$;
```

```
NOTICE:  これは NOTICE：処理は続く
WARNING:  これは WARNING：処理は続く
NOTICE:  WARNING の後も続いています
ERROR:  これは EXCEPTION：ここで中断される
CONTEXT:  PL/pgSQL function inline_code_block line 6 at RAISE
```

**`RAISE EXCEPTION` の行で止まり、最後の `NOTICE` は実行されていません。** そして出力が `ERROR:` になっている点に注目してください。`RAISE EXCEPTION` は、PostgreSQL が出す普通のエラーとまったく同じ扱いになります。

## 5. 入力を検証する：`RAISE EXCEPTION`

関数やプロシージャは他の人から呼ばれます。**おかしな引数で呼ばれたら、処理を進めずにエラーで止めるのが正しい**です。

商品の価格を更新するプロシージャに、2 つの検証を入れます。

```sql
CREATE OR REPLACE PROCEDURE set_product_price(p_product_id integer, p_price numeric)
LANGUAGE plpgsql
AS $$
DECLARE
    v_name text;
BEGIN
    -- 検証① 価格が正の数か
    IF p_price <= 0 THEN
        RAISE EXCEPTION '価格は正の数を指定してください'
            USING DETAIL = format('指定された価格: %s', p_price),
                  HINT   = '0 より大きい数を指定してください。';
    END IF;

    -- 検証② その商品が存在するか
    SELECT product_name INTO v_name FROM products WHERE product_id = p_product_id;
    IF NOT FOUND THEN
        RAISE EXCEPTION '商品ID % は存在しません', p_product_id;
    END IF;

    UPDATE products SET price = p_price WHERE product_id = p_product_id;
    RAISE NOTICE '% の価格を % に更新しました', v_name, p_price;
END;
$$;
```

不正な価格で呼びます。

```sql
CALL set_product_price(1, -100);
```

```
ERROR:  価格は正の数を指定してください
DETAIL:  指定された価格: -100
HINT:  0 より大きい数を指定してください。
CONTEXT:  PL/pgSQL function set_product_price(integer,numeric) line 6 at RAISE
```

存在しない商品で呼びます。

```sql
CALL set_product_price(999, 100);
```

```
ERROR:  商品ID 999 は存在しません
CONTEXT:  PL/pgSQL function set_product_price(integer,numeric) line 13 at RAISE
```

### 5-1. `USING` で情報を足す

`RAISE EXCEPTION` にはメッセージ以外の情報を添えられます。よく使うのは 2 つです。

| キー | 何を書くか | 表示 |
|:---|:---|:---|
| `DETAIL` | **何が起きたか**の具体的な値 | `DETAIL:` |
| `HINT` | **どうすれば直るか** | `HINT:` |

**エラーメッセージは、読んだ人が対処できて初めて価値があります。** 「エラーが発生しました」だけのメッセージは、調査時間を増やすだけです。何が渡されたか（`DETAIL`）と、どうすればよいか（`HINT`）を書く癖をつけてください。

`CONTEXT:` の行は PostgreSQL が自動で付けます。**どの関数の何行目で起きたか**が分かるので、デバッグのときはここを見ます。

## 6. 【手を動かす】例外を投げると、それまでの更新はどうなるか

**これが例外処理でいちばん大事な性質です。**

途中まで `UPDATE` して、最後に例外を投げるプロシージャを作ります。

```sql
-- まず現在の価格を確認
SELECT product_id, product_name, price FROM products WHERE product_id IN (1, 2) ORDER BY product_id;
```

```
 product_id | product_name |  price  
------------+--------------+---------
          1 | Laptop       | 1200.00
          2 | Smartphone   |  800.00
(2 rows)
```

```sql
CREATE OR REPLACE PROCEDURE raise_after_update()
LANGUAGE plpgsql
AS $$
BEGIN
    UPDATE products SET price = 1 WHERE product_id = 1;
    RAISE NOTICE '商品1 の価格を 1 に更新しました';

    UPDATE products SET price = 2 WHERE product_id = 2;
    RAISE NOTICE '商品2 の価格を 2 に更新しました';

    RAISE EXCEPTION '最後の最後で失敗しました';
END;
$$;

CALL raise_after_update();
```

```
NOTICE:  商品1 の価格を 1 に更新しました
NOTICE:  商品2 の価格を 2 に更新しました
ERROR:  最後の最後で失敗しました
CONTEXT:  PL/pgSQL function raise_after_update() line 9 at RAISE
```

**2 つの `UPDATE` は「更新しました」と表示されています。** では、価格はどうなったか。

```sql
SELECT product_id, product_name, price FROM products WHERE product_id IN (1, 2) ORDER BY product_id;
```

```
 product_id | product_name |  price  
------------+--------------+---------
          1 | Laptop       | 1200.00
          2 | Smartphone   |  800.00
(2 rows)
```

**元のままです。1 円にも 2 円にもなっていません。**

これは [[15-1_導入_トランザクションとACID|15-1]] の**原子性**そのものです。`CALL` は 1 つの SQL 文なので、自動コミットが `BEGIN` と `COMMIT` で包んでいます。途中でエラーになれば `COMMIT` に到達しないので、**そのプロシージャの中の変更は全部巻き戻ります**。

> 💡 **これは PL/pgSQL の大きな利点です。**
> 「途中で失敗したら、中途半端なデータが残る」という心配をしなくてよい、ということです。検証に失敗したら `RAISE EXCEPTION` で投げてしまえば、それまでの更新は自動で消えます。**自分で「元に戻す `UPDATE`」を書く必要はありません。**

## 7. エラーを捕まえる：`EXCEPTION` 句

`BEGIN … END;` に `EXCEPTION` 句を足すと、**その中で起きたエラーを捕まえて、別の処理に振り替える**ことができます。

```sql
BEGIN
    -- エラーが起きうる処理
EXCEPTION
    WHEN 条件名 THEN
        -- その条件のときの処理
    WHEN OTHERS THEN
        -- それ以外すべて
END;
```

`reviews` には `UNIQUE (product_id, customer_id)` 制約があります（1 人 1 商品につき 1 レビュー）。商品1・顧客1 のレビューはすでに存在するので、同じ組み合わせを入れると一意制約違反になります。

```sql
BEGIN;

DO $$
BEGIN
    INSERT INTO reviews (review_id, product_id, customer_id, rating, comment, review_date)
    VALUES (100, 1, 1, 5, '重複するレビュー', CURRENT_DATE);

    RAISE NOTICE '登録できました';
EXCEPTION
    WHEN unique_violation THEN
        RAISE NOTICE 'すでにレビュー済みです';
        RAISE NOTICE 'SQLSTATE = % / SQLERRM = %', SQLSTATE, SQLERRM;
END;
$$;

ROLLBACK;
```

```
BEGIN
NOTICE:  すでにレビュー済みです
NOTICE:  SQLSTATE = 23505 / SQLERRM = duplicate key value violates unique constraint "reviews_product_id_customer_id_key"
DO
ROLLBACK
```

**エラーで止まらず、`EXCEPTION` 句の中が実行されました。**

### 7-1. `SQLSTATE` と `SQLERRM`

`EXCEPTION` 句の中では、2 つの特別な変数が使えます。

| 変数 | 中身 |
|:---|:---|
| `SQLSTATE` | エラーコード（5 桁）。上の例では `23505`（一意制約違反） |
| `SQLERRM` | エラーメッセージの文字列 |

**この 2 つは必ずセットで出してください。** コードだけでは人が読めず、メッセージだけではプログラムで判別できません。

### 7-2. よく使う条件名

| 条件名 | いつ起きるか |
|:---|:---|
| `unique_violation` | 一意制約・主キーの重複 |
| `foreign_key_violation` | 参照先が存在しない |
| `not_null_violation` | NOT NULL の列に NULL |
| `check_violation` | CHECK 制約違反 |
| `division_by_zero` | ゼロ除算 |
| `no_data_found` | `STRICT` で 0 件（→ §8） |
| `too_many_rows` | `STRICT` で複数件（→ §8） |
| `OTHERS` | 上記以外すべて |

### 7-3. `EXCEPTION` を書く範囲は狭くする

`EXCEPTION` 句はブロック単位なので、**大きなブロック全体に付けると「どこで起きたか」が分からなくなります**。

[[12-1_PLpgSQLの基礎とDOブロック|12-1]] §6 で「ブロックは入れ子にできる」と書いたのは、この使い分けのためです。**エラーを捕まえたい部分だけを内側のブロックで囲む**のが基本の形です。次の §8 でその形を使います。

## 8. 「1 件のはず」を保証する：`SELECT ... INTO STRICT`

[[12-2_変数とSQLの実行|12-2]] §2 で見た問題に戻ります。`SELECT ... INTO` は 0 件でも複数件でもエラーになりませんでした。

**`INTO` の後ろに `STRICT` を付けると、ちょうど 1 件でなければ例外になります。**

| 状況 | 起きる例外 |
|:---|:---|
| 0 件 | `no_data_found`（SQLSTATE `P0002`） |
| 2 件以上 | `too_many_rows`（SQLSTATE `P0003`） |

```sql
DO $$
DECLARE
    v_name text;
BEGIN
    -- ① 0件のケース
    BEGIN
        SELECT name INTO STRICT v_name FROM customers WHERE customer_id = 999;
    EXCEPTION
        WHEN no_data_found THEN
            RAISE NOTICE '0件だったので例外になった（SQLSTATE=%）', SQLSTATE;
    END;

    -- ② 複数件のケース
    BEGIN
        SELECT name INTO STRICT v_name FROM customers;
    EXCEPTION
        WHEN too_many_rows THEN
            RAISE NOTICE '複数件だったので例外になった（SQLSTATE=%）', SQLSTATE;
    END;

    -- ③ ちょうど1件のケース
    SELECT name INTO STRICT v_name FROM customers WHERE customer_id = 1;
    RAISE NOTICE 'ちょうど1件なので成功: %', v_name;
END;
$$;
```

```
NOTICE:  0件だったので例外になった（SQLSTATE=P0002）
NOTICE:  複数件だったので例外になった（SQLSTATE=P0003）
NOTICE:  ちょうど1件なので成功: Alice
```

**捕まえたい部分だけを内側の `BEGIN … EXCEPTION … END;` で囲んでいる**点を見てください（§7-3）。

### 8-1. `STRICT` を使うか、`FOUND` で確かめるか

| 場面 | 書き方 |
|:---|:---|
| **1 件あるのが当然**で、なければ異常（主キーで引く、など） | `INTO STRICT`。異常はエラーで止める |
| **0 件もありうる**ので、それに応じた処理をしたい | `INTO` + `IF NOT FOUND`（[[12-2_変数とSQLの実行|12-2]] §3） |

**「1 件あるはず」と思って書いたクエリには `STRICT` を付けてください。** NULL が黙って混入して遠くで症状が出るより、その場で止まった方がはるかに早く直せます。

## 9. 【手を動かす】エラーを握りつぶすとどうなるか

`WHEN OTHERS THEN` で全部捕まえると、**どんなエラーでも「成功」として返ってしまいます**。これが実務でいちばん多い事故です。

「エラーをログに残してから、エラーとして返す」ためには、**引数なしの `RAISE;`** で捕まえたエラーを投げ直します（**再スロー**）。

ただし、ここに落とし穴があります。実際に測ります。

### 9-1. 実験の準備

**この節の実験だけで使うテーブルです。最後に削除します。**

```sql
DROP TABLE IF EXISTS demo_error_logs;

CREATE TABLE demo_error_logs (
    log_id    serial PRIMARY KEY,
    logged_at timestamptz DEFAULT now(),
    message   text
);
```

同じ処理を 2 つ作ります。**違いは最後の `RAISE;` があるかないかだけ**です。

```sql
-- 版A：ログを書いて、再スローする
CREATE OR REPLACE PROCEDURE log_and_reraise()
LANGUAGE plpgsql
AS $$
BEGIN
    UPDATE products SET price = 1 WHERE product_id = 1;
    RAISE EXCEPTION 'わざと失敗させます';
EXCEPTION
    WHEN OTHERS THEN
        INSERT INTO demo_error_logs (message) VALUES (SQLERRM);
        RAISE;                      -- ★ 再スローする
END;
$$;

-- 版B：ログを書いて、再スローしない
CREATE OR REPLACE PROCEDURE log_and_swallow()
LANGUAGE plpgsql
AS $$
BEGIN
    UPDATE products SET price = 1 WHERE product_id = 1;
    RAISE EXCEPTION 'わざと失敗させます';
EXCEPTION
    WHEN OTHERS THEN
        INSERT INTO demo_error_logs (message) VALUES (SQLERRM);
                                    -- ★ RAISE; を書かない
END;
$$;
```

### 9-2. 版A（再スローする）を呼ぶ

```sql
CALL log_and_reraise();
SELECT count(*) AS log_count FROM demo_error_logs;
```

```
ERROR:  わざと失敗させます
CONTEXT:  PL/pgSQL function log_and_reraise() line 4 at RAISE
```

```
 log_count 
-----------
         0
(1 row)
```

**呼び出し元にはちゃんとエラーが返りました。しかしログは 0 件です。**

理由は §6 と同じです。再スローするとエラーが `CALL` の外まで伝わり、**この文全体が巻き戻ります**。ログの `INSERT` も「この文の中の変更」なので、一緒に消えます。

### 9-3. 版B（再スローしない）を呼ぶ

```sql
CALL log_and_swallow();
SELECT count(*) AS log_count FROM demo_error_logs;
SELECT price FROM products WHERE product_id = 1;
```

```
CALL
```

```
 log_count 
-----------
         1
(1 row)
```

```
  price  
---------
 1200.00
(1 row)
```

**ログは残りました。しかし `CALL` は成功しています。** 呼び出し元は失敗したことを知りません。

なお、`UPDATE` は**どちらの版でも巻き戻っています**（価格は 1200.00 のまま）。`EXCEPTION` 句に入った時点で、そのブロック内の変更は取り消されているためです。

### 9-4. どう考えればいいか

この 2 つは**同時には成立しません**。

| やり方 | 呼び出し元への通知 | DB内のログ |
|:---|:---|:---|
| 版A（`RAISE;` する） | **エラーとして伝わる** | 残らない |
| 版B（握りつぶす） | 成功と誤認される | **残る** |

**基本は版Aです。** 呼び出し元に失敗を伝えないのは、より大きな事故につながります。

そのうえで「エラーの記録も残したい」なら、**DB のテーブルに残すのを諦め、`RAISE` のメッセージとしてアプリ側やサーバログに届ける**のが素直です。DB のテーブルに残しつつエラーも返す方法もありますが、この研修の範囲を超えます。

> **覚えておくべき原則**: **`WHEN OTHERS THEN` で捕まえて何もしない（または NOTICE を出すだけ）は書かない。** 捕まえるなら「捕まえた理由」と「その後どうするか」を必ず決めてください。捕まえる理由がないなら、`EXCEPTION` 句を書かないのが正解です。

### 9-5. 後片付け

```sql
DROP PROCEDURE log_and_reraise;
DROP PROCEDURE log_and_swallow;
DROP TABLE demo_error_logs;
```

## 10. この章で作ったものの片付け

登録した関数・プロシージャはデータベースに残ります。消したいときは次のとおりです。

```sql
DROP FUNCTION  IF EXISTS discounted_price(integer, integer);
DROP FUNCTION  IF EXISTS category_sales();
DROP PROCEDURE IF EXISTS add_stock(integer, integer, integer);
DROP PROCEDURE IF EXISTS customer_summary(integer, text, bigint);
DROP PROCEDURE IF EXISTS set_product_price(integer, numeric);
DROP PROCEDURE IF EXISTS raise_after_update();
```

**`DROP` には引数の型まで書く癖をつけてください。** 名前が一意なら `DROP FUNCTION 名前` と省略もできますが、PostgreSQL では**同じ名前で引数の型が違う関数を複数作れる**（オーバーロード）ため、その場合は次のように拒否されます（実測）。

```
ERROR:  function name "f_ov" is not unique
HINT:  Specify the argument list to select the function unambiguously.
```

引数の型を書いておけば、後からオーバーロードが増えても片付けのコードが壊れません。

> ⚠️ **`CREATE OR REPLACE` は、引数や戻り値の型を変えると失敗します。**
> 「引数を 1 つ足したい」「戻り値を `numeric` から `text` に変えたい」というときは、`OR REPLACE` では上書きできません。先に `DROP` してから作り直してください。

## この章のまとめ

- **関数は `RETURNS` で戻り値を宣言し、`SELECT` や `FROM` の中で呼べる**
- **複数行・複数列を返すなら `RETURNS TABLE` + `RETURN QUERY`**
- **プロシージャは値を返さず `CALL` で呼ぶ。** 値を渡したいなら `OUT` 引数
- **`SELECT` で使いたいなら関数、更新処理をまとめるならプロシージャ**
- **関数の中で `COMMIT` / `ROLLBACK` は書けない。** プロシージャは条件付き → [[15-3_補足_PLpgSQLの中のトランザクション制御|15-3]]
- **`RAISE` は `NOTICE` / `WARNING` は続行、`EXCEPTION` は中断**
- **おかしな引数は `RAISE EXCEPTION` で止める。** `USING DETAIL` と `HINT` で、読んだ人が対処できるメッセージにする
- **例外を投げれば、それまでの更新は自動で巻き戻る。** 自分で戻す処理を書く必要はない
- **`EXCEPTION WHEN 条件名 THEN` で捕まえられる。** `SQLSTATE` と `SQLERRM` はセットで出す
- **`EXCEPTION` を書く範囲は狭くする。** 捕まえたい部分だけを内側のブロックで囲む
- **「1 件あるはず」のクエリには `INTO STRICT`**（0 件 → `no_data_found` / 複数件 → `too_many_rows`）
- **握りつぶすな。** 再スロー（`RAISE;`）すると DB 内のログも巻き戻る。両方は取れないので、呼び出し元への通知を優先する

次はこの章の応用として、**書いた覚えがないのに勝手に動く仕組み（トリガー）**と、**実行時に SQL を組み立てる方法（動的 SQL）**を扱います。

→ [[12-5_トリガーと動的SQL|12-5 トリガーと動的 SQL]]
