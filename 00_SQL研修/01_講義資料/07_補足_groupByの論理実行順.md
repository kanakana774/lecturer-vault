# GROUP BY と集約関数の論理実行イメージ

## 0. SQL の論理実行順（全部）

**SQL は書いた順には処理されません。** 書く順は `SELECT` → `FROM` → `WHERE` → … ですが、
処理される順は `FROM` から始まって `SELECT` は後ろのほうです。

**まだ習っていない句も含めて、先に全部並べておきます。** ここが分かると、
このあと各章で出てくる「なぜこれは書けないのか」がほとんど自分で説明できるようになります。

| # | 句 | 何をするか | 扱う章 |
| :--- | :--- | :--- | :--- |
| ① | `FROM` / `JOIN … ON` | 対象の表を決め、つなぐ | [[00_SQL研修/01_講義資料/08_結合|08_結合]] |
| ② | `WHERE` | **行**を絞る | [[02_CRUDについて]] / [[02_演算子]] |
| ③ | `GROUP BY` | 行をグループにまとめる | [[07_集約関数]] |
| ④ | `HAVING` | **グループ**を絞る | [[07_集約関数]] |
| ⑤ | `SELECT` | 列と式を評価する。**別名（`AS`）が付くのはここ** | [[02_CRUDについて]] |
| ⑥ | ウィンドウ関数 | `OVER (...)` を計算する | [[18-1_ウィンドウ関数]] |
| ⑦ | `DISTINCT` | 重複した行を除く | [[07_集約関数]] |
| ⑧ | `UNION` / `INTERSECT` / `EXCEPT` | 別の `SELECT` の結果と縦につなぐ | [[00_SQL研修/01_講義資料/09_集合演算子|09_集合演算子]] |
| ⑨ | `ORDER BY` | 並べる | [[02_CRUDについて]] |
| ⑩ | `LIMIT` / `OFFSET` | 件数を切る | [[02_CRUDについて]] |

### この順序から導けること

「なぜエラーになるのか」を暗記する必要はありません。**上の番号を見れば決まります。**

| 「なぜ？」 | 番号を見れば | 実際に出るエラー |
| :--- | :--- | :--- |
| `SELECT` で付けた別名が `WHERE` で使えない | 別名が付くのは⑤、`WHERE` は② | `column "p" does not exist` |
| 集計関数を `WHERE` に書けない | 集計の値が決まるのは③④。②の時点ではまだ無い | `aggregate functions are not allowed in WHERE` |
| ウィンドウ関数を `WHERE` に書けない | ⑥は②より後 | `window functions are not allowed in WHERE` |
| `HAVING` に `GROUP BY` に無い列を書けない | ④の時点で行はグループに束ねられている | `must appear in the GROUP BY clause or be used in an aggregate function` |
| 別名が `ORDER BY` では使える | ⑨は⑤より後だから | （通る） |
| `ORDER BY` / `LIMIT` は集合演算の**全体に1つ**しか書けない | ⑨⑩は⑧より後 | （→ [[00_SQL研修/01_講義資料/09_集合演算子|09_集合演算子]] §2-3） |
| `DISTINCT` がウィンドウ関数の**計算後**の値に効く | ⑦は⑥より後 | （→ [[18-1_ウィンドウ関数]]） |

> [!warning] ⚠️ `GROUP BY` の別名だけは順序どおりではありません
> `GROUP BY` は③で `SELECT` の⑤より前なので、**標準SQLでは別名を書けません。**
> PostgreSQL は拡張としてこれを許しています（→ [[07_集約関数]] §2-3）。

> [!note]- これは「論理的な」順序です
> 実際にDBが動く順番はこの通りではありません。同じ答えになる範囲で並べ替えたり、
> まとめたりします（→ [[17-2_実践_EXPLAINの読み方]]）。
> **「どの句が何を相手にしているか」を決めるための順序**だと考えてください。
> この資料の最後（→ §注意点）にも、この論理モデルで説明できない点をまとめてあります。

## 対象 SQL

```sql
SELECT dept_id, AVG(salary) AS avg_salary
FROM employee
WHERE salary >= 300000
GROUP BY dept_id
HAVING AVG(salary) > 400000
ORDER BY avg_salary DESC;
```

## この例で通る句

§0 の①〜⑩のうち、この SQL が通るのは次の6つです。**番号は §0 のものをそのまま使います。**
ウィンドウ関数・`DISTINCT`・集合演算が無いので、**⑥⑦⑧は飛んで⑤から⑨へ進みます。**

| ステップ | 句           | 処理内容                                         | テーブル状態イメージ                              |
| -------- | ------------ | ------------------------------------------------ | ------------------------------------------------- |
| ①        | **FROM**     | 対象テーブルを読み込み                           | employee（全行）                                  |
| ②        | **WHERE**    | 各行に条件を適用し、**行**を絞り込み             | salary > 300000 の行のみ残る                      |
| ③        | **GROUP BY** | group by キー ごとに行をグループ化               | グループごとに `{dept_id, salary一覧}` が束になる |
| ④        | **HAVING**   | 各グループに条件を適用し、**グループ**を絞り込み | `AVG(salary) > 400000` のグループだけ残る         |
| ⑤        | **SELECT**   | グループから表示列を作成（キーと集計結果など）   | `{dept_id, avg_salary}` の中間テーブル生成        |
| ⑨        | **ORDER BY** | 最終出力を並び替え                               | avg_salary の降順にソートされた出力               |

**以降はこの6段を、手元の表が1段ずつどう変わるかという形で追います。**

## 注意点：この論理モデルでカバーできない点

1. **物理的な実行順は必ずしもこの通りではない**

   - 実際の DB エンジンは、WHERE → GROUP BY → HAVING → SELECT → ORDER BY
     の順に**論理的に**動作しますが、内部では最適化により
     集計とフィルタが同時処理されることがあります。
   - 例：`HAVING AVG(salary) > 400000` を実行前に
     一部推測してスキップする（クエリプラン最適化）。

2. **グループ化後の「一時テーブル」は概念的なもの**

   - 実際にはハッシュやソートベースの集約アルゴリズムが使われ、
     中間テーブルが物理的に存在するとは限りません。

3. **SELECT 句の評価は内部的に遅延される**

   - 多くの実装では、`GROUP BY` や `HAVING` が完了した後に
     SELECT が評価されますが、パイプライン処理で並行的に動くこともあります。
