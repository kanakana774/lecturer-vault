# PostgreSQL のデータ型とリテラル

テーブル設計において、各列（カラム）にどのような種類のデータを格納するかを定義するのが**データ型**です。適切なデータ型を選ぶことは、データの整合性を保ち、パフォーマンスを最適化するうえで非常に重要です。

## 主要なデータ型

PostgreSQL で頻繁に使用される主要なデータ型を以下にまとめます。

| カテゴリ            | データ型                                              | 説明                                      | 具体例                        |
| :-------------- | :------------------------------------------------ | :-------------------------------------- | :------------------------- |
| **整数型**         | `SMALLINT`                                        | 2バイトの小さな整数。(-32,768 〜 32,767)           | `10`, `-1000`              |
|                 | `INTEGER` (または `INT`)                             | 4バイトの一般的な整数。(約 -21億 〜 21億)              | `123`, `-500000`           |
|                 | `BIGINT`                                          | 8バイトの大きな整数。(約 -922京 〜 922京)             | `9876543210`               |
| **任意精度<br>数値型** | `NUMERIC(p, s)`<br>`DECIMAL(p, s)`                | **誤差のない正確な**数値を格納。pは全体の桁数、sは小数点以下の桁数。   | `123.45`, `999.00`         |
| **浮動小数<br>点数型** | `REAL`                                            | **単精度**の浮動小数点数（**近似値**）。                | `1.23`                     |
|                 | `DOUBLE PRECISION`                                | **倍精度**の浮動小数点数（**近似値**）。                | `123.456789`               |
| **文字列型**        | `VARCHAR(n)`                                      | 最大n文字の可変長文字列。                           | `'Hello'`, `'商品A'`         |
|                 | `TEXT`                                            | 長さ制限のない可変長文字列。                          | `'長い文章...'`                |
|                 | `CHAR(n)`                                         | 常にn文字の固定長文字列（不足分は空白で埋まる）。                | `'ab   '`                  |
| **論理型**         | `BOOLEAN`                                         | 真偽値 (`TRUE`, `FALSE`) と `NULL` を格納。     | `TRUE`, `FALSE`            |
| **日付/<br>時刻型**  | `DATE`                                            | 日付（年、月、日）のみを格納。                         | `'2025-11-01'`             |
|                 | `TIMESTAMP`                                       | 日付と時刻を格納（**タイムゾーンなし**）。                 | `'2025-11-01 15:30:00'`    |
|                 | `TIMESTAMP WITH TIME ZONE`<br>(または `TIMESTAMPTZ`) | 日付と時刻を格納（**タイムゾーン付き**）。内部的にUTCに変換して保持。  | `'2025-11-01 15:30:00+09'` |
|                 | `INTERVAL`                                        | **「期間」や「時間の間隔」**を格納する。日付/時刻型の計算に用いる。    | `'1 day'`, `'3 months'`    |

> 🐘 **どこまで通じる話か**
> 上の表のうち **`TEXT` と `TIMESTAMPTZ`（略記）は PostgreSQL 固有**です。それ以外（`INTEGER` `NUMERIC` `VARCHAR(n)` `CHAR(n)` `BOOLEAN` `DATE` `TIMESTAMP` `INTERVAL` など）は標準SQLの型なので、他の RDBMS でもほぼそのまま通じます。
> ただし**同じ名前でも中身が違う**ことがあります（例: Oracle の `FLOAT` は PostgreSQL の `REAL` とは別物、Oracle の `NUMBER` は整数専用ではない）。移植のときは名前ではなく**精度と範囲**を見比べてください。

> [!note]- `FLOAT` という名前は精度を表さない
> `FLOAT` は `DOUBLE PRECISION` の別名として使えますが、桁数を付けた `FLOAT(p)` は p が 24 以下なら `REAL` になります（実測）。
>
> ```sql
> SELECT pg_typeof(1.0::float(24)), pg_typeof(1.0::float(25));
> ```
> ```
>  real | double precision
> ```
>
> 名前だけでは精度が決まらないので、資料やコードでは `REAL` / `DOUBLE PRECISION` と書き分けた方が安全です。

## データ型の選び方

### 正確な数値か、近似値か（NUMERIC vs REAL / DOUBLE PRECISION）

|         | `NUMERIC(p, s)` / `DECIMAL(p, s)` | `REAL` / `DOUBLE PRECISION` |
| :------ | :-------------------------------- | :-------------------------- |
| 格納される値  | **正確な値**                          | **近似値**                     |
| 丸め誤差    | 生じない                              | ごくわずかに生じ、計算を重ねるほど積み上がる      |
| 速度      | 遅い（10進計算をソフトウェアで行う）               | 速い（CPU が直接扱う）               |
| 向いている用途 | 金額、在庫数、会計データ                      | 科学計算、統計分析、精度より速度が要る計算       |

⚠️ **金額計算に `REAL` / `DOUBLE PRECISION` を使わない。** 1円のズレが後から追えなくなります。厳密な精度が求められる場所では**必ず `NUMERIC`** を選んでください。

> [!note]- なぜ「近似値」になるのか
> 浮動小数点数は値を**2進数**で保持します。10進数の `0.1` は2進数にすると `0.0001100110011001100110011...` と循環小数になり、有限のビット数では表しきれません。
> そのため格納した時点でわずかに違う値へ丸められ、足し合わせるほど誤差が積み上がっていきます。`NUMERIC` は10進数のまま桁ごとに計算するのでこの丸めが起きません（その分だけ遅い）。

### 文字列型の選び方（VARCHAR / TEXT / CHAR）

| 型            | 長さ                        | いつ使うか                          |
| :----------- | :------------------------ | :----------------------------- |
| `VARCHAR(n)` | 最大 n **文字**の可変長           | 上限に業務上の意味があるとき（郵便番号7桁、コード10桁など） |
| `TEXT`       | 制限なしの可変長                  | 上限を決める理由が無いとき（本文、備考など）          |
| `CHAR(n)`    | **常に n 文字**（不足分は空白で埋められる） | **新規設計では使わない**                 |

- PostgreSQL では `VARCHAR(n)` と `TEXT` に**パフォーマンスの差はほとんどありません**。文字数制限を掛けたいかどうかだけで選びます。
- `VARCHAR(n)` の n は**バイト数ではなく文字数**です。日本語でも `VARCHAR(10)` に10文字入ります。
- 他の RDBMS との互換性を重視するなら `VARCHAR(n)`（`TEXT` は標準SQLの型ではありません）。

⚠️ **`CHAR(n)` は空白詰めの独自ルールを持つので避ける。** 領域は n 文字分を消費するのに、連結や `length()` では末尾の空白が無視されます（実測）。

```sql
CREATE TEMP TABLE c5(c char(5));
INSERT INTO c5 VALUES ('ab');
SELECT '['||c||']' AS 連結, length(c) AS 文字数, octet_length(c) AS バイト数 FROM c5;
```

```
 連結 | 文字数 | バイト数
------+--------+----------
 [ab] |      2 |        5
```

「詰められた空白は見えないのに領域は使っている」ため、桁数の勘定が合わなくなります。固定長を表現したいだけなら `VARCHAR(n)` で足ります。

### 日付・時刻型の選び方（TIMESTAMP vs TIMESTAMPTZ）

|          | `TIMESTAMP`（タイムゾーンなし）   | `TIMESTAMP WITH TIME ZONE`（`TIMESTAMPTZ`） |
| :------- | :---------------------- | :--------------------------------------- |
| 格納されるもの  | 入力された日時の**文字面そのまま**     | UTC に変換した**一瞬（時刻の点）**                    |
| 元のタイムゾーン | 持たない                    | **保存されない**（UTC に潰れる）                     |
| 出力       | どのセッションで読んでも同じ          | **セッションの `TimeZone` 設定に合わせて変換される**       |
| 向いている用途  | 壁時計としての時刻（営業時間、時間割）     | いつ起きたか（登録日時、更新日時、ログ）                     |

「タイムゾーン付き」という名前から**タイムゾーンが一緒に保存されると誤解しやすい**ですが、そうではありません。`TIMESTAMPTZ` が保存するのは UTC に直した一瞬だけで、**表示のたびにセッションのタイムゾーンで読み直しています**（実測）。

```sql
CREATE TEMP TABLE tz(t timestamp, z timestamptz);
INSERT INTO tz VALUES ('2025-11-01 15:30:00', '2025-11-01 15:30:00+09');

SET TimeZone='Asia/Tokyo';       SELECT * FROM tz;
SET TimeZone='UTC';              SELECT * FROM tz;
SET TimeZone='America/New_York'; SELECT * FROM tz;
```

```
          t          |           z
---------------------+------------------------
 2025-11-01 15:30:00 | 2025-11-01 15:30:00+09   ← Asia/Tokyo
 2025-11-01 15:30:00 | 2025-11-01 06:30:00+00   ← UTC
 2025-11-01 15:30:00 | 2025-11-01 02:30:00-04   ← America/New_York
```

`t`（`TIMESTAMP`）はどのセッションでも同じ文字列を返します。`z`（`TIMESTAMPTZ`）は**同じ一瞬を指したまま、表示だけが変わります**。

⚠️ **記録用の日時は既定で `TIMESTAMPTZ` を選ぶ。** 「国内向けサービスだから `TIMESTAMP` でいい」は後で困ります。サーバーの時刻設定が変わったり、海外から参照されたりしたとき、`TIMESTAMP` に入れた `15:30` は**どのタイムゾーンの15時半なのかを復元できません**。

### 「期間」を扱う INTERVAL 型

`INTERVAL` 型は、「1日」「3ヶ月」といった**時間の長さ**を格納します。主に日付や時刻の加算・減算に用いることで、柔軟な日時計算を実現します。

```sql
-- 現在時刻の30分後
SELECT NOW() + INTERVAL '30 minutes';

-- 特定の日付から1年2ヶ月前
SELECT '2025-01-01'::DATE - INTERVAL '1 year 2 months';
```

> ここで学んだ選択基準は、[[00_SQL研修/02_問題/01_SQLとは、CREATE文]] の設計課題でそのまま使います。

## SQL におけるリテラル

SQL 文の中に直接記述する値を**リテラル**と呼びます。

### リテラルの種類

| 種類           | 例                                       | 説明                                                               |
| :----------- | :-------------------------------------- | :--------------------------------------------------------------- |
| 文字列リテラル      | `'Hello World'`, `'123'`                | シングルクォーテーション(`'`)で囲みます。                                          |
| 数値リテラル       | `123`, `3.14`, `-5`                     | 引用符なしでそのまま記述します。                                                 |
| 論理値リテラル      | `TRUE`, `FALSE`                         | 真偽値を表すキーワードです。                                                   |
| 日付/時刻/期間リテラル | `'2025-01-01'`, `'10:30:00'`, `'1 day'` | 文字列リテラルと同じ形式で書き、文脈から解釈されます。明示するなら `DATE '2025-01-01'`（→ 型リテラル構文）。 |
| NULLリテラル     | `NULL`                                  | 値が存在しない「未知」の状態を表します。                                             |

### NULL — 「値が無い」ではなく「不明」

`NULL` は**値が不明である**ことを表す特別な状態で、空文字 `''` や数値の `0` とは**全く別物**です。`''` も `0` も「そういう値が入っている」ことを示しますが、`NULL` は「何が入るべきか分からない」ことを示します。

**`NULL` は比較できません。** 不明な値と何かを比べた結果は、真でも偽でもなく**不明（`NULL`）**になります（実測）。

```sql
SELECT 1 = NULL AS eq, 1 <> NULL AS ne, NULL = NULL AS nullnull;
```

```
   eq   |   ne   | nullnull
--------+--------+----------
 (NULL) | (NULL) | (NULL)
```

`WHERE` 句は結果が `TRUE` になった行だけを返すので、`WHERE col = NULL` は**エラーにならず、1行も返しません**。これが `NULL` の判定に `=` ではなく `IS NULL` / `IS NOT NULL` を使う理由です。

この「`TRUE` / `FALSE` / `NULL` の三値論理」は、以降の章でも形を変えて現れます。

| どこで出てくるか  | 何が起きるか                               | 詳しくは        |
| :-------- | :----------------------------------- | :---------- |
| `IS NULL` | `=` では判定できないので専用の演算子を使う              | [[02_演算子]]  |
| `NOT IN`  | リストに `NULL` が混ざると**1行も返らなくなる**       | [[02_演算子]]  |
| 集約関数      | `COUNT(*)` 以外は `NULL` を**数えない・足さない** | [[07_集約関数]] |
| 外部結合      | 相手の行が無い列が `NULL` で埋まる                | [[08_結合]]   |

## 型変換 (Type Casting)

### 明示的な型変換（推奨）

意図しない挙動を防ぎ、SQL の可読性を高めるため、データ型の変換は明示的に行うことを強く推奨します。

| 構文            | 形式                       | 特徴                                    |
| :------------ | :----------------------- | :------------------------------------ |
| **`CAST` 関数** | `CAST('string' AS type)` | **SQL標準**。最も汎用的で、他のデータベースとの互換性が高い。    |
| **`::` 型**    | `'string'::type`         | **PostgreSQL固有の構文**。簡潔で書きやすい。         |
| **型リテラル構文**   | `type 'string'`          | **SQL標準**。主に日付、時刻、期間リテラルを記述する際に用いられる。 |

*   **使い分けのポイント**
    *   **互換性優先**: `CAST` を使用します。
    *   **PostgreSQL環境での簡潔さ**: `::` が便利です。
    *   **日付/時刻/期間リテラルの明示**: `DATE '2025-11-01'` や `INTERVAL '1 day'` のように `type 'string'` 形式を使うと可読性が向上します。

### 暗黙的な型変換に頼らない

PostgreSQL は**型に厳しい**データベースです。「文脈から適当に変換してくれる」と期待して書くと、動くつもりの SQL がエラーになります。まず次の2つを見比べてください（実測）。

```sql
SELECT 100 + '50';        -- 150 … 動く
SELECT 100 + '50'::text;  -- ERROR:  operator does not exist: integer + text
```

上が動くのは「文字列が数値に変換された」からではありません。**引用符で囲んだだけの `'50'` は、まだ型が決まっていない（`unknown`）**からです。

```sql
SELECT pg_typeof('50');   -- unknown
```

`unknown` は文脈に合わせて型が決まるので、`100 + '50'` では相手に合わせて `integer` として解釈されます。一方 `'50'::text` は**すでに `text` 型だと確定している**ため、`integer + text` という演算子が無い、というエラーになります。

つまり PostgreSQL は、**型が確定した値の暗黙変換をほとんど行いません**。列と比較する場合も同じです（実測）。

```sql
CREATE TEMP TABLE p(code varchar(10), qty int);
INSERT INTO p VALUES ('1234', 5);

SELECT * FROM p WHERE qty = '5';     -- 動く（'5' は unknown → integer と解釈される）
SELECT * FROM p WHERE code = 1234;   -- ERROR:  operator does not exist: character varying = integer
```

だからこそ、**リテラルの側を列の型に合わせて書く**のが基本です（`WHERE code = '1234'`）。

⚠️ **型を合わせるために列側へキャストを書くと、インデックスが効かなくなる。** `WHERE code::int = 1234` はエラーを消せますが、加工した式にはインデックスを使えないため全件走査になります。→ [[17-2_実践_EXPLAINの読み方]] §5-①
