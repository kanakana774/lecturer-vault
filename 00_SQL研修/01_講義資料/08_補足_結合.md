# 結合を意図どおり制御する

[[08_結合]] で結合の種類を扱いました。**実務でバグになるのは、種類の選び間違いよりも「制御を外したこと」です。**

この資料では、結合が意図から外れる**3つの罠**と、その前段にある**経路の選び方**を扱います。テーブルは [[08_結合]] と同じ（[[00_SQL研修/02_問題/08_結合から使用するテーブル|08_結合から使用するテーブル]]）です。

| | 何が起きるか | どこで |
| :--- | :--- | :--- |
| 罠① | `ON`に書くべき条件を`WHERE`に書き、`LEFT JOIN`が`INNER JOIN`に化ける | [[08_結合]] §5 |
| 罠② | `LEFT JOIN`のあとに`INNER JOIN`を書き、残したはずの行が消える | §3 |
| 罠③ | 独立した1対多を2つ同時に結合し、行が掛け算で増える | §4 |

**3つとも「行が静かに消える／増える」だけで、エラーにはなりません。** だから気づきにくく、集計値が狂った状態でそのまま納品されます。

---

## 1. ON句の正体：それは「評価式」である

`ON`句には`t1.id = t2.id`と書くのが普通ですが、`ON`句が見ているのは**「この行の組をくっつけてよいか」が真かどうか**だけです。等値比較である必要はありません。

これが分かると、罠①（§`08_結合` §5）と罠②（§3）が同じ理屈だと見えてきます。

### ON TRUE：常に真なら全行がくっつく

```sql
SELECT count(*) AS 行数
FROM customers AS c
LEFT JOIN memberships AS m ON TRUE;
```

```
 行数
------
   44
(1 row)
```

`customers`11行 × `memberships`4行 = 44行。`ON`句が常に真を返すので、条件なしに全組み合わせがくっつきます（＝`CROSS JOIN`と同じ）。

### ON句に「一致しない」条件を書く

`ON`句に`IS NULL`のような条件を混ぜると、`LEFT JOIN`と`INNER JOIN`で挙動がはっきり分かれます。

```sql
-- LEFT JOIN：左は全部残り、右はすべて NULL で埋まる
SELECT c.name, o.order_id
FROM customers AS c
LEFT JOIN orders AS o
	   ON c.customer_id = o.customer_id
	  AND o.order_id IS NULL
ORDER BY c.customer_id;
```

```
  name   | order_id
---------+----------
 Alice   |     NULL
 Bob     |     NULL
 Charlie |     NULL
 (…11行すべて order_id は NULL)
(11 rows)
```

```sql
-- INNER JOIN：同じ ON 句で 0 行
SELECT c.name, o.order_id
FROM customers AS c
INNER JOIN orders AS o
	   ON c.customer_id = o.customer_id
	  AND o.order_id IS NULL;
```

```
 name | order_id
------+----------
(0 rows)
```

`orders.order_id`は主キーなので`NULL`になりません。つまり`ON`句は**どの行の組に対しても真にならない**。

- `LEFT JOIN`は「くっつく相手がいなかった」と解釈し、**左を全部残して右を`NULL`で埋める**
- `INNER JOIN`は「くっつく組が1つもない」ので**0行**

**`ON`句の条件は、行を消す力を持ちません。** 消すのは`WHERE`句だけです。ここが罠①の正体です。

## 2. 経路の選択：ER図から意味の正しいルートを探す

罠の話に入る前に、その前段です。**結合を書き間違える前に、そもそも通る道を間違えることがあります。**

![[sql_lesson2_ERD.png]]

SQLを書くときは、実行順序とは逆に考えます。

### ステップ1：欲しい列を決める

「顧客名（`customers.name`）と、その人が買った商品名（`products.product_name`）が欲しい」

### ステップ2：ER図で経路を見つける

始点`CUSTOMERS`から終点`PRODUCTS`まで、どの表を経由するか辿ります。

```
CUSTOMERS → ORDERS → ORDERITEMS → PRODUCTS
```

### ステップ3：意味の正しい経路を選ぶ

`CUSTOMERS`から`PRODUCTS`へは**別の道もあります**。そして道が違えば、答えの意味が変わります。

| 経路 | 何が取れるか |
| :--- | :--- |
| `CUSTOMERS → ORDERS → ORDERITEMS → PRODUCTS` | **買った商品**（お金を払った事実） |
| `CUSTOMERS → REVIEWS → PRODUCTS` | **レビューを書いた商品**（買っていなくても書ける） |

どちらもSQLとしては正しく動き、それらしい表が返ります。**エラーにならないので、経路を間違えたことに気づけません。**

> ⚠️ **「どの表を経由したか」で答えのビジネス的な意味が変わります。** 結合を書く前に、ER図の上で指を動かして経路を確認してください。

## 3. 罠②：LEFT JOIN を殺す INNER JOIN

3つ以上のテーブルを結合するとき、**結合の順番と種類**を間違えると行が消えます。

### 失敗例

「**すべての顧客**を表示し、注文があればその商品名も出す」という意図で書いたSQLです。

```sql
SELECT
	c.name,
	p.product_name
FROM
	customers AS c
	LEFT JOIN orders AS o ON c.customer_id = o.customer_id
	INNER JOIN orderitems AS oi ON o.order_id = oi.order_id   -- ← ここが罠
	INNER JOIN products AS p ON oi.product_id = p.product_id;
```

21行返ってきます。それらしい表なのでこのまま通してしまいがちですが、**何人の顧客が出ているかを数える**と、意図から外れているのが分かります。

```sql
SELECT
	count(*) AS 行数,
	count(DISTINCT c.customer_id) AS 顧客数
FROM
	customers AS c
	LEFT JOIN orders AS o ON c.customer_id = o.customer_id
	INNER JOIN orderitems AS oi ON o.order_id = oi.order_id
	INNER JOIN products AS p ON oi.product_id = p.product_id;
```

```
 行数 | 顧客数
------+--------
   21 |      9
(1 row)
```

顧客は11人いるのに**9人**しか出ていません。

1. `customers LEFT JOIN orders`の時点では、注文のない顧客も`o.order_id`が`NULL`の行として残っている
2. 次の`INNER JOIN orderitems`で`oi.order_id = o.order_id`を評価する。`o.order_id`が`NULL`なので、この条件は**真にならない**
3. `INNER JOIN`は真にならない行を捨てるので、**注文のない顧客がここで消える**

消えたのは **Charlie と Grace**（一度も注文していない2人）です。せっかく`LEFT JOIN`で残したのに、次の`INNER JOIN`が取り消してしまいました。

### 解決策：たどった先も LEFT JOIN にする

```sql
SELECT
	c.name,
	p.product_name
FROM
	customers AS c
	LEFT JOIN orders AS o ON c.customer_id = o.customer_id
	LEFT JOIN orderitems AS oi ON o.order_id = oi.order_id
	LEFT JOIN products AS p ON oi.product_id = p.product_id;
```

23行返り、**同じように数えると顧客数は11**。全員が残りました。

**`products`まで`LEFT JOIN`にする必要があります。** `products`は`orderitems`の親なので一見`INNER`でよさそうですが、`oi`が`NULL`で埋まった行では`oi.product_id`も`NULL`なので、`= p.product_id`が真になりません。ここだけ`INNER`に戻すと、また9人に減ります（実測: 21行・9顧客）。

> ⚠️ **一度`LEFT JOIN`した表を経由してさらに結合するなら、その先も`LEFT JOIN`にする。** 「`LEFT`で残した行は、右側の列がすべて`NULL`になっている」ことを忘れると必ず踏みます。

## 4. 罠③：行の増殖（独立した1対多を2つ結合する）

1つの表に対して、**互いに関係のない「1対多」を2つ同時に結合**すると、行数が掛け算で増えます。

### シナリオ

`warehouses`（倉庫）を中心に、次の2つを一度に出したいとします。

- 1つの倉庫には**複数の在庫**（`inventory`）がある … 1対多
- 1つの倉庫には**複数のスタッフ**（`staff`）がいる … 1対多

**在庫とスタッフの間には何の関係もありません。** ここが原因になります。

### 実行してしまうと危険なSQL

```sql
SELECT
	w.warehouse_name,
	i.product_id,
	s.name AS staff_name
FROM
	warehouses AS w
	INNER JOIN inventory AS i ON w.warehouse_id = i.warehouse_id
	INNER JOIN staff AS s ON w.warehouse_id = s.warehouse_id
ORDER BY
	w.warehouse_name, i.product_id, s.name;
```

**36行**返ります。Osaka倉庫だけを抜き出すと、何が起きたか一目で分かります。**在庫6件 × スタッフ2人 = 12行**、同じ`product_id`が2回ずつ出ています。

```sql
-- 上のSQLに WHERE を足して Osaka だけ見る
SELECT
	w.warehouse_name,
	i.product_id,
	s.name AS staff_name
FROM
	warehouses AS w
	INNER JOIN inventory AS i ON w.warehouse_id = i.warehouse_id
	INNER JOIN staff AS s ON w.warehouse_id = s.warehouse_id
WHERE
	w.warehouse_name = 'Osaka Warehouse'
ORDER BY
	i.product_id, s.name;
```

```
 warehouse_name  | product_id | staff_name
-----------------+------------+------------
 Osaka Warehouse |          1 | Frank
 Osaka Warehouse |          1 | Quinn
 Osaka Warehouse |          4 | Frank
 Osaka Warehouse |          4 | Quinn
 Osaka Warehouse |          5 | Frank
 Osaka Warehouse |          5 | Quinn
 Osaka Warehouse |          8 | Frank
 Osaka Warehouse |          8 | Quinn
 Osaka Warehouse |         11 | Frank
 Osaka Warehouse |         11 | Quinn
 Osaka Warehouse |         12 | Frank
 Osaka Warehouse |         12 | Quinn
(12 rows)
```

倉庫ごとに数えると、**掛け算になっている**ことがはっきりします。

```sql
SELECT
	w.warehouse_name,
	count(*) AS 結合後の行数,
	count(DISTINCT i.product_id) AS 在庫件数,
	count(DISTINCT s.staff_id) AS スタッフ数
FROM
	warehouses AS w
	INNER JOIN inventory AS i ON w.warehouse_id = i.warehouse_id
	INNER JOIN staff AS s ON w.warehouse_id = s.warehouse_id
GROUP BY
	w.warehouse_name
ORDER BY
	w.warehouse_name;
```

```
 warehouse_name  | 結合後の行数 | 在庫件数 | スタッフ数
-----------------+--------------+----------+------------
 Osaka Warehouse |           12 |        6 |          2
 Tokyo Warehouse |           24 |        8 |          3
(2 rows)
```

「在庫6 + スタッフ2 = 8行くらい」と思うところが、`6 × 2 = 12行`。結合は条件に合うものを**すべて組み合わせる**ので、在庫とスタッフの全パターンが作られます。

### この罠が深刻な理由：集計が狂う

行が増えただけなら見れば気づきます。**問題は、その上で`SUM`すると静かに間違うことです。**

```sql
SELECT
	w.warehouse_name,
	SUM(i.stock_quantity) AS total_stock
FROM
	warehouses AS w
	INNER JOIN inventory AS i ON w.warehouse_id = i.warehouse_id
	INNER JOIN staff AS s ON w.warehouse_id = s.warehouse_id
GROUP BY
	w.warehouse_name
ORDER BY
	w.warehouse_name;
```

```
 warehouse_name  | total_stock
-----------------+-------------
 Osaka Warehouse |         490
 Tokyo Warehouse |         816
(2 rows)
```

`staff`の結合を外すと、正しい在庫合計が出ます。

```sql
SELECT
	w.warehouse_name,
	SUM(i.stock_quantity) AS total_stock
FROM
	warehouses AS w
	INNER JOIN inventory AS i ON w.warehouse_id = i.warehouse_id
GROUP BY
	w.warehouse_name
ORDER BY
	w.warehouse_name;
```

```
 warehouse_name  | total_stock
-----------------+-------------
 Osaka Warehouse |         245
 Tokyo Warehouse |         272
(2 rows)
```

**Osaka は2倍（スタッフ2人）、Tokyo は3倍（スタッフ3人）** になっています。`490 = 245 × 2`、`816 = 272 × 3`。**在庫がスタッフの人数分だけ重複して足されている**わけです。

数字が「ありえない大きさ」なら気づけますが、倍率が2倍程度だと**それらしい数字のまま間違う**ので、いちばん怖いパターンです。

### 解決策1：結合する前に集計しておく

```sql
WITH warehouse_stock AS (
	-- 先に倉庫ごとの在庫合計を出す（この時点では1倉庫1行）
	SELECT warehouse_id, SUM(stock_quantity) AS total_stock
	FROM inventory
	GROUP BY warehouse_id
)
SELECT
	w.warehouse_name,
	ws.total_stock,
	s.name AS staff_name
FROM
	warehouses AS w
	LEFT JOIN warehouse_stock AS ws ON w.warehouse_id = ws.warehouse_id
	LEFT JOIN staff AS s ON w.warehouse_id = s.warehouse_id
ORDER BY
	w.warehouse_name, s.name;
```

```
  warehouse_name   | total_stock | staff_name
-------------------+-------------+------------
 Fukuoka Warehouse |        NULL | Rupert
 Osaka Warehouse   |         245 | Frank
 Osaka Warehouse   |         245 | Quinn
 Tokyo Warehouse   |         272 | Eve
 Tokyo Warehouse   |         272 | Oscar
 Tokyo Warehouse   |         272 | Peggy
(6 rows)
```

**在庫を「1倉庫1行」にしてから結合したので、行数はスタッフの数だけ**（6行）で済み、`total_stock`も正しい値です。同じ値が繰り返し表示されますが、**足し合わせていない**ので集計は狂いません。

Fukuoka の`total_stock`が`NULL`なのは、在庫レコードが1件も無いためです（`LEFT JOIN`なので倉庫の行自体は残っています）。

### 解決策2：クエリを分ける

「在庫一覧」と「スタッフ一覧」は、そもそもビジネス上べつの情報です。1つの表に無理に押し込めず、**別々に取得してアプリケーション側で並べる**のも正しい設計です。

> ⚠️ **結合結果の行数が、親の行数からも子の行数からも説明できないときは、独立した1対多を同時に結合していないか確認してください。**
> ここで`DISTINCT`を付けて重複を消すのは**対症療法で、危険です**。行数は直っても、`SUM`はすでに狂っています。

> [!note]- なぜ1対多でテーブルが分かれるのか
> `orders`に`amount`や`method`を持たせず`payments`を分けているのも同じ理屈です。
> - **分割払いに対応するため** … 1つの注文に対して支払いが複数回発生しうる
> - **状態を表せるため** … 「注文済みだが未払い」を、`payments`にレコードが無いことで表現できる
>
> **「1対多」の関係があるところでは必ず表が分かれます。** 結合は、分かれた関係を元の業務の形に戻す作業です（→ [[00_なぜテーブルを分けるのか]]）。

## 5. 非等価結合：IDの一致だけが結合ではない

`ON`句は評価式（§1）なので、`=`以外も書けます。実務では**外部キーが無くても「意味的な繋がり」で結合する**ことがあり、これを**非等価結合**と呼びます。

### シナリオ：勤務日時点での時給を特定する

- **`attendance_logs`（勤怠実績）** … 誰が（`employee_id`）、いつ（`work_date`）、何時間（`hours_worked`）働いたか
- **`historical_rates`（時給マスタ）** … 従業員ごとの時給の履歴。従業員IDの列名が`staff_code`と**異なり**、昇給によって適用期間（`start_date`〜`end_date`）ごとに時給が違う

この2つには外部キー制約がなく、ID の列名も違います。**IDだけで結合すると、1つの勤務に複数の時給が紐づいて給与が計算できません。**

「**勤務日が、その時給の適用期間内にある**」という条件を足して、はじめて正しい時給が1つに決まります。

```sql
WITH
	attendance_logs (employee_id, work_date, hours_worked) AS (
		VALUES
			(101, DATE '2025-10-25', 8),
			(101, DATE '2025-11-10', 8),   -- 昇給後の勤務
			(202, DATE '2025-11-15', 7)
	),
	historical_rates (staff_code, rate, start_date, end_date) AS (
		VALUES
			(101, 1000, DATE '2025-04-01', DATE '2025-10-31'),   -- 101 の旧時給
			(101, 1100, DATE '2025-11-01', DATE '2026-03-31'),   -- 101 の新時給（昇給）
			(202, 1200, DATE '2025-04-01', DATE '2026-03-31')
	)
SELECT
	a.employee_id,
	a.work_date,
	a.hours_worked,
	r.rate,
	a.hours_worked * r.rate AS daily_wage
FROM
	attendance_logs AS a
	LEFT JOIN historical_rates AS r
		ON a.employee_id = r.staff_code                          -- 条件1: 列名の違うIDで紐付ける
		AND a.work_date BETWEEN r.start_date AND r.end_date      -- 条件2: 勤務日が適用期間内
ORDER BY
	a.employee_id, a.work_date;
```

**実行結果:**

```
 employee_id | work_date  | hours_worked | rate | daily_wage
-------------+------------+--------------+------+------------
         101 | 2025-10-25 |            8 | 1000 |       8000
         101 | 2025-11-10 |            8 | 1100 |       8800
         202 | 2025-11-15 |            7 | 1200 |       8400
(3 rows)
```

同じ従業員101 の勤務が、勤務日によって**違う時給に結合されている**ところが要点です。

- `2025-10-25`の勤務 → 適用期間`2025-04-01`〜`2025-10-31`の時給`1000`
- `2025-11-10`の勤務 → 適用期間`2025-11-01`〜`2026-03-31`の時給`1100`

`ON`句に「IDの一致」と「期間の内外」という**性質の違う条件を組み合わせる**ことで、単純な結合では出せない答えが得られます。

> ⚠️ 日付は`DATE '2025-10-25'`のように**日付型として書く**こと。`'2025-10-25'`のままだと文字列比較になります。`YYYY-MM-DD`形式なら結果はたまたま合いますが、**日付として比べていない**ので、形式が違うデータが混ざった瞬間に壊れます。

## 6. まとめ

| | 覚えること |
| :--- | :--- |
| **`ON`句は評価式** | 「くっつけてよいか」を判定するだけ。**行を消す力はない**（§1） |
| **経路が意味を決める** | ER図で、業務的に正しい表を辿る。間違えてもエラーにならない（§2） |
| **罠①** | `OUTER JOIN`の右側を絞るなら`ON`句へ。`WHERE`に書くと`INNER JOIN`に化ける（[[08_結合]] §5） |
| **罠②** | `LEFT JOIN`した先をさらに結合するなら、そこも`LEFT JOIN`（§3） |
| **罠③** | 独立した1対多を同時に結合すると行が掛け算で増え、`SUM`が狂う（§4） |

**3つの罠は、どれもエラーを出しません。** だから最後に必ず**行数を確認する**癖をつけてください。

- 結合しても行数が変わらないはずなのに増えた → 罠③
- 一覧に出るはずの件数より少ない → 罠①か罠②
- 集計値が「それらしいが微妙に大きい」 → 罠③
