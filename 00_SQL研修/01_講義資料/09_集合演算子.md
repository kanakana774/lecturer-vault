### SQLの集合演算子とは

集合演算子は、2つ以上の`SELECT`文の結果を、行を追加する形で**縦方向に結合**するための演算子です。

`JOIN`が「列を横に増やす」のに対し、集合演算子は「行を縦に増やす（あるいは減らす）」演算だと考えてください。つなぐ相手は**テーブルではなく`SELECT`文の結果**なので、片方は`WHERE`で絞っただけ、もう片方は`JOIN`した結果、というように**作り方が違っていても構いません**。

**🐘 マークは PostgreSQL 固有の話です。** それ以外はどのDBでも通じます。この章の演算子はほとんどが標準SQLなので、🐘 は数えるほどしか出てきません。

## 1. 4つの演算子

「**顧客がいる街**」と「**倉庫がある街**」という2つの集合を、4通りにつないでみます。

### 1-1. UNION：和集合（重複を排除）

複数の`SELECT`文の結果を1つにまとめます。その際、**完全に重複する行は1行にまとめて表示**します。

```sql
SELECT 列リスト FROM テーブル1
UNION
SELECT 列リスト FROM テーブル2;
```

#### 具体例

顧客がいる街と倉庫がある街を、まとめて「関係のある街の一覧」にします。

```sql
SELECT city FROM customers
UNION
SELECT location FROM warehouses
ORDER BY city;
```

**実行結果:** 11行 + 3行 = 14行が、**4行**になります。

```
  city
---------
 Fukuoka
 Nagoya
 Osaka
 Tokyo
(4 rows)
```

### 1-2. UNION ALL：和集合（重複を保持）

`UNION`とは異なり、**重複する行もそのまま全て表示**します。重複チェックを行わない分、`UNION`より高速です（→ §5）。

```sql
SELECT city FROM customers
UNION ALL
SELECT location FROM warehouses;
```

**実行結果:** 14行がそのまま出ます。

```
  city
---------
 Tokyo
 Osaka
 Nagoya
 Tokyo
 Tokyo
 Fukuoka
 Tokyo
 Osaka
 Nagoya
 Tokyo
 Osaka
 Tokyo
 Osaka
 Fukuoka
(14 rows)
```

上の11行が`customers`、下の3行が`warehouses`です。**単に下にくっつけているだけ**だと分かります。

### 1-3. INTERSECT：積集合（共通部分）

**両方に共通して存在する行のみ**を返します。`UNION`と同じく重複は排除されます。

```sql
SELECT city FROM customers
INTERSECT
SELECT location FROM warehouses
ORDER BY city;
```

**実行結果:** 顧客も倉庫もある街だけが残ります。

```
  city
---------
 Fukuoka
 Osaka
 Tokyo
(3 rows)
```

#### INTERSECT ALL：個数の少ない方に合わせて残す

`UNION`に`UNION ALL`があるように、`INTERSECT`にも`INTERSECT ALL`があります。重複を排除せず、**両側の個数のうち少ない方だけ**残します。

「スタッフの配属倉庫」と「在庫がある倉庫」で比べます。倉庫1はスタッフ3人・在庫8品目、倉庫2はスタッフ2人・在庫6品目です。

```sql
SELECT warehouse_id FROM staff
INTERSECT ALL
SELECT warehouse_id FROM inventory
ORDER BY warehouse_id;
```

```
 warehouse_id
--------------
            1
            1
            1
            2
            2
(5 rows)
```

倉庫1が`min(3, 8) = 3`行、倉庫2が`min(2, 6) = 2`行。`ALL`を付けなければ`1`と`2`の2行です。

### 1-4. EXCEPT / MINUS：差集合

最初の`SELECT`文の結果から、2番目の`SELECT`文の結果に**存在する行を取り除いた結果**を返します。こちらも重複は排除されます。

DBMSによってキーワードが異なります。**標準SQLは`EXCEPT`**で、`MINUS`は Oracle 独自の綴りです。

- **`EXCEPT`**: PostgreSQL, SQL Server, SQLite, MySQL 8.0.31以降
- **`MINUS`**: Oracle

```sql
SELECT city FROM customers
EXCEPT
SELECT location FROM warehouses
ORDER BY city;
```

**実行結果:** 「顧客はいるのに倉庫がない街」が分かります。

```
  city
--------
 Nagoya
(1 row)
```

#### EXCEPT は左右を入れ替えると結果が変わる

`UNION`と`INTERSECT`は左右を入れ替えても同じ結果になりますが、**`EXCEPT`だけは変わります**。「AとBの違い」ではなく「AからBを引く」演算だからです。

```sql
SELECT location FROM warehouses
EXCEPT
SELECT city FROM customers
ORDER BY location;
```

```
 location
----------
(0 rows)
```

0件です。「倉庫はあるが顧客がいない街」は無い、という別の問いの答えになりました。**入れ替えると問いそのものが変わります。**

#### EXCEPT ALL：個数で引き算する

`EXCEPT ALL`は重複を排除せず、**左の個数から右の個数を引いた分**だけ残します。

```sql
SELECT warehouse_id FROM staff
EXCEPT ALL
SELECT warehouse_id FROM inventory
ORDER BY warehouse_id;
```

```
 warehouse_id
--------------
            3


(3 rows)
```

倉庫3はスタッフ1人・在庫0品目なので`1 - 0 = 1`行。未配属（`NULL`）は2人・在庫側に無いので`2 - 0 = 2`行。倉庫1と2は左より右のほうが多いため0行です。`ALL`を付けなければ`3`と`NULL`の2行になります。

`INTERSECT ALL`と`EXCEPT ALL`は、**突合で「同じ行が何行あるか」まで一致させたいとき**に使います（→ §4-2）。

> 🐘 `INTERSECT ALL` / `EXCEPT ALL` は標準SQLですが、**SQL Server は未対応**です（`INTERSECT` / `EXCEPT` は使えます）。MySQL は 8.0.31 以降で使えます。

#### 対称差（どちらか片方にしかない）

両方向の`EXCEPT`を`UNION`でつなぐと、「片方にしかない行」が取れます。

「管理職がいる倉庫」と「在庫がある倉庫」で見てみます。

```sql
(SELECT warehouse_id FROM staff WHERE position LIKE '%Manager'
 EXCEPT
 SELECT warehouse_id FROM inventory)
UNION
(SELECT warehouse_id FROM inventory
 EXCEPT
 SELECT warehouse_id FROM staff WHERE position LIKE '%Manager')
ORDER BY 1;
```

```
 warehouse_id
--------------
            2
            3
(2 rows)
```

倉庫3（Fukuoka）は**管理職はいるが在庫が無い**、倉庫2（Osaka）は**在庫はあるが管理職がいない**。片方向だけでは、どちらか一方しか見つかりません。

## 2. 書き方の規則

意味を覚えても、ここを知らないと**エラーで手が止まります**。4つあります。

### 2-1. 列の数は一致、型は「互換」であればよい

**列の数は完全に一致していなければなりません。**

```sql
SELECT 1, 2 UNION ALL SELECT 3;
-- ERROR:  each UNION query must have the same number of columns
```

一方、**データ型は「一致」でなく「互換であればよい」**、つまり片方に寄せられるなら通ります。

```sql
SELECT 1 AS n UNION ALL SELECT 2.5;   -- 通る（両方 numeric に解決される）
```

```
  n
-----
   1
 2.5
```

寄せられない組み合わせはエラーになります。

```sql
SELECT 1 AS n UNION ALL SELECT 'abc';
-- ERROR:  invalid input syntax for type integer: "abc"
```

> ⚠️ `integer` と `numeric` のように**黙って型が変わる**ことがあります。件数や桁数が想定と違うときは、まずここを疑ってください。

### 2-2. 列名は左端の SELECT が決める

結果の列名には、**いちばん左の`SELECT`で付けた名前だけ**が使われます。右側の列名は結果からは見えません。

```sql
SELECT city FROM customers
UNION
SELECT location FROM warehouses
ORDER BY location;
-- ERROR:  column "location" does not exist
-- DETAIL:  There is a column named "location" in table "*SELECT* 2",
--          but it cannot be referenced from this part of the query.
```

`city`と`location`のように**左右で列名が違う**場合は、左端の`SELECT`で意味の通る別名を付けます。

```sql
SELECT city AS place FROM customers
UNION
SELECT location FROM warehouses
ORDER BY place;
```

### 2-3. ORDER BY / LIMIT は全体に1つ、いちばん最後に書く

枝（個々の`SELECT`）に直接書くと**構文エラー**になります。

```sql
SELECT city FROM customers ORDER BY city
UNION
SELECT location FROM warehouses;
-- ERROR:  syntax error at or near "UNION"
```

正しくは、**全体の末尾に1つだけ**書きます。

```sql
SELECT city FROM customers
UNION
SELECT location FROM warehouses
ORDER BY city;
```

どうしても枝ごとに絞りたいときは、**枝を括弧で囲みます**。

```sql
(SELECT city     FROM customers  ORDER BY city     LIMIT 2)
UNION ALL
(SELECT location FROM warehouses ORDER BY location LIMIT 2);
```

```
  city
---------
 Fukuoka
 Nagoya
 Fukuoka
 Osaka
(4 rows)
```

> 🐘 **`LIMIT`は標準SQLではありません。** 標準は`FETCH FIRST 2 ROWS ONLY`で、PostgreSQL はどちらも使えます（Oracle・SQL Server は`FETCH FIRST`側）。`ORDER BY`は標準なので、そのままどのDBでも通じます。

> ⚠️ **`ORDER BY`を書かなければ、結果の並び順は保証されません。** 集合演算子は重複排除に並べ替えやハッシュを使うため、入力順にも辞書順にもなりません。**順序が要るなら必ず`ORDER BY`を書く。**

### 2-4. INTERSECT が先に結合する

3つ以上つないだとき、**`INTERSECT`は`UNION`／`EXCEPT`より優先して評価されます**（掛け算が足し算より先に計算されるのと同じ）。左から順に処理されるわけではありません。

```sql
-- 括弧なし → EXCEPT (INTERSECT ...) と解釈される
SELECT city FROM customers
EXCEPT
SELECT location FROM warehouses
INTERSECT
SELECT 'Tokyo'
ORDER BY 1;
```

```
  city
---------
 Fukuoka
 Nagoya
 Osaka
(3 rows)
```

```sql
-- 左から順に、と書いたつもりならこちら
(SELECT city FROM customers
 EXCEPT
 SELECT location FROM warehouses)
INTERSECT
SELECT 'Tokyo'
ORDER BY 1;
```

```
 city
------
(0 rows)
```

3件と0件。**同じ順番に並べただけで結果がまるで違います。**

> ⚠️ **3つ以上つなぐときは、必ず括弧で意図を書く。** エラーにならず黙って違う結果を返すため、レビューでも見落とされます。

## 3. NULL の扱い

**集合演算子は`NULL`同士を「同じ値」とみなします。**

`WHERE`で`=`を使った比較では、`NULL = NULL`は`TRUE`になりません。だから`WHERE col = NULL`では`NULL`の行は取れず、`IS NULL`を使う必要がありました（02章）。**集合演算子だけは、この扱いが違います。**

`staff`テーブルには配属倉庫が`NULL`のインターンが2人（Heidi、Sybil）います。ここを使って確かめます。

### 3-1. 4つの演算子は NULL をどう扱うか

「Clerk と Intern の配属倉庫」（A）と「2022年以降に入社した人の配属倉庫」（B）という2つの集合を使います。**どちらにも`NULL`が2件ずつ**含まれます。

```sql
-- A：Clerk と Intern の配属倉庫 → 1, 2, 2, NULL, NULL
SELECT warehouse_id FROM staff WHERE position IN ('Clerk', 'Intern');

-- B：2022年以降に入社した人の配属倉庫 → 1, 2, 3, NULL, NULL
SELECT warehouse_id FROM staff WHERE hire_date >= '2022-01-01';
```

この2つをつなぐと、合計4件の`NULL`はこう扱われます。

| つなぎ方 | `NULL`がどうなるか | 件数 |
| :--- | :--- | :--- |
| `A UNION B` | **1行にまとまる** | 4件 |
| `A UNION ALL B` | **4行そのまま残る** | 10件 |
| `A INTERSECT B` | **両方にある値として残る** | 3件 |
| `B EXCEPT A` | 右にも`NULL`があるので**打ち消されて消える** | 1件 |

`INTERSECT`で実際に見てみます。

```sql
SELECT warehouse_id FROM staff WHERE position IN ('Clerk', 'Intern')
INTERSECT
SELECT warehouse_id FROM staff WHERE hire_date >= '2022-01-01'
ORDER BY warehouse_id;
```

```
 warehouse_id
--------------
            1
            2

(3 rows)
```

最終行の空欄が`NULL`です。**`=`では取り出せない`NULL`が、「両方にある値」として取れています。**

### 3-2. NOT IN の罠と、EXCEPT による回避

「**まだ誰も持っていない会員ランク**」を探します。`memberships`には Bronze / Silver / Gold / Platinum の4つがあり、Platinum は誰も持っていないので**答えは Platinum の1件**です。

`customers`が実際に持っているランクを`NOT IN`に並べて書けば、ちゃんと取れます。

```sql
SELECT membership_id, rank_name
FROM memberships
WHERE membership_id NOT IN (1, 2, 3);
```

```
 membership_id | rank_name
---------------+-----------
             4 | Platinum
(1 row)
```

ところが、**このリストに`NULL`を1つ足すだけで0件になります。**

```sql
SELECT membership_id, rank_name
FROM memberships
WHERE membership_id NOT IN (1, 2, 3, NULL);
```

```
 membership_id | rank_name
---------------+-----------
(0 rows)
```

`4 NOT IN (1, 2, 3, NULL)` は「4は`NULL`と違う」を判定できず`UNKNOWN`になり、`WHERE`は`TRUE`でない行を落とすためです。**エラーが出ず、静かに0件になる**のが厄介なところです。

そして実務では、この`NULL`が見えません。右側の値は手で並べるのではなく**別のテーブルから作る**ことになるからです（10章のサブクエリ）。`customers.membership_id`にはランク未設定の Charlie がいるので、**その形で書くと必ずこの罠を踏みます。**

集合演算子で書けば、この罠がありません。`NULL`を値として扱うからです。

```sql
SELECT membership_id FROM memberships
EXCEPT
SELECT membership_id FROM customers
ORDER BY membership_id;
```

```
 membership_id
---------------
             4
(1 row)
```

`customers`側に`NULL`が入っていても、答えは Platinum の1件で変わりません。

> ⚠️ **`NOT IN`の右側に`NULL`が混ざりうるなら、`NOT IN`は使わない。** 「0件のはずがないのに0件」はまずこれを疑ってください。避け方は2つで、右側から`NULL`を除くか、集合演算子で書くかです。

## 4. 実務での使いどころ

### 4-1. UNION ALL：横持ちを縦持ちに変換する

1行に複数の日付が並んだ表を、「イベント種別」列を持つ縦長の履歴に変えます。集計やタイムライン表示の前処理として頻出です。

```sql
SELECT order_id, 'Shipped'   AS event, shipped_date  AS event_date
FROM shipments WHERE order_id IN (1, 5)
UNION ALL
SELECT order_id, 'Delivered',          delivery_date
FROM shipments WHERE order_id IN (1, 5)
ORDER BY order_id, event_date;
```

```
 order_id |   event   | event_date
----------+-----------+------------
        1 | Shipped   | 2022-01-06
        1 | Delivered | 2022-01-08
        5 | Shipped   | 2022-01-27
        5 | Delivered |
(4 rows)
```

`'Shipped'` / `'Delivered'` のような**固定値の列を足して行の出自を持たせる**のが定石です。注文5はまだ配送中なので`delivery_date`が`NULL`のまま出ています。

ここで`UNION`を使ってはいけません。出荷と配達は、たまたま日付が一致しても別の行だからです。同じ形をした月次テーブル（`sales_202601`, `sales_202602`, …）を1本にまとめるのも`UNION ALL`の仕事です。

### 4-2. EXCEPT：新旧データの突合

**`EXCEPT`の実務での一番の使い道がこれです。** システム移行やバッチ再実行の後、移行元と移行先が一致しているかを確認します。

**両方向を調べて、両方が0件で、はじめて「一致」と言えます。** 片方向だけでは、移行先に余計な行が増えていても気づけません。

ここでは移行先のつもりのデータを`WITH`で作り、`orders`と突き合わせてみます（注文4が欠落、注文2の`status`が変化、注文99が余分）。

```sql
WITH orders_new AS (
	SELECT
		order_id,
		CASE WHEN order_id = 2 THEN 'Completed' ELSE status END AS status
	FROM orders
	WHERE order_id <> 4
	UNION ALL
	SELECT 99, 'Completed'
)
(SELECT '移行元のみ' AS side, order_id, status FROM orders
 EXCEPT ALL
 SELECT '移行元のみ',        order_id, status FROM orders_new)
UNION ALL
(SELECT '移行先のみ' AS side, order_id, status FROM orders_new
 EXCEPT ALL
 SELECT '移行先のみ',        order_id, status FROM orders)
ORDER BY order_id, side;
```

```
    side    | order_id |  status
------------+----------+-----------
 移行元のみ |        2 | Pending
 移行先のみ |        2 | Completed
 移行元のみ |        4 | Cancelled
 移行先のみ |       99 | Completed
(4 rows)
```

注文2は**両側に出ている＝値が変わった行**、注文4は**消えた行**、注文99は**増えた行**だと読み取れます。

ここで`EXCEPT`ではなく`EXCEPT ALL`を使っているのは、**同じ行が何行あるかまで一致させたい**からです（→ §1-4）。`EXCEPT`だと、片方に重複行が余っていても消えてしまい、突合の漏れになります。

### 4-3. VALUES を片側に置く：マスタに無い値を探す

「取り込もうとしている商品名のうち、マスタに無いものはどれか」を調べます。

```sql
SELECT * FROM (VALUES ('Laptop'), ('Tablet'), ('Socks'), ('Keyboard')) AS t(name)
EXCEPT
SELECT product_name FROM products
ORDER BY name;
```

```
   name
----------
 Keyboard
 Tablet
(2 rows)
```

`'Tablet'`と`'Keyboard'`が商品マスタに未登録だと分かります。

#### VALUES は INSERT 専用ではない

`VALUES`は`INSERT`の一部ではありません。**それ自体が「行の並び」を作る式**で、`SELECT`の結果と同じように扱えます。単独で文にもなります。

```sql
VALUES (1, 'a'), (2, 'b');
```

```
 column1 | column2
---------+---------
       1 | a
       2 | b
(2 rows)
```

`SELECT`の結果と同じ扱いなので、`ORDER BY`や`LIMIT`も付けられ、**集合演算子の枝にそのまま置けます**（`SELECT`で包まなくてよい）。

```sql
VALUES ('Laptop'), ('Tablet')
EXCEPT
SELECT product_name FROM products;
```

```
 column1
---------
 Tablet
(1 row)
```

列名が`column1`になっているのは、`VALUES`側に名前が無く、**左端が列名を決める**（§2-2）ためです。上の最初の例で`SELECT * FROM (VALUES ...) AS t(name)`と書いたのは、**列名を`name`にしたかった**からです。

`VALUES`が置ける場所は、この章までで出てきたものだと次の4つです。

| 置き場所 | 例 |
| :--- | :--- |
| `INSERT`の値 | `INSERT INTO t VALUES (1), (2)` |
| 単独の文 | `VALUES (1), (2);` |
| 集合演算子の枝 | `VALUES (1) UNION SELECT ...` |
| `FROM`句（名前を付ける） | `FROM (VALUES (1)) AS t(id)` |

> 🐘 **列名が`column1`, `column2` … になるのは PostgreSQL 固有です。** 標準SQLは`VALUES`の列名を定めていないので、DBによって違います。名前を使うなら`AS t(...)`で自分で付けてください。

### 4-4. EXCEPT：全称命題（すべて〜である）を解く

集合演算子は「否定」を表現するのが得意です。これを利用して、**「メンバー全員が〇〇であるチーム」**のような、集約関数で書くと複雑になるクエリを簡潔に書けます。

「全員が待機」を直接書くのは難しいので、**「全体」から「待機でない人がいるチーム」を引きます**。

```sql
WITH
	teams (member, team_id, status) AS (
		VALUES
			('ジョー', 1, '待機'),
			('ケン', 1, '出動中'),
			('ミック', 1, '待機'),
			('カレン', 2, '出動中'),
			('キース', 2, '休暇'),
			('ジャン', 3, '待機'),
			('ハート', 3, '待機'),
			('ディック', 3, '待機'),
			('ベス', 4, '待機'),
			('アレン', 5, '出動中'),
			('ロバート', 5, '休暇'),
			('ケーガン', 5, '待機')
	)

-- 全チーム
SELECT team_id FROM teams

EXCEPT

-- 待機じゃないメンバーがいるチーム
SELECT team_id FROM teams WHERE status <> '待機'

ORDER BY team_id;
```

```
 team_id
---------
       3
       4
(2 rows)
```

チーム3（全員待機）とチーム4（1人だけで待機）が残ります。

## 5. パフォーマンス：既定は UNION ALL

`UNION` / `INTERSECT` / `EXCEPT` は、**重複を排除するために並べ替え（またはハッシュ）を行います**。行数が多いとここが効いてきます。

**重複が起きないと分かっている、あるいは重複しても構わないなら`UNION ALL`を使ってください。** `UNION ALL`は結果を単に連結するだけなので、この処理が丸ごと不要になります。

逆に言えば、`UNION`を選ぶのは「重複が起きうる**うえに**排除したい」場合だけです。「なんとなく`UNION`」は避けます。

`INTERSECT` / `EXCEPT` に`ALL`を付けても、重複の個数を数える必要があるため`UNION ALL`ほど安くはなりません。

> [!note]- インデックスは効かないのか
> 集合演算子は**それぞれの枝を実行し終えてから**結果同士を突き合わせます。したがってインデックスが効くのは**枝の内側の`WHERE`や`JOIN`まで**で、突き合わせ自体には効きません。枝を`WHERE`で早めに絞ることが、集合演算の高速化としては一番効きます。実行計画の読み方は17章で扱います。
>
> 🐘 突き合わせは PostgreSQL の実行計画では`HashSetOp`や`SetOp`という名前で現れます。**この節点名は PostgreSQL 固有**です。「枝を実行してから突き合わせる」という考え方自体はどのDBでも同じです。

## 6. まとめ：JOIN と集合演算子の使い分け

| 項目 | JOIN（結合） | 集合演算子（UNION, etc.） |
| :--- | :--- | :--- |
| **結合方向** | **横**（列が増える） | **縦**（行が増える／減る） |
| **つなぐもの** | テーブル同士 | `SELECT`の結果同士 |
| **列の制約** | 自由 | **列数が一致し、型が互換であること** |
| **NULLの比較** | 結合されない（`UNKNOWN`） | **一致とみなす** |
| **主な用途** | 属性の追加（名前と価格を紐付ける等） | データの統合・比較（新旧の突合等） |
| **計算負荷** | 結合キーのインデックスに依存 | 重複排除（並べ替え／ハッシュ）による負荷 |

## 7. 補足：JOIN による集合演算の代用

`EXCEPT`／`INTERSECT`が使えない環境（MySQL 8.0.30以前など）や、**除外したうえで右側の列も見たい**場合は、`JOIN`で似たことができます。

§3-2 の「まだ誰も持っていない会員ランク」を`LEFT JOIN`で書くとこうなります。

```sql
SELECT m.membership_id, m.rank_name
FROM memberships m
LEFT JOIN customers c ON m.membership_id = c.membership_id
WHERE c.membership_id IS NULL   -- 結合できなかった行だけを残す
ORDER BY m.membership_id;
```

```
 membership_id | rank_name
---------------+-----------
             4 | Platinum
(1 row)
```

`EXCEPT`版は`membership_id`しか返せませんが、こちらは**`rank_name`も一緒に出せます**。「BになかったAの行」だけでなく「Bにあった場合はその値も」を1本で取りたいなら`LEFT JOIN`を選びます。

> ⚠️ **ただし、代用は`EXCEPT`と等価ではありません。** 上の例で一致したのは、左側の`memberships.membership_id`が主キーで`NULL`を含まないからです。**左右の両方に`NULL`がありうる列では結果が割れます。**

> [!note]- 割れる例と、その直し方
> `ON`句の`=`は`NULL`同士を結合しないため、左の`NULL`行が「相手が無かった行」として残ってしまいます。
>
> ```sql
> -- EXCEPT：1件
> SELECT * FROM (VALUES ('A'), (NULL)) AS l(v)
> EXCEPT
> SELECT * FROM (VALUES ('B'), (NULL)) AS r(v);
> ```
>
> ```
>  v
> ---
>  A
> (1 row)
> ```
>
> ```sql
> -- LEFT JOIN 代用：2件。NULL が残る
> SELECT DISTINCT l.v
> FROM (VALUES ('A'), (NULL)) AS l(v)
> LEFT JOIN (VALUES ('B'), (NULL)) AS r(v) ON l.v = r.v
> WHERE r.v IS NULL;
> ```
>
> ```
>  v
> ---
>  A
>
> (2 rows)
> ```
>
> 揃えるには**2箇所**直します。`ON`を`IS NOT DISTINCT FROM`に変えるだけでは足りません。結合できた相手の値も`NULL`なので、`WHERE r.v IS NULL`が**結合できた行まで拾ってしまう**からです。
>
> 1. `ON l.v IS NOT DISTINCT FROM r.v` — `NULL`同士を結合する（🐘 標準SQLですが Oracle には無く、SQL Server も 2022 以降のみです）
> 2. 判定には**`NULL`にならない列**を使う — 主キーを使うか、右側に`1 AS matched`のような目印の列を足して`WHERE matched IS NULL`とする
>
> ②は`NULL`を含む列に限らず、`LEFT JOIN` + `WHERE 〜 IS NULL`という書き方そのものの落とし穴です。**判定には必ず`NULL`にならない列を選んでください。**
