## なぜ排他制御が要るか

**在庫や座席のような共有データは、何本ものトランザクションが同時に触ります。** ここで順番を考える単位は、1文ではなく**トランザクション**（15-1 の `BEGIN`〜`COMMIT` の塊）です。

| トランザクションの流し方 | 壊れるか | 速さ |
| :--- | :--- | :--- |
| 1つが終わるまで次を始めない（**直列**） | 壊れない | 全員が前のトランザクションの終わりを待つので遅い |
| 同時に進める（**並列**） | あるトランザクションの途中に、別のトランザクションの文が割り込むと壊れる | 速い |

![[15-2_並列で壊れる例と壊れない例.excalidraw]]

**文を1つずつ順番に実行するだけでは足りません。** §4-1 のロストアップデートでは、どの文も単独では正しく実行されています。壊れるのは、2つのトランザクションの文が**交互に**並んだからです。

**欲しいのは「結果はトランザクションを直列に流したときと同じ、速さは並列」。これを実現する仕組みが排他制御です。** [[15-1_導入_トランザクションとACID|15-1]] §3 の I（分離性）がこれにあたります。

### いつ壊れるか

**並列がいつも危ないわけではありません。危ないのは、同じデータに書き込みが絡むときだけです。** この章の §1〜§4 は、この表の下3行を扱います。

| 2つの処理の重なり方 | 何もしなければ | DBの扱い | 節 |
| :--- | :--- | :--- | :--- |
| 読みも書きも重ならない | 壊れない | 何もしない | — |
| 同じデータを両方が読むだけ | 壊れない | 何もしない | — |
| 同じ行を両方が書く | 壊れる | **その行だけ直列にする**（行ロック） | §1 |
| 片方が読み、片方が書く | 壊れる | **版を分け、読む側には確定済みの版を見せる。待たせない**（MVCC）。**読む側に何が見えてよいか**の段階が分離レベル | §2・§3 |
| **読んだ値をもとに書く** | **壊れる** | **上の2つの間をすり抜ける。** 読んだ値が、書くときには古くなっている | §3-2 後半・§4 |

**最後の行は、既定の設定ではDBが埋めてくれません。** 埋め方は2通りです。

- **DBに任せる** → §3-2 後半（REPEATABLE READ・SERIALIZABLE。当直の例もここ）
- **アプリで書き方を変える** → §4 明示的な行ロック

**「結果は直列と同じ」を完全に保証するのは SERIALIZABLE だけです。** その代わり衝突のたびにエラーになり、リトライが要ります。だから既定の READ COMMITTED は保証を緩め、残った隙間は必要な箇所だけアプリで埋めます（§3-3）。

§5 はロックで直列にしたことの代償（デッドロック）、§6 はロックと MVCC の代償を踏まえたトランザクションの区切り方です。

## 0. 準備

**窓を2つ開く。** pgAdmin なら同じDBでクエリツールを2回、psql ならターミナルを2つ。片方を**窓A**、もう片方を**窓B**とします。

> ⚠️ **同じタブで交互に打っても再現しません。** 接続が2本あることが前提です。

**この章だけで使う列を1つ足します**（§4-4 で使用）。

**リセット手順**（値が分からなくなったら実行）：

`version` 列は `TRUNCATE` では消えないので、入れ直せば全行 `1` に戻ります。

## 1. 書き込み同士はぶつかる

### 1-1.【2窓】`UPDATE` は待たされる

| | 実行するSQL | 結果 |
| :--- | :--- | :--- |
| 窓A | `BEGIN;` → `UPDATE products SET price = price + 100 WHERE product_id = 1;` | すぐ返る |
| 窓B | `UPDATE products SET price = price + 50 WHERE product_id = 1;` | **返ってこない** |
| 窓A | `COMMIT;` | → **その瞬間、窓Bが完了** |

窓Aが握っていた時間ぶん、まるごと待たされています。

**`UPDATE` は対象行に行ロックを自動的に取り、ロックは `COMMIT` / `ROLLBACK` まで外れません。**

> **これが「`COMMIT` を忘れる」ことの怖さです。** 放置すると、その行を触る全員が止まります。

### 1-2. 待たされた側はどの値を読み直すか

```sql
SELECT price FROM products WHERE product_id = 1;   -- 1350.00
```

**1200 → +100（窓A）→ +50（窓B）＝ 1350。** 窓Bが「待ち始めた時点の 1200」に足して 1250 にはなりません。

**既定の READ COMMITTED では、待たされた `UPDATE` はロックが外れた後に対象行を読み直してから実行されます。**

> ⚠️ **`price = price + 50` のようにDBに計算させているから正しいのです。**
> アプリで `SELECT` した値から計算して `price = 1250` と**絶対値で書き戻す**と、この保護は効きません。→ §4-1

### 1-3. 誰が誰を待っているか

**§1-1 の状態のまま**——窓Aは `COMMIT` せず、窓Bは返ってこないまま——**3つ目の窓C**を開いて調べます。

| | 実行するSQL | いまの状態 |
| :--- | :--- | :--- |
| 窓A | `BEGIN;` → `UPDATE products SET price = price + 100 WHERE product_id = 1;` | `COMMIT` せずに放置 |
| 窓B | `UPDATE products SET price = price + 50 WHERE product_id = 1;` | 返ってこないまま |
| **窓C** | ↓ の調査SQL | ← ここから覗く |

```sql
SELECT pid,
       pg_blocking_pids(pid) AS 待たせている相手,
       wait_event_type       AS 待ちの種類,
       left(query, 50)       AS 待っているSQL
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

```
  pid  | 待たせている相手 | 待ちの種類 |                    待っているSQL
-------+------------------+------------+----------------------------------------------------
  9872 | {21716}          | Lock       | UPDATE products SET price = price + 50 WHERE produ
```

**「PID 9872 は PID 21716 に待たされている」**と読みます。

**出るのは待たされている側（窓B）の行だけです。** `cardinality(pg_blocking_pids(pid)) > 0` で「誰かに待たされている接続」に絞っているので、SQL 欄に出るのも**止まっているほうのSQL**（`+ 50`）。待たせている窓Aを見るには、`待たせている相手` に出た PID を次の §1-4 で引き直します。

### 1-4. 犯人の状態を見て、必要なら止める

```sql
SELECT pid, state, now() - xact_start AS 経過時間, left(query, 50) AS 最後のSQL
FROM pg_stat_activity WHERE pid = 21716;
```

```
  pid  |        state        |    経過時間     |                  最後のSQL
-------+---------------------+-----------------+-----------------------------------------------
 21716 | idle in transaction | 00:00:06.304382 | UPDATE products SET price = price + 100 WHERE
```

| `state` | 意味 | どうするか |
| :--- | :--- | :--- |
| `active` | いま実行中 | 終わるのを待つ |
| **`idle in transaction`** | **`BEGIN` したまま放置。`COMMIT` 漏れ** | **放っても終わらない。**人を探す |
| `idle` | トランザクションも開いていない | 無害 |

> ⚠️ **`query` は「今実行中のSQL」ではなく「最後に実行したSQL」です。** 必ず `state` とセットで読んでください。

```sql
SELECT pg_cancel_backend(21716);     -- 実行中のクエリだけキャンセル（穏当）
SELECT pg_terminate_backend(21716);  -- 接続ごと切断（トランザクションはロールバック）
```

> ⚠️ **`idle in transaction` の相手に `pg_cancel_backend` は効きません**（キャンセルすべきクエリが無いため）。`t` が返っても止まっていないので `pg_terminate_backend` を使います。
> 本番で切る前に、何をしている接続か確認し、可能なら持ち主に連絡を。

**クエリ暗記ではなく、覚えてもらうのは「固まったら外から確認できる／最後は止められる」ということです。**

> 🐘 名前は PostgreSQL 固有。Oracle は `V$SESSION` と `ALTER SYSTEM KILL SESSION`、MySQL は `SHOW PROCESSLIST` と `KILL`。

## 2. 読み取りは待たされない：MVCC

### 2-1.【2窓】`UPDATE` 中でも `SELECT` は即座に返る

|     | 実行するSQL                                                            | 結果                        |
| :-- | :----------------------------------------------------------------- | :------------------------ |
| 窓A  | `BEGIN;` → `UPDATE products SET price = 120 WHERE product_id = 1;` | —                         |
| 窓B  | `SELECT price FROM products WHERE product_id = 1;`                 | **待たない。1200.00**（書き換え前の値） |

窓Aが `COMMIT` した後に読むと 120 が返ります。**これが MVCC（多版型同時実行制御）です。**

### 2-2. なぜ古い値が読めるのか

**PostgreSQL は `UPDATE` で元の行を上書きせず、新しい行を別に追加します。** 各行に「いつからいつまで有効か」を持たせ、ディスク上に**複数のバージョンが並んでいます。**

各トランザクションは**スナップショット**（自分に見える世界）を持ち、そこに入っているバージョンを読みます。**読む側は誰ともぶつからないので待ちません。** スナップショットを**いつ取るか**は分離レベルで決まります（§3-2）。

| | ブロックするか |
| :--- | :--- |
| 読み取り vs 読み取り | しない |
| **読み取り vs 書き込み** | **しない**（MVCC のおかげ） |
| 書き込み vs 書き込み（同じ行） | **する** |

![[15-2_MVCCのバージョン分岐.excalidraw]]

### 2-3. 代償

**古いバージョンが溜まるので、回収する `VACUUM` が要ります。** 覚えるのは「**MVCC だから `VACUUM` が要る**」という繋がりだけで十分です。性能の話は17章。

> [!note]- もう少し詳しく
> 通常は autovacuum が裏で走ります。ただし**更新が激しいテーブルや、長時間トランザクションが居座っているとき**は回収が追いつかず、テーブルが膨らみます（読むページ数が増えて遅くなる）。
>
> **「まだ誰かから見えるか」の基準は、DB全体で共通の数値1つです。** 実態は**「いま生きているトランザクションのうち、いちばん小さいID」**で、次のSQLで見えます。
>
> ```sql
> SELECT pg_snapshot_xmin(pg_current_snapshot());   -- 例: 23600
> ```
>
> 古い行を回収してよいかは、**その行を消したトランザクションのIDが、この数値より小さいか**——それだけで決まります。だから：
>
> - **古いトランザクションが何を読んでいるかは、記録されていません。** 判定に使うのはIDの大小だけなので、**放置されたセッションと縁もゆかりも無いテーブル**の古い行まで、まとめて回収不能になります（→ §6-4）
> - **REPEATABLE READ だけの話ではありません。** `BEGIN` して更新したまま `idle in transaction` で放置された READ COMMITTED のセッションも、同じようにこの数値を止めます（→ §1-4）
>
> 詳細は [[17-1_導入_物理構造とスキャン方式|17-1]] §6-5。

> 🐘 MVCC 自体はどのDBにもありますが、Oracle や MySQL は古い版を**別領域（UNDO）に退避**するのでテーブルは膨らみません。**「`VACUUM` が要る」のは PostgreSQL 固有の事情**です。

## 3. 分離レベル

**覚えて帰るのは §3-1 と §3-3 です。** §3-2 は、**シンプルなルール1つから挙動を予測できるか**を PostgreSQL で確かめる節です。

### 3-1. 4つの現象と4段階

| 現象 | 何が起きるか |
| :--- | :--- |
| **ダーティリード** | 他の**未確定**の変更が見えてしまう |
| **ノンリピータブルリード** | 同じ行を2回読んだら**値が変わっていた** |
| **ファントムリード** | 同じ条件で2回読んだら**行が増えていた** |
| **直列化異常** | 上の3つが1つも起きていないのに、**2つ揃うと業務ルールが破れる**（→ §3-2 末尾の折りたたみ） |

**分離レベルは、この4つをどこまで防ぐかの段階です。上に行くほど安全になり、上に行くほど同時に捌けなくなります。**

| 分離レベル | ダーティ | ノンリピータブル | ファントム | 直列化異常 |
| :--- | :----: | :------: | :----: | :---: |
| Read Uncommitted | 発生 | 発生 | 発生 | 発生 |
| **Read Committed（既定）** | 防ぐ | 発生 | 発生 | 発生 |
| Repeatable Read | 防ぐ | 防ぐ | 発生 | 発生 |
| Serializable | 防ぐ | 防ぐ | 防ぐ | 防ぐ |

> 🐘 **現象と段階の名前は標準SQLで、どのDBでも通じます。覚えて帰るのはこの2つの表です。**
> ただし**どう実現するかはDBによって違い**、PostgreSQL はこの表と2箇所ズレます。
> ① **Read Uncommitted は実装が無く、Read Committed として動く**（＝ダーティリードは起きない）
> ② **Repeatable Read はファントムも防ぐ**（理由は §3-2）

### 3-2.【2窓】スナップショットをいつ取るか

**PostgreSQL の分離レベルは、ルール1つに還元できます。**

| 分離レベル | 自分に見える世界（スナップショット）を |
| :--- | :--- |
| **READ COMMITTED（既定）** | **文ごとに取り直す** |
| **REPEATABLE READ 以上** | **最初の1文で取ったきり、最後まで使う** |

**このルールから③④を予測してから実行してください。** 窓Aがトランザクションを開いたまま同じ `SELECT` を2回。その合間に窓Bが割り込みます。窓Aの分離レベルだけを変えて2回試した実測です。

| 時点 | | 実行するSQL | READ COMMITTED（既定） | REPEATABLE READ |
| :--- | :--- | :--- | ---: | ---: |
| ① | 窓A | `BEGIN TRANSACTION ISOLATION LEVEL <レベル>;`<br>`SELECT price FROM products WHERE product_id = 1;`<br>`SELECT count(*) FROM products WHERE category_id = 1;` | 1200<br>4 | 1200<br>4 |
| ② | 窓B | `UPDATE products SET price = 1300 WHERE product_id = 1;`<br>`INSERT INTO products (product_id, product_name, category_id, price)`<br>`  VALUES (900, 'Ghost', 1, 1);` | — | — |
| ③ | 窓A | **①と同じ** `SELECT price FROM products WHERE product_id = 1;` | **1300**（変わった） | 1200 |
| ④ | 窓A | **①と同じ** `SELECT count(*) FROM products WHERE category_id = 1;` | **5**（増えた） | 4 |
| ⑤ | 窓A | `COMMIT;` | 成功 | 成功 |

**②の窓Bは自動コミットで打ちます**（`BEGIN` を書かない）。窓Aが読み直す③④の時点で、窓Bの変更が確定していることが条件です。

**③がノンリピータブルリード、④がファントムリードです。** READ COMMITTED は文ごとに取り直すので、確定した変更がそのつど見えます。**REPEATABLE READ は取り直さないので、値も行数も動きません。** ③と④は同じルールの表裏なので**まとめて防がれます**——§3-1 の「PostgreSQL は Repeatable Read でファントムも防ぐ」はこれです。

**同じルールから、書くときの挙動も予測できます。** 取り直せない REPEATABLE READ は、他人が確定させた最新の行に積めません。④の後に窓Aが同じ行を `UPDATE` すると、**ロックを待ったうえで**落ちます。

```
ERROR:  could not serialize access due to concurrent update
```

READ COMMITTED が待った後に読み直して続けられる（§1-2）のも、同じルールの裏返しです。

> [!note]- ルールで防げないもの：直列化異常と SERIALIZABLE
> **スナップショットは「自分が読んだ後、他人が何をしたか」を見ません。** そのため次のような壊れ方だけは、REPEATABLE READ でも防げません。
>
> 「**当直は最低1人**」を守るコードで、当直のAとBが**同時に**休みを申請します。
>
> | 時点 | 窓A | 窓B |
> | :--- | :--- | :--- |
> | ① | 当直の人数を数える → **2人** | |
> | ② | | 当直の人数を数える → **2人** |
> | ③ | 「もう1人いる」→ 自分を休みにする | |
> | ④ | | 「もう1人いる」→ 自分を休みにする |
> | ⑤ | `COMMIT;` | `COMMIT;` → **当直0人** |
>
> **Aが触った行とBが触った行は別**なので、値も行数も変わっていません（＝ノンリピータブルもファントムも起きていない）。**それでも2つ揃うと当直が0人になります。** 1つずつ順に実行すれば絶対に起きない——だから「**直列化**異常」です。
>
> **SERIALIZABLE だけが、スナップショットに加えて「どの範囲を読んだか」まで覚えています。** そのため**同じ行を1つも触っていない相手とでも、`COMMIT` の瞬間に落ちることがあります。**

### 3-3. どれを使うか

**既定の READ COMMITTED のままでよい。** 理由は3つ：①多くの処理は同じ行を2回読まない ②同時実行性能が最も高い ③リトライを書かなくてよい。

**上げるならリトライ処理が必須です。** REPEATABLE READ 以上は衝突すると落ちるので（§3-2）、書かずに上げると繁忙時にエラーが多発します。「同じデータを2回読む間に変わると困る」処理（月次集計など）でだけ、**リトライとセットで**検討します。

**「特定の行を他人に触らせたくない」だけなら、分離レベルより次の行ロックです。**

**以降の §4・§5 は、すべて既定の READ COMMITTED での話です。** とくに §4-4 の楽観ロックは、§1-2 の「待たされた `UPDATE` は読み直してから実行される」に乗っています。

## 4. 明示的な行ロック

**「読んで、計算して、書き戻す」処理の書き方です。** まず壊れ方を見て（§4-1）、書き方を3つ順に出し（§4-2〜§4-4）、選び方を表にします（§4-5）。最後に、自分で書かなくても取られているロックを見ます（§4-6）。

**ここも §1-2 のルール1つで予測できます。**

> **待たされた `UPDATE` は、ロックが外れた後に行を読み直してから実行される。**

| | このルールでどうなるか |
| :--- | :--- |
| **壊れ方**（§4-1） | アプリが**絶対値**を書くと、読み直しの恩恵がゼロになる |
| **① DBに計算させる**（§4-2） | 読み直した値から引くので、必ず相手の更新が入った後の値になる |
| **② 悲観ロック**（§4-3） | **唯一ルールの外。** 読む時点で押さえるので、そもそも古い値を掴まない |
| **③ 楽観ロック**（§4-4） | 読み直すと `version` が進んでいるので、`AND version = 読んだ値` に合わず0件 |

### 4-1.【2窓】ロックを取らないと在庫が壊れる（ロストアップデート）

**在庫50個に、窓Aが5個・窓Bが3個の注文。正解は 42。** アプリは「①読む ②計算する ③書き戻す」の3ステップとします。

> ⚠️ 2つの窓を**同時に**は実行できません。**1文ずつ交互に**打ってください。

1. 窓A：`BEGIN;` → `SELECT stock_quantity ...` … **50 を読む**
2. 窓B：`BEGIN;` → `SELECT stock_quantity ...` … **同じく 50 を読む**
3. 窓A：アプリが **50 - 5 = 45** を計算 → `UPDATE inventory SET stock_quantity = 45 ...;` → `COMMIT;`
4. 窓B：アプリが **50 - 3 = 47** を計算 → `UPDATE inventory SET stock_quantity = 47 ...;` → `COMMIT;`

```
窓Aが読んだ値: 50
窓Bが読んだ値: 50
最終的な在庫  : 47      ← 42 になるはずが 47
```

**窓Aの「5個引く」が完全に消えました。これがロストアップデートです。**

**§2 の MVCC が裏目に出ています。** 読み取りが待たされないので、**2つの窓が同じ 50 を読めてしまう。** そのうえ手順3・4で `45` / `47` という**絶対値**を書いているので、待たされた窓Bが行を読み直しても、**書き込む 47 は①で読んだ 50 から計算したまま**です。

> **在庫がマイナスになる、二重に売れる、の原因です。** テストでは同時に叩かないので発覚せず、**本番の繁忙時にだけ起きます。**

### 4-2. パターン①：DBに計算させる

**そもそも読んだ値をアプリに持ち出さなければ、壊れません。**

```sql
UPDATE inventory
   SET stock_quantity = stock_quantity - 5   -- ★ いまDBに入っている値から引く
 WHERE product_id=1 AND warehouse_id=1
   AND stock_quantity >= 5;                  -- ★ 「足りるか」の判断も WHERE に書く
```

**§1-2 の `price = price + 100` がこれです。** ルールどおり、引かれるのは**必ず相手の更新が入った後の値**になります。在庫が足りなければ `WHERE` に合わないので、**更新0件**で返ります。**エラーではありません。**

> [!note]- 在庫不足を `ERROR` で止めたいなら（`CHECK` 制約）
> | 在庫が足りないとき、どう返ってほしいか | 書き方 | 返り |
> | :--- | :--- | :--- |
> | **業務エラーとして扱いたい**（「在庫が足りません」と画面に出す） | `WHERE ... AND stock_quantity >= 5` | **更新0件** |
> | **異常として止めたい**（そもそも起きてはいけない） | `CHECK (stock_quantity >= 0)` | **`ERROR`** |
>
> `CHECK` でも在庫マイナスは防げます。ただし破ったときに返るのは `ERROR` で、PostgreSQL では [[15-1_導入_トランザクションとACID|15-1]] §2 のとおり**トランザクション全体が中断状態**になります。15-1 §3-2 の**「アプリで判断し、制約は最後の砦として置く」**が、そのままここに当てはまります。

**①で書けるなら①です。** ロックも追加の列も要りません。**次の②③は「①では書けないとき」の話**になります。

### 4-3. パターン②：悲観ロック（`SELECT ... FOR UPDATE`）

**①で書けないのは、読んだ値を使ってアプリが判断・計算してから書き戻す場合**——判断が `WHERE` に収まらないときです。**「どうせぶつかる」と構えて、読む時点でロックを取ります。**

```sql
BEGIN;
SELECT stock_quantity FROM inventory
 WHERE product_id=1 AND warehouse_id=1
 FOR UPDATE;                                   -- ★ 読んだ瞬間に押さえる
UPDATE inventory SET stock_quantity = 45 WHERE product_id=1 AND warehouse_id=1;
COMMIT;
```

窓Bも `FOR UPDATE` を付けると、**`UPDATE` ではなく `SELECT` の時点で待たされます。**

```
窓Bの SELECT ... FOR UPDATE : 3,229ms 待たされた
窓Bが読んだ値: 45      ← 窓Aの COMMIT 後の値
最終的な在庫  : 42     ← 正しい
```

**待つ位置が `UPDATE` から `SELECT` に前倒しされたのが本質です。** そもそも古い値を掴めなくなります。

> [!note]- 待ちたくないとき（`NOWAIT` / `SKIP LOCKED`）
> ```sql
> SELECT * FROM products WHERE product_id = 1 FOR UPDATE NOWAIT;
> -- ERROR:  could not obtain lock on row in relation "products"
>
> SELECT product_id FROM products WHERE product_id IN (1,2,3) ORDER BY product_id
> FOR UPDATE SKIP LOCKED;   -- 1,2 がロック中なら 3 だけ返る
> ```
> - **`NOWAIT`** … 待つくらいなら失敗させて「混み合っています」と返したいとき
> - **`SKIP LOCKED`** … **ジョブキューの定番。**複数ワーカーが互いに違う行を掴む
> - N秒だけ待つなら `SET LOCAL lock_timeout = '3s';`

### 4-4.【2窓】パターン③：楽観ロック（`version` 列）

**「どうせめったにぶつからない」と構えて、押さえずに書き戻し時に確認します。** §0 で足した `version` 列を使います。

```sql
BEGIN;
SELECT stock_quantity, version FROM inventory WHERE product_id=1 AND warehouse_id=1;
-- → 50 / version 1。アプリが 50-5=45 を計算
UPDATE inventory
   SET stock_quantity = 45,
       version = version + 1            -- ★ 更新したら version を進める
 WHERE product_id=1 AND warehouse_id=1
   AND version = 1;                     -- ★ 読んだときの version のままなら
COMMIT;
```

窓Aから順に実行した実測：

```
窓A : UPDATE 1
窓B : UPDATE 0      ← 2,901ミリ秒待たされたのち、0件

 stock_quantity | version
----------------+---------
             45 |       2
```

**窓Bは失敗しましたが、エラーは出ていません。** 返ってきたのは `UPDATE 0` だけです。**ルールどおり**、待たされた `UPDATE` が行を読み直した時点で `version` はもう `2`。`AND version = 1` に合う行が無くなります。**読み直しの仕組みが、ここでは「他人に先を越された」検知装置として働いています。**

**在庫の値そのもの（`AND stock_quantity = 50`）を条件にしないのは、「50 → 45 → 50」と戻された場合を見逃すからです。** `version` は増える一方なので戻りません。

**そして「楽観ロック＝待たない」ではありません。** 同じ行の `UPDATE` 同士はやはり待ちます（実測 2,901ミリ秒）。無くせるのは「**読んでから書き戻すまでの間**」＝人が画面を開いている時間のロックです。

> ⚠️ **`UPDATE 0` を見ていないコードは、楽観ロックを書いていないのと同じです。** 0件でも例外は飛びません。たいていのライブラリは更新件数を数値で返すので、**その戻り値を必ず見ること。**

> [!example]- リトライ（検知したあとどう直すか）
> ```sql
> SELECT stock_quantity, version FROM inventory WHERE product_id=1 AND warehouse_id=1;
> -- → 45 / version 2。アプリが 45-3=42 を計算
> UPDATE inventory SET stock_quantity = 42, version = version + 1
>  WHERE product_id=1 AND warehouse_id=1 AND version = 2;
> -- UPDATE 1 → 42 / version 3
> ```

> [!note]- フレームワークが自動化していることもあります
> Spring Data JPA の `@Version` は、`WHERE version = ?` と `SET version = version + 1` を自動で付け、0件なら例外を投げてくれます。**中で起きているのは、いま手で書いたものと同じです。**

![[15-2_楽観ロックと悲観ロック.excalidraw]]

### 4-5. ①②③のどれを選ぶか

|              | ① DBに計算させる                                            | ② 悲観ロック                                             | ③ 楽観ロック                                                               |
| :----------- | :---------------------------------------------------- | :-------------------------------------------------- | :-------------------------------------------------------------------- |
| **書き方**      | `SET stock = stock - 5`<br>`WHERE ... AND stock >= 5` | `SELECT ... FOR UPDATE`<br>→ アプリ側で計算 <br>→ `UPDATE` | `SELECT`（version も）<br>→ アプリ側で計算 <br>→`UPDATE ... AND version = 読んだ値` |
| **使うのは**     | **`WHERE` に条件を書けるとき**                                 | 読んでから書くまでに挟まるのが<br>**アプリの処理だけ**（ミリ秒）／**競合が頻繁**      | 間に**人の操作**や<br>**外部システムの応答**が挟まる／**競合が稀**                             |
| **競合したら**    | 待って、読み直して実行                                           | **待つ**                                              | **待たずに0件で返る**                                                         |
| **失敗の受け取り方** | 更新0件                                                  | （失敗しない）                                             | 更新0件                                                                  |

**順番は：①で書けないか疑う → 書けないなら、人が挟まるなら③ → 挟まらず競合が頻繁なら②。**

②を選ぶと**挟まっている時間ぶんロックを握り続けます**（編集画面を5分開くなら、その5分間ずっと）。③は逆に、競合が頻繁だと**リトライ地獄**になります。

> ⚠️ **①と③はどちらも「更新0件を見て判断する」作法です。** 「エラーが出なかったから成功」と書くと、①では在庫不足に気づけず、③では他人の更新を上書きします。

> [!note]- 4つめ：そもそも競合させない
> - **足し引きを別テーブルに追記する**（`INSERT` は同じ行を取り合わない。現在値は合計で求める）
>   … **イベントソーシングの一番素朴な形**です。銀行が残高を書き換えず入出金明細を積むのがこれ。
>   現在値は `SUM` で出すので**その場で正しい値が出ます**。代償は読み取りが重くなること
> - **キューに積んで1つずつ処理する**（`SKIP LOCKED` はこのための道具）
>   … こちらは逆に**非同期＝結果整合**。「受け付けました」を先に返し、後からワーカーが処理します。
>   取り合う相手が「同じ在庫行」から「キューの別々の行」に変わるのがポイント
>
> 設計レベルの判断ですが、**「ロックで悩んだら、取り合わない形にできないか」**という発想は持っておいてください。

### 4-6.【2窓】ロックは自動で、最小限に取られる

**自分で書くのは実質 `FOR UPDATE` だけです。** 残りは PostgreSQL が必要最小限の強さで勝手に取っています。**要点は「どの行に取られるか」**——ふつうは自分が触る行ですが、**外部キーだけは別テーブルの行**です。

| モード                 | どの行に取るか                | 誰が取るか                                     | その行に対して止めるもの                                       |
| :------------------ | :--------------------- | :---------------------------------------- | :------------------------------------------------ |
| `FOR UPDATE`        | **自分が更新・削除する行**        | **自分で書く**／`DELETE`・**キー列を変える** `UPDATE` が自動 | 他のすべての行ロックと更新                                     |
| `FOR NO KEY UPDATE` | **自分が更新する行**           | **キー列を変えない** `UPDATE` が自動                 | `FOR UPDATE`・`FOR NO KEY UPDATE`・`FOR SHARE`      |
| `FOR SHARE`         | **自分が参照する行**           | **自分で書く**ときだけ                             | 更新・削除                                             |
| `FOR KEY SHARE`     | **参照先（親テーブル）の行** ←ここだけ別テーブル | **外部キーの参照時に自動**                           | 削除とキー列の変更だけ                                       |

ここでいう**キー列とは、主キーやユニーク制約に使われている列**のこと。裏を返すと、**ふつうの `UPDATE` はほとんどが `FOR NO KEY UPDATE`** です。**下に行くほど邪魔しません。**

**`FOR NO KEY UPDATE` と `FOR KEY SHARE` は、取られる行が違うので、そもそも取り合いになりません。** これを2窓で見ます。窓Aで顧客6番を参照する注文を挿入し、`COMMIT` しないでおきます。

```sql
BEGIN;
INSERT INTO orders (order_id, customer_id, order_date, status) VALUES (999, 6, CURRENT_DATE, 'Pending');
```

| 窓Bの操作                                                        | 結果           |
| :----------------------------------------------------------- | :----------- |
| `UPDATE customers SET city = 'Kyoto' WHERE customer_id = 6;` | **成功**（待たない） |
| `DELETE FROM customers WHERE customer_id = 6;`               | **待たされた**    |

**窓Aが `orders` を挿入したのに、ロックが取られているのは `customers` の6番の行です。** 種類は `FOR KEY SHARE`——「参照している主キーが消えたり変わったりしなければいい」という最小限のロックなので、**住所の変更は通り、削除だけ止まります。**

> **「注文を登録しただけなのに顧客マスタの更新が固まった」は、FK の自動ロックが原因**であることがよくあります。
> 逆に、**FK のために自分で `FOR SHARE` を書く必要はありません。**

> ⚠️ **この4つのモードは `pg_locks` を見ても出てきません。** 行ロックはロック管理表ではなく**行そのものに書かれる**ためです。

> [!note]- `FOR SHARE` を自分で書くとどうなるか
> 「参照するので変更はさせない。でも参照したいだけの人とは共存してよい」というものです。
>
> | 窓Aが `FOR SHARE` 中に、窓Bが… | 結果 |
> | :--- | :--- |
> | 同じ行を `FOR SHARE` | **1.864ms で成功**（待たない） |
> | 同じ行を `UPDATE` | **5,880ms 待たされた** |

## 5. デッドロック

### 5-1.【2窓】起こしてみる

**ロックを取る順番を逆にするだけ**で起きます。

| 順 | 窓A（商品1 → 2） | 窓B（商品2 → 1） |
| :--- | :--- | :--- |
| ① | `BEGIN;` `UPDATE ... product_id = 1;` | |
| ② | | `BEGIN;` `UPDATE ... product_id = 2;` |
| ③ | `UPDATE ... product_id = 2;` → **待つ** | |
| ④ | | `UPDATE ... product_id = 1;` → **待つ** |

互いに相手を待つので永久に進みません。**約1秒後、PostgreSQL が片方を殺します。**

```
ERROR:  deadlock detected
DETAIL:  Process 25544 waits for ShareLock on transaction 18430; blocked by process 14048.
Process 14048 waits for ShareLock on transaction 18431; blocked by process 25544.
CONTEXT:  while updating tuple (0,21) in relation "products"
ROLLBACK
```

**どちらが犠牲になるかは選べません。**

### 5-2. 検知の仕組み

ロック待ちが **`deadlock_timeout`（既定 1秒）**を超えたときだけ調べます（毎回調べるとコストが高いため）。**1秒くらい待つのは正常**です。

### 5-3. 対策：ロックを取る順番を揃える

**全員が同じ順番で取れば起きません。**

```sql
-- ✕ 注文に入っていた順（バラバラ）      ○ 常にID昇順
UPDATE ... WHERE product_id = 5;         UPDATE ... WHERE product_id = 2;
UPDATE ... WHERE product_id = 2;         UPDATE ... WHERE product_id = 5;
```

複数行をまとめて取るなら **`ORDER BY` を付けるだけ**で揃います。

```sql
SELECT * FROM products WHERE product_id IN (5, 2, 9) ORDER BY product_id FOR UPDATE;
```

**優先順位：① ロック順序を統一 ＞ ② トランザクションを短くする ＞ ③ リトライ（最後の保険）**

> **デッドロックは「起きたら設計を見直す」サインです。** リトライで握りつぶすと、負荷が上がるほど発生率が上がっていずれ回らなくなります。

## 6. トランザクションの境界を決める

[[15-1_導入_トランザクションとACID|15-1]] §3-1 で保留にした「**大きすぎると何が困るのか**」に、ここで答えます。

### 6-1. 境界とは「一緒に無かったことにできる範囲」

![[15-2_トランザクションの境界.excalidraw]]

「注文1件＝1トランザクション」。**1000件のバッチなら、1000件で1つではなく1件ずつ1000回**です。

### 6-2. 中に入れてはいけないもの

| 入れてはいけないもの | 例 |
| :--- | :--- |
| **外部APIの呼び出し** | 決済代行、配送業者の照会 |
| **メール・通知の送信** | 注文確認メール、Slack通知 |
| **ファイルへの書き込み** | CSV出力、S3、PDF生成 |
| **ユーザーの操作待ち** | 確認ダイアログ、画面表示 |
| **重い集計処理** | 全件スキャンのレポート |

**理由は2つ。**

1. **`ROLLBACK` で取り消せない。** 送ったメールも呼んだ決済APIも戻せません。**DBだけ巻き戻って外の世界だけ実行済み**、という一番直しにくい不整合になります
2. **相手の応答時間ぶん行ロックを握り続ける。** 外部APIが30秒詰まれば、その行を触りたい人が全員30秒止まります（→ §1-1）

**正しい形は「コミットしてから、外に出す」。**

```
BEGIN;
在庫を引く / 注文を作る / 明細を作る
COMMIT;
------------------------------------------------
メールを送る   ← コミットしてから
```

### 6-3. 長すぎると起こること

| | 起きること | 見た場所 |
| :--- | :--- | :--- |
| ① | **その行を触る人が全員待たされる** | §1-1 |
| ② | **`VACUUM` が古い版を回収できず、テーブルが膨らむ** | §2-3 |
| ③ | **デッドロックの確率が上がる** | §5-3 |

**①はその行を触る人だけ、②は関係のないテーブルまで遅くします。** 害の広がり方が違います。

---

> **トランザクションは短く。ただし、業務として一緒に取り消したい範囲より小さくしてはいけない。**

前半だけ覚えると `COMMIT` を刻みすぎて §4-1 のように壊れ、後半だけ覚えると外部API呼び出しを抱えたままロックを握ります。**両方セットで1つのルールです。**

## まとめ

| | 覚えること |
| :--- | :--- |
| **書き込み同士** | 同じ行なら待つ。ロックは**トランザクションが終わるまで**外れない |
| **読み取り** | MVCC のおかげで**待たされない**。古い値が読める |
| **分離レベル** | **既定の READ COMMITTED のままでよい。上げるならリトライ処理とセット** |
| **ロストアップデート** | 「読んで、計算して、書き戻す」は**壊れる**。①DBに計算させる ②悲観 ③楽観 の3択（§4-5） |
| **楽観ロック** | 失敗は**エラーではなく `UPDATE 0`**。更新件数を見ないなら書いていないのと同じ |
| **`FOR SHARE`** | 自分で書く場面は少ない。**FK は勝手に、参照先の親行に `FOR KEY SHARE` を取っている** |
| **デッドロック** | **ロック順序を揃える**。約1秒後に片方が `ROLLBACK` |
| **境界** | **短く。ただし一緒に取り消したい範囲より小さくしない。** 外部API・メールは中に入れない |
| **困ったとき** | 外から確認でき、最後は止められる（§1-3・§1-4） |
