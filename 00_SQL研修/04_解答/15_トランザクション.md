## 問題 1: 【2窓】行ロックと待機
- **目的**: 同じ行への書き込み同士がぶつかると、後から来た側がロック解放まで待たされることを体験する。

### 問題:
書き込み同士がぶつかったとき何が起きるかを体験します。

**【手順】**

1. **窓A** で実行します。**`COMMIT` はまだ打ちません。**
   ```sql
   BEGIN;
   UPDATE products SET price = price + 100 WHERE product_id = 1;
   ```
2. **窓B** で実行します。
   ```sql
   UPDATE products SET price = price + 50 WHERE product_id = 1;
   ```
3. **窓Bが返ってこないこと**を確認します（実行ボタンが「実行中」のまま／プロンプトが戻らない）。
4. **窓A** で `COMMIT;` を実行します。
5. **窓Bが即座に完了すること**を確認します。
6. 価格を確認します。
   ```sql
   SELECT price FROM products WHERE product_id = 1;
   ```

**【問1】** 最終的な価格はいくらになりましたか。
**【問2】** **なぜその値になったのか**を説明してください。特に、**窓Bは「1200」と「1300」のどちらを元に +50 したのか**、そう考える理由も書いてください。
**【問3】** 窓Bはなぜ待たされたのですか。**ロックの言葉を使って**説明してください。

### 解答:

**【問1】** 最終的な価格

```
  price
---------
 1350.00
```

**【問2】** なぜその値になったのか

**窓Bは「1300」を元に +50 しています。**

```
1200（初期値）
  ↓ 窓A が +100
1300
  ↓ 窓B が +50
1350
```

窓Bが「自分が実行を開始した時点の 1200」に +50 して 1250 になったりはしません。

**【問3】** なぜ待たされたのか

- 窓Aの `UPDATE` は、対象行（product_id=1）に**行ロック（排他ロック）を自動的に取得**した
- 行ロックは、**トランザクションが終わる（`COMMIT` / `ROLLBACK`）まで解放されない**
- 窓Bも同じ行を `UPDATE` しようとして同じロックを要求したが、窓Aが握っているので**取得できるまで待機**した
- 窓Aが `COMMIT` した瞬間にロックが解放され、窓Bが取得して処理を再開した

### 解説:

**理由**：既定の分離レベル **READ COMMITTED** では、**ロック待ちから解放された `UPDATE` は、対象の行を読み直してから実行されます。** `price = price + 50` の `price` は、**待ちが終わった時点の最新の確定値**として評価されます。

> ⚠️ **これは `price + 50` のようにDB側で計算しているから正しく動いています。**
> アプリで `SELECT` した値を使って計算し、絶対値で `UPDATE` すると壊れます（→ 問題4）。

実測では窓Bの `UPDATE` は **5,958ミリ秒**かかりました（＝窓Aが握っていた時間ぶん、まるごと待たされた）。

## 問題 2: 【1窓】中断したトランザクションから復帰する
- **目的**: エラーで中断したトランザクションの挙動を知り、`SAVEPOINT` で途中から復帰できるようになる。

### 問題:
実務で必ず一度は踏むエラーと、その回避方法を体験します。

**【手順】**

1. 次を上から順に実行し、**出力を1行ずつ確認**してください。
   ```sql
   BEGIN;
   UPDATE products SET price = 1500 WHERE product_id = 1;
   SELECT 1/0;                            -- わざとエラーを起こす
   SELECT 'この行は実行されるか?';
   COMMIT;
   ```
2. 価格を確認します。
   ```sql
   SELECT price FROM products WHERE product_id = 1;
   ```

**【問1】** 3行目のエラーの後、4行目の `SELECT` はどうなりましたか。**表示されたエラーメッセージをそのまま書いてください。**
**【問2】** `COMMIT;` と打ったのに、返ってきた文字列は何でしたか。
**【問3】** `UPDATE` の結果は残りましたか。
**【問4】** **【本題】** 上の一連の処理を、**「`UPDATE` は活かしたまま、`SELECT 1/0` の失敗だけをなかったことにして、続きを実行する」**形に書き換えてください。
ヒント：[[15-1_導入_トランザクションとACID|15-1]] §4 で学んだコマンドを使います。

### 解答:

**【問1】** 4行目の `SELECT` はどうなったか

```
ERROR:  current transaction is aborted, commands ignored until end of transaction block
```

「このトランザクションは中断されています。トランザクションブロックが終わるまで、コマンドは無視されます」という意味です。

**【問2】** `COMMIT;` の戻り

```
ROLLBACK
```

**`COMMIT` と打ったのに `ROLLBACK` が返ります。** 中断したトランザクションは確定できず、強制的に巻き戻されます。

**【問3】** `UPDATE` の結果

**残りません。** 価格は 1200.00 のままです。

**【問4】** `UPDATE` を活かして続きを実行する ── `SAVEPOINT`

```sql
BEGIN;
UPDATE products SET price = 1500 WHERE product_id = 1;

SAVEPOINT sp1;                     -- ★ 危ない処理の前に目印を置く

SELECT 1/0;                        -- エラー発生 → 中断状態になる
SELECT 'この行は拒否される';        -- ← 拒否される

ROLLBACK TO SAVEPOINT sp1;         -- ★ 目印まで戻る＝中断状態から復帰する

SELECT 'ここからは実行できる';      -- ← 実行できる
UPDATE products SET price = 1600 WHERE product_id = 1;
COMMIT;
```

### 解説:

実測の出力：

```
BEGIN
UPDATE 1
SAVEPOINT
ERROR:  division by zero
ERROR:  current transaction is aborted, commands ignored until end of transaction block
ROLLBACK                           ← ROLLBACK TO SAVEPOINT が成功した
      ?column?
--------------------
 ここからは実行できる
UPDATE 1
COMMIT
```

```sql
SELECT price FROM products WHERE product_id = 1;
```

```
  price
---------
 1600.00
```

**1500 への更新も、復帰後の 1600 への更新も、両方確定しています。**

> **`ROLLBACK TO SAVEPOINT` は「中断状態からの復帰手段」でもある**——これが実務で効きます。
> `ROLLBACK`（全部捨てる）しか知らないと、長いトランザクションの途中でエラーが出た瞬間に全部やり直しになります。

## 問題 3: 【2窓】読み取りは待たされない（MVCC）
- **目的**: 読み取りは書き込みに待たされないことを体験し、問題1との違いを説明できるようになる。

### 問題:

**【手順】**

1. **窓A** で実行します。**`COMMIT` はまだ打ちません。**
   ```sql
   BEGIN;
   UPDATE products SET price = 120 WHERE product_id = 1;
   ```
2. **窓B** で実行します。
   ```sql
   SELECT price FROM products WHERE product_id = 1;
   ```
3. **窓A** で `COMMIT;` を実行します。
4. **窓B** でもう一度同じ `SELECT` を実行します。

**【問1】** 手順2の `SELECT` は待たされましたか。返ってきた値はいくつでしたか。
**【問2】** 手順4ではいくつでしたか。
**【問3】** 問題1では窓Bが待たされたのに、ここでは待たされませんでした。**この違いはなぜ生まれるのですか。**

### 解答:

**【問1】** 手順2の `SELECT`

**待たされません。実測 0.917ミリ秒**で返ってきます。値は **1200.00**（＝窓Aが書き換える前の値）。

**【問2】** 手順4の `SELECT`

**120.00**（＝窓Aが確定した後の値）。

**【問3】** 問題1との違い

| | 窓Bの操作 | 結果 |
| :--- | :--- | :--- |
| 問題1 | `UPDATE`（**書き込み**） | 待たされる |
| 問題3 | `SELECT`（**読み取り**） | 待たされない |

**行ロックがブロックするのは「他のトランザクションによる変更やロック取得」だけです。** ロックを付けない単純な `SELECT` は、そもそもロックを要求しないので、誰ともぶつかりません。

| | ブロックするか |
| :--- | :--- |
| 読み取り vs 読み取り | しない |
| **読み取り vs 書き込み** | **しない** |
| 書き込み vs 書き込み（同じ行） | **する** |

### 解説:

確定前の変更と、確定済みの古い値が同時に保持されているため、窓Aは自分の新しい値を、窓Bは古い確定値を、どちらも待たずに読めます。この**読み取りが待たされない仕組み**を **MVCC（Multi-Version Concurrency Control、多版型同時実行制御）** と呼びます（→ [[15-2_実践_ロックとMVCC|15-2]] §2-2）。

## 問題 4: 【2窓】在庫が壊れる ── ロストアップデート
- **目的**: 「読んで、計算して、書き戻す」が壊れることを体験し、悲観ロックと楽観ロックを使い分けられるようになる。

### 問題:
**この章で一番実務に直結する問題です。**

在庫50個の商品に、2人の顧客がほぼ同時に注文しました。**窓Aが5個、窓Bが3個**です。正しい結果は `50 - 5 - 3 = 42` のはずです。

アプリケーションは次の3ステップで在庫を引きます（よくある実装です）。

```
① 在庫を SELECT で読む
② アプリ側で「読んだ値 − 注文数」を計算する
③ 計算結果を UPDATE で書き戻す
```

**【手順】**

> ⚠️ 2つの窓を**同時に**実行することはできません。**窓A→窓B→窓A→窓B と、1文ずつ交互に**実行してください。

1. 在庫を初期化します。
   ```sql
   UPDATE inventory SET stock_quantity = 50, version = 1 WHERE product_id = 1 AND warehouse_id = 1;
   ```
2. **窓A** で、①と②まで実行します。
   ```sql
   BEGIN;
   SELECT stock_quantity FROM inventory WHERE product_id=1 AND warehouse_id=1;
   -- 読めた値をメモする。アプリが「読めた値 - 5」を計算したことにする
   ```
3. **窓B** でも、①と②まで実行します。
   ```sql
   BEGIN;
   SELECT stock_quantity FROM inventory WHERE product_id=1 AND warehouse_id=1;
   -- 読めた値をメモする。アプリが「読めた値 - 3」を計算したことにする
   ```
4. **窓A** で③を実行して確定します。**計算結果を絶対値で書き込みます。**
   ```sql
   UPDATE inventory SET stock_quantity = 45 WHERE product_id=1 AND warehouse_id=1;
   COMMIT;
   ```
5. **窓B** でも③を実行して確定します。
   ```sql
   UPDATE inventory SET stock_quantity = 47 WHERE product_id=1 AND warehouse_id=1;
   COMMIT;
   ```
6. 結果を確認します。
   ```sql
   SELECT stock_quantity FROM inventory WHERE product_id=1 AND warehouse_id=1;
   ```

**ここから、同じ壊れ方をもう一つの方法で防ぎます。** 使うのは [[15-2_実践_ロックとMVCC|15-2]] §0-3 で追加した `version` 列です。

7. 在庫を初期化します（手順1と同じ）。
   ```sql
   UPDATE inventory SET stock_quantity = 50, version = 1 WHERE product_id = 1 AND warehouse_id = 1;
   ```
8. **窓A** で `BEGIN;` → `SELECT` を実行します（**50 / 1** を読む）。
   ```sql
   BEGIN;
   SELECT stock_quantity, version FROM inventory WHERE product_id=1 AND warehouse_id=1;
   ```
9. **窓B** でも同じく `BEGIN;` → `SELECT` を実行します（同じく **50 / 1** を読む）。
10. **窓A → 窓B の順**に、次を実行して `COMMIT` します。
    ```sql
    UPDATE inventory
       SET stock_quantity = 45,          -- 窓Bは 47
           version = version + 1
     WHERE product_id=1 AND warehouse_id=1
       AND version = 1;
    COMMIT;
    ```

**【問1】** 最終的な在庫はいくつになりましたか。**42 になりましたか。**
**【問2】** どちらの注文が消えましたか。**なぜ消えたのか**を、手順2・3で両方が読んだ値に着目して説明してください。
**【問3】** **【本題】** 手順2〜5を**修正して、正しく 42 になるようにしてください。** 追加するのは1箇所だけです。
**【問4】** 修正版では、**窓Bはどの手順で待たされるようになりましたか。** 修正前（問題1）と比べて、待つ位置がどう変わったか説明してください。
**【問5】** そもそも `UPDATE inventory SET stock_quantity = stock_quantity - 5 ...` と1文で書けば、この問題は起きません。**では、なぜ実務で3ステップの実装が必要になるのですか。**（ヒント：在庫が足りなかったら注文を断りたい）
**【問6】** 手順10で、**窓Bの `UPDATE` は成功しましたか。** 返ってきたメッセージを**そのまま**書いてください。**エラーは出ましたか。**
**【問7】** 窓Bのアプリは、この結果を受けてどう振る舞うべきですか。**実際にその通りに手を動かして、最終在庫を 42 にしてください。**（打ったSQLも書いてください）
**【問8】** **【紙】** 問3のやり方（`FOR UPDATE`）と、問7のやり方（`version` を条件にした `UPDATE`）は、どちらも 42 になりました。では次の場合はどちらを使うべきですか。**理由も書いてください。**
> Webの編集画面で、ユーザーが商品情報を開き、**5分かけて入力してから**保存ボタンを押す

### 解答:

**【問1】** 最終的な在庫

```
 stock_quantity
----------------
             47
```

**42 になりません。**

**【問2】** どちらが消えたか／なぜ

**窓Aの「5個引く」が消えました。**

```
窓Aが読んだ値: 50
窓Bが読んだ値: 50      ← ここが問題
```

**両方が同じ 50 を読めてしまった**ことが原因です。

問題3で確認したとおり、**MVCC のおかげで読み取りは待たされません。** 便利な性質ですが、ここでは裏目に出ます。2つの窓は互いの存在を知らないまま、**どちらも「在庫は50だ」という前提で計算**してしまいました。

- 窓A：50 − 5 = 45 を書き込む
- 窓B：50 − 3 = 47 を書き込む（窓Aの `UPDATE` を待った**後**に、**自分が持っている 47** をそのまま書く）

`UPDATE` 同士はぶつかるので窓Bは待たされます。しかし**待っている間に窓Bが持っている「47」という値は更新されません。** 待ちが明けた瞬間、45 を 47 で上書きします。

これが**ロストアップデート（更新の喪失）**です。

**【問3】** 修正版

**`SELECT` に `FOR UPDATE` を付けるだけ**です。

```sql
-- 窓A
BEGIN;
SELECT stock_quantity FROM inventory
 WHERE product_id=1 AND warehouse_id=1
 FOR UPDATE;                          -- ★ ここだけ追加
-- （50 を読む → アプリが 50-5=45 を計算）
UPDATE inventory SET stock_quantity = 45 WHERE product_id=1 AND warehouse_id=1;
COMMIT;
```

```sql
-- 窓B（同じく FOR UPDATE を付ける）
BEGIN;
SELECT stock_quantity FROM inventory
 WHERE product_id=1 AND warehouse_id=1
 FOR UPDATE;                          -- ★ ここで待たされる
-- （45 を読む → アプリが 45-3=42 を計算）
UPDATE inventory SET stock_quantity = 42 WHERE product_id=1 AND warehouse_id=1;
COMMIT;
```

実測：

```
窓Aが読んだ値: 50
窓Bの SELECT ... FOR UPDATE : 3,229ms 待たされた
窓Bが読んだ値: 45
最終的な在庫  : 42     ← 正しい
```

**【問4】** 待つ位置の変化

| | 窓Bが待たされる場所 |
| :--- | :--- |
| 修正前 | `UPDATE`（＝**計算した後**） |
| 修正後 | `SELECT ... FOR UPDATE`（＝**読む時点**） |

**待ちが前倒しされたことが本質です。**

修正前は「古い値を掴んだ状態で待つ」ので、待ちが明けても手元の値は古いままでした。修正後は**そもそも古い値を掴めない**ので、待ちが明けてから読む値は必ず最新です。

**【問5】** なぜ3ステップの実装が必要になるのか

`UPDATE inventory SET stock_quantity = stock_quantity - 5` の1文では、**在庫が足りるかどうかを判断できない**からです。

在庫2個の商品に5個の注文が来た場合、この1文は**在庫を -3 にしてしまいます**。実務では「在庫が足りなければ注文を断る」という**判断**が必要で、そのためには一度値を読んで比較しなければなりません。

```
① 読む      ← 判断材料を得る
② 判断する   ← 足りなければエラー
③ 書き戻す
```

**この「読んでから判断する」パターンが必要な瞬間、`FOR UPDATE` が必要になります。**

（※ 実は1文でも `WHERE ... AND stock_quantity >= 5` と条件を足せば、在庫不足のときは**更新0件**になるので判断できます。ただし「なぜ0件だったのか」——在庫不足なのか、そもそも商品が無いのか——は区別がつきません。業務エラーとして理由を返したい場合は `FOR UPDATE` ＋ 明示的な判断のほうが素直です。→ [[15-2_実践_ロックとMVCC|15-2]] §4-4 のパターン①）

**【問6】** 窓Bの `UPDATE` はどうなったか

```
UPDATE 0
```

**エラーは出ません。** 返ってきたのは「0行を更新しました」というメッセージだけです。実測では **2,901ミリ秒待たされたのち**、`UPDATE 0` が返りました。その時点の行はこうなっています。

```
 stock_quantity | version
----------------+---------
             45 |       2
```

窓Aの更新だけが残り、`version` が 1 → 2 に進んでいます。

**【問7】** 検知したあと、どうするか

**読み直して、計算し直して、もう一度実行する**（＝リトライ）。

```sql
-- 窓B（やり直し）
SELECT stock_quantity, version FROM inventory WHERE product_id=1 AND warehouse_id=1;
-- → 今度は 在庫45 / version 2。アプリが 45-3=42 を計算

UPDATE inventory
   SET stock_quantity = 42,
       version = version + 1
 WHERE product_id=1 AND warehouse_id=1
   AND version = 2;      -- 読み直した version を条件にする
```

実測：

```
 stock_quantity | version
----------------+---------
             45 |       2

UPDATE 1

 stock_quantity | version
----------------+---------
             42 |       3
```

**【問8】** 5分かけて入力する編集画面ではどちらか

**楽観ロック（`version` を条件にした `UPDATE`）です。**

`FOR UPDATE`（悲観ロック）を使うと、**ユーザーが編集画面を開いた瞬間から保存ボタンを押すまでの5分間、ずっと行ロックを握り続ける**ことになります。その間、他の誰もその商品を更新できません。しかもユーザーがそのままブラウザを閉じたら、**トランザクションは `COMMIT` も `ROLLBACK` もされないまま残ります**（＝問題6で見た `idle in transaction` の状態です）。

**判断ルールはこうです**（→ [[15-2_実践_ロックとMVCC|15-2]] §4-4）。

| 読んでから書き戻すまで | 使うもの |
| :--- | :--- |
| 一瞬（アプリの中で完結する） | **悲観ロック**（`FOR UPDATE`） |
| **人間の操作が挟まる** | **楽観ロック**（`version` を条件にした `UPDATE`） |
| そもそも単純な加減算 | **1文で書く**（`SET stock = stock - 5 WHERE ... AND stock >= 5`） |

### 解説:

**なぜ手順10で `UPDATE 0` になるのか。** 問題1（→ [[15-2_実践_ロックとMVCC|15-2]] §1-2）で確認したとおり、**待たされた `UPDATE` は、ロックが外れた後に対象行を読み直してから実行されます。** 読み直した時点で `version` はすでに 2 なので、`AND version = 1` という条件に合う行が1行も無くなります。

問題1では「読み直すおかげで正しく計算される」仕組みでした。ここでは同じ仕組みが、**「他人に先を越されたことを検知する装置」**として働いています。これが**楽観ロック**です。

**`UPDATE 0` はエラーではありません。** JDBC の `executeUpdate()` も MyBatis の Mapper メソッドも、更新件数を `int` で返すだけで例外は投げません。**この戻り値を捨てているコードは、楽観ロックを書いていないのと同じです。**

**なぜ `stock_quantity` そのものではなく `version` を条件にするのか。** `AND stock_quantity = 50` でも同じように検知できそうに見えますが、**「50 → 45 → 50」と誰かが値を戻した場合を見逃します。** 値が同じに戻っていれば条件が成立してしまうからです。**`version` は増える一方**なので、戻ることがありません。だから専用の列を1本用意します。**どの列を更新する処理でも同じ形で書ける**、という利点もあります。

## 問題 5: 【2窓】デッドロックを起こして、直す
- **目的**: デッドロックを自分で起こして、ロックを取る順番を揃えれば防げることを理解する。

### 問題:

**【手順（起こす）】**

> ⚠️ 2つの窓を**同時に**実行することはできません。**窓A→窓B→窓A→窓B と、1文ずつ交互に**実行してください。

1. **窓A** で実行します。
   ```sql
   BEGIN;
   UPDATE products SET price = price + 1 WHERE product_id = 1;
   ```
2. **窓B** で実行します。
   ```sql
   BEGIN;
   UPDATE products SET price = price + 1 WHERE product_id = 2;
   ```
3. **窓A** で実行します（**返ってこなくなります**）。
   ```sql
   UPDATE products SET price = price + 1 WHERE product_id = 2;
   ```
4. **窓B** で実行します。
   ```sql
   UPDATE products SET price = price + 1 WHERE product_id = 1;
   ```
5. **約1秒待ちます。**

**【問1】** 手順5の後、何が起きましたか。**エラーメッセージをそのまま書いてください。** また、**どちらの窓が犠牲になりましたか。**
**【問2】** なぜこの状態になったのかを、「窓Aは○○を待っている／窓Bは××を待っている」の形で説明してください。
**【問3】** PostgreSQL はこの状態を検知するまで**約1秒待ちました。** すぐに検知しないのはなぜだと思いますか。次のSQLの結果も踏まえて答えてください。
```sql
SHOW deadlock_timeout;
```
**【問4】** **【本題】** 上の手順を**デッドロックが起きないように書き換えてください。** SQLの中身は変えず、**順番だけ**を変えます。

### 解答:

**【問1】** 何が起きたか

**約1秒後、窓B（手順4を実行した側）がエラーで落ちます。**

```
ERROR:  deadlock detected
DETAIL:  Process 25544 waits for ShareLock on transaction 18430; blocked by process 14048.
Process 14048 waits for ShareLock on transaction 18431; blocked by process 25544.
HINT:  See server log for query details.
CONTEXT:  while updating tuple (0,21) in relation "products"
ROLLBACK
```

**窓Bは自動的に `ROLLBACK` され、窓Aは何事もなく処理を続行できます。**

> どちらが犠牲になるかは**選べません。** PostgreSQL が決めます。

**【問2】** なぜこの状態になったか

- **窓Aは、商品2 を待っている**（商品2 は窓Bがロック中）
- **窓Bは、商品1 を待っている**（商品1 は窓Aがロック中）

互いに相手のトランザクション終了を待っているので、**放っておけば永久に進みません**。これがデッドロックです。

原因は**ロックを取る順番が逆だった**ことです。

| | 1番目 | 2番目 |
| :--- | :--- | :--- |
| 窓A | 商品1 | 商品2 |
| 窓B | 商品2 | 商品1 |

**【問3】** なぜすぐ検知しないのか

```
 deadlock_timeout
------------------
 1s
```

PostgreSQL は、**ロック待ちが `deadlock_timeout`（既定1秒）を超えたときだけ**デッドロックの有無を調べます。

**デッドロックの検査そのものにコストがかかる**（「誰が誰を待っているか」の待ちグラフを全部たどって循環を探す必要がある）ためです。ロック待ちは日常的に発生するもので、そのほとんどはすぐ解消します。**毎回検査していたら、正常な待ちのためにCPUを浪費します。**

だから「1秒くらい待つ」のは異常ではなく、**設計どおりの動作**です。

**【問4】** 起きないように書き換える

**両方とも「商品1 → 商品2」の順にします。** SQLの中身は変えません。

```sql
-- 窓A
BEGIN;
UPDATE products SET price = price + 1 WHERE product_id = 1;
UPDATE products SET price = price + 1 WHERE product_id = 2;
COMMIT;
```

```sql
-- 窓B（順番を A と揃える）
BEGIN;
UPDATE products SET price = price + 1 WHERE product_id = 1;   -- ★ ここで素直に待つだけ
UPDATE products SET price = price + 1 WHERE product_id = 2;
COMMIT;
```

実測（窓Aが約4秒握った状態で窓Bを実行）：

```
--- 窓A ---  COMMIT
--- 窓B ---  COMMIT
 product_id |  price
------------+---------
          1 | 1202.00
          2 |  802.00
```

**どちらもエラーにならず、両方の +1 が反映されています。** 窓Bは商品1のところで素直に待ち、窓Aが終わってから順に進むだけです。

### 解説:

複数行をまとめてロックする場合は、**`ORDER BY` を付ける**だけで順序が揃います。

```sql
SELECT * FROM products WHERE product_id IN (5, 2, 9) ORDER BY product_id FOR UPDATE;
```

> **対策の優先順位**
> 1. **ロック順序を統一する**（最も効果的。設計時のルールにする）
> 2. **トランザクションを短くする**（待ち合う時間そのものを減らす）
> 3. **デッドロックエラーを受けたらリトライする**（確率は下げられても0にはできないので、最後の保険）
>
> 3だけで済ませると、負荷が上がるほど発生率が上がっていずれ回らなくなります。**デッドロックは「設計を見直せ」というサインです。**

## 問題 6: 【2窓】固まったときに犯人を探す
- **目的**: `pg_stat_activity` でロック待ちの原因になっている接続を特定し、止めるかどうかを判断できるようになる。

### 問題:
問題1の状態（窓Aが `COMMIT` せず、窓Bが待たされている）を**もう一度作ってください。**
その状態のまま、**3つ目の窓**（または待っていない側の窓）から調査します。

**【手順】**

1. 待たされている接続と、待たせている接続を探します。
   ```sql
   SELECT pid,
          pg_blocking_pids(pid) AS 待たせている相手,
          wait_event_type       AS 待ちの種類,
          left(query, 50)       AS 実行中のSQL
   FROM pg_stat_activity
   WHERE cardinality(pg_blocking_pids(pid)) > 0;
   ```
2. 犯人のPIDが分かったら、その接続が何をしているか調べます。
   ```sql
   SELECT pid, state, xact_start, now() - xact_start AS 経過時間, left(query, 80)
   FROM pg_stat_activity WHERE pid = <調べたPID>;
   ```
3. 犯人を実際に止めてみます。**まず穏当なほうから試してください。**
   ```sql
   -- 窓C
   SELECT pg_cancel_backend(<犯人のPID>);
   ```
   実行したら、**もう一度手順2のクエリを打って、本当に止まったか確認**してください。

**【問1】** 「待たせている相手」に表示されたPIDは、どちらの窓のものでしたか。各窓で `SELECT pg_backend_pid();` を実行して確認してください。
**【問2】** 手順2で犯人の `state` は何と表示されましたか。**その状態が意味することを説明してください。**
**【問3】** 手順2の `query` 列には `UPDATE ...` が表示されているはずです。**この接続は、いまその `UPDATE` を実行している最中ですか。** 答えと、その理由を書いてください。
**【問4】** 手順3の `pg_cancel_backend` は何を返しましたか。**犯人は止まりましたか。** 止まっていないとしたら、それはなぜですか。また、**どうすれば止められますか。**
**【問5】** 本番環境でこれらを実行する前に、**確認すべきこと**を挙げてください。

### 解答:

**【問1】** 待たせている相手

**窓A（`COMMIT` していない側）のPID**が表示されます。

実測の出力：

```
  pid  | 待たせている相手 | 待ちの種類 |                 実行中のSQL
-------+------------------+------------+---------------------------------------------
 23380 | {9452}           | Lock       | UPDATE products SET price = price + 1 WHERE
```

**「PID 23380 は、PID 9452 に待たされている」**と読みます。各窓で `SELECT pg_backend_pid();` を実行すれば、どちらがどちらか確認できます。

- `23380` = 窓B（待たされている側）
- `9452` = 窓A（`COMMIT` していない犯人）

`wait_event_type` が `Lock` になっているのが、**ロック待ちであることの証拠**です。

**【問2】** 犯人の `state`

実測の出力：

```
  pid  |        state        |     elapsed     |                    q
-------+---------------------+-----------------+------------------------------------------
 23448 | idle in transaction | 00:00:02.955006 | UPDATE products SET price = price + 100
```

**`idle in transaction` ＝「トランザクションを開いたまま、何もしていない」**という意味です。

**これが最も危険な状態です。** クエリを実行中（`active`）なら、いずれ終わって解放されます。しかし `idle in transaction` は**人間が `COMMIT` を打つまで永久に終わりません。** その間ずっとロックを握り続けます。

**【問3】** `query` 列の `UPDATE` は「今実行中」か

**いいえ、実行中ではありません。**

`query` は**その接続が最後に実行したSQL**を表示する列です。`state` が `active` でない限り、そのSQLは**すでに終わっています。** 今回の犯人は `state = idle in transaction` なので、`UPDATE` はとっくに完了していて、`COMMIT` が来るのを待っているだけです。

**【問4】** `pg_cancel_backend` は効いたか

**`t`（成功）が返ってきますが、止まりません。**

まず2つのコマンドの違いを整理します。

| コマンド | 何をするか |
| :--- | :--- |
| `pg_cancel_backend(PID)` | **実行中のクエリだけ**をキャンセルする。接続とトランザクションは生き残る |
| `pg_terminate_backend(PID)` | **接続そのものを切断**する。開いていたトランザクションは `ROLLBACK` される |

**穏当なのは `pg_cancel_backend` なので、まずこちらを試すのは正しい判断です。**

ただし今回のように `idle in transaction`（＝実行中のクエリが無い）状態では、**`pg_cancel_backend` は効きません。** キャンセルする対象が無いからです。

**厄介なのは、効いていないのに `t`（成功）が返ってくることです。** 実測：

```sql
SELECT pg_cancel_backend(23448);
```

```
 cancel_result
---------------
 t              ← 成功したように見えるが…
```

```sql
SELECT pid, state FROM pg_stat_activity WHERE pid = 23448;
```

```
  pid  |        state
-------+---------------------
 23448 | idle in transaction   ← 何も変わっていない
```

**戻り値の `t` は「シグナルを送れた」という意味であって、「止まった」という意味ではありません。** 必ず `pg_stat_activity` で結果を確認してください。

**止めるには `pg_terminate_backend` を使います。**

```sql
SELECT pg_terminate_backend(23448);   -- 接続ごと切る。トランザクションはロールバックされる
```

**【問5】** 本番で実行する前に確認すべきこと

1. **その接続が何をしているか**（`state` と `query` をセットで。`xact_start` からの経過時間、`application_name`、`client_addr` も）
2. **切って安全か**。長時間動いている集計バッチかもしれません。切ると最初からやり直しになります
3. **持ち主に連絡が取れるか**。人が操作している接続なら、まず声をかけるのが先です
4. **切ったあとどうなるか**。アプリが自動リトライして同じ状態を作り直すだけ、ということもあります

### 解説:

`idle in transaction` が長時間続いている接続を見つけたら、それが障害の原因です。典型的な原因は次の3つです。

- 開発者がクエリツールで `BEGIN` して放置している（昼休みなど）
- アプリケーションが `COMMIT` / `ROLLBACK` を呼ばずに例外を投げた
- 自動コミットが off のツールで `UPDATE` だけ打った

**`query` は必ず `state` とセットで読んでください。** ここを読み違えると「重い `UPDATE` が走っている」という誤診になり、まったく的外れな調査が始まります。

| `state` | `query` の意味 |
| :--- | :--- |
| `active` | **今実行中**のSQL |
| `idle in transaction` | **最後に実行した**SQL。今は何もしていない |
| `idle` | 最後に実行したSQL。トランザクションも開いていない（無害） |

**根本原因を直さずに切るだけだと、同じことが繰り返されます。** 切るのは応急処置、原因調査とセットで行ってください。

## 問題 7: 在庫引き当てを伴う注文処理
- **目的**: 問題4で手作業でやった `FOR UPDATE` による排他制御を、プロシージャとして実装できるようになる。

### 問題:
問題4で手作業でやったことを、**プロシージャとして実装**します。

顧客から注文を受けた際、在庫をチェックして注文を確定させるプロシージャ `proc_create_order` を作成してください。

**【仕様】**

1. **引数**: `p_customer_id`（顧客ID）, `p_product_id`（商品ID）, `p_warehouse_id`（倉庫ID）, `p_quantity`（注文数）
2. **排他制御**: 在庫確認から更新までの間に他のセッションが同じ在庫を書き換えないよう、`INVENTORY` の該当行に**行ロックを取得**すること（**問題4の答えがそのまま使えます**）
3. **在庫チェック**:
   - 指定された倉庫に十分な在庫があるか確認する
   - 在庫が不足している場合は `RAISE EXCEPTION` で処理を中断する
4. **注文処理**:
   - `ORDERS` に新規レコードを挿入（`STATUS` は `'Pending'` 固定）
   - `ORDERITEMS` に明細レコードを挿入
   - `INVENTORY` の `STOCK_QUANTITY` を注文数ぶん減算
5. **一貫性**: いずれかでエラーが起きたら全ての変更が無効になること

> 💡 **`EXCEPTION` ハンドラの中に `ROLLBACK` を書かないでください。** 理由は [[15-3_補足_PLpgSQLの中のトランザクション制御|15-3]] §3 にあります。**書かなくても巻き戻ります。**

**【テスト実行例】**

**正常系：**
```sql
CALL proc_create_order(1, 1, 1, 5);
-- ORDERS, ORDERITEMS が増え、INVENTORY の在庫が 50→45 に減っていることを確認
```

**異常系（在庫不足）：**
```sql
CALL proc_create_order(1, 9, 1, 10);
-- 商品ID:9 (Luxury Sofa) は在庫2しかないため、エラーになりテーブルは更新されない
```

**【発展】** 窓を2つ開いて、**同じ商品に対して同時に `CALL`** してみてください。片方が待たされることを確認しましょう。

### 解答:

```sql
CREATE OR REPLACE PROCEDURE proc_create_order(
    p_customer_id  INT,
    p_product_id   INT,
    p_warehouse_id INT,
    p_quantity     INT
)
LANGUAGE plpgsql
AS $$
DECLARE
    v_order_id      INT;
    v_current_stock INT;
BEGIN
    -- ① 排他制御：対象の在庫レコードに行ロックを取る
    --    （他トランザクションは、この行を読む時点で待たされる）
    SELECT stock_quantity INTO v_current_stock
      FROM inventory
     WHERE product_id = p_product_id AND warehouse_id = p_warehouse_id
     FOR UPDATE;

    -- ② 在庫チェック
    IF v_current_stock IS NULL THEN
        RAISE EXCEPTION '指定された商品または倉庫が存在しません。(商品ID=%, 倉庫ID=%)',
                        p_product_id, p_warehouse_id;
    ELSIF v_current_stock < p_quantity THEN
        RAISE EXCEPTION '在庫不足です。現在の在庫: %, 注文数: %', v_current_stock, p_quantity;
    END IF;

    -- ③ ORDERS へ挿入（IDは本来シーケンスを使う。ここでは簡易的に MAX+1）
    SELECT COALESCE(MAX(order_id), 0) + 1 INTO v_order_id FROM orders;
    INSERT INTO orders (order_id, customer_id, order_date, status)
    VALUES (v_order_id, p_customer_id, CURRENT_DATE, 'Pending');

    -- ④ ORDERITEMS へ挿入
    INSERT INTO orderitems (order_item_id, order_id, product_id, quantity)
    VALUES ((SELECT COALESCE(MAX(order_item_id), 0) + 1 FROM orderitems),
            v_order_id, p_product_id, p_quantity);

    -- ⑤ 在庫の減算
    UPDATE inventory
       SET stock_quantity = stock_quantity - p_quantity
     WHERE product_id = p_product_id AND warehouse_id = p_warehouse_id;

    RAISE NOTICE '注文完了: ORDER_ID %, 商品ID %, 数量 %', v_order_id, p_product_id, p_quantity;
END;
$$;
```

実測結果（正常系）：

```
NOTICE:  注文完了: ORDER_ID 14, 商品ID 1, 数量 5
CALL

 stock_quantity
----------------
             45        ← 50 から 5 減った
```

実測結果（異常系・在庫不足）：

```
ERROR:  在庫不足です。現在の在庫: 2, 注文数: 10
CONTEXT:  PL/pgSQL function proc_create_order(integer,integer,integer,integer) line 14 at RAISE
```

エラー後にデータが汚れていないことも確認：

```
 orders_count
--------------
           14        ← 増えていない

 stock_quantity
----------------
              2      ← 減っていない
```

### 解説:

**① `EXCEPTION` ハンドラを書いていません。**

仕様5「エラーが起きたら全ての変更が無効になること」は、**何も書かなくても満たされます。** `RAISE EXCEPTION` でプロシージャが異常終了すれば、そのトランザクション全体が巻き戻ります。

**わざわざ `EXCEPTION WHEN OTHERS THEN ... ROLLBACK;` と書くのは間違いです。**

- **不要**：ハンドラに入った時点で、すでに巻き戻っています
- **有害**：外側でトランザクションが開いていると `invalid transaction termination` で落ちます

→ 詳しくは [[15-3_補足_PLpgSQLの中のトランザクション制御|15-3]] §3

**② `FOR UPDATE` がこのプロシージャの心臓部です。**

これが無いと、問題4で見たロストアップデートがそのまま起きます。「在庫を読む → 足りるか判断する → 減算する」の間に他のセッションが割り込めないよう、**読む時点で押さえています。**

**③【発展】2窓で同時に `CALL` すると**

**後から実行した側は、先の `CALL` が終わるまで待たされます。** `FOR UPDATE` が効いている証拠です。順番に処理されるので、在庫は正しく 10 減ります。

> **`FOR UPDATE` は「同時に来た注文を、順番待ちの列に並ばせる」仕組み**だと理解すると分かりやすいです。

## 問題 8: 未発送注文の一括発送バッチ（分割コミット）
- **目的**: バッチ処理を分割コミットで書き、トランザクションを短く保つ理由を説明できるようになる。

### 問題:
`STATUS = 'Processing'` の注文を「出荷済み（Shipped）」に更新するバッチ `proc_batch_shipping` を作成してください。

**【仕様】**

1. **対象抽出**: `ORDERS` から `STATUS = 'Processing'` の注文をすべて抽出する
2. **ループ処理**: 1件ずつループで処理する
3. **更新内容**:
   - `SHIPMENTS` に新規レコードを作成（`Status`: `'In Transit'`, `Shipped_Date`: 当日）
   - `ORDERS` の `STATUS` を `'Shipped'` に更新
4. **分割コミット**: **1件処理が終わるたびに `COMMIT`** すること

作成できたら実行して、`STATUS = 'Processing'` の注文が `'Shipped'` になることを確認してください。

```sql
SELECT order_id, status FROM orders WHERE status = 'Processing' ORDER BY order_id;
CALL proc_batch_shipping();
SELECT order_id, status FROM orders WHERE order_id = 7;
```

**【問1】** 100万件を1つの `BEGIN ... COMMIT` で処理した場合の問題を、**2つ**挙げてください。（ヒント：ひとつは [[15-2_実践_ロックとMVCC|15-2]] §1-1 で体験したことです）
**【問2】** `BEGIN; CALL proc_batch_shipping(); COMMIT;` のように、**外側をトランザクションで囲んで**実行するとどうなりますか。実際に試して、エラーメッセージを書いてください。また、**なぜそうなるのか**も説明してください。

### 解答:

```sql
CREATE OR REPLACE PROCEDURE proc_batch_shipping()
LANGUAGE plpgsql
AS $$
DECLARE
    v_order       RECORD;
    v_shipment_id INT;
BEGIN
    FOR v_order IN
        SELECT order_id FROM orders WHERE status = 'Processing' ORDER BY order_id
    LOOP
        SELECT COALESCE(MAX(shipment_id), 0) + 1 INTO v_shipment_id FROM shipments;
        INSERT INTO shipments (shipment_id, order_id, shipped_date, status)
        VALUES (v_shipment_id, v_order.order_id, CURRENT_DATE, 'In Transit');

        UPDATE orders SET status = 'Shipped' WHERE order_id = v_order.order_id;

        RAISE NOTICE '注文ID: % の発送処理に成功しました。', v_order.order_id;

        COMMIT;        -- ★ 1件ごとに確定する
    END LOOP;
END;
$$;
```

**【問1】** 100万件を1つの `BEGIN ... COMMIT` で処理する問題

**① 長時間ロックを握り続ける**

問題1（[[15-2_実践_ロックとMVCC|15-2]] §1-1）で体験したとおり、**行ロックはトランザクションが終わるまで解放されません。** 100万件を1トランザクションで更新すると、**処理が終わるまで100万行すべてがロックされたまま**です。その間、それらの行を触ろうとした利用者は全員待たされます。

**② 失敗したときに最初からやり直しになる**

90万件目でサーバーが落ちたら、**89万9,999件ぶんの処理がすべて消えます。** 分割コミットしていれば「すでに `Shipped` になったものは飛ばして、90万件目から再開する」という運用ができます。

（他にも「MVCC の古いバージョンが `VACUUM` で回収できず溜まり続ける」「ロックを握る時間が長いぶんデッドロックの確率が上がる」があります。）

**【問2】** 外側をトランザクションで囲むと

実測：

```
BEGIN
NOTICE:  注文ID: 7 の発送処理に成功しました。
ERROR:  invalid transaction termination
CONTEXT:  PL/pgSQL function proc_batch_shipping() line 28 at COMMIT
ROLLBACK
```

（`CONTEXT` の行番号は、書いたプロシージャの `COMMIT` の位置によって変わります。）

**プロシージャ内の `COMMIT` で落ちます。** そして「成功した」とログに出た注文も、まるごと巻き戻っています。

```
 order_id |   status
----------+------------
        7 | Processing     ← 成功していたはずの 7 番も戻っている
```

**プロシージャの中で `COMMIT` できるのは、呼び出し側がトランザクションを開始していないときだけ**です。外側で `BEGIN;` されていると、プロシージャは「他人が始めたトランザクションの一部」として動いています。その途中で勝手に確定すると、**呼び出し側が想定しているトランザクションの境界が壊れます。** だから PostgreSQL が拒否します。

→ [[15-3_補足_PLpgSQLの中のトランザクション制御|15-3]] §2-1

### 解説:

> ⚠️ **自動コミットが off のツールやアプリから `CALL` すると、暗黙に `BEGIN` されているので同じエラーになります。**
> 「psql では動いたのに、アプリから呼んだら `invalid transaction termination` が出る」の正体はこれです。→ [[15-1_導入_トランザクションとACID|15-1]] §2-2

**「トランザクションは短く」**——これがこの章を通した結論です（→ [[15-2_実践_ロックとMVCC|15-2]] §6）。

## 問題 9: 【紙】トランザクションの境界を引き直す
- **目的**: 「一緒に無かったことにできる範囲」でトランザクションの境界を引けるようになる。

### 問題:
**この問題ではSQLを打ちません。** 読んで考えて、日本語で答えてください。

ある通販サイトの「注文を確定する」処理が、次のように書かれていました。

```
BEGIN;
  ① SELECT stock_quantity FROM inventory WHERE ... FOR UPDATE;   -- 在庫を押さえる
  ② IF 在庫 < 注文数 THEN ROLLBACK; 「在庫切れです」を返す;
  ③ INSERT INTO orders ...;
  ④ INSERT INTO orderitems ...;
  ⑤ UPDATE inventory SET stock_quantity = 在庫 - 注文数 WHERE ...;
  ⑥ 決済代行サービスのAPIを呼ぶ;          -- ★ 平均1.2秒。混雑時は最大30秒かかる
  ⑦ 注文確認メールをお客様に送信する;      -- ★
  ⑧ 管理画面用のPDFをファイルに書き出す;   -- ★
COMMIT;
```

①〜⑤は問題ありません。**問題は★を付けた⑥⑦⑧です。**

**【問1】** ⑥⑦⑧をトランザクションの中に置いてはいけない理由を、**2つの観点から**説明してください。
（ヒント：ひとつは「`ROLLBACK` したときに何が起きるか」、もうひとつは「①で取ったロックはいつ外れるか」）
**【問2】** **【本題】** この処理の**境界を引き直してください。** どこで `COMMIT` し、⑥⑦⑧をどう扱いますか。擬似コードで書いてください。
**【問3】** **【発展】** ある日、決済代行サービスが混雑して⑥に30秒かかりました。**このとき、同じ商品を注文しようとした他のお客様には何が起きますか。** [[15-2_実践_ロックとMVCC|15-2]] §1-1 で実測した内容を使って説明してください。

### 解答:

**【問1】** ⑥⑦⑧を中に置いてはいけない理由

**観点① `ROLLBACK` で取り消せない副作用だから**

⑥⑦⑧はすべて**DBの外に対する操作**です。トランザクションが `ROLLBACK` されても、これらは元に戻りません。

| | `ROLLBACK` したら |
| :--- | :--- |
| ①〜⑤（DBの操作） | **なかったことになる** |
| ⑥ 決済API | **決済は実行済みのまま。**お金だけ引き落とされて注文が存在しない |
| ⑦ メール送信 | **送ったメールは戻せない。**「ご注文ありがとうございます」だけ届いて注文が無い |
| ⑧ ファイル出力 | **ファイルは残ったまま** |

たとえば⑦でメール送信に失敗して例外が飛ぶと、①〜⑤は巻き戻りますが、**⑥の決済だけが実行済みで残ります。** これは一番直しにくい種類の不整合です。

**観点② その間ずっと行ロックを握り続けるから**

①で `FOR UPDATE` を取った在庫の行は、**`COMMIT` するまでロックが外れません**（→ [[15-2_実践_ロックとMVCC|15-2]] §1-1）。⑥が30秒かかれば、**その30秒間ずっとロックしたまま**です。

**【問2】** 境界の引き直し

```
BEGIN;
  ① SELECT ... FOR UPDATE;
  ② 在庫チェック（足りなければ ROLLBACK して「在庫切れ」を返す）
  ③ INSERT INTO orders ...;
  ④ INSERT INTO orderitems ...;
  ⑤ UPDATE inventory ...;
COMMIT;                            ← ここまでがDBの仕事。ここでロックが外れる
-------------------------------------------------------------
  ⑥ 決済代行サービスのAPIを呼ぶ;     ← コミットしてから
  ⑦ 注文確認メールを送信する;
  ⑧ PDFを書き出す;
```

**判断基準は「一緒に無かったことにできるか」です。** ①〜⑤は片方だけ成立したら壊れるので1つの塊。⑥⑦⑧は巻き戻せないので、外に出します。

**【問3】** 決済APIが30秒かかったとき、他のお客様に何が起きるか

**同じ商品を注文しようとしたお客様は、全員30秒待たされます。**

問題1（[[15-2_実践_ロックとMVCC|15-2]] §1-1）の実測では、窓Aが約6秒握っていたとき、窓Bの `UPDATE` は **5,958ミリ秒**——**握られていた時間ぶん、まるごと**待たされました。ロックは `COMMIT` するまで外れないので、待ち時間は「相手が握っている時間」そのものです。

したがって決済に30秒かかれば、**その在庫行を触りたい注文はすべて約30秒止まります。** 秒間10件の注文が来ていれば、300件が滞留します。

**そして最悪なのは、これがテストでは絶対に発覚しないことです。** テスト環境では決済APIのモックが即座に返り、同時アクセスもありません。**本番の繁忙時、決済代行が混み合ったときにだけ、突然サイト全体が固まります。**

### 解説:

> **「では⑥の決済が失敗したらどうするのか」——これは良い疑問です。**
> 答えは「**トランザクションで解決しようとしない**」です。決済失敗は業務上ありうる事象なので、注文の `status` を `'Payment Failed'` に更新する、といった**業務的な後始末**で扱います。DBのロールバックで巻き戻すべき問題ではありません。
>
> ⑦⑧の実装の受け皿として、**送信予定テーブル**という定番のやり方があります。「送るべきメール」を1行 `INSERT` するところまでをトランザクションに入れ、別プロセスが後から読んで送ります。送信自体が失敗しても再送できるので堅牢です。

**これが「トランザクションの中で外部APIを呼ばない」という原則が存在する理由です。** 自分のシステムの応答時間が、**他社のシステムの調子に直結してしまう**——それを避けるために境界を引きます。
