# 11章 演習 解答：テーブル構造変更と削除と再定義

**PostgreSQL 17 で実際に動かした結果を載せています。** **問題 1〜7 が「削除と再定義」、問題 8〜16 が「構造変更」** です。

この章は `DROP` / `TRUNCATE` / `ALTER TABLE` で**テーブルそのものを書き換えます。** 上から順に実行すると、後の章で使うテーブルが元の形ではなくなります。終わったら「準備」のリセット手順で戻してください。

---

## 準備

### 使用するテーブル

**8章以降と同じテーブルをそのまま使います。** 新しく作るものはありません。
まだ作っていない場合は [[00_SQL研修/02_問題/08_結合から使用するテーブル|08_結合から使用するテーブル]] で作成してください。

この章で触るのは `Reviews` / `Inventory` / `Warehouses` / `Staff` / `Customers` / `Products` / `Orders` / `Payments` / `Shipments` / `Memberships` です。

> ⚠️ **この章はロールバックで戻せません。** `DROP` と `TRUNCATE` は暗黙にコミットこそしませんが、テーブルや行が消えた状態で先へ進むため、途中でやり直したくなったら下のリセット手順を使ってください。

### リセット手順

構造そのものを壊す章なので、**DBを作り直して入れ直します。**

1. `DROP DATABASE` → `CREATE DATABASE`
2. [[00_SQL研修/02_問題/08_結合から使用するテーブル|08_結合から使用するテーブル]] の「DDL」を実行する
3. 同じページの「テストデータ」を上から順に実行する

**この章だけは `TRUNCATE用` では戻りません。** テーブル定義そのものを変えるので、作り直す必要があります。

## 問題 1: テーブルを丸ごと削除する
- **目的**: `DROP TABLE` がデータではなくテーブル定義ごと消すものだと理解する。

### 問題:
テーブル Reviews（商品レビュー）を削除してください。

### 解答:
```sql
DROP TABLE Reviews;
```

---

## 問題 2: 定義を残してデータだけ消す
- **目的**: `TRUNCATE TABLE` がテーブル定義（カラム・制約）を残したまま全行を消すことを理解する。

### 問題:
Inventory テーブルの在庫情報をリセットしたい。
ただし テーブル定義（カラムや制約）は残すようにしてください。

### 解答:
```sql
TRUNCATE TABLE Inventory;
```

### 解説:
`DROP TABLE` との違いは「入れ物が残るかどうか」です。`TRUNCATE` のあとも `SELECT * FROM Inventory;` は 0 行を返します（テーブルは存在する）。`DROP` したあとは「そんなテーブルは無い」というエラーになります。

---

## 問題 3: 依存関係ごと削除する
- **目的**: 他テーブルから外部キーで参照されているテーブルを `DROP TABLE ... CASCADE` で削除する。

### 問題:
倉庫 Warehouses テーブルを削除したいが、外部キーで Inventory や Staff に参照されています。
依存関係も含めて一括削除してください。

### 解答:
```sql
DROP TABLE Warehouses CASCADE;
```

### 解説:
`CASCADE` が消すのは**依存しているオブジェクト**であって、参照している側のテーブルではありません。ここで一緒に消えるのは `Inventory` と `Staff` が持っていた**外部キー制約**だけで、両テーブルとその行はそのまま残ります。`CASCADE` を付けないと `cannot drop table warehouses because other objects depend on it` で失敗します。

---

## 問題 4: DELETE と TRUNCATE の使い分け（全件リセット）
- **目的**: 全件を消すだけなら `TRUNCATE` のほうが効率的だと理由付きで説明できるようになる。

### 問題:
Inventory テーブルに数千件の在庫データが入っている。
一度、すべての在庫をリセットしたい。
DELETE と TRUNCATE のどちらを使えば効率的か？理由も答えてください。

### 解答:
```
TRUNCATE

全件削除に特化しており、高速でログも最小限。
定義は残るため「リセット」に最適。
```

### 解説:
`DELETE` は 1 行ずつ削除対象としてログに残しながら消すため、件数に比例して遅くなります。`TRUNCATE` はデータの入っている領域をまとめて捨てるので、件数がいくつでもほぼ一定の速さです。

---

## 問題 5: DELETE と TRUNCATE の使い分け（条件付き削除）
- **目的**: 条件を付けて一部だけ消せるのは `DELETE` だけだと理解する。

### 問題:
OrderItems テーブルから、product_id = 1001 の商品に関するデータを削除したい。
DELETE と TRUNCATE のどちらを使うべきか？理由も答えてください。

### 解答:
```
DELETE

条件付き削除ができるのは DELETE。
TRUNCATE は全件削除しかできない。
```

---

## 問題 6: DELETE と TRUNCATE の使い分け（外部キーがある場合）
- **目的**: 参照されているテーブルには `TRUNCATE` がそのまま使えないことを理解する。

### 問題:
Payments テーブルを Orders に外部キーで参照している場合において、Orders のデータを一括削除したい。
DELETE と TRUNCATE のどちらを使うべきか？理由も答えてください。

### 解答:
```
DELETE

TRUNCATE は外部キー制約があると基本的に使えない（エラーになる）。
DELETE なら外部キーを考慮しながら削除可能。
```

### 解説:
PostgreSQL で参照されている側のテーブルを `TRUNCATE` すると `cannot truncate a table referenced in a foreign key constraint` で止まります。`TRUNCATE Orders CASCADE;` と書けば通りますが、これは**参照している側（Payments・OrderItems・Shipments）まで空になる**という意味なので、「Orders だけ消したい」ときの答えにはなりません。

## 問題 7: 連番を 1 から振り直す
- **目的**: 全件削除と連番（採番カウンタ）のリセットを一度に行う方法を理解する。

### 問題:
在庫管理システムの Inventory テーブルには AUTO_INCREMENT の id カラムがある。
このテーブルを一度空にしたあと、新しいデータを入れる際に idを1から再スタートさせたい。
DELETE と TRUNCATE のどちらを使うべきか？理由も答えてください。

### 解答:
```
TRUNCATE

テーブルが一度 ドロップ＆再作成 に近い動作をするので、
AUTO_INCREMENT カウンタは リセットされ、1から再スタートする。
```

### 解説:
`DELETE` では採番カウンタが動かないため、全件消しても次の id は続きの番号になります。
なお PostgreSQL に `AUTO_INCREMENT` という語はなく、`SERIAL` / `GENERATED AS IDENTITY`（実体はシーケンス）で採番します。**PostgreSQL の `TRUNCATE` は既定ではシーケンスを戻しません。** 1 から振り直すには次のように書きます。

```sql
TRUNCATE TABLE Inventory RESTART IDENTITY;
```

MySQL の `TRUNCATE` は黙って 1 に戻るので、同じつもりで書くと結果がズレます。

## 問題 8: 列を追加する
- **目的**: `ALTER TABLE ... ADD COLUMN` で既存テーブルに列を足せるようになる。

### 問題:
Customers テーブルに「生年月日」を管理するカラム birth_date（DATE型）を追加してください。

### 解答:
```sql
ALTER TABLE Customers
ADD COLUMN birth_date DATE;
```

### 解説:
既存の行の `birth_date` は `NULL` で埋まります。`NOT NULL` を付けたいときは、`DEFAULT` を同時に指定するか、値を埋めてから制約を付けます（→ 問題 16）。

---

## 問題 9: 列のデータ型を変える
- **目的**: `ALTER COLUMN ... TYPE` で既存列のデータ型を変更する。

### 問題:
Products テーブルの price を整数型（INT）に変更してください。

### 解答:
```sql
ALTER TABLE Products
ALTER COLUMN price TYPE INT;
```

### 解説:
`DECIMAL(10,2)` → `INT` は情報が減る方向の変換です。小数部は切り捨てではなく**四捨五入**されて消えます。文字列型など自動で変換できない型へ変えるときは `USING` 句で変換方法を書く必要があります。

---

## 問題 10: 列を削除する
- **目的**: `ALTER TABLE ... DROP COLUMN` で不要になった列を消せるようになる。

### 問題:
Customers テーブルのカラム phone を削除してください。

### 解答:
```sql
ALTER TABLE Customers
DROP COLUMN phone;
```

## 問題 11: 列名を変更する
- **目的**: `ALTER TABLE ... RENAME COLUMN` で列名だけを変えられることを理解する。

### 問題:
Staff テーブルのカラム position を job_title に名前変更してください。

### 解答:
```sql
ALTER TABLE Staff
RENAME COLUMN position TO job_title;
```

### 解説:
名前が変わるだけで、入っているデータもデータ型もそのままです。ただし**この列を参照しているビューやアプリのSQLは追随して直す必要があります。**

---

## 問題 12: デフォルト値を設定する
- **目的**: `ALTER COLUMN ... SET DEFAULT` で、値を省略した `INSERT` に既定値が入るようにする。

### 問題:
Orders テーブルの status 列に、デフォルト値 'Pending' を設定してください。

### 解答:
```sql
ALTER TABLE Orders
ALTER COLUMN status SET DEFAULT 'Pending';
```

### 解説:
`DEFAULT` が効くのは**これから `status` を省略して `INSERT` する行**だけです。既に入っている行の `NULL` が 'Pending' に書き換わることはありません。解除は `DROP DEFAULT` です。

---

## 問題 13: CHECK 制約を追加する
- **目的**: `ADD CONSTRAINT ... CHECK` で、列に入れてよい値を限定する。

### 問題:
Payments テーブルの method に チェック制約 を追加し、
支払い方法が 'Credit Card', 'BankTransfer', 'Cash' のいずれかのみ登録できるようにしてください。

### 解答:
```sql
ALTER TABLE Payments
ADD CONSTRAINT chk_payment_method
CHECK (method IN ('Credit Card', 'BankTransfer', 'Cash'));
```

### 解説:
制約を追加する時点で、**既存の全行がその条件を満たしているか**が検査されます。1 行でも違反していると追加自体が失敗するので、実務では先に `SELECT ... WHERE method NOT IN (...)` で違反行を洗い出します。

---

## 問題 14: UNIQUE 制約を追加する
- **目的**: `ADD CONSTRAINT ... UNIQUE` で列の値の重複を禁止する。

### 問題:
Customers テーブルの email にユニーク制約を追加してください。

### 解答:
```sql
ALTER TABLE Customers
ADD CONSTRAINT uq_customers_email UNIQUE (email);
```

### 解説:
`UNIQUE` は `NULL` を重複とみなしません。email が `NULL` の顧客（Charlie）が複数いても制約は通ります。「必ず入っていて、かつ重複しない」にしたければ `NOT NULL` と併用します。

---

## 問題 15: 主キーを張り替える
- **目的**: 主キー列を落として、複数列の複合主キーに作り替える手順を理解する。

### 問題:
Shipments テーブルを以下のように変更しましょう。

1. PKである shipment_id のカラムの削除
2. order_id, shipped_date の組み合わせが一意になるように主キー制約を追加

### 解答:
```sql
ALTER TABLE shipments
DROP COLUMN shipment_id;

ALTER TABLE shipments
ADD CONSTRAINT pk_shipments PRIMARY KEY (order_id, shipped_date);
```

### 解説:
列を落とすと、その列に付いていた主キー制約も一緒に消えます（`DROP CONSTRAINT` を別に書く必要はありません）。新しく主キーにした `order_id` と `shipped_date` は、**自動的に `NOT NULL` になります。** 既に `NULL` や重複がある列は主キーにできません。

---

## 問題 16: NULL のある列を NOT NULL にする
- **目的**: 既存データを整えてから制約を付ける、という順番の必然性を理解する。

### 問題:
Customers テーブルで membership_id を 必須（NOT NULL） にしたい。
ただし既に NULL が入っている行があるため、以下の手順で操作を行ってください。

1. Memberships テーブルに membership_id を 999 として「仮のランク（General）」を追加
2. Customers テーブルの membership_id が NULL のデータを仮のランクで更新
3. Customers テーブルの membership_id を 必須に変更

### 解答:
```sql
-- ① 仮ランクを追加
INSERT INTO Memberships (membership_id, rank_name, discount_rate)
VALUES (999, 'General', 0.00);

-- ② NULLを仮ランクに更新
UPDATE Customers
SET membership_id = 999
WHERE membership_id IS NULL;

-- ③ NOT NULL制約を付与
ALTER TABLE Customers
ALTER COLUMN membership_id SET NOT NULL;
```

### 解説:
この順番でなければ通りません。③を先に実行すると `column "membership_id" of relation "customers" contains null values` で失敗し、②を先に実行すると 999 が Memberships に無いため外部キー違反で失敗します。**「参照先を用意する → 値を埋める → 制約を付ける」** が既存テーブルを必須化するときの定石です。
