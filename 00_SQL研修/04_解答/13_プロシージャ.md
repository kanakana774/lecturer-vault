# 13章 演習 解答：関数・プロシージャ・トリガー・動的SQL

**PostgreSQL 17 で全問実行して確認しています。掲載している出力はすべて実測です。** 成功ケースと失敗ケースの両方を確認しています。

> **この演習の前提**
> - 対応する講義は [[12-4_関数とプロシージャと例外処理|12-4]]／[[12-5_トリガーと動的SQL|12-5]] です。
> - 使用するテーブルは [[00_SQL研修/02_問題/08_結合から使用するテーブル|08_結合から使用するテーブル]] で作成したもの（8章以降と同じ）です。**問題 4 だけ、履歴を残すテーブルを自分で作ります。**
> - 変数は `v_`、引数は `p_`、行データを入れる変数は `r_` を付けてください。
> - 関数・プロシージャ名は小文字スネークケース（`update_customer_membership` のような形）で作ってください。
> - 書式は次で統一します。
>   - プロシージャ: `CREATE OR REPLACE PROCEDURE 名前(...) LANGUAGE plpgsql AS $$ ... $$;`
>   - 関数: `CREATE OR REPLACE FUNCTION 名前(...) RETURNS 型 LANGUAGE plpgsql AS $$ ... $$;`

## 準備

### ID の採番について

このデータベースの主キーは**自動採番ではありません**。新しい行を登録する問題では、`SELECT COALESCE(MAX(id), 0) + 1 INTO v_new_id FROM テーブル;` で自分で採番してください（[[12-2_変数とSQLの実行|12-2]] §9）。

実務では同時実行で ID が衝突するのでシーケンスを使いますが、ここでは**「テーブルの現在の状態を見て次を決める」**ロジックの練習として、この形で書きます。

### リセット手順

作ったプロシージャを呼ぶとデータが変わるので、初期状態に戻すときは**テストデータを入れ直します。**

1. [[00_SQL研修/02_問題/08_結合から使用するテーブル|08_結合から使用するテーブル]] の「TRUNCATE用」を実行する
2. 同じページの「テストデータ」を上から順に実行する

**プロシージャ・関数・トリガーはこれでは消えません。** それらは章末の「後片付け」で落とします。

## 問題 1: 会員ランク更新プロシージャ
- **目的**: 引数を受け取るプロシージャを作り、`RAISE EXCEPTION` で不正な入力を弾く。

### 問題:
顧客の会員ランクを更新するプロシージャ `update_customer_membership` を作ってください。

- **引数**: `p_customer_id`、`p_membership_id`
- **検証**（どちらも `RAISE EXCEPTION` で止める）:
    1. `p_membership_id` が `memberships` に存在しない場合 → `指定された会員ランクが存在しません。`
    2. `p_customer_id` が `customers` に存在しない場合 → `顧客IDが存在しません。`
- **更新**: `customers.membership_id` を更新する。
- **通知**: 成功したら `顧客 [名前]（ID:[ID]）のランクを [ランク名] に更新しました。` を `RAISE NOTICE` で出す。

**要件:**

- 検証は**更新の前**に行うこと。
- `RAISE EXCEPTION` には `USING DETAIL` で「渡された値」を添えること。

### 解答:
```sql
CREATE OR REPLACE PROCEDURE update_customer_membership(
    p_customer_id   integer,
    p_membership_id integer
)
LANGUAGE plpgsql
AS $$
DECLARE
    v_customer_name customers.name%TYPE;
    v_rank_name     memberships.rank_name%TYPE;
BEGIN
    -- 検証① 会員ランクの存在確認（あとで通知に使うので名前も取る）
    SELECT rank_name INTO v_rank_name
      FROM memberships WHERE membership_id = p_membership_id;
    IF NOT FOUND THEN
        RAISE EXCEPTION '指定された会員ランクが存在しません。'
            USING DETAIL = format('指定された membership_id: %s', p_membership_id);
    END IF;

    -- 検証② 顧客の存在確認（あとで通知に使うので名前も取る）
    SELECT name INTO v_customer_name
      FROM customers WHERE customer_id = p_customer_id;
    IF NOT FOUND THEN
        RAISE EXCEPTION '顧客IDが存在しません。'
            USING DETAIL = format('指定された customer_id: %s', p_customer_id);
    END IF;

    -- 更新
    UPDATE customers
       SET membership_id = p_membership_id
     WHERE customer_id = p_customer_id;

    RAISE NOTICE '顧客 %（ID:%）のランクを % に更新しました。',
        v_customer_name, p_customer_id, v_rank_name;
END;
$$;
```


### 期待結果:

**成功**

```sql
SELECT customer_id, name, membership_id FROM customers WHERE customer_id = 1;
ROLLBACK;
```

```

```


```

CONTEXT:  PL/pgSQL function update_customer_membership(integer,integer) line 16 at RAISE
```


### 解説:
**この問題で確認すること**
- 引数を受け取るプロシージャを作り、`CALL` で呼べる（→ [[12-4_関数とプロシージャと例外処理|12-4]] §2）
- `RAISE EXCEPTION` で不正な入力を弾ける（→ [[12-4_関数とプロシージャと例外処理|12-4]] §5）
- `SELECT ... INTO` + `IF NOT FOUND` で存在チェックができる（→ [[12-2_変数とSQLの実行|12-2]] §3）


- **検証と値の取得を 1 回の `SELECT INTO` で兼ねている**のがこの解答の要点です。「`EXISTS` で存在確認 → もう一度 `SELECT` で名前を取る」と書くとクエリが 2 回になります。`SELECT INTO` + `FOUND` なら 1 回で済みます。**§問題2 とは逆の使い分け**なので、対比させると理解が定着します。
- `USING DETAIL` を書かせているのは、「何を渡したらエラーになったか」がログに残る価値を体感させるためです。
- **`memberships.rank_name%TYPE` を使っています。** `text` や `varchar(50)` と直接書いた解答も動きますが、`%TYPE` を使う理由（[[12-2_変数とSQLの実行|12-2]] §6）を確認してください。
- 更新の成否は `FOUND` で見なくてよいのか、と聞かれたら鋭い質問です。検証②で顧客の存在を確認済みなので、ここでは 1 件更新されることが保証されています。

## 問題 2: 購入履歴を確認するレビュー投稿プロシージャ
- **目的**: `IF EXISTS` / `IF NOT EXISTS` による複数の検証を組み合わせ、`COALESCE(MAX(id), 0) + 1` で採番する。

### 問題:
その商品を買ったことがある顧客だけがレビューを投稿できるプロシージャ `post_product_review` を作ってください。

- **引数**: `p_customer_id`、`p_product_id`、`p_rating`、`p_comment`
- **検証**（どちらも `RAISE EXCEPTION` で止める）:
    1. その顧客がその商品を 1 度も注文していない（`orders` と `orderitems` を見る）→ `購入履歴がないためレビューできません。`
    2. すでにその顧客がその商品にレビューを書いている → `既にレビュー投稿済みです。`
- **採番**: `review_id` は `reviews` の最大値 + 1（1 件もなければ 1）
- **登録**: `review_date` には当日（`CURRENT_DATE`）を入れる。
- **通知**: 成功したら `レビューを登録しました（review_id: [ID]）`

> [!Note]
> 検証 2 は `reviews` の `UNIQUE (product_id, customer_id)` 制約と同じことを見ています。**制約に任せてエラーにするのではなく、あえて事前に検証している**理由を考えてみてください（ヒント: 制約違反のエラーメッセージは、呼び出した人に何をすべきか伝えません）。

### 解答:
```sql
CREATE OR REPLACE PROCEDURE post_product_review(
    p_customer_id integer,
    p_product_id  integer,
    p_rating      integer,
    p_comment     text
)
LANGUAGE plpgsql
AS $$
DECLARE
    v_new_review_id integer;
BEGIN
    -- 検証① 購入履歴（あるかないかだけなので EXISTS）
    IF NOT EXISTS (
        SELECT 1
          FROM orders o
          JOIN orderitems oi ON oi.order_id = o.order_id
         WHERE o.customer_id = p_customer_id
           AND oi.product_id = p_product_id
    ) THEN
        RAISE EXCEPTION '購入履歴がないためレビューできません。'
            USING DETAIL = format('customer_id=%s, product_id=%s', p_customer_id, p_product_id);
    END IF;

    -- 検証② 二重投稿
    IF EXISTS (
        SELECT 1 FROM reviews
         WHERE customer_id = p_customer_id AND product_id = p_product_id
    ) THEN
        RAISE EXCEPTION '既にレビュー投稿済みです。';
    END IF;

    -- 採番（1件も無ければ 1 になる）
    SELECT COALESCE(MAX(review_id), 0) + 1 INTO v_new_review_id FROM reviews;

    INSERT INTO reviews (review_id, product_id, customer_id, rating, comment, review_date)
    VALUES (v_new_review_id, p_product_id, p_customer_id, p_rating, p_comment, CURRENT_DATE);

    RAISE NOTICE 'レビューを登録しました（review_id: %）', v_new_review_id;
END;
$$;
```

### 解説:
**この問題で確認すること**
- 複数の検証を組み合わせられる（→ [[12-4_関数とプロシージャと例外処理|12-4]] §5）
- `IF EXISTS` / `IF NOT EXISTS` で存在チェックができる（→ [[12-2_変数とSQLの実行|12-2]] §4）
- `COALESCE(MAX(id), 0) + 1` で採番できる（→ [[12-2_変数とSQLの実行|12-2]] §9）


- **問題文の Note の答え合わせ**: 検証②を省いても `UNIQUE (product_id, customer_id)` 制約が守ってくれます。しかしそのとき返るのは `duplicate key value violates unique constraint "reviews_product_id_customer_id_key"` です（[[12-4_関数とプロシージャと例外処理|12-4]] §7 の実測）。呼び出した人にとって「何をすればいいか」が分かりません。**事前検証は「制約の代わり」ではなく「分かるメッセージを返すため」**にやる、という整理をしてください。
- 制約は残したまま検証も書く、が正解です。**検証だけにして制約を外すのは誤り**です（同時実行では検証をすり抜けます）。ここは 15章の伏線になります。
- 購入履歴の判定に `orders` と `orderitems` の両方が必要な理由（商品は `orderitems` 側、顧客は `orders` 側）を確認してください。
- **`p_rating` の範囲検証は要求していません。** 問題 4 のトリガーで押さえるので、そこで「同じ検証をどこに置くべきか」を議論できます。

## 問題 3: 複数倉庫から在庫を引き当てる注文プロシージャ
- **目的**: 検証・登録・ループ更新を1つのプロシージャに組み立て、例外で途中の更新が巻き戻ることを確かめる。

### 問題:
1 つの商品が複数の倉庫に分かれて保管されていることを考慮し、在庫がある倉庫から順に引き当てて注文を作るプロシージャ `place_order_with_stock_allocation` を作ってください。

- **引数**: `p_customer_id`、`p_product_id`、`p_quantity`
- **処理の流れ**:
    1. **在庫チェック**: `inventory` からその商品の**合計**在庫数を取得し、`p_quantity` より少なければ `全倉庫で在庫が不足しています（合計在庫: X）` で `RAISE EXCEPTION`。
    2. **注文登録**: `orders` に登録（`status` は `'Pending'`、`order_date` は当日）。`order_id` は MAX+1。
    3. **明細登録**: `orderitems` に登録。`order_item_id` は MAX+1。
    4. **在庫引き当て**: `warehouse_id` の昇順に見ていき、必要数に達するまで各倉庫の `stock_quantity` を減らす。
        - 例: 55 個の注文に対し、倉庫1 に 50 個・倉庫2 に 10 個ある場合 → 倉庫1 を 0 個、倉庫2 を 5 個にする。
        - 在庫 0 の倉庫は飛ばす。
        - 必要数に達したらループを抜ける。
- **通知**: 各倉庫からの引き当てごとに `倉庫[ID] から [個数] 個引き当てました`、最後に `注文完了：Order ID [ID], 合計 [個数] 個の在庫を引き当てました。`

> [!Note]
> 各倉庫から引き当てるのが難しければ、まず**倉庫ID=1 しか存在しないと仮定して**解いて構いません。動いたら複数倉庫に対応させてみましょう。

**確認してほしいこと（発展）:**

完成したら、**手順 1 の在庫チェックを手順 3 の後ろに移した版**も作って、在庫が足りない数量で呼んでみてください。

- `orders` への `INSERT` は成功し、`RAISE NOTICE` も出るはずです。
- そのあと例外になります。
- **例外の後、`orders` の件数を数えてください。** 増えていますか、増えていませんか。
- なぜそうなるのか説明できますか（→ [[12-4_関数とプロシージャと例外処理|12-4]] §6）。

### 解答:
```sql
CREATE OR REPLACE PROCEDURE place_order_with_stock_allocation(
    p_customer_id integer,
    p_product_id  integer,
    p_quantity    integer
)
LANGUAGE plpgsql
AS $$
DECLARE
    v_total_stock  integer;
    v_new_order_id integer;
    v_new_item_id  integer;
    v_remaining    integer := p_quantity;   -- まだ引き当てていない数
    v_taken        integer;
    r_inventory    RECORD;
BEGIN
    -- ① 合計在庫の確認
    SELECT COALESCE(sum(stock_quantity), 0) INTO v_total_stock
      FROM inventory WHERE product_id = p_product_id;

    IF v_total_stock < p_quantity THEN
        RAISE EXCEPTION '全倉庫で在庫が不足しています（合計在庫: %）', v_total_stock
            USING HINT = '注文数を減らすか、入荷を待ってください。';
    END IF;

    -- ② 注文の登録
    SELECT COALESCE(MAX(order_id), 0) + 1 INTO v_new_order_id FROM orders;
    INSERT INTO orders (order_id, customer_id, order_date, status)
    VALUES (v_new_order_id, p_customer_id, CURRENT_DATE, 'Pending');

    -- ③ 明細の登録
    SELECT COALESCE(MAX(order_item_id), 0) + 1 INTO v_new_item_id FROM orderitems;
    INSERT INTO orderitems (order_item_id, order_id, product_id, quantity)
    VALUES (v_new_item_id, v_new_order_id, p_product_id, p_quantity);

    -- ④ 倉庫IDの昇順に引き当てる
    FOR r_inventory IN
        SELECT warehouse_id, stock_quantity
          FROM inventory
         WHERE product_id = p_product_id
         ORDER BY warehouse_id
    LOOP
        CONTINUE WHEN r_inventory.stock_quantity = 0;   -- 在庫0の倉庫は飛ばす

        v_taken     := least(r_inventory.stock_quantity, v_remaining);
        v_remaining := v_remaining - v_taken;

        UPDATE inventory
           SET stock_quantity = stock_quantity - v_taken
         WHERE product_id = p_product_id
           AND warehouse_id = r_inventory.warehouse_id;

        RAISE NOTICE '倉庫% から % 個引き当てました', r_inventory.warehouse_id, v_taken;

        EXIT WHEN v_remaining = 0;                      -- 必要数に達したら終了
    END LOOP;

    RAISE NOTICE '注文完了：Order ID %, 合計 % 個の在庫を引き当てました。',
        v_new_order_id, p_quantity;
END;
$$;
```

### 解説:
**この問題で確認すること**
- 検証・登録・ループ更新を 1 つのプロシージャに組み立てられる
- ループの中で状態を持ち回れる（→ [[12-3_制御構造|12-3]] §4）
- 例外を投げれば途中の更新が巻き戻ることを理解している（→ [[12-4_関数とプロシージャと例外処理|12-4]] §6）


- **`v_remaining` の持ち回りがこの問題の核**です。ループの外で宣言し、各回で減らしていく形に気づけるかどうか。
- `least(r_inventory.stock_quantity, v_remaining)` を使わず `IF` で場合分けした解答も正解です（「この倉庫で足りる／足りない」の 2 分岐）。どちらでもよいことを伝えてください。
- **`EXIT WHEN v_remaining = 0` を書き忘れると、必要数に達した後も倉庫を回り続けます。** `v_taken` が 0 になるので在庫は減りませんが、無駄な `UPDATE` が走ります。`\d` や実行後の在庫値では気づけないので、`RAISE NOTICE` の出力回数で確認させてください。
- **`ORDER BY warehouse_id` を落とすと「倉庫IDの昇順」という要件を満たしません。** 実行計画によって順序が変わるので、たまたま正しく見えることがあります。

#### 発展課題の答え：在庫チェックを後ろに移した場合

問題文の「発展」で作らせる版です。

```sql
CREATE OR REPLACE PROCEDURE place_order_check_late(
    p_customer_id integer, p_product_id integer, p_quantity integer
)
LANGUAGE plpgsql
AS $$
DECLARE
    v_total_stock  integer;
    v_new_order_id integer;
BEGIN
    -- 先に注文を登録してしまう
    SELECT COALESCE(MAX(order_id), 0) + 1 INTO v_new_order_id FROM orders;
    INSERT INTO orders (order_id, customer_id, order_date, status)
    VALUES (v_new_order_id, p_customer_id, CURRENT_DATE, 'Pending');
    RAISE NOTICE 'Order ID % を登録しました', v_new_order_id;

    -- 後から在庫をチェックする
    SELECT COALESCE(sum(stock_quantity), 0) INTO v_total_stock
      FROM inventory WHERE product_id = p_product_id;

    IF v_total_stock < p_quantity THEN
        RAISE EXCEPTION '全倉庫で在庫が不足しています（合計在庫: %）', v_total_stock;
    END IF;
END;
$$;
```

```sql

CALL place_order_check_late(1, 1, 100);
SELECT count(*) AS orders_after FROM orders;
```

```
(1 row)

ERROR:  全倉庫で在庫が不足しています（合計在庫: 60）
CONTEXT:  PL/pgSQL function place_order_check_late(integer,integer,integer) line 15 at RAISE
 orders_after 
--------------
           13
(1 row)
```

**`INSERT` は成功し `NOTICE` も出たのに、件数は 13 のまま増えていません。**

`CALL` は 1 つの SQL 文なので、自動コミットが `BEGIN` と `COMMIT` で包んでいます。例外で `COMMIT` に到達しないため、プロシージャ内の変更は**すべて巻き戻ります**（[[12-4_関数とプロシージャと例外処理|12-4]] §6、[[15-1_導入_トランザクションとACID|15-1]] §1）。

> **講師用メモ**: ここで「じゃあ検証の位置はどこでもいいのか」と聞かれたら、**「データは壊れないが、無駄な処理をする」**と答えてください。巻き戻せても、それまでの `INSERT` と `UPDATE` のコストは払っています。**検証は最も早いタイミングで**が原則です。

## 問題 4: 価格変更の履歴を残すトリガー
- **目的**: `OLD` / `NEW` を使うトリガー関数を書き、`WHEN` 句で無駄な発火を抑える。

### 問題:
`products` の価格が変更されたとき、変更前後の価格を自動で記録する仕組みを作ってください。

1. **履歴テーブル `price_logs` を作る。** 列は次のとおり。
    - `log_id`（主キー・自動採番でよい）
    - `changed_at`（既定値は現在時刻）
    - `product_id`
    - `old_price`
    - `new_price`
2. **トリガー関数 `products_log_price_change` を作る。** `price_logs` に 1 行追加する。
3. **トリガー `products_after_price_change` を作る。** `products` の `UPDATE` の**後**に、**1 行ごと**に動くようにする。

**要件:**

- **価格が実際に変わったときだけ記録されること。** `product_name` だけを更新したときや、同じ価格で更新したときは記録しないこと。
- 記録するだけなので、トリガー関数の戻り値は `NULL` でよい。

**確認すること:** 次の 3 つを実行して、`price_logs` に **1 件だけ**入ること。

```sql
UPDATE products SET price = 1300 WHERE product_id = 1;          -- 記録される
UPDATE products SET product_name = 'Laptop' WHERE product_id = 1; -- 記録されない
UPDATE products SET price = 1300 WHERE product_id = 1;          -- 記録されない（同じ価格）
```

### 解答:
```sql
-- ① 履歴テーブル
DROP TABLE IF EXISTS price_logs;

CREATE TABLE price_logs (
    log_id     serial PRIMARY KEY,
    changed_at timestamptz DEFAULT now(),
    product_id integer,
    old_price  numeric(10, 2),
    new_price  numeric(10, 2)
);

-- ② トリガー関数
CREATE OR REPLACE FUNCTION products_log_price_change()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO price_logs (product_id, old_price, new_price)
    VALUES (OLD.product_id, OLD.price, NEW.price);

    RETURN NULL;   -- AFTER トリガーの戻り値は無視される
END;
$$;

-- ③ トリガー
CREATE OR REPLACE TRIGGER products_after_price_change
    AFTER UPDATE ON products
    FOR EACH ROW
    WHEN (OLD.price IS DISTINCT FROM NEW.price)
    EXECUTE FUNCTION products_log_price_change();
```


### 期待結果:

**実測**

```sql
BEGIN;
UPDATE products SET price = 1300 WHERE product_id = 1;            -- 記録される
UPDATE products SET product_name = 'Laptop' WHERE product_id = 1; -- 記録されない
UPDATE products SET price = 1300 WHERE product_id = 1;            -- 記録されない（同じ価格）

SELECT product_id, old_price, new_price FROM price_logs ORDER BY log_id;
ROLLBACK;
```

```
BEGIN
UPDATE 1
UPDATE 1
UPDATE 1
 product_id | old_price | new_price 
------------+-----------+-----------
          1 |   1200.00 |   1300.00
(1 row)

ROLLBACK
```

**`UPDATE` は 3 回走ったのに、ログは 1 件だけです。**


### 解説:
**この問題で確認すること**
- トリガー関数（`RETURNS trigger`）とトリガーを作れる（→ [[12-5_トリガーと動的SQL|12-5]] §1）
- `OLD` / `NEW` を使える（→ [[12-5_トリガーと動的SQL|12-5]] §3）
- `WHEN` 句で無駄な発火を抑えられる（→ [[12-5_トリガーと動的SQL|12-5]] §4）


- **`WHEN` 句を書かない解答が多いはずです。** その場合ログが 3 件になります。**まず `WHEN` なしで書かせて 3 件になるのを見せてから `WHEN` を足す**と、必要性が体感できます。
- **`<>` ではなく `IS DISTINCT FROM`** を使う理由を必ず確認してください。`price` が NULL になり得る設計なら、`OLD.price <> NEW.price` は NULL を返して条件を満たさず、**NULL への変更が記録から漏れます**。
- トリガー関数の中で `IF OLD.price <> NEW.price THEN ... END IF;` と書く解答も結果は同じです。違いは「トリガー関数が呼ばれるかどうか」で、`WHEN` 句なら**関数の呼び出し自体が起きません**（[[12-5_トリガーと動的SQL|12-5]] §4）。10万行の `UPDATE` では差が出ます。
- `AFTER` を `BEFORE` にしても記録はできますが、**`BEFORE` は「まだ書き込まれていない」段階**なので、後続の別トリガーが `NEW` を書き換えたら記録と実データがずれます。記録は `AFTER` が正解です。
- `RETURN NEW` と書いた解答でも動きます（`AFTER` の戻り値は無視される）。減点は不要ですが、意味を伝えてください。

## 問題 5: テーブル名と列名を引数で受け取る関数（動的 SQL）
- **目的**: `EXECUTE` と `format()` の `%I` で動的SQLを組み立て、値は `USING` でバインドする。

### 問題:
「指定したテーブルの、指定した列が、指定した値より大きい行の件数」を返す関数 `count_rows_over` を作ってください。

- **引数**: `p_table_name text`、`p_column_name text`、`p_min_value numeric`
- **戻り値**: `bigint`（件数）

**要件（重要）:**

- テーブル名と列名は `format()` の **`%I`** で埋め込むこと。
- 比較する値は **`USING` でバインド**すること。**`%L` や `||` で埋め込まないこと。**
- 組み立てた SQL の結果は `EXECUTE ... INTO` で受け取ること。

**確認すること:** 次が動くこと。

```sql
SELECT count_rows_over('products',  'price',          500) AS products_over_500,
       count_rows_over('inventory', 'stock_quantity',  20) AS inventory_over_20,
       count_rows_over('reviews',   'rating',           3) AS reviews_over_3;
```

**考えてほしいこと:** テーブル名・列名は `%I`、値は `USING` と使い分ける理由は何でしょうか。「値も `%I` にすればいいのでは」「テーブル名も `USING` で渡せばいいのでは」がなぜ成り立たないかを説明できますか（→ [[12-5_トリガーと動的SQL|12-5]] §7-3）。

### 解答:
```sql
CREATE OR REPLACE FUNCTION count_rows_over(
    p_table_name  text,
    p_column_name text,
    p_min_value   numeric
)
RETURNS bigint
LANGUAGE plpgsql
AS $$
DECLARE
    v_count bigint;
BEGIN
    EXECUTE format('SELECT count(*) FROM %I WHERE %I > $1', p_table_name, p_column_name)
       INTO v_count
      USING p_min_value;

    RETURN v_count;
END;
$$;
```


### 期待結果:

**実測**

```sql
SELECT count_rows_over('products',  'price',          500) AS products_over_500,
       count_rows_over('inventory', 'stock_quantity',  20) AS inventory_over_20,
       count_rows_over('reviews',   'rating',           3) AS reviews_over_3;
```

```
 products_over_500 | inventory_over_20 | reviews_over_3 
-------------------+-------------------+----------------
                 3 |                 7 |              5
(1 row)
```


### 解説:
**この問題で確認すること**
- `EXECUTE` で動的 SQL を実行できる（→ [[12-5_トリガーと動的SQL|12-5]] §6）
- `format()` の `%I` を使える（→ [[12-5_トリガーと動的SQL|12-5]] §6-1）
- 値は `USING` でバインドできる（→ [[12-5_トリガーと動的SQL|12-5]] §7-2）


- **`INTO` と `USING` の順番**に注意。`EXECUTE 文字列 INTO 変数 USING 値` の順です。逆に書くと構文エラーになります。
- **問題文の「考えてほしいこと」の答え**:
    - **値を `%I` にできない理由**: `%I` は識別子として引用するので、`500` が `"500"` という**列名**として扱われ、「そんな列はない」というエラーになります。
    - **テーブル名を `USING` で渡せない理由**: `USING` は SQL のパラメータ（`$1`）に値を渡す仕組みです。SQL のパラメータは**値の位置にしか置けません**。`FROM $1` という構文は成立しません。テーブル名が変われば SQL の構造そのものが変わるため、実行計画を作る前に確定していなければならないのです。
- **`%L` でも動きますが `USING` が第一候補**です。`%L` は文字列として組み立てるので、毎回違う SQL 文が作られます。`USING` なら SQL 文は 1 種類で、値だけが差し替わります（[[12-5_トリガーと動的SQL|12-5]] §7-3）。
- **`||` で連結した解答が出たら、必ず [[12-5_トリガーと動的SQL|12-5]] §7-1 のインジェクションを再現させてください。** 「動いたからいい」で終わらせないことが重要です。
- 存在しないテーブル名を渡すとエラーになります。**関数の中で「そのテーブルが存在するか」を検証したいなら `information_schema` を見る必要がある**という発展の話もできますが、研修の範囲外です。

## 後片付け

演習が終わったら、作ったものを消しておいてください。**特にトリガーを残すと、後の演習で原因の分かりにくいエラーになります。**

```sql
DROP PROCEDURE IF EXISTS update_customer_membership(integer, integer);
DROP PROCEDURE IF EXISTS post_product_review(integer, integer, integer, text);
DROP PROCEDURE IF EXISTS place_order_with_stock_allocation(integer, integer, integer);

DROP TRIGGER  IF EXISTS products_after_price_change ON products;
DROP FUNCTION IF EXISTS products_log_price_change();
DROP TABLE    IF EXISTS price_logs;

DROP FUNCTION IF EXISTS count_rows_over(text, text, numeric);
```

### 解説:

**過去にあったエラーの全リスト**

| エラー / 症状 | 原因と対処 |
|:---|:---|
| `cannot open SELECT INTO query as cursor` | `FOR ... IN` の `IN` の後の `SELECT` に `INTO` を書いている（[[12-3_制御構造|12-3]] §3-1） |
| `column reference "..." is ambiguous` | 引数名・変数名が列名と同じ。`p_` / `v_` を付ける（[[12-1_PLpgSQLの基礎とDOブロック|12-1]] §5） |
| `CREATE OR REPLACE` が失敗する | 引数の数・型、戻り値の型を変えた。先に `DROP` が必要（[[12-4_関数とプロシージャと例外処理|12-4]] §10） |
| `DROP FUNCTION` で `function name "..." is not unique` | 同名で引数違いの関数が複数ある。`DROP FUNCTION count_rows_over(text, text, numeric)` のように引数の型まで書く（名前が一意なら省略可・実測確認済み） |
| プロシージャを `SELECT` で呼んでエラー | プロシージャは `CALL` で呼ぶ（[[12-4_関数とプロシージャと例外処理|12-4]] §3） |
| 問題4 でログが 3 件になる | `WHEN` 句を書いていない |
| 問題4 で NULL への価格変更が記録されない | `<>` を使っている。`IS DISTINCT FROM` にする |
| 問題5 で `column "500" does not exist` | 値を `%I` で埋め込んでいる。値は `USING` か `%L` |
| 後の演習で謎のエラーが出る | 問題4 のトリガーを消し忘れている。問題ファイル末尾の「後片付け」を実行する |
