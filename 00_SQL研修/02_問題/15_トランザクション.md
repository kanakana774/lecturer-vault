## 問題 4: 【2窓】在庫が壊れる ── ロストアップデート
- **目的**: 「読んで、計算して、書き戻す」が壊れることを体験し、悲観ロックと楽観ロックを使い分けられるようになる。

### 問題:
**この章で一番実務に直結する問題です。**

在庫50個の商品に、2人の顧客がほぼ同時に注文しました。**窓Aが5個、窓Bが3個**です。正しい結果は `50 - 5 - 3 = 42` のはずです。

アプリケーションは次の3ステップで在庫を引きます（よくある実装です）。

```
① 在庫を SELECT で読む
② アプリ側で「読んだ値 − 注文数」を計算する
③ 計算結果を UPDATE で書き戻す
```

**【手順】**

> ⚠️ 2つの窓を**同時に**実行することはできません。**窓A→窓B→窓A→窓B と、1文ずつ交互に**実行してください。

1. 在庫を初期化します。
   ```sql
   UPDATE inventory SET stock_quantity = 50, version = 1 WHERE product_id = 1 AND warehouse_id = 1;
   ```
2. **窓A** で、①と②まで実行します。
   ```sql
   BEGIN;
   SELECT stock_quantity FROM inventory WHERE product_id=1 AND warehouse_id=1;
   -- 読めた値をメモする。アプリが「読めた値 - 5」を計算したことにする
   ```
3. **窓B** でも、①と②まで実行します。
   ```sql
   BEGIN;
   SELECT stock_quantity FROM inventory WHERE product_id=1 AND warehouse_id=1;
   -- 読めた値をメモする。アプリが「読めた値 - 3」を計算したことにする
   ```
4. **窓A** で③を実行して確定します。**計算結果を絶対値で書き込みます。**
   ```sql
   UPDATE inventory SET stock_quantity = 45 WHERE product_id=1 AND warehouse_id=1;
   COMMIT;
   ```
5. **窓B** でも③を実行して確定します。
   ```sql
   UPDATE inventory SET stock_quantity = 47 WHERE product_id=1 AND warehouse_id=1;
   COMMIT;
   ```
6. 結果を確認します。
   ```sql
   SELECT stock_quantity FROM inventory WHERE product_id=1 AND warehouse_id=1;
   ```

**ここから、同じ壊れ方をもう一つの方法で防ぎます。** 使うのは [[15-2_実践_ロックとMVCC|15-2]] §0-3 で追加した `version` 列です。

7. 在庫を初期化します（手順1と同じ）。
   ```sql
   UPDATE inventory SET stock_quantity = 50, version = 1 WHERE product_id = 1 AND warehouse_id = 1;
   ```
8. **窓A** で `BEGIN;` → `SELECT` を実行します（**50 / 1** を読む）。
   ```sql
   BEGIN;
   SELECT stock_quantity, version FROM inventory WHERE product_id=1 AND warehouse_id=1;
   ```
9. **窓B** でも同じく `BEGIN;` → `SELECT` を実行します（同じく **50 / 1** を読む）。
10. **窓A → 窓B の順**に、次を実行して `COMMIT` します。
    ```sql
    UPDATE inventory
       SET stock_quantity = 45,          -- 窓Bは 47
           version = version + 1
     WHERE product_id=1 AND warehouse_id=1
       AND version = 1;
    COMMIT;
    ```

**【問1】** 最終的な在庫はいくつになりましたか。**42 になりましたか。**
**【問2】** どちらの注文が消えましたか。**なぜ消えたのか**を、手順2・3で両方が読んだ値に着目して説明してください。
**【問3】** **【本題】** 手順2〜5を**修正して、正しく 42 になるようにしてください。** 追加するのは1箇所だけです。
**【問4】** 修正版では、**窓Bはどの手順で待たされるようになりましたか。** 修正前（問題1）と比べて、待つ位置がどう変わったか説明してください。
**【問5】** そもそも `UPDATE inventory SET stock_quantity = stock_quantity - 5 ...` と1文で書けば、この問題は起きません。**では、なぜ実務で3ステップの実装が必要になるのですか。**（ヒント：在庫が足りなかったら注文を断りたい）
**【問6】** 手順10で、**窓Bの `UPDATE` は成功しましたか。** 返ってきたメッセージを**そのまま**書いてください。**エラーは出ましたか。**
**【問7】** 窓Bのアプリは、この結果を受けてどう振る舞うべきですか。**実際にその通りに手を動かして、最終在庫を 42 にしてください。**（打ったSQLも書いてください）

## 問題 9: 【紙】トランザクションの境界を引き直す

### 問題:
**この問題ではSQLを打ちません。** 読んで考えて、日本語で答えてください。

ある通販サイトの「注文を確定する」処理が、次のように書かれていました。

```
BEGIN;
  ① SELECT stock_quantity FROM inventory WHERE ... FOR UPDATE;   -- 在庫を押さえる
  ② IF 在庫 < 注文数 THEN ROLLBACK; 「在庫切れです」を返す;
  ③ INSERT INTO orders ...;
  ④ INSERT INTO orderitems ...;

```

①〜⑤は問題ありません。**問題は★を付けた⑥⑦⑧です。**

**【問1】** ⑥⑦⑧をトランザクションの中に置いてはいけない理由を、**2つの観点から**説明してください。
