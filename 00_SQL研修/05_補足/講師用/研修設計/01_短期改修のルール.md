# 短期改修のルール — 既存の完成品を直すとき

> 更新: 2026-09-02 / 対象: `00_SQL研修/01_講義資料/` `02_問題/` `04_解答/` の**既存章を直す**作業
> 位置づけ: **作業の作法の正本。** [[00_見直しの進め方]] は `00_SQL研修_改訂/` に**新しく作る**長期作業の計画書で、前提が違う。

---

## 0. なぜ別に要るか

[[00_見直しの進め方]] §3 は「新しく作る資料は `00_SQL研修_改訂/` に置く。`00_SQL研修/` には一切書き込まない」を前提に書かれている。

しかし**既存章の短期改修は `00_SQL研修/` を直接直す**。誤りを見つけたら次の研修までに直す必要があり、改訂版の完成を待てないため。前提が違うので、従うものを分ける。

| | 長期（新設） | 短期（改修） |
| :--- | :--- | :--- |
| 対象 | `00_SQL研修_改訂/` | `00_SQL研修/` の既存章 |
| 目的 | 二層構造で作り直す | 誤りを消す・抜けを埋める |
| 従うもの | [[00_見直しの進め方]] | **このファイル** |
| 単位 | 章の新設 | 1章ずつ、その章の中で完結 |

**混ぜない。** 短期改修で章を新設したり、章構成を変えたりしない。

## 1. 着手前に確かめる3つ

**直す前にこの3つを見る。順番も守る。** ここを飛ばすと、直したこと自体が事故になる。

### 1-1. その章の位置 → 使えるテーブルが決まる

**独自のサンプルテーブルを作らない。** 章の位置で使うテーブルが決まっている（[[00_見直しの進め方]] §9-1）。

| 章の位置 | 使うテーブル |
| :--- | :--- |
| 結合（08章）より前 | `04_解答/02_DDL（前半用）.md` の**4テーブル** |
| 08章以降 | `02_問題/08_結合から使用するテーブル.md` の**11テーブル** |

問題・解答は既にこれに従っている。**講義資料だけ独自サンプルだと、研修生は章の中で2つの世界を行き来する。** 資料に `CREATE TABLE` / `DROP TABLE` が出てきたら、まず疑う。

テストデータには `【狙い①〜⑩】` がDDL内にコメントで入っている。**狙いに乗せると例が短くなる**（例: Platinum は「まだ誰もいないランク」なので `EXCEPT` の答えにそのまま使える）。

### 1-2. どこまで教えたか → 使える構文が決まる

**先出し禁止**（[[00_見直しの進め方]] §2 原則6）。まだ講義していない構文を、その章の資料や課題で使わない。**説明の例に使うのも先出し**。

引っかかりやすいところ:

| 構文 | 初出 | 09章時点で |
| :--- | :--- | :--- |
| `IN` / `NOT IN`（**リテラルのリスト**） | 02_演算子 | 使える |
| `IN (SELECT ...)` / サブクエリ | 10_サブクエリ | **使えない** |
| 相関サブクエリ・`NOT EXISTS` | 10章の補足 | **使えない** |
| `JOIN` | 08_結合 | 使える |
| `FROM (SELECT ...)`（派生表） | 10_サブクエリ | **使えない** |
| ウィンドウ関数 | 18章 | **使えない** |

`JOIN` は使えても、**2つの集合を比べるために `FROM (SELECT ...) a JOIN (SELECT ...) b` と書けば派生表＝サブクエリ**になる。「使える構文の組み合わせ」で先出しになる形に注意する。

### 1-3. 既に他の章で断っているか → 重複させない

同じ注意書きを2箇所に書くと、片方が必ず古くなる。**書く前に vault を検索する。**

```bash
grep -rn "<書こうとしている語>" --include=*.md 00_SQL研修/01_講義資料/
```

例: `LIMIT` が標準SQLでないことは **`02_CRUDについて.md` に既にある**。09章に書くと二重管理になる。

## 2. 書くときの作法

`CLAUDE.md`（vault直下）の「加筆は注釈でなく構造で」が正本。短期改修で特に効くのは次の3つ。

### 2-1. 加筆は節を立てる。注釈を積まない

- 書き足す内容は、まず**どの節に属するか**を決める。無ければ節を作る
- **同じ位置に対になるものが来たら、同じ粒度で節にする。** `UNION ALL` が §1-2 にあるなら、`INTERSECT ALL` は §1-3 の中、`EXCEPT ALL` は §1-4 の中。片方だけ折りたたみ注釈に逃がさない
- 加筆したら、**包含された古い注釈を消す**。消すところまでが加筆
- 注釈に残していいのは `⚠️`（落とし穴）／`🐘`（適用範囲）／`[!note]-` `[!example]-`（読み飛ばしてよい枝葉）だけ

### 2-2. 🐘 は「標準SQL と PostgreSQL の差」だけ

原則5「製品固有の名前は忘れてよく、原理は残る。**どちらかを資料内で断る**」の実務ルール。

**書く:**

- その構文・名前が **PostgreSQL 固有**で、標準SQL には無い（例: 実行計画の `HashSetOp` / `SetOp` という節点名）
- 標準SQL に**あるのに PostgreSQL の挙動が違う**
- **原理は共通だが呼び名だけ違う**（例: `WAL`）

**書かない:**

- **PostgreSQL が標準どおりで、ずれているのが他製品のとき。** 🐘 の主語は PostgreSQL。「`EXCEPT` が標準で、Oracle だけ `MINUS` と綴る」は PostgreSQL の話ではないのでノイズ
- **他製品の対応状況カタログ**（「SQL Server は未対応」「MySQL 8.0.31 以降」など）。研修で触らない製品の対応表は、正確でも研修生には使えないノイズになる
- 実装差の細部（例: `VALUES` の暗黙列名が `column1` になる、等）
- **他の章で既に断っていること**（→ §1-3）

**書式は `> 🐘 **どこまで通じる話か**` の callout**（01_データ型・01_RDBMSとDDL・02_CRUD と同じ）。章頭に凡例は置かない。

> [!note]- 🐘 が1〜2個しか出ない章もある
> それが正常。標準SQLの章（結合・集約・集合演算子・サブクエリ）は 🐘 がほとんど出ない。**無理に探して付けない。** 逆に 12章（PL/pgSQL）・15章（MVCC）・17章（EXPLAIN）は 🐘 が主役になる。

### 2-3. 実測する。目算で書かない

`CLAUDE.md`「実測と検証環境」が正本。短期改修で必ずやること:

- **載せる出力・件数・エラーメッセージは psql で叩いて確かめる。** 「たぶんこう出る」を書かない
- **`NULL` は空欄にせず `NULL` と書く。** psql の既定は空欄で、資料に貼ると「値が無い」のか「`NULL` なのか」「桁が揃っていないだけ」なのか読めない。検証時に **`\pset null 'NULL'`** を付ければ、実測のまま `NULL` と出る

  ```
   warehouse_id          warehouse_id
  --------------        --------------
              3                     3
                   →             NULL
                                 NULL
  (3 rows)              (3 rows)
  ```

- **`ORDER BY` の無いクエリの結果を、並んだ形で載せない。** 集合演算子・`GROUP BY` はハッシュ順で返る。並べたいなら `ORDER BY` を書く
- 検証用DBは `tmp_` 接頭辞で作り、**同じセッションで `DROP DATABASE`**
- 直したら、**その章の SQL ブロックを頭から通しで実行**して記載と突き合わせる（コピペで動かない資料を残さない）

検証セッションの入り口は毎回これ（`CLAUDE.md`「実測と検証環境」＋ `\pset`）。

```bash
export PGPASSWORD=aevic PGCLIENTENCODING=UTF8
export PGOPTIONS="-c lc_messages=C"; export LC_ALL=C   # メッセージを英語に固定
PSQL="/c/Program Files/PostgreSQL/17/bin/psql.exe"
"$PSQL" -w -U postgres -h localhost -d <DB名> -c "\pset null 'NULL'" -f <検証SQL>
```

### 2-4. 図は拾い画を使わない

差し替える機会があれば Excalidraw で作り、`_excalidraw/` に置いて `![[名前.excalidraw]]` で埋め込む（`excalidraw` skill）。

**拾い画は章とズレる。** 一般的な図は、その章で扱わないものを含み、扱うものを欠く（例: 集合論のベン図は補集合と直和を含み、`UNION ALL` を欠いていた）。**図の見出しは節見出しと1対1**にする。

## 3. 完了チェックリスト

1章直すごとにこれを通す。

- [ ] `CREATE TABLE` / `DROP TABLE` が資料に無い（§1-1 のテーブルを使っている）
- [ ] 先出しした構文が無い（§1-2）
- [ ] SQL ブロックを頭から通しで実行し、**記載の出力・件数と一致**した（§2-3）
- [ ] 結果の `NULL` を空欄にせず `NULL` と書いた（§2-3）
- [ ] `ORDER BY` 無しの結果を並べて載せていない
- [ ] 検証用 `tmp_` DB を落とした
- [ ] 追記に包含された古い注釈を消した（§2-1）
- [ ] 🐘 が §2-2 の基準に収まっている。他章と重複していない
- [ ] `%%` の作業メモ・`> claudeへ` が残っていない
- [ ] 完成品から詳細版へのリンクが無い
- [ ] 論理単位でコミットした（`_base/02_協業ルール.md` §3）

## 4. [[00_見直しの進め方]] との差分

**§3 作業ルールの次の2行は、短期改修には適用しない。** このファイルが優先する。

- 「新しく作る資料は `00_SQL研修_改訂/` に置く。`00_SQL研修/` には一切書き込まない」
- 「既存の完成品（`00_SQL研修/01_講義資料/`）は更新しない。改修は当面やらない」

配布物への混入を避けるという**元の意図は有効**なので、`00_SQL研修_改訂/` に未完成の新設資料を置く運用は変えない。短期改修は既存章の中で完結するので、混入の問題が起きない。

`03_詳細版/` を触らないルール（②蒸留を過ぎたら蒸留しない）は**短期改修でも守る**。
