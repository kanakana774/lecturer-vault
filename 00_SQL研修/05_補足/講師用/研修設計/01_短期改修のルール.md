# 短期改修のルール — 既存の完成品を直すとき

> 更新: 2026-09-10 / 対象: `00_SQL研修/01_講義資料/` `02_問題/` `04_解答/` の**既存章を直す**作業
> 位置づけ: **作業の作法の正本。** [[00_見直しの進め方]] は `00_SQL研修_改訂/` に**新しく作る**長期作業の計画書で、前提が違う。

---

## 0. なぜ別に要るか

[[00_見直しの進め方]] §3 は「新しく作る資料は `00_SQL研修_改訂/` に置く。`00_SQL研修/` には一切書き込まない」を前提に書かれている。

しかし**既存章の短期改修は `00_SQL研修/` を直接直す**。誤りを見つけたら次の研修までに直す必要があり、改訂版の完成を待てないため。前提が違うので、従うものを分ける。

| | 長期（新設） | 短期（改修） |
| :--- | :--- | :--- |
| 対象 | `00_SQL研修_改訂/` | `00_SQL研修/` の既存章 |
| 目的 | 二層構造で作り直す | 誤りを消す・抜けを埋める |
| 従うもの | [[00_見直しの進め方]] | **このファイル** |
| 単位 | 章の新設 | 1章ずつ、その章の中で完結 |

**混ぜない。** 短期改修で章を新設したり、章構成を変えたりしない。

## 1. 着手前に確かめる3つ

**直す前にこの3つを見る。順番も守る。** ここを飛ばすと、直したこと自体が事故になる。

### 1-1. その章の位置 → 使えるテーブルが決まる

**独自のサンプルテーブルを作らない。** 章の位置で使うテーブルが決まっている（[[00_見直しの進め方]] §9-1）。

| 章の位置 | 使うテーブル |
| :--- | :--- |
| 結合（08章）より前 | [[02_DDL（前半用）]] の**4テーブル**（`customers_mst` / `products_mst` / `orders_trn` / `order_details_trn`） |
| 08章以降 | [[00_SQL研修/02_問題/08_結合から使用するテーブル\|08_結合から使用するテーブル]] の**11テーブル** |

**ECサイトを題材にしているのは意図的。** 実務で扱う構造であり、かつ研修生自身が利用者として馴染んでいる可能性が高い。題材を変えるとこの2つの利点が両方消える。

問題・解答は既にこれに従っている。**講義資料だけ独自サンプルだと、研修生は章の中で2つの世界を行き来する。** 資料に `CREATE TABLE` / `DROP TABLE` が出てきたら、まず疑う。

テストデータには `【狙い①〜⑩】` がDDL内にコメントで入っている。**狙いに乗せると例が短くなる**（例: Platinum は「まだ誰もいないランク」なので `EXCEPT` の答えにそのまま使える）。

#### 例外 — 講義資料だけ、`WITH` の中に限ってオリジナルを作れる

次のどれかに当たるときは、講義資料に限りオリジナルの構造・データを作ってよい。

- **値そのものが説明の主役**で、記憶に残る例が要る
- 説明の便宜上、既存テーブルより明らかに分かりやすい
- そもそも既存のECバックエンドの構造では説明できない

**ただし `CREATE TABLE` は書かない。`WITH` 句（CTE）で1つのSQLの中に閉じる。** スコープは短いほうがよく、資料をコピペした研修生のDBにも残らない。

**課題（`02_問題/` `04_解答/`）にこの例外は無い。** テーブル構造は上の表のとおり一貫させる。

### 1-2. どこまで教えたか → 使える構文が決まる

**先出し禁止**（[[00_見直しの進め方]] §2 原則6）。まだ講義していない構文を、その章の資料や課題で使わない。**説明の例に使うのも先出し**。

引っかかりやすいところ:

| 構文 | 初出 | 09章時点で |
| :--- | :--- | :--- |
| `IN` / `NOT IN`（**リテラルのリスト**） | 02_演算子 | 使える |
| `IN (SELECT ...)` / サブクエリ | 10_サブクエリ | **使えない** |
| 相関サブクエリ・`NOT EXISTS` | 10章の補足 | **使えない** |
| `JOIN` | 08_結合 | 使える |
| `FROM (SELECT ...)`（派生表） | 10_サブクエリ | **使えない** |
| ウィンドウ関数 | 18章 | **使えない** |

`JOIN` は使えても、**2つの集合を比べるために `FROM (SELECT ...) a JOIN (SELECT ...) b` と書けば派生表＝サブクエリ**になる。「使える構文の組み合わせ」で先出しになる形に注意する。

### 1-3. 既に他の章で断っているか → 重複させない

同じ注意書きを2箇所に書くと、片方が必ず古くなる。**書く前に vault を検索する。**

```bash
grep -rn "<書こうとしている語>" --include=*.md 00_SQL研修/01_講義資料/
```

例: `LIMIT` が標準SQLでないことは **`02_CRUDについて.md` に既にある**。09章に書くと二重管理になる。

## 2. 書くときの作法

`CLAUDE.md`（vault直下）の「加筆は注釈でなく構造で」が正本。短期改修で特に効くのは次の3つ。

### 2-1. 加筆は節を立てる。注釈を積まない

- 書き足す内容は、まず**どの節に属するか**を決める。無ければ節を作る
- **同じ位置に対になるものが来たら、同じ粒度で節にする。** `UNION ALL` が §1-2 にあるなら、`INTERSECT ALL` は §1-3 の中、`EXCEPT ALL` は §1-4 の中。片方だけ折りたたみ注釈に逃がさない
- 加筆したら、**包含された古い注釈を消す**。消すところまでが加筆
- 注釈に残していいのは `⚠️`（落とし穴）／`🐘`（適用範囲）／`[!note]-` `[!example]-`（読み飛ばしてよい枝葉）だけ

### 2-2. 原理から類推できることは書かない

**その節で示した原理から容易に類推できることは、書かない。** 同じことの言い換えが増えるだけで、
注釈が積もって資料がログになる（→ §2-1）。

- 例: 「`DISTINCT` が消すのは完全に同じ値だけ」を示したあとに、大文字小文字・全角半角・
  空白の話を並べない。**原理は同じ**なので、残すなら**1行に畳む**
- どうしても残したいときは `[!note]-` に入れて**2行以内**。開かなくても読み進められる形にする
- **説教にしない。** 「〜を疑ってください」「〜を心がけましょう」で始まる文は、たいてい原理の言い換え

**判定は「この文を消しても、研修生は同じ結論に着けるか」。** 着けるなら消す。

### 2-3. 🐘 は「標準SQL と PostgreSQL の差」だけ

原則5「製品固有の名前は忘れてよく、原理は残る。**どちらかを資料内で断る**」の実務ルール。

**書く:**

- その構文・名前が **PostgreSQL 固有**で、標準SQL には無い（例: 実行計画の `HashSetOp` / `SetOp` という節点名）
- 標準SQL に**あるのに PostgreSQL の挙動が違う**
- **原理は共通だが呼び名だけ違う**（例: `WAL`）

**書かない:**

- **PostgreSQL が標準どおりで、ずれているのが他製品のとき。** 🐘 の主語は PostgreSQL。「`EXCEPT` が標準で、Oracle だけ `MINUS` と綴る」は PostgreSQL の話ではないのでノイズ
- **他製品の対応状況カタログ**（「SQL Server は未対応」「MySQL 8.0.31 以降」など）。研修で触らない製品の対応表は、正確でも研修生には使えないノイズになる
- 実装差の細部（例: `VALUES` の暗黙列名が `column1` になる、等）
- **他の章で既に断っていること**（→ §1-3）

**書式は `> 🐘 **どこまで通じる話か**` の callout**（01_データ型・01_RDBMSとDDL・02_CRUD と同じ）。章頭に凡例は置かない。

> [!note]- 🐘 が1〜2個しか出ない章もある
> それが正常。標準SQLの章（結合・集約・集合演算子・サブクエリ）は 🐘 がほとんど出ない。**無理に探して付けない。** 逆に 12章（PL/pgSQL）・15章（MVCC）・17章（EXPLAIN）は 🐘 が主役になる。

### 2-4. 実測する。目算で書かない

`CLAUDE.md`「実測と検証環境」が正本。短期改修で必ずやること:

- **載せる出力・件数・エラーメッセージは psql で叩いて確かめる。** 「たぶんこう出る」を書かない
- **`NULL` は空欄にせず `NULL` と書く。** psql の既定は空欄で、資料に貼ると「値が無い」のか「`NULL` なのか」「桁が揃っていないだけ」なのか読めない。検証時に **`\pset null 'NULL'`** を付ければ、実測のまま `NULL` と出る

  ```
   warehouse_id          warehouse_id
  --------------        --------------
              3                     3
                   →             NULL
                                 NULL
  (3 rows)              (3 rows)
  ```

- **`ORDER BY` の無いクエリの結果を、並んだ形で載せない。** 集合演算子・`GROUP BY` はハッシュ順で返る。並べたいなら `ORDER BY` を書く
- 検証用DBは `tmp_` 接頭辞で作り、**同じセッションで `DROP DATABASE`**
- 直したら、**その章の SQL ブロックを頭から通しで実行**して記載と突き合わせる（コピペで動かない資料を残さない）

検証セッションの入り口は毎回これ（`CLAUDE.md`「実測と検証環境」＋ `\pset`）。

```bash
export PGPASSWORD=aevic PGCLIENTENCODING=UTF8
export PGOPTIONS="-c lc_messages=C"; export LC_ALL=C   # メッセージを英語に固定
PSQL="/c/Program Files/PostgreSQL/17/bin/psql.exe"
"$PSQL" -w -U postgres -h localhost -d <DB名> -c "\pset null 'NULL'" -f <検証SQL>
```

### 2-5. 研修生は pgAdmin で操作する。psql の操作説明を配布物に書かない

**研修生は全員 pgAdmin を使う。** psql を叩くのは講師が検証するときだけ。

- **`01_講義資料/` `02_問題/` `04_解答/` に psql のメタコマンドや設定の説明を書かない。**
  `\pset` `\d` `\timing` `\copy` などは研修生の手元では使えないので、書いても実行できない
- **`\pset null 'NULL'` は §2-4 のとおり「検証する側の道具」。** 資料に `NULL` と書いたあとで
  「手元で同じ見た目にするには」と添えたくなるが、それは**講師の環境の話**で研修生には使えない。
  §2-4 が要求しているのは**載せる値が `NULL` だと読めること**で、画面の再現ではない
- 例外は [[99_補足_psqlコマンドチートシート]] だけ。psql そのものを扱う補足なので、そこに閉じる

**出力の見た目が pgAdmin と一致しないのは構わない。** 資料の `----+----` の罫線や `(5 rows)` は
psql の体裁だが、**資料が示しているのは値であって画面ではない。** 揃えようとしなくてよい。

> [!note]- なぜ明文化したか
> 06章（CASE式）の改修で、`NULL` を `NULL` と表示した出力を載せたあと、
> 「手元で同じ見た目にしたい場合は `\pset null 'NULL'` を実行してください」という注記を
> 講義資料に書いてしまった（2026-09-07）。研修生は pgAdmin なので実行できない注記だった。

### 2-6. 図は拾い画を使わない

差し替える機会があれば Excalidraw で作り、`_excalidraw/` に置いて `![[名前.excalidraw]]` で埋め込む（`excalidraw` skill）。

**拾い画は章とズレる。** 一般的な図は、その章で扱わないものを含み、扱うものを欠く（例: 集合論のベン図は補集合と直和を含み、`UNION ALL` を欠いていた）。**図の見出しは節見出しと1対1**にする。

## 3. 課題を直すとき

`02_問題/` `04_解答/` に固有の作法。講義資料だけを直すなら §2 まででよい。

### 3-1. リセットは「入れ直す」に統一する

**`UPDATE` 列挙型はテストデータを1行直すたびに追随が要る**ので、触った章から順にこの形へ寄せる（2026-09-08 に全章を寄せ終えた）。

**戻し方を章ごとに発明しない。** 使う型は次の2つだけで、章ごとに変わるのは「どのDDL／テストデータか」だけ。

**前半4テーブルの章**（08章より前）:

> ### リセット手順
>
> データを変える問があるので、初期状態に戻すときは**DBを作り直して入れ直す**。
>
> 1. `DROP DATABASE` → `CREATE DATABASE`
> 2. DDL を実行する
> 3. テストデータの `INSERT` を実行する

**08章以降の章**: DDL は [[00_SQL研修/02_問題/08_結合から使用するテーブル|08_結合から使用するテーブル]] にあり、同じページに `TRUNCATE用` が用意してある。DBごと落とさず**入れ直すだけで済む**。

> 1. `TRUNCATE用` を実行する
> 2. 同じページの「テストデータ」を上から順に実行する

- **11章だけは `TRUNCATE用` では戻らない**（テーブル定義そのものを変えるので、DBから作り直す）
- **章で足した列は `TRUNCATE` では消えない。** 15章の `inventory.version` は入れ直せば既定値の `1` に戻る
- 個別の `UPDATE` で戻す形は**残さない**（テストデータとの二重管理になる）
- **問ごとに「リセットしてください」を繰り返さない。** 章頭に1回書き、データを壊す問に一言添えるだけ
- `BEGIN` … `ROLLBACK` に閉じられる問は、そもそもリセットが要らない形にする
  （03_UPDATE の追加課題・06_SELECT特殊 の問9〜12・06_CASE式 の問8 がこの形）
- **問の中の「初期化」はリセットではない。** 15章 問4 の `UPDATE inventory SET stock_quantity = 50, version = 1` は
  競合を起こすための仕込みなので、章頭のリセット手順を参照させず、その手順の中に置く
- `SELECT` だけの章は**リセット不要と明記する**
- **「戻ったかどうか」の確認SQLは載せない。** 入れ直せば戻るのが自明なので、件数や合計値の
  チェックは手順を長くするだけになる（2026-09-08 に全章から外した）

**索引や設定を戻す章（17章）はこの限りではない。** 17章は別DB（10万行を生成する）で、
戻す対象はテストデータではなく**インデックスと統計情報**。テストデータとの二重管理にならないので、
「主キー以外のインデックスを全部消して `VACUUM ANALYZE`」のままでよい。

### 3-2. 問題文だけで答えが決まるか

**解答を見ないと意図が分からない問題文は不備。** 書いたら「問題文だけを渡された研修生が想定解に着くか」で判定する。

- **出力する列と、1レコードの単位（粒度）が問題文から決まるか。** 決まらなければ問題文が足りない
- 集計は「**〜ごとに**」を必ず書く。「顧客ごとに」と書けば1行＝1顧客だと伝わる
- 並び順や件数が答えを決めるなら問題文で指定する（`ORDER BY` が要る問で書き忘れると答えが揺れる）
- **日本語はシンプルに。** 一文一義、修飾を重ねない

### 3-3. 求めた結果に意味があるか

**「で、それが何？」になる問を出さない。** 求めた結果が業務上の問い（誰に何を渡す数字か）に対応していること。意味のない集計は研修生を困らせるうえ、実務でも書かない。

- 例: 「商品ごとの平均注文個数」より「在庫が切れそうな商品」。同じ構文を使いながら答えが読める
- 構文の練習が主目的の問でも、**結果の読み方を1行添える**と意味が立つ

### 3-4. テストデータの整合性を崩さない

**状態を持つ列を、他テーブルの状態と矛盾させない。** 例: 注文のステータスが「完了」なのに、同じ注文の配送が「配送中」。研修生は結合結果を読んで混乱し、「そういうデータもある」と誤って学ぶ。

- 矛盾を**わざと**入れるなら（不整合を検出させる問など）、狙いをDDLのコメントに書く
- 追加・修正したら、そのテーブルを使う章の解答を**再実行して期待結果を差し替える**

### 3-5. テストデータを触る前に依存関係表を引く

`04_解答/08_結合から使用するテーブル.md` の**依存関係表**が、どの行がどの問を支えているかの逆引き（配布しない）。

- **1行でも変えるなら、先にこの表を引く。** 採番（`MAX(id)+1`）や件数を答えにしている問は、**無関係な行を1行足しただけで資料の数値がズレる**
- 変えたら**表も更新する**。表の更新までがデータ修正
- DDLとテストデータは `02_問題/` と `04_解答/` に**同じ内容で2つある**（`08_結合から使用するテーブル.md`）。片方だけ直さない
- 前半4テーブル（[[02_DDL（前半用）]]）側には表が無い。前半のデータを触るなら、同じ形の表を作ってから

## 5. [[00_見直しの進め方]] との差分

**§3 作業ルールの次の2行は、短期改修には適用しない。** このファイルが優先する。

- 「新しく作る資料は `00_SQL研修_改訂/` に置く。`00_SQL研修/` には一切書き込まない」
- 「既存の完成品（`00_SQL研修/01_講義資料/`）は更新しない。改修は当面やらない」

配布物への混入を避けるという**元の意図は有効**なので、`00_SQL研修_改訂/` に未完成の新設資料を置く運用は変えない。短期改修は既存章の中で完結するので、混入の問題が起きない。

`03_詳細版/` を触らないルール（②蒸留を過ぎたら蒸留しない）は**短期改修でも守る**。
