# A 入力を整える

## 手1 — 仕様が一意に定まらない点を洗い出させる

> **`docs/` の設計書と既存コードを根拠に、Todo と Tag の CRUD、および Todo の登録・更新時の**
> **Tag 紐づけを実装するうえで、仕様が一意に定まらない点を洗い出してください。実装はしません。**
>
> **各件について次を書いてください。**
>
> **| 箇所 | 定まらない点 | 根拠（どの資料のどこを見て、そう判断したか） | 実装した場合に結果を決めるもの | 取りうる選択肢 |**
>
> **次の3つに分類してください。**
>
> **1. 資料どうしが食い違っているもの**
> **2. どの資料にも書かれていないもの**
> **3. 書かれていないため、実行時の既定の挙動が結果を決めてしまうもの**
>
> **3 を厚く出してください。1 と 2 は資料を突き合わせれば見つかりますが、**
> **3 は実装を想定しないと表に出ません。**

### なぜこう投げるか

| | |
|---|---|
| **「実装はしません」** | **AIは生成が得意で、自分から止まるのが苦手。**その性質を逆に使い、手を動かす前に未決だけを吐かせる |
| **「根拠（どの資料のどこを見て）」** | **ケース一覧の基準と同じ。**ここで根拠を書かせておくと、そのまま `実装計画.md` へ移せる |
| **「実装した場合に結果を決めるもの」** | **3分類目を引き出す装置。**「決まっていない」で止めず、**代わりに何が決めるのか**まで答えさせる |
| **「3 を厚く」** | 資料の突き合わせで出る 1・2 に流れるのを防ぐ。**指示しないと楽なほうに寄る** |

**⚠ 3 に「MyBatis の結果マッピング」「Jackson のシリアライズ」のような具体例を書かない。**
書いた時点で拾えて当たり前になり、**プロンプトが効いたのかどうかが測れなくなる。**

### 出たもの

**14件。**読んだのは設計書7種と既存コード・参照テスト（26ファイル）。

| 分類 | 件数 | 例 |
|---|---|---|
| **1 資料どうしが食い違っている** | **3** | Todo更新に「進捗状況」が含まれるか（要件定義書とOpenAPIが食い違う） |
| **2 どの資料にも書かれていない** | **4** | **紐づけのある Tag を削除したときの `todo_tag`** ／ 検索語の `%` `_` |
| **3 既定の挙動が結果を決める** | **7** | **存在チェックと更新のあいだに削除されたとき（409 か 404 か）** ／ 重複 `tagId` の存在チェック |

**2 と 3 が過半。**設計書を突き合わせるだけでは出ない層が、**実装を想定させることで表に出た。**
