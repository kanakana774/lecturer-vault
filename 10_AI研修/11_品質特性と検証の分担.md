## 0. なぜこれが要るか

**機能要件／非機能要件の2分類では、完成判定ができない。**
それは「顧客が要求したこと」の分類であって、
**顧客は要求しないが満たさないと出せないもの**（層構成・出所の記録）が抜ける。

そして——

> **AIが担保できるのは「動くこと」まで。**
> **「動く」と「完成」の差が、この文書の中身。**

## 1. 採用する枠組み

### JIS X 25010（ISO/IEC 25010）· 製品品質モデル

**独自の分類を作らず、規格の語彙を使う。** 理由は3つ。

- 語彙が外部で通じる（客先・レビューで説明できる）
- 網羅性を自分で保証しなくていい
- **陳腐化しない**（`06_研修の芯.md` 設計原則4）

### 版の選択: **2011 / JIS X 25010:2013 系（8特性）**

| | |
|---|---|
| ISO/IEC 25010:2023 | 現行版。9特性。ユーザビリティが Interaction Capability に変更。2011年版は 25002（概要）・25010（製品品質）・25019（利用時品質）に再構成された |
| **JIS X 25010:2013（=ISO/IEC 25010:2011）** | **8特性。日本語の解説記事が揃っている** |

**新人が検索したときに情報が出てくる方が教材として実用的。**
研修で使うのは8特性のうち5〜6個なので、改訂差分はほぼ影響しない。

**表記**: 教材では「**JIS X 25010（ISO/IEC 25010）**」と併記する。両方で検索が当たる。

### ⚠ 規格は「確認方法」も「置き場」も持たない

**25010 は「何を担保するか」だけの分類。** 確認方法も、どの文書に書くかも規定していない。
だから同じ特性の中に、テストで測れるものと読まないと分からないものが混在する。

**これは規格の欠陥ではない。** 確認方法は技術で変わる（昔は目視だったものが静的解析で自動化される）。
**規格が陳腐化しないのは、そこを持たないから。**

→ **確認方法と置き場の軸は自分たちで持つ。** それが §3 の列。

## 2. 3つの軸は直交する

| 軸 | 中身 | 出所 |
|---|---|---|
| **軸1: 何を担保するか** | 8つの品質特性 | **規格** |
| **軸2: どう確かめるか** | **テスト**（実行結果を見る）／**目視**（コードの書かれ方を見る）／**機械**（静的解析） | **自分たち** |
| **軸3: どこに書いてあるか** | 設計書／DoD／コーディング規約／決定記録／CI設定 | **組織の文書体系** |

**特性からは、検証手段も置き場も決まらない。**

| 例 | 特性 | 検証手段 | 定義場所 |
|---|---|---|---|
| レスポンス 500ms 以内 | 性能効率性 | **テスト** | 非機能要件 |
| **N+1** | **性能効率性** | **目視** | **コーディング規約／DoD** |
| 認証なしで 401 | セキュリティ | **テスト** | API仕様書 |
| 例外メッセージの露出 | セキュリティ | **目視** | **セキュリティ実装基準／DoD** |

**N+1 が分かりやすい例。** 特性としては性能効率性だが、
10件のテストデータでは**実行結果に差が出ない**（Todoが10件返るのは同じ）。
クエリが1回か11回かは**コードを読むかSQLログを見るしかない**。
そして**どの設計書にも書かれない**。規約か DoD にしか居場所がない。

**🐘 これは「軸が直交する」ことの説明であって、この課題で N+1 が起きるという話ではない。**
実測では**1つも出なかった**（07 §10-22）。DoD を渡した結果であって、目視項目から外す理由にはならない。

### 研修生に言う一文

> **テストは「何が返ったか」しか見られない。**
> **「どう書かれているか」は、人が読むしかない。**

これで「緑＝完了ではない」が一段深くなる。
**緑が不十分なのではなく、そもそも見ている対象が違う。**
→ 配属後、**テストが緑でもレビューが通らない**理由がこれ1つで説明できる。

### 表から読めること

- **セキュリティはほぼ全部が目視。性能効率性も主要なものは目視。機能適合性は全部テスト。**
- **保守性がほぼ全部目視で、しかも最大の塊。** AIが書いたコードで問題が出る場所そのもの。
- **上流が用意するものは全部「設計書」に集まり、チームが用意するものは全部「DoD／規約」に集まる。**
  設計書を読んでも DoD の項目は1つも出てこない。**だから設計書だけ渡しても完成しない。**
- 段③（Red → Green）で終わるのは **機能適合性・信頼性** ＝ **AIが得意な側**。
  段④（目視）に残るのは **セキュリティ・性能効率性・保守性** ＝ **渡さないと満たされない側**。
  → **DoD ／ `CLAUDE.md` が右側を一手に引き受けている構造。**
- **DoD は規格順ではなく実務順に並んでいる。** 規格外の2件が「人が見る」の同じ欄にある。
  → **DoD は 25010 から作られていない。** §2 の「軸は直交する」の実例が現物にそのまま出ている。
- **「チーム」列が効くことは実測で確かめた**（07 §10-22）。設計書が「`tags` の各要素についてループして登録」と指示していても、
  **DoD を一緒に渡すとAIは DoD を優先し、`<foreach>` で1本にまとめた**（`tags` 5件でSQL3本）。
- **さらに DoD から N+1 を外しても、N+1 は戻らなかった**（07 §10-24・★9）。`LEFT JOIN` ＋ `<collection>` でSQL1本。
  AIは「**DoD から外れたことは判断を変える理由にしていない。置き場がレビューに移っただけと読んだ**」と述べた。
  → **右側は「渡せば守られる」で、しかも外しても崩れない。** ただし**それを確かめられるのは目視だけ**なので、項目は減らせない。
- **「自分」列の空白は、放っておくとAIが埋める。** 上の JOIN を選んだ理由の2つ目が
  **「一覧は件数上限が仕様上無いので、件数が増えるほど代償が大きい」**だった（★9・`04 ㉔`）。
  → **段②で挙がった空白が、段③の実装判断に効いた実例。** 決めずに渡すと、AIが決めて、しかも黙っている。

### 「試験性」に注目

**テスト自体の品質は、保守性の副特性として規格の中にある。** 独立した何かではない。
→ 「AIが書いたテストを疑う」が思いつきではなく、**規格上の品質特性の1つ**として位置づく。

### 段③の Red は、試験性の一部しか取れない

段③は **コミットごとに「テストを書く → 赤を確認 → 実装 → 緑」**（07 §5・§10-20）。
赤を見せさせるのは、「仕様から書け」の一文と違って**機械的に検証できる**から。

ただし 07 §5 が線を引いている——

> **⚠ Red は「落ちうる」ことしか証明しない。期待値が仕様と違っていても落ちる。そこは段④の仕事として残る。**

| 試験性の中身 | どこで取るか |
|---|---|
| assert が空でない／何かを本当に検証している | **段③の Red**（落ちない＝何もアサートしていない）。**ただし下の⚠2つ** |
| 実装を写していない | **段③の Red**（実装前に書くので構造的に不可能） |
| **assert が body を見ている** | **段④の目視** |
| **期待値が仕様から来ている** | **段④の目視。Red では取れない** |
| **実行順に依存しない** | **段④の目視** |

**⚠ Red の弱さは2つとも実測で出た**（`10_シミュレーション/03_委任_出てくるもの.md` ★6・★10）。

| 弱さ | 中身 | 効き方 |
|---|---|---|
| **偶然一致** | **404 を期待するテストは、そのパスにハンドラが1つも無いと実装前に通る。** コミット2・3で発生し、同じパスに `POST` が生えたコミット5では 405 で落ちて起きなかった | **実装が進むほど Red は信用できる＝最初のコミットほど弱い** |
| **アサートの一部しか走らない** | **`@ExpectedDatabase` はテストが成功したときしか検証されない**（spring-test-dbunit の仕様）。ステータスコードで落ちた段階では **DB の検証が1件も走らない** | **「赤を見た」は「全部のアサートを通した」ではない** |

→ **どちらも「段④で受入条件と突き合わせる仕事は消えない」に落ちる。**

**参照実装を Controller層の統合テストにした**（07 §9-10・§10-21）のは、
「body を見ている」に**基準の現物を与える**ため。ユニットテストだけを見せると、body を見る形が分からない。

## 4. 規格に収まらないもの（正直に外に置く）

**無理に当てはめない。「規格の外」と明示する。** §3 の表では末尾の「（規格外）」行に分けてある。

### 4-1. プロセス品質

| 観点 | 例 | 定義場所 |
|---|---|---|
| **出所が残っているか** | 仕様か、自分の判断か、AIの判断か | `docs/決定事項.md` の出所列 |
| **説明できるか** | 「なぜこう書いたのか」に答えられるか | — |
| **範囲の妥当性** | 頼んでいないファイル・テーブルを変えていないか／依存を足していないか | **DoD「人が見る」に載っている** |
| **黙って決めていないか** | **設計書と DoD が衝突したとき、報告せず片方に寄せていないか** | 段④の問い（07 §6・§10-22） |
| **明示** | PR でAIに書かせた部分が分かるか | `.github/PULL_REQUEST_TEMPLATE.md` |

> **25010 は成果物を見て評価するモデル。経緯は評価対象にならない。**
> **人が書いていた時代は、これが自動的に成立していた。書いた本人が説明できたから。**
> **AIに書かせると成立しなくなる。だから明示的に足す。**

**規格の内側／外側を分けて見せること自体が教材になる。**「なぜ足したか」を説明できる形なので。
**そして DoD は既に足している。** 規格外の2件が「人が見る」に入っているのは、実務が先に必要としたから。

### 4-2. ライセンス

**25010 に該当特性が無い。** 法務・ガバナンスの領域。
→ **段⓪のガバナンス4項目に置いたまま**にする。§3 では規格外枠に置く。

## 5. 誰が用意するか — 線引き

### 置き場の判断軸: **どのくらいの範囲に効くか × どのくらい持つか**

| 置き場 | 何を書くか | 寿命 | 管理 |
|---|---|---|---|
| **`CLAUDE.md`** | **全機能に共通で恒久的なもの**——層構成・使うコマンド・設計書の場所・禁止事項・**DoD を畳んだ「完了の定義」節** | プロジェクトと同じ | **チーム**（git管理・PRで変える） |
| **`09_配布物/DoD.md`** | **DoD の正本。** 全変更に共通の最低ライン | 同上 | **チーム**（講師が配る） |
| **`docs/決定事項.md`** | **この案件で自分が決めたこと**（決めたこと／理由／**出所**） | 案件が終わるまで | **実装者。研修生が書く唯一のドキュメント** |
| **プロンプト** | その回だけの指示 | 1回 | 実装者 |
| **CheckStyle** | **機械で判定できる規約** | 恒久 | **組織** |

**受入条件は3層**（DoD＝講師が配る／機能ごと＝AIが出す／追加分＝人が足す）。
**独立ファイルにするかは決まっていない**（→ 未決11）。07 では段②の提出物としか書かれていない。

### 実務の原則2つ

**① 機械で強制できるものは、文章に書かない。**
「命名規則を守れ」と書くより CheckStyle を通させる方が確実。
**指示は薄いほど守られる**（長い指示ファイルは全体の遵守率が落ちる）。
→ **`CLAUDE.md` は機械化できないもの専用にする。**

**⚠ これは今はまだ成立していない。** `pom.xml` に CheckStyle plugin が入っていない（07 §9-11 未着手・`DoD.md` 末尾の「未整備」注記）。
plugin を入れるまでは「既存と書き方が揃っている」も人が見ることになる。

**② 案件別のものを `CLAUDE.md` に書かない。**
案件終了後に残って、次の案件で嘘になる。ファイルを分けて参照させる。

```markdown
実装の前に docs/決定事項.md を読むこと。
```

これは 07 §5 の `CLAUDE.md` 6項目の ⑥ と同じ。**指示ファイルから決定事項を参照させる形は既に確定している。**

### 線引きの結論

> **ジュニアが自分で書くのは `docs/決定事項.md` だけ。**

| | なぜ |
|---|---|
| **チーム配布**（`CLAUDE.md` ／ DoD ／ CheckStyle） | **全機能・全員に効くから、個人が案件ごとに書き直すものではない。** ジュニアが書くと案件ごとにブレる／既存の規約と矛盾する |
| **自分で書く**（`docs/決定事項.md`） | **設計書の穴は案件ごとに違う。その場にいる人しか埋められない** |

**研修生に言うこと**:
**「AIにこう指示すべきか」を毎回ゼロから考える必要はない。**
考えるのは**設計書に書かれていないこと**だけ。それ以外は既にリポジトリにある。

**逆方向も1行**:
`docs/決定事項.md` に何度も同じことを書いていたら、それは**チームの規約に上げるべきもの**というサイン。
**その提案はジュニアがしていい**（自分で書き換えるのではなく、レビューで提案する）。

## 6. ジュニアが知っておくべきこと

### 「知る」には2段階ある

| 段階 | 何ができる | 誰に必要 |
|---|---|---|
| **名前を知っている** | **見つけられる／人に聞ける** | **全員（ジュニア含む）** |
| 原理を説明できる | 判定・対処・例外の見極めができる | シニア |

> **目視の本質は「名前で引く」こと。名前を知らないものは探せない。**
> 「なんか変」では検索も質問もできない。

**`CLAUDE.md` に書いてあっても同じ。** 指示ファイルは守らせる保証がない。
誰かが確認しないと成立せず、それは実装者しかいない。
→ **チームが書いたから自分は知らなくていい、にはならない。**

### 持つべき名前は7つ

| 名前 | 一言で | 深さ | 既習 |
|---|---|---|---|
| **N+1** | 一覧を取った後、件数分のクエリが飛ぶ | **原理まで** | 2か月目 |
| **トランザクション境界** | どこからどこまでが一括で戻るか | **原理まで** | 2か月目 |
| **DTO ／ Entity 分離** | DBの都合をそのまま外に出さない | 名前＋理由 | 2か月目 |
| **層の責務** | Controller に業務ロジックを書かない | 名前＋理由 | 2か月目 |
| **`SELECT *` 禁止** | 列が増減したときに黙って壊れる | 名前＋理由 | 2か月目 |
| **例外の外部露出** | 内部情報がレスポンスに出る | 名前＋理由 | 2か月目 |
| **テストの追認** | 実装を見て書いたテストは実装のバグを追認する | **原理まで** | **新規** |

**研修で新規に増やすのは1つだけ。**（`06_研修の芯.md` 設計原則5「新しく教える技術をゼロにする」）

## 7. AIに聞いてよいか — 2種類を分ける

| 聞くこと | 可否 |
|---|---|
| **「N+1とは何か」** | **◎ 最適。** 教科書より速く、Java／MyBatis の文脈で答える |
| **「このコードにN+1はあるか」** | **△ 補助まで** |

後者が補助止まりな理由:

**① 名前を知らないと聞けない。**
「このコードに問題はある?」ではAIは何かしら答えるが、網羅かどうか分からない。
**語彙が先で、質問はその後。**

**② 書いたAIに聞くと通ることがある。**
自分の出力を妥当と判定しがち。単独では担保にならない。
→ これは **5-1（AIレビューの仕分け）で扱う**ので、段④で先取りしない。

### 「書いたAIに聞く」と「別のAIに聞く」は別物（2026-08-26 実測）

**②の前提は「書いたAIに聞く」場合の話だった。** 実装していない別のエージェントを立てて、
**問いもチェックリストも渡さず**「引き継いだものを確かめて、気づいたことを挙げてください」だけ渡したところ、
**§3 の規格外4行が全部出た**（R1・`10_シミュレーション` ／ 07 §10-25）。

手抜きではない。8件の指摘＋7件の「判断できなかったこと」＋5件の「答えられない箇所」。
設計書を通読し、DDLと `pg_constraint` を突き合わせ、**捨てDBを立ててアプリを起動し curl で12パターン**叩いている。
しかも本質を突いた——**「設計書が DoD に反する手順を書いている事実自体が仕様担当に上げる話で、実装者が黙って片方を選んで終わらせる案件ではない。同じ設計書で他の機能を作る人が毎回同じ衝突を踏む」**。

**⚠ 測ったのは「強いモデルに検証させたら出るか」で、「3か月目の新人が出せるか」ではない。**
だから結論はこうなる——

> **問い（07 §6 の12本）の価値は「AIに出させるための呼び水」ではない。**
> **人が自分で見るための足場である。**

**§3 の規格外4行も §8 の停止条件も、そのまま残る。** 畳むのは「**聞かないと出てこない**」という理由づけだけで、
**行そのものは残る**（出るとしても、出させたのはAIで、それを判定するのは人）。

**ただし段④と段⑤の境界に穴が空いた** — 別のAIに投げると **5-1（AIレビューの仕分け）が段④でできてしまう**。→ **`07 §12-15`**。

### 実務での使い方

> **自分で名前を引いて見つける → AIに「なぜこれが問題か」を確認する → 直し方を相談する。**
> **発見は人、説明と対処はAI。**

## 8. 目視の停止条件

> **目視の量は、コードの量ではなく、チェックリストの項目数で決まる。**
> **リストを一巡したら終わり。差分の大きさで変わらない。**

コードを頭から読むのではなく、**項目ごとに該当箇所だけを引く。**

### チェックリストは新規に作らない

**`09_配布物/DoD.md` の「人が見る」欄がチェックリストそのもの**（**9項目**。2026-08-26 にトランザクション境界とテストの実質性を追加）。ここで足すのは**見る場所の列だけ**。

| 項目 | **見る場所** | やること | 出典 |
|---|---|---|---|
| **N+1** | **一覧取得の Service メソッドだけ** | ループの中に Mapper 呼び出しがないか。**5行見れば分かる** | DoD |
| **トランザクション境界** | **Service の public メソッドのシグネチャ ＋ 削除・更新の順序** | `@Transactional` の有無と位置（**一覧を眺めるだけ**）／**順序が制約の不在に暗黙依存していないか** | DoD |
| **レスポンスの中身** | **Controller の戻り値の型 ＋ そのクラスのフィールド** | Entity が出ていないか（**型名を見るだけ**）／内部ID・設定値・DB都合のカラムが混ざっていないか | DoD |
| **層の責務** | **Controller の各メソッドの中身** | if ／ 計算 ／ Mapper 直呼びがないか | DoD |
| **`SELECT *`** | **Mapper XML** | 列を明示しているか。**検索1回** | DoD |
| **例外の外部露出** | **例外ハンドラ1ファイル ＋ エラー時のレスポンス実物** | Postman で叩いて body を見る | DoD |
| **頼んでいない変更** | **`git diff --stat`（コミット単位）** | 段② 2-2 で承認した「触るファイル一覧」と突き合わせる | DoD |
| **依存の追加** | **`pom.xml` の差分** | 段③開始時の pom と一致するか | DoD |
| **テストの実質性** | **テスト1〜2本のみ** | body と DB を見ているか／期待値が仕様から来ているか／実行順に依存しないか | DoD |

**上4つは「読む」ですらなく、型と注釈を見るだけ。次の2つは検索と Postman。その次の2つは `git diff` を見るだけ。**
→ 研修生に見せると、目視が思ったより軽い作業だと分かる。

**⚠ 07 §6 の「新人が出すのは6カテゴリ」とは別物。**
あちらは `08_ギャップ` 付録A の15カテゴリのうち新人が扱う6カテゴリ、こちらは DoD の項目。数が近いので混同しやすい。

### 停止したときに言うこと

> **リストを一巡した。ここまでは自分で確認した。**
> **これ以外に問題があるかは、自分では分からない。だからレビューを頼む。**

**「全部見ました」ではなく「このリストを見ました」。**
これが 4-3（どこまでやるかを決める）の提出形。

### リストの外側 = 地図

付録Aの15カテゴリ約60項目は、**このリストの外側の地図**として渡す（作業ではない）。

> **見たのは DoD の欄。残り9カテゴリは名前だけ知っている。判定できないので、レビューで見てもらう。**

**名前を知っていれば「見てもらう」と言える。** これが地図を渡す理由。
**07 §6 は既に同じことを書いている**（「全量を見せた上で仕分けさせる／残りは『自分では判定できないのでレビューを頼む』と言えるための材料」）。**ここは変更不要。**

## 9. 実装後の確認は誰がやるか

### 全部、実装者がやる

**レビューは網ではない。**
「レビューで見てもらえる」を前提に自分の確認を薄くするのは、実務で一番嫌われる形。

理由は単純で、**レビュアーは実装者ほど文脈を持っていない。**
何を決めて、何を渡して、AIが何を勝手に決めたかを知っているのは実装者だけ。

### レビュアーが見るのは「別のもの」

| | **実装者（自分）** | **レビュアー** |
|---|---|---|
| 受入条件との一致 | **全部** | 見ない（信頼する） |
| DoD の「人が見る」欄 | **全部** | サンプリング |
| 出所・範囲 | **全部** | PR の記述を見る |
| 前提知識が要る判断 | 判定できない | **ここを見る** |
| 他機能との整合 | 見えない | **ここを見る** |
| 基準そのもの | 持っていない | **ここを持つ** |

**レビュアーは「自分では判定できないもの」を見る。**
実装者ができることをやり残して回すのではない。

### AIが入って変わった点

> **昔は「書いた本人が全部知っている」が自動的に成立していた。**
> **AIに書かせると、実装者自身が「知らないコード」を持つことになる。**
> **だから確認の責任は減るのではなく、増えている。**

自分で書いていないものを、自分が書いたものとして説明できる状態にする作業が乗る。
→ 5-3（AIに任せた範囲／自分が担保した範囲）・5-4 に直結。

### ジュニアの正しい線の引き方

> **「自分では判定できないので、レビューを頼む」と言えることまでがジュニアの仕事。**
> **「見ていません」はダメ。「見たが判定できませんでした」は正しい。**
