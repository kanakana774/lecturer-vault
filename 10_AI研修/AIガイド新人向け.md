# AIガイド（新人向け）
%%
この資料は自社開発のリーダーが受託案件でエージェントとの開発業務を行うジュニアに対して書いたガイドです。
研修完了後は、SES案件だけでなく、自社開発チームに配属される可能性もあるので、これを優先度の高いレファレンスとして研修設計していきたい。
%%


> **目的**: AI エージェント（Claude Code / ChatGPT 等）を業務で使ううえでの「守るべき原則」と「実際に成果が出る使い方」を1本にまとめたもの。
> **読み方**: Part 1〜2 と Part 5 は全員必読（ツール・環境非依存）。**Part 5 のチェックリストはタスクのたびに手元で見てください。** Part 3 は Claude Code を使う人向けの実践編だが、考え方は他ツールにも流用できる。Part 4 は失敗に心当たりが出たときに読み返す。付録は、案件固有のルールをこのガイドに接続するための雛形なので、配属先ごとに埋めて使う。
> **事故ったと思ったら**: 何よりも先に **2.11** を開いてください。
> **本書が決めないこと**: 使うツール・隔離環境の有無・自動承認の範囲・成果物の置き場所は、チーム／案件ごとに決めるものです（→ 2.8）。本書は「どう決めるにせよ守ること」を書いています。
> **前提**: AI は「作業を代行してくれる部下」ではなく「異常に速いが、平気で嘘をつく同僚」。速さの恩恵を受けつつ嘘を潰す仕組みを持つことが、このガイドの中身です。

---

## Part 1 — 6つの基本原則（全AIツール共通）

この6原則が土台です。以降のすべてのルールは、この原則を実務に落としたものにすぎません。

### 原則1. 人間が最終責任を負う

> AI エージェントの出力・操作の結果責任は、利用した本人（またはその上長）にある。「AI がそう出力した」は免責にならない。

- あなたが PR を出した時点で、そのコードは **あなたが書いたもの** として扱われます。「Claude が生成した部分なので」という説明は、レビューでも障害報告でも通用しません。
- したがって **自分が説明できないコードをマージしてはいけません。** レビューで「なぜこの条件分岐が必要？」と聞かれて答えられないなら、その差分はまだ理解していないということです。理解するまで読むか、作り直させてください。
- 「AI に任せた範囲」も含めて、成果物の品質・納期・顧客影響はあなたの責任範囲です。

### 原則2. 最小権限

> AI に与える権限・接続は、業務に必要な最小限に。

- AI エージェントに渡す認証情報・接続先は「そのタスクに必要な分だけ」。本番 DB の書き込み権限を持ったまま調査タスクを走らせない。
- **AI が触れられる範囲を、作業に必要なところまで絞る。** 手段は環境しだいです —— 作業ディレクトリを限定する／読み取りだけ許可する／作業用の別アカウントを使う／コンテナ・VM で隔離する。どれを採るかはチームの方針に従ってください。**共通して守るのは「他案件のコードや個人情報を含む場所が見える状態で、自動実行を任せない」こと。**
- **確認をスキップする設定（自動承認）を使う範囲を、先に決めておく。** 少なくとも、取り消しがきかない操作が起きうる場面では使わない。
- **本番・共有環境への変更を AI に直接実行させない。**「コマンドと狙いを AI に説明させる → 人間が実行する → 出力を AI に確認させる」の対話式にする（詳細は 2.7）。
- 作業が終わったら不要な認証は落とす。認証情報が平文で保存される環境は少なくありません。

### 原則3. データを守る

> 何を入力してよいかはデータ分類に従う。個人情報・認証情報等は入力しない。

**入力してはいけないもの（原則）**

| 分類 | 例 |
|---|---|
| 認証情報 | API キー、DB パスワード、秘密鍵、アクセストークン、`.env` の中身 |
| 個人情報 | 氏名・メールアドレス・電話番号・住所を含む実データ、顧客名簿、取引・注文データ |
| 顧客の非公開情報 | 未公開の売上数値、契約条件、社内限定の設計資料 |

- **どうしても実データが必要な場合の加工は、「氏名を消したから大丈夫」ではありません。** 会員 ID・注文番号のように、社内のデータベースと照合すれば個人を特定できる値は、法律上まだ個人情報として扱われます。安全なのは次のいずれかです。
  - 構造だけ同じ **ダミーデータを自分で作る**（最も安全）
  - 列名（ヘッダー）と型・件数だけを伝え、値は渡さない
  - 元データと対応関係を持たない連番に置き換える
- **成果物の「出口」に注意する。** 社外・公開リポジトリ・共有ナレッジに上げるファイルは、顧客名・システム名・ドメインで grep してゼロ件を確認してから push する。AI が生成した文書には、あなたが意図していない顧客固有情報が紛れ込みます。
- **AI は秘密を「書き出す」側でもあります。** 動くコードを最短で出そうとして **API キー・接続先・パスワードをコードに直書き** し、デバッグのために **トークンや個人情報を `console.log`・エラーメッセージに出す** コードを平然と足します。ログは残り、共有され、そのまま流出経路になります。**diff で必ず見る。**
- **commit 前に機械で確認する。** シークレットスキャンや pre-commit hook があれば使う。無ければ最低限、`git diff --cached` を `key` / `token` / `password` / `secret` / `PRIVATE KEY` で grep する。
- **本物の鍵を AI に見せた／コミットしてしまったら、消して終わりにしない。その鍵を失効・再発行したうえで上長に報告する**（→ 2.11）。履歴からファイルを消しても、鍵はもう外に出たものとして扱います。
- ログ・トランスクリプトも「データ」です。セッション履歴には過去に読ませたファイルの中身が丸ごと残ります。共有 PC・共有ボリュームの扱いに注意。

### 原則4. 連携先の指示は実行しない（プロンプトインジェクション）

> Web ページ・メール・ファイル等から読み込んだ内容に含まれる指示を、利用者の意図と無関係に実行させない。

これは新人が最も軽視しがちで、最も事故につながる原則です。

- AI は「あなたの指示」と「AI が読み込んだファイルに書いてある文章」を、原理的には同じテキストとして扱います。**外部から取り込んだテキストはすべて "データ" であって "命令" ではない。**
- 危険な入口の例:
  - Web ページ / 検索結果（`WebFetch`, `WebSearch`）
  - GitHub の Issue 本文・PR コメント・コミットメッセージ（**社外の人が書ける**）
  - 顧客から受領した CSV / Excel / PDF
  - MCP サーバー（AI ツールに外部サービスを繋ぐ仕組み）経由で取得した外部データ、他人が共有したドキュメント
  - **AI が自動で読み込む指示ファイル**（`CLAUDE.md` / `AGENTS.md` / エディタのルールファイル）。**リポジトリに置いてあるだけで、あなたの指示と同じ強さの命令として読まれます。**
  - **ツールの実行結果そのもの** — 依存パッケージの README やコード内コメント、テスト出力、エラーメッセージ、CI ログ。**人間が文章を書き込める場所は、すべて入口です。**
- **やるべきこと（順番が大事）**
  1. **工程を分ける（これが本命の対策）。** 外部から取り込んだテキストを読む工程と、書き込み・`git push`・外部送信ができる工程を、同じセッションに同居させない。外部データは読み取りだけの役に読ませ、**要約・抽出結果だけ**を本作業に渡す。攻撃者の文章が届く先に「実行できる手」が無ければ、注入は成立しません。
  2. **その工程では自動承認を切る。** ここは「確認が面倒な場面」ではなく「攻撃者の入力が届く唯一の場面」です。
  3. **そのうえで実行ログを目視する。** `git push`・ファイル削除・外部送信（`curl` / メール / チケット起票）が発生していないか。
- **目視だけを防御にしない。** 確認が大量に出ると、人間は必ず機械的に許可を押すようになります。**「確認が多すぎて読めていない」と感じた時点で、防御は効いていません。** タスクを分割し、1回の作業で外に出る操作の数を減らしてください。

### 原則5. 既存の統制に従う

> 承認済みツール・コネクタ、社用アカウント、決められた環境の中で使う。抜け道を作らない。

- 会社が承認していない AI サービスに業務コードを貼らない。「無料だから」「精度がいいから」は理由になりません。
- 個人アカウント（個人の ChatGPT / 個人 GitHub）で業務データを扱わない。
- **ブランチ保護・レビュー必須・CI といった既存の統制を、AI 作業の都合で外さない。** これは新人が自分の判断で外す操作ではありません。外さないと進まない状況になったら、まず上長・リードに相談してください（外さずに済む手段があるのがほとんどです）。権限を持つ人がやむを得ず外す場合も、①外す前に影響を確認 → ②作業 → ③**即座に**元に戻す → ④戻ったことを確認、までを1セットで行い、いつ・誰が・なぜ外したかを記録に残します。
- 確認を一括でスキップする設定（各ツールの「危険モード」「全自動承認」）は、**取り消しがきかない操作が起きない範囲**に限定する。
- **顧客との契約・規約を確認する。** 案件によっては AI の利用可否や、成果物への利用明記が定められていることがあります。**「特に何も言われていない」は「使ってよい」ではありません。** 可否と条件が確認できるまでは、顧客のコード・データを AI に渡さない（→ 2.8）。

### 原則6. 出力を鵜呑みにしない

> 生成物は正確性も適切性も保証されない。利用者の責任で内容を確認し、そのまま引用・公開して他者の著作権等を侵害しないようにする。

- AI は **もっともらしい嘘を、自信たっぷりに、大量に** 出します。存在しない関数、存在しない設定オプション、実在しないファイルパス、実行されていないコードを根拠にした結論。
- 特に危険なのが **「動いているように見えるコード」** と **「筋の通った説明」** です。どちらも検証しない限り正しさの証拠になりません。
- 生成された文章・図・コードをそのまま外部提出物にしない。ライセンス・著作権に触れうる長い引用が混ざることがあります。
- **検証の具体的なやり方が Part 2 です。**

## Part 2 — 仕事の進め方（AIを使う前提の実務ルール）

原則6「鵜呑みにしない」を、実際の手順に落としたものです。ここが本ガイドの中心です。

### 2.1 段階を刻む — 一度に「PR まで作って」と言わない

AI に長い工程をまとめて任せると、途中の判断ミスが後段まで伝播して、最後に全部やり直しになります。

**推奨する刻み方:**

```
① 調査（どこを直せば効くのか）      → 人間が結論を確認
② 実装方針の合意（何を・何をやらないか）→ 人間が承認
③ 実装                              → 人間が diff を読む
④ コミット                          → 人間が指示
⑤ push                              → 人間が指示
⑥ PR 作成                           → 人間が本文を確認
```

各段階で人間が「OK」を出してから次に進む。特に **④以降（外に出る操作）は必ず明示的に指示する。** AI に「良きに計らって」と言うと、確認していない差分が push されます。

### 2.2 「実コード根拠」を必ず取る — file:line で語らせる

AI の調査結果を受け取るときのルール:

- ❌「◯◯の処理は Foo クラスで行われています」
- ✅「◯◯の処理は `app/services/foo.php:214` の `Foo::apply()` で行われている。該当行は `if ($rate > 0) { ... }`」

**ファイルパス・行番号・その行の実際の中身** の3点セットが揃っていない主張は、まだ「仮説」です。自分でそのファイルを開いて確認するまで、設計判断の根拠にしてはいけません。

**特に注意すべき罠:**

| 罠 | 内容 |
|---|---|
| **死にコード誤認** | grep でヒットしたコードが、実際には呼ばれていない（旧実装・feature flag OFF・別世代のテンプレート）。「実際に実行される（live）コードか」を、呼び出し経路を辿って確定させる。 |
| **静的 grep での断定** | 「コードに無いから表示されない」は誤り。実行時に組み立てられる・外部サービスが差し込む・キャッシュ済みの旧出力が返る、といった理由で実際の挙動はズレる。**実物を叩いて確認する。** |
| **過去情報の陳腐化** | 過去の調査メモや AI の記憶にある行番号は当時のもの。**現在のコードで再検証してから使う。** |
| **ブランチ違い** | 「実装済み」と「リリース済み」は別。feature ブランチにしかない実装を master 前提で語らない。 |

### 2.3 断定の前に反証する — 敵対的検証

「たぶんこれが原因です」で止めない。**その結論を壊しにいく** 工程を1つ挟みます。

- AI に対して「**この結論を否定してください。反例を探してください**」と明示的に指示する。肯定方向に聞くと肯定材料しか出てきません。
- 判断が重い場面（本番障害の原因特定、大規模改修の対象確定、live/dead 判定）では、**独立した別セッション／別エージェントに反証だけをさせる** と精度が上がります。
- 網羅性が要るところは推測で埋めない。「CSV 全件をパターン分類する」「呼び出し元を全部列挙する」のように、機械的に全部見る。

### 2.4 完了主張には証拠を添える

**「テストが通りました」「動作確認できました」は、実際にコマンドを走らせた出力が無い限り信用しない。** AI もあなたも、です。

- AI が「修正しました、これで動きます」と言ったら、`実際に実行して、出力を見せて` と返す。
- 自分が報告するときも同じ。「ローカルで確認済み」ではなく「`make test` を実行し、42 passed / 0 failed。ログは以下」まで書く。
- **失敗した事実は隠さず報告する。** テストが落ちているのに「完了」と書くのが、最も信用を失う行為です。
- **テストを AI に書かせるときは、「何が正しいか」を先に人間が決める。** 順番が逆だと、AI は仕様ではなく「いまの実装の振る舞い」をテストにします。実装にバグがあれば、バグごと固定されます。入力・期待出力・境界値・異常系を先に箇条書きにしてから依頼してください。
- **「テストが落ちたので直しました」と言われたら、実装を直したのかテストを緩めたのかを diff で確認する。** アサーションの削除・skip の追加・例外の握り潰しは、直っていないサインです。**green は「壊れていない」証拠であって「正しい」証拠ではありません。**

### 2.5 コードと文書を同期する

- **PR 本文（Description）と実装は常に一致させる。** 実装方針が途中で変わったら PR 本文も直す。AI に最初に書かせた本文が、最終実装と食い違ったまま残るのが典型的な事故です。
- 依頼文・PR 本文は簡潔に。チームのテンプレートに従い、無ければ「要約」と「変更点」が数行で読める形にする。長い文章は読まれません。
- 調査結果やレビュー結果をドキュメントに残す場合、改版時に **旧版を消さない**（版を分ける／同一ファイル内で版を上げる）。「なぜ結論が変わったか」が追える形にする。

### 2.6 暫定実装には「削除条件」を書く

キャンペーン対応・急ぎの回避策など、後で消す前提のコードは必ず PR 説明に書く:

- リバート想定であること
- **いつ消すのか**（キャンペーン終了時 / 新実装への切替時 / 恒久対応 PR マージ時）

書かないと永久に残ります。AI は「後で消す」を覚えていてくれません。

### 2.7 不可逆・共有への操作は対話式にする

以下は **AI に直接実行させない**（コマンドを提示させ、人間が実行し、出力を AI に読ませる）:

- 本番・ステージング・共有開発環境への変更
- クラウドインフラの作成/削除（特に「一覧に無いものを全部消す」系のコマンドは方向を取り違えると壊滅的）
- `git push --force`、履歴の書き換え、ブランチ削除
- 外部への送信（メール・Slack・チケット起票・API POST）

**着手前に必ず「向き先」を確認する。** どのプロジェクト／どの環境／どのブランチに対して操作しようとしているかを、コマンド（`gcloud config list`, `git remote -v`, `kubectl config current-context` 等）で AI と人間の認識を合わせてから始める。

通常のコミット取り消しは `git revert` を使う（履歴を残し、経緯を追える形にする）。force push は最後の手段です。

### 2.8 チームで先に決めておくこと

環境やツールはチーム・案件ごとに違います。以下は **あなたが個人で決めることではなく、配属時に確認すること** です。

| 決めること | 確認の観点 |
|---|---|
| 使ってよい AI ツールとアカウント | 承認済みか。個人アカウント・無償プランの併用は不可か。**入力が学習に使われない設定・契約になっているか** |
| AI に見せてよい範囲 | どのディレクトリ・どのデータまでか。隔離環境（コンテナ/VM/専用マシン）を使うか |
| 自動承認してよい操作の範囲 | どこまでを確認なしで実行させてよいか |
| AI レビューの位置づけ | 人間レビューの代替にはしない、が原則。チームの運用を確認する |
| 成果物の置き場所と命名 | 調査結果・レビュー結果をどこに、どう名付けて残すか（→ 3.8） |
| 許容するライセンス | 追加してよい OSS ライセンスの範囲（→ 2.10） |
| 事故時の報告先 | 誤入力・予定外操作に気づいたとき、誰に第一報を入れるか（→ 2.11） |
| 顧客側の規約 | AI 利用の可否、成果物への明記義務の有無 |

決まっていない現場もあります。その場合は **確認が取れるまで保守側に倒して始めてよい** です —— 会社が承認しているツールだけを使い、AI に見せる範囲は対象リポジトリ1つに絞り、自動承認は読み取り系（閲覧・検索・テスト実行）まで、成果物は対象リポジトリ内にチケット ID / PR 番号を含む名前で置く。そのうえで「こう始めています。ここは確認したいです」と着手時にチームへ一言共有してください。**「決まっていないので聞きませんでした」が一番まずい状態です。**

### 2.9 「動くか」だけでなく「危なくないか」を見る

ここまでは「正しく動くか」の話でした。**AI は動くコードを書きますが、安全なコードを選ぶとは限りません。** 危険な書き方でも機能テストは通るので、2.4 の実行ログでは捕まりません。顧客のシステムに混入したとき最も高くつくのがこの種の欠陥です。diff は、機能とは **別のパスで** もう一度読んでください。

| 見るところ | 危ない兆候 |
|---|---|
| 入力の扱い | SQL を文字列連結で組み立てている（プレースホルダを使っていない）／ユーザー入力をそのまま HTML・シェル・ファイルパスに埋めている |
| 認可 | 「ログイン済みか」は見ているが「**その人が見てよいデータか**」を見ていない |
| 秘密情報 | キー・トークンをコードやログ出力に直書きしている（→ 原則3） |
| 既存機構の迂回 | 共通のエスケープ関数・認可ヘルパを使わず、AI が独自に書き直している |
| エラー処理 | 例外を握り潰している／画面やレスポンスに内部情報を出している |

- **一番早い確認方法は「このプロジェクトの既存の同種処理と並べて比べる」こと。** 既存の書き方から外れていたら、AI が自分の学習内容で書いています。指示も **「このリポジトリの既存の書き方に合わせて」** が効きます。
- CI に静的解析・シークレットスキャン・依存の脆弱性チェックがあるなら、**AI 生成差分こそ必ず通す。** 赤いまま「AI が直したので大丈夫」と押し通さない（原則5）。

### 2.10 依存とライセンスを勝手に増やさせない

**依存を1つ増やすことは、顧客のシステムに負債を1つ増やすこと** です。あなたではなくチームの判断になります。

- 実装前に **「標準機能・このリポジトリの既存実装で書けないか」を先に探させる。** 追加が必要なら理由と代替案を出させ、人間が決める。
- **AI が挙げたパッケージ名をそのまま `install` しない。** AI は、もっともらしい名前の **実在しないパッケージ** を平気で提案します。攻撃者はその名前を先回りして登録し、悪意あるコードを置いています。**AI に聞き返して確認しない**（同じ嘘が返ります）。公式レジストリ（npm / PyPI / pkg.go.dev / Packagist 等）を自分で開き、作者・公開日・利用状況・リポジトリの実在を見る。
- **ライセンスを確認してから入れる。** AI は学習したコードの断片をほぼそのまま出すことがあり、GPL / AGPL 由来のコードが混ざると **顧客に納品したシステム全体にソース公開義務が及びうる** —— 受託でいちばん重い事故です。MIT / BSD / Apache-2.0 でも著作権表示とライセンス文の保持が条件で、AI は先頭のライセンスヘッダーを落とします。
- **見覚えのない、やけに完成度の高い塊が出てきたら疑う。** 特徴的な関数名やコメントで検索し、既存 OSS のコピーでないか確かめる。出所が確認できないコードはマージしない（自分で書き直す）。
- `package.json` / `go.mod` / `composer.json` / `requirements.txt` の **差分は毎回読む。** 頼んでいないのに変わっていたら理由を確認する。許容ライセンスの方針は案件ごとに違います（→ 2.8）。

### 2.11 事故ったら、自分で判断せず即報告する

> **事故ったと思ったら、まずここを開いてください。**

情報・法務の事故は **時間が経つほど傷が深くなります。** いちばん危険なのは事故そのものではなく、黙っていることです。次に一つでも当てはまったら、**深刻度を自分で判断せず**、手を止めてその場で上長へ第一報を入れてください。

- 認証情報・個人情報・顧客の非公開情報を AI に入力した（**疑いを含む**）
- AI が予定外の操作（push・削除・外部送信）を実行した
- 承認されていない AI サービスに業務データを貼った
- AI が出したコードが既存 OSS のコピーではないかと疑わしい／ライセンスが確認できない（→ 2.10）

1. **手を止める。** 成果物を push しない。**消して取り繕わない**（証跡が消えると影響範囲を確定できなくなります）。
2. **「いつ／どのツールに／どの情報を／どこまで」の4点だけ** 事実のまま伝える。分からない部分は「不明」でよい。
3. 認証情報なら **失効・再発行**（→ 原則3）。該当セッションの ID・実行ログは残す。
4. **顧客への連絡は自分でしない。** 経路と文面は会社が決めます。

**報告そのもので責められることはありません。遅れたことだけが問題になります。**

## Part 3 — Claude Code 実践編

ここからはツール固有の話です。他のツールを使う場合も、考え方（役割を分ける／型を持つ／仕組みで防ぐ）はそのまま流用できます。

**「AI に上手く指示する」より「AI が失敗しにくい環境を作る」ほうが効きます。**

### 3.1 最初にやること

1. **プロジェクトの正書を読む** — リポジトリ直下の `CLAUDE.md` / `AGENTS.md` / `README.md`。ここにプロジェクト固有のルール（ブランチ運用、起動方法、既知の罠）が書かれています。Claude は自動で読みますが、**あなたも読んでください。** AI が守れているかを判断できるのはあなただけです。
2. **作業範囲を確認してから起動する** — どのディレクトリまで見せるか、どこまで自動承認するかは **チームの取り決めに従います**（2.8）。決まっていなければ起動前に確認し、**範囲を決めずに始めない**こと。
3. **同じ場所から起動する習慣をつける** — セッション履歴は起動ディレクトリに紐づきます。毎回違う場所から起動すると過去セッションを引けなくなります。

### 3.2 タスクの「型」を持つ

毎回ゼロから指示を書くのではなく、頻出タスクは決まった流れに乗せます。

```
調査 → 実装 → レビュー → リリース
```

| フェーズ     | やること                                               | 成果物         |
| -------- | -------------------------------------------------- | ----------- |
| **調査**   | 改修対象の live コードを file:line で確定。多角的に調べ、結論を敵対的に反証する   | 調査報告書（md）   |
| **実装**   | スコープ確定 → 実装 ↔ 独立レビュー を指摘ゼロまで反復 → PR                | PR          |
| **レビュー** | タスクに対して「過不足なく」直っているかを検証（漏れ / スコープ外 / バグ）＋動作確認手順を作る | レビュー報告書（md） |
| **リリース** | リリースブランチ作成 → リリース先ブランチへの PR                        | リリース PR     |

ポイントは **「実装」と「レビュー」を別の AI に分ける** こと。書いた本人（同一コンテキストの AI）は自分の間違いに気づきません。**独立したサブエージェント／別セッションに diff だけを渡してレビューさせ、critical / high / medium の指摘がゼロになるまで回す。**

### 3.3 skill — 上手くいった手順を「型」として保存する

同じ流れを3回やったら skill 化のサインです。skill は「このタスクではこう進める」という手順書を、AI が自動で読み込む形で置いたものです。

- **効果**: 毎回同じ品質で回る。指示が短くなる。チームで共有できる。
- **書き方の勘所**: 手順だけでなく **「このプロジェクト固有の罠」と「機械チェックのコマンド」** を書く。人間の注意力に頼る手順は必ずすり抜けます。
- **注意**: 顧客固有の情報を含む skill を、社外・共有リポジトリに上げない（原則3）。上げる前に顧客名・システム名で grep する。

### 3.4 memory — 「調べ直すのが高い事実」だけを残す

Claude には永続メモリがあります。何でも書くと逆に精度が落ちるので、**書く対象を絞ります。**

**書くべき**

- 再調査コストが高い構造的事実（「この処理の実体は A ではなく B にある」「この2つは同名だが別物」）
- 一度ハマった罠と、その回避方法
- ユーザー／チームから受けた指示・フィードバックと **その理由**
- 「実装済みだがリリースされていない」といった、コードを読んでも分からない状態

**書かなくてよい**

- コードを読めば分かること（ファイル構成、関数の役割）
- git 履歴に残っていること
- そのセッションでしか使わない一時情報

**重要**: メモリは書かれた時点の事実です。**ファイル名・行番号・フラグ名を含むメモリは、使う前に現コードで存在確認する。**

### 3.5 サブエージェント — 役割を分けて使う

1つの AI に全部やらせず、目的別に分けると精度とコストが両方改善します。

| 役割 | 用途 | ポイント |
|---|---|---|
| **探索役** | 「どこにあるか」の列挙。定義箇所、呼び出し元、該当ファイル一覧 | 判断させない。file:line の一覧だけ返させる。軽いモデルで十分 |
| **反証役** | 1つの主張を **壊す** ためだけにコードを読む | 1回につき主張は1つ。複数あるなら並列に投げる。強いモデルを使う |
| **レビュー役** | diff に対する独立レビュー | 実装したセッションとは分ける |

標準で用意されているサブエージェントを使ってもよいですし、役割ごとに自分で定義しても構いません。**重要なのは「調べる係」「疑う係」「作る係」を混ぜないこと** です。

**副次効果**: 大量の grep 出力・ファイル全文を親セッションに持ち込まずに済むため、コンテキストが汚れません。

### 3.6 hooks — 人間の注意力に頼らない仕組みを作る

繰り返し起きるミスは、注意ではなく **自動チェック** で潰します。Claude Code には hooks（特定のタイミングでコマンドを走らせる仕組み）があり、例えばこういうことができます:

- **完了主張の検証**: AI が「テストが通った」と言ったのに、直前に実際のテストコマンドを実行した形跡が無ければ差し戻す
- **要約時の情報保全**: 長いセッションが圧縮されるとき、「file:line 根拠」「live/dead 判定とその根拠」「PR 番号」「合意したスコープ」「否定済みの仮説」は原文のまま残すよう指示する
- **危険操作の遮断**: 特定コマンドを実行前に止める

新人のうちは自分で書く必要はありません（チームに用意されていれば従ってください）。ただし **「同じミスを2回したら、仕組みで防げないか考える」** という発想は最初から持ってください。これは hooks に限らず、CI・lint ルール・チェックリストでも同じことです。

### 3.7 コンテキスト管理

- 長いセッションは要約（compact）されます。要約時に **判断の根拠が落ちる** のが一番怖い。重要な結論は md ファイルに書き出しておく。
- 話題が変わったらセッションを分ける。1セッションに詰め込むと、無関係な過去の文脈が判断を歪めます。
- 過去セッションは復帰できます（`claude --resume <セッションID>`）。ただし **当時の行番号は現コードで再検証** すること。

### 3.8 成果物の置き場所と命名を決めておく

AI に作らせた md が散乱すると、どれが最新か分からなくなります。**置き場所と命名はチームで決め（→ 2.8）、正書（`CLAUDE.md` / `AGENTS.md`）に書いて AI にも守らせる。** 決めるべきは「どこに置くか」「どう名付けるか（PR 番号・チケット ID を含めると迷わない）」「改版のルール（旧版を消さない）」の3点だけです。

## Part 4 — アンチパターン集

新人が実際にやりがちな失敗です。ひとつでも身に覚えがあれば Part 2 に戻ってください。

| # | アンチパターン | 何が起きるか | 対処 |
|---|---|---|---|
| 1 | 生成された diff を読まずに commit する | 意図しない変更・デバッグコード・無関係なファイルが混入 | `git diff` を全部読む。読めない量なら分割させる |
| 2 | 「動きました」を実行せずに信じる | ステージングで初めて壊れる | 実行ログを見るまで完了扱いしない（2.4） |
| 3 | grep 1回で「使われていない」と断定する／過去のメモの行番号をそのまま使う | 死にコードだと思って直したら本番が壊れる／存在しない行を根拠に設計する | 呼び出し経路を辿る。実物を叩く。現コードで再検証（2.2） |
| 4 | 一度に「調査から PR まで」を投げる | どこで判断を間違えたか分からず全部やり直し | 段階を刻む（2.1） |
| 5 | 全自動承認モードで放置して離席 | 予定外の push / 削除 / 外部送信 | 自動承認する操作の範囲を絞る。取り消しがきかない操作が起きうる場面では使わない（原則2・原則5） |
| 6 | 外部から取り込んだテキストを無検証で処理させる | プロンプトインジェクション | 読む工程と実行できる工程を分ける。実行ログを目視（原則4） |
| 7 | 実データ（顧客名簿・本番 CSV）をそのまま読ませる | 情報漏えい | ダミーに置き換えてから渡す。ID だけでは不十分（原則3） |
| 8 | 動いたので、セキュリティ観点で読まずに PR を出す | injection・認可漏れ・キー直書きが顧客システムに入る | 機能とは別のパスで diff を読む（2.9） |
| 9 | AI が挙げたパッケージ・出所不明のコードの塊をそのまま取り込む | 実在しない名前を攻撃者が先に登録している／OSS ライセンス違反で納品差し戻し | レジストリで実在と素性を確認。出所不明は自分で書き直す（2.10） |
| 10 | PR 本文を最初に書かせたまま放置 | 実装と説明が食い違い、レビューで指摘される | 実装が変わったら本文も直す（2.5） |
| 11 | AI の説明が理解できないまま先に進む | 障害時に説明できない | 分かるまで聞く。それでも分からなければ人間に聞く |
| 12 | 同じ失敗が続いても、指示を足して回し続ける | 差分が汚れたまま時間だけ溶ける | 3回で止める。差分を捨てて前提から確認し直す（2.3） |
| 13 | 「AI がそう言ったので」と報告する／失敗を報告せず取り繕う | 信用を失い、傷が深くなる | 責任は自分にある（原則1）。事実をそのまま出す（2.4・2.11） |

## 最後に

AI を使うと、**コードが出てくる速度は上がりますが、それが正しいと確かめる速度は上がりません。** したがって仕事のボトルネックは「書くこと」から「確かめること」へ移ります。

上達した人とそうでない人の差は、プロンプトの上手さではありません。**確かめる仕組みをどれだけ持っているか** です。

- 根拠を file:line で要求する
- 結論を反証させる
- 完了主張に実行ログを要求する
- 同じミスを2回したら仕組みで止める

この4つを習慣にしてください。

`調査 → 実装 → レビュー → リリース` の各フェーズに対応する skill／手順書を列挙します（3.2・3.3）。案件特化版と汎用版が両方あるなら併記し、どちらを使うかを明記します。

### A.3 この案件で必ず踏む地雷（先に知っておく）

「AI が平気で間違えるが、この案件では致命的」なものを先に書きます。典型的に書くべき種類:

- **出力キャッシュ・CDN** — コードを直しても旧出力が返る経路と、その確認方法（キャッシュ更新パラメータ・端末種別ごとの分割など）
- **配信物と素描画の差** — 開発環境のプレビューでは出ないが、本物の配信 HTML では出る不具合の有無と確認手段
- **端末判定** — レスポンシブではなく UA 判定で別 HTML を出しているか。その場合の検証方法
- **死にコード・旧世代実装の残存** — grep のヒット＝現役ではない領域と、live 判定の方法（2.2）
- **言語・ランタイムのバージョン制約** — 使えない構文（AI は新しい構文を平気で書く）と、機械チェックの方法
- **リポジトリ構成の罠** — submodule／monorepo／fork と upstream の多重リモートなど。CLI で必ず明示すべきオプション
- **ブランチ運用** — 「実装済み ≠ リリース済み」になる構造（feature ブランチにしかない実装の扱い）

### A.4 環境（本案件における 原則2 / 2.8 の具体形）

- AI の実行環境（コンテナ／VM／専用アカウント）と、**AI から見える範囲・見えない範囲**
- ホスト側でしかできない操作（Docker 操作・ブラウザでの実機確認など）と、その担当が人間であること
- 共有環境・クラウドへの変更が **対話式**（AI は実行しない）であること（2.7）
- 着手時に「向き先」を確認するコマンド（例: `gcloud config list`、`git remote -v`、`kubectl config current-context`）

### A.5 成果物の置き場所（本案件における 3.8 の具体形）

```
<レビュー報告書の置き場所>/<命名規則>     ← 再レビューは同一ファイルで版を上げる
<調査報告書の命名規則>                    ← 改版はサフィックスで区別。旧版は消さない
<再現手順・依頼書などの命名規則>
```

決めるのは「どこに置くか」「どう名付けるか（PR 番号・チケット ID を含める）」「改版のルール（旧版を消さない）」の3点です。

### A.6 やってはいけないこと

- 共有 skill リポジトリ・社外に **案件固有情報を含むファイルを上げない。** 上げる前に grep すべきキーワード（顧客名・システム名・ドメイン・環境名）をここに列挙しておく。
- 保護されたブランチへの force push。やむを得ない場合の手順（保護解除 → 作業 → **即座に**復帰 → 確認）と、その手順書の場所。
- 顧客環境・共有開発環境への AI による直接操作（原則2・2.7）。
