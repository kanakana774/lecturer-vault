# 通しの流れ

## 目的

> ### AIに書かせたコードの品質を、自分で担保できるようにする。

対象は**3か月目の新人**。題材は**2か月目と同じ Todo API**（Java 21 / Spring Boot 3.4.1 / MyBatis）。
**実装するのはAI。研修生がやるのは、コンテキストを整えて、委任して、検証すること。**

---

## 全体

```
【前提】 ガバナンス ── 理解度テストに合格 → 本編

【本編】
  入口（自分）        →      中（AI）      →     出口（自分）
  A 入力を整える            B 任せる           C 確かめる
   （半日）                 （半日）           （半日）
```

| 段 | やること | 提出物 |
|---|---|---|
| **⓪ ガバナンス** | 客先ルール・渡してよいもの・記録・PRでの明示 | **理解度テスト合格** |
| **A 入力を整える** | 配られたものを、AIに渡せる状態にする | **設計書の差分／`テストケース一覧.md`／`確認事項.md`** |
| **B 任せる** | 1コミットずつ、4手を回す | **作業ブランチ（7コミット）／増えた `確認事項.md`** |

| **評価** | 議論を返す。そのあと模範アプローチを示す | — |

**各段の提出物が、次の段の入力になる。**

### 手順

| | やること | 出るもの |
|---|---|---|
| **A-1 確認** | 配られたものを見る（何があるか・`CLAUDE.md` に何が書いてあるか・要件定義書とアーキ図を通読） | — |

**A-3 のケースは、1件ごとに「入力・事前状態・期待する結果」。**
**`機械` か `目視` かの判定と、設計書のどこから来たかの根拠を添える。**
**★根拠が書けないケースは、そこの仕様がまだ決まっていない** → **A-2 へ戻る。**

**★抜け漏れチェックの模範アプローチ:** **別のAIにケース一覧をレビューさせる。**
**★理解が怪しいケースは、AIに設計書の該当箇所を引かせる。**丸呑みを防ぐ。

**★やり方は指定しない。** アプローチは無数にある。**どう辿ったかを、あとで議論する。**

## B 任せる（半日）

**A でケース一覧に合意している。** B は**1コミットずつ、4手を回すだけ。**

|     | やること | 誰が |
| --- | --- | --- |
| ① | **そのコミットで満たすケースを、`テストケース一覧.md` からテストに書く**（実装ではなく仕様から書く） | AI |
| ② | **実装前に `mvn test` を走らせ、①のテストが失敗する出力を見せる** | AI |
| ③ | **実装する。①のテストは変えない**（変える必要が出たら、変えずに理由を報告する） | AI |
| ④ | **`mvn test` と `mvn checkstyle:check` を通してコミットする** | AI |

**7コミット**: 土台（Entity・Form・Query）→ Tag（CRUD 5本）→ Todo（`POST` → `GET(1件)` → `GET(一覧)` → `PUT` → `DELETE`）

- **auto を使ってよい。ただし取り消しがきかない操作では使わない**（コミット・ファイル削除・DB操作）。**`settings.json` の `ask` がその線を引いている**
- **4手は `CLAUDE.md` に書いて渡す。** 研修生から見える手数を増やさない
- **リモートはまだ足さない。** 提出は C-5

### 設計から逸れたら、設計書に書き戻す

> **設計書と違う実装にしたら、設計書を直し、`確認事項.md` に1行足してから報告してください（「いつ」列は `実装中`）。**

**「いつ」が `実装中` の行が、そのまま「AIが設計から逸れた箇所」。**
**⚠ 逸れたものは全部上げる。「自分で決めてよい逸脱」は無い。**

**提出物: 作業ブランチ（7コミット）＋ 増えた `確認事項.md`**

## C 確かめる（半日）

| | 何をするか |
|---|---|
| **C-1** | **`git diff` で変更範囲を確認する**（**実装計画の「変更するファイル」が参照点**） |
| **C-2** | **テストケース一覧と突き合わせる**（`目視` の行と DoD 9項目が作業リスト）＋**講師が指定した「テスト」行を1〜2件、実装を壊して赤になるか確かめる** |
| **C-3** | **問いに答える**（AIが仕様に無いことを独自に決めた箇所はどこか、など）。**拾った逸脱は、設計書と `確認事項.md` に自分で書き足す** |
| **C-4** | **別セッションのAIに自分の成果物をレビューさせ**、正しい／的外れ／判断できない に仕分ける |
| **C-5** | **リモートを足して push → PR を作り、セルフレビューする** |

**★C-2 の指定は講師がする。** 分岐か異常系を含む行から選ぶ。自分で選ばせると、通りやすい行を選べる。

**★C-4 は検証ではなく、A の答え合わせ。** **「的外れ」の数が、そのまま A で渡し漏れた情報の量**になる。

**⚠ C-4 は C-5 より先。** 逆にすると、**セルフレビューのコメントをAIが読んだ状態**になる。
**⚠ C-4 は検証手段に数えない。** 同じ資料を読むので同じ誤読をするし、**渡していない情報は原理的に見えない**。

### テストコードは読ませない。壊して確かめる

> **指定された「テスト」行に対応する実装を1行壊し、`mvn test` を走らせる。**
> **赤にならなければ、そのテストは何も検証していない。**

**新しい道具はゼロ**（`mvn test` と `git checkout .` だけ）。**判定は機械的**（赤か緑か）。

**なぜ読ませないのか:** **人の手抜きは荒れて見えるが、AIの取り違えは自然で一貫して見える。**
**「読んで違和感がない」は、正しさの証拠にならない。**

**提出物: `検証記録.md` ＋ PR（セルフレビュー済み）**

| | 測り方 |
|---|---|

| 段 | 講師の役 |
|---|---|
| **⓪** | 講義 ＋ 理解度テスト |

> [!warning]- 実測: 12件のうち6件で即答できなかった（2026-09-04・講師の試走）
> **詰まり方が2種類ある。**
>
> | | 例 | 対処 |
> |---|---|---|
> | **決めればいいだけ** | `version` の初期値／型変換失敗時のステータス／`%` `_` のエスケープ | **事前に決めておく** |

> **講師はまず「その指摘が正しいか」を判定する必要がある。**答えを用意しておくだけでは足りない。

> **`tags` の重複IDの扱いも決まった**（「複合キーにしたら、どのみち当たる」）。独立した12件ではない。
