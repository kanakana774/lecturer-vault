# 通しの流れ

## 目的

> ### AIに書かせたコードの品質を、自分で担保できるようにする。

対象は**3か月目の新人**。題材は**2か月目と同じ Todo API**（Java 21 / Spring Boot 3.4.1 / MyBatis）。
**実装するのはAI。研修生がやるのは、コンテキストを整えて、委任して、検証すること。**

---

## 全体

```
【前提】 ガバナンス ── 理解度テストに合格 → 本編

【本編】
  入口（自分）        →      中（AI）      →     出口（自分）
  A 入力を整える            B 任せる           C 確かめる
   （半日）                 （半日）           （半日）
```

| 段 | やること | 提出物 |
|---|---|---|
| **⓪ ガバナンス** | 客先ルール・渡してよいもの・記録・PRでの明示 | **理解度テスト合格** |
| **A 入力を整える** | 配られたものを、AIに渡せる状態にする | **設計書の差分／`受入条件.md`／`確認事項.md`** |
| **B 任せる** | 1コミットずつ、4手を回す | **作業ブランチ（7コミット）／増えた `確認事項.md`** |
| **C 確かめる** | 動いた、ではなく正しいと言える形にする | **`検証記録.md`／PR（セルフレビュー済み）** |
| **評価** | 議論を返す。そのあと模範アプローチを示す | — |

**各段の提出物が、次の段の入力になる。**

⚠ **A・B・C で 1.5日。1週間のうち残りの配分は未決。**

---

## 必要なもの

**全部、講師が用意する。**

```
todo-app-api/                    ← 実装が入る
├── CLAUDE.md                    AIへの指示。規約・DoD 9項目・B の4手・ローカル前提・
│                                「推測せず全部聞いて」。★意図を研修生に説明する
├── .claude/settings.json        AIに許す操作の範囲。触らない
├── pom.xml ／ todo_checks.xml   2か月目と同じ ＋ checkstyle
└── src/
     ├── 2か月目の雛形そのまま   空フォルダ・共通例外・SecurityConfig・testTools
     └── 参照実装1本             Todo 1件取得の完成品 ＋ 統合テスト1本

todo-app-api-docs/               ← ★研修生が書き戻す（読むだけではない）
├── 要件定義書・アーキ図・DB定義書・OpenAPI・エラーコード表・プログラム設計
│                                ★実物のまま。矛盾も記載漏れも入っている
├── 受入条件.md                  ★空の雛形。「対象外」節つき（提出物）
└── 確認事項.md                  ★空の雛形。A・B・C で行が増える（提出物）

（リポジトリの外）検証記録.md      ★問い記入済みの雛形。AIに渡さない（提出物）

（リモートは C-5 で足す）          A・B の間は GitHub を見せない
```

> ### ★ もうひとつ、**仕様管理者役（講師）がその場にいて、聞けば答える**こと。
> **これが無いと A が回らない。**だから**「聞かれたら何と答えるか」を先に用意しておく**必要がある。

**★決まったことは設計書に書き戻す。`確認事項.md` に残るのは「聞いた事実」だけ。**
**書き戻し先が設計書なのは A・B・C とも同じ。**違うのは書く人で、**B はAI、A と C は自分**。

雛形の実例は `12_研修の流れ_説明用.md`。

---

## ⓪ ガバナンス — 前提

**答えがあるので、教えて、測って、終わらせる。**

1. 客先のルールを確認する
2. 渡してはいけないものを渡さない
3. 何を渡したか記録する
4. AIに書かせた部分を PR で明示する

**理解度テストに合格して、次に進む。**

---

## A 入力を整える（半日）

**課題で配られるもの**と、**AIに最終的に渡すもの**は別物。**その差分を作るのが A。**

### 達成しておくこと

**道具の話の前に、これが目的。**

| | 達成しておくこと | 誰が |
|---|---|---|
| **1** | **合格の基準** — 何が満たされれば正しいか（**設計書 ＋ DoD から**） | **研修生** |
| **2** | **入力の確定** — 矛盾・記載漏れを潰し、**設計書を直す** | **研修生** |
| **3** | **範囲** — やらないこと・触ってよい場所 | 配布時点で揃っている |
| **4** | **制約** — 規約・DoD・ローカル前提が、AIが読む場所にある | 配布時点で揃っている |

**研修生がやるのは 1 と 2。** 3・4 は `受入条件.md` の「対象外」節と `CLAUDE.md` に入っているので、**確認するだけ。**

> **実装前の作業は「早くやるため」ではなく、「汚染される前に固定するため」。**
> **実装を見てから基準を作ると、必ず実装に寄る。**

### ゴール

> ### **AIに「独断で決めることになる事項」を挙げさせて、もう出てこない。**

**ゼロを数えるのではなく、「もう一周聞いても新しいものが出ない」で判定する。**
**研修生が自分でその場で確かめられて、講師の主観が入らない。**

### 手順

| | やること | 出るもの |
|---|---|---|
| **A-1 確認** | 配られたものを見る（何があるか・`CLAUDE.md` に何が書いてあるか） | — |
| **A-2 確定** | **AIに穴を出させ、講師に聞き、設計書を直す** | **直った設計書**／`確認事項.md` |
| **A-3 合格基準** | **受入条件を作る**（設計書から ＋ **DoD から**） | `受入条件.md` |
| **A-4 判定** | **AIに「独断で決めることは何か」と聞く** | **出たら A-2 へ戻る。出なければ B へ** |

**A-2 ⇄ A-3 も往復する。** **受入条件が書けない箇所は、そこの仕様がまだ決まっていない**という検出器になる。

**★やり方は指定しない。** アプローチは無数にある。**どう辿ったかを、あとで議論する。**

### 穴の出どころは3つ。A-2 で全部拾う

| | 例 |
|---|---|
| **資料どうしの食い違い** | content は要件定義30／DB定義100 |
| **どこにも書いていない** | Tag削除時の `todo_tag`、部分一致の `%` `_` |
| **★フレームワークの既定が決めてしまう** | 重複行の畳み込み・全フィールド出力・30文字の数え方・空白1文字 |

**★3つ目は資料を突き合わせても出ない。** 設計書に書いていないから突き合わせようがない。
**AIに直接聞かないと出てこない。**

### 何が揃った状態になるか

| 問い | 置き場 | 配られた状態 | **B開始時** |
|---|---|---|---|
| **何を作るか** | 設計書 | 矛盾・記載漏れあり | **矛盾が消え、答えが書き戻されている** |
| **どうなれば完了か** | `受入条件.md` | 空の雛形 | **埋まっている。検証手段付き** |
| **どこまでやるか** | `受入条件.md` の「対象外」節 | 配布済み | **確認した** |
| **どう作るか** | `CLAUDE.md` | 配布済み | **意図を理解した** |

**提出物: 設計書の差分 ＋ `受入条件.md` ＋ `確認事項.md`（全行、回答済み）**

---

## B 任せる（半日）

**A-4 で実装計画は承認済み。** B は**1コミットずつ、4手を回すだけ。**

|     | やること | 誰が |
| --- | --- | --- |
| ① | **そのコミットで満たす受入条件を、テストに書く**（実装ではなく仕様から書く） | AI |
| ② | **実装前に `mvn test` を走らせ、①のテストが失敗する出力を見せる** | AI |
| ③ | **実装する。①のテストは変えない**（変えたいときは変えずに理由を報告） | AI |
| ④ | **`mvn test` と `mvn checkstyle:check` を通してコミットする** | AI |

**7コミット**: 土台（Entity・Form・Query）→ Tag（CRUD 5本）→ Todo（`POST` → `GET(1件)` → `GET(一覧)` → `PUT` → `DELETE`）

- **auto は禁止。** ステップごとに承認させる（流れを見せるため）
- **4手は `CLAUDE.md` に書いて渡す。** 研修生から見える手数を増やさない
- **リモートはまだ足さない。** 提出は C-5

### 設計から逸れたら、設計書に書き戻す

> **設計書と違う実装にしたら、設計書を直し、`確認事項.md` に1行足してから報告してください（いつ＝B）。**

**「いつ＝B」の行が、そのまま「AIが設計から逸れた箇所」。**
**⚠ 逸れたものは全部上げる。「自分で決めてよい逸脱」は無い。**

**提出物: 作業ブランチ（7コミット）＋ 増えた `確認事項.md`**

---

## C 確かめる（半日）

| | 何をするか |
|---|---|
| **C-1** | **`git diff` で変更範囲を確認する**（`受入条件.md` の「対象外」節が参照点） |
| **C-2** | **受入条件と突き合わせる**（「目視」行が作業リスト）＋**「テスト」行を1〜2件、実装を壊して赤になるか確かめる** |
| **C-3** | **問いに答える**（AIが仕様に無いことを独自に決めた箇所はどこか、など）。**拾った逸脱は、設計書と `確認事項.md` に自分で書き足す** |
| **C-4** | **別セッションのAIに自分の成果物をレビューさせ**、正しい／的外れ／判断できない に仕分ける |
| **C-5** | **リモートを足して push → PR を作り、セルフレビューする** |

**⚠ C-4 は C-5 より先。** 逆にすると、**セルフレビューのコメントをAIが読んだ状態**になる。
**⚠ C-4 は検証手段に数えない。** 同じ資料を読むので同じ誤読をするし、**渡していない情報は原理的に見えない**。

### テストコードは読ませない。壊して確かめる

> **受入条件の「テスト」行から1〜2件選び、対応する実装を1行壊して `mvn test` を走らせる。**
> **赤にならなければ、そのテストは何も検証していない。**

**新しい道具はゼロ**（`mvn test` と `git checkout .` だけ）。**判定は機械的**（赤か緑か）。

**なぜ読ませないのか:** **人の手抜きは荒れて見えるが、AIの取り違えは自然で一貫して見える。**
**「読んで違和感がない」は、正しさの証拠にならない。**

**提出物: `検証記録.md` ＋ PR（セルフレビュー済み）**

## 評価

| | 測り方 |
|---|---|
| **ガバナンス** | **理解度テスト。合格が必要** |
| **A** | **アプローチを議論する。**成果物の正しさは測らない |
| **B** | 逸れた箇所を全部上げたか（`確認事項.md` の「いつ＝B」の行） |
| **C** | **検証記録とPRを読んで、議論を返す** |

**添削はしない／評価はする／議論はする。**

**議論の材料は C で数として出る。**

| A が甘いと | どこに出るか |
|---|---|
| **入力の確定が甘い** | `確認事項.md` の「いつ＝B」が増える |
| **合格の基準が甘い** | 検証手段の無い受入条件が出る |
| **渡し漏れがある** | C-4 の「的外れ」が増える |

**議論のあとに、模範アプローチ（一例）を示す。** 事前に配ればなぞるだけになる。

## 講師がやること

| 段 | 講師の役 |
|---|---|
| **⓪** | 講義 ＋ 理解度テスト |
| **A** | **★仕様管理者役。**聞かれたら答え、矛盾を裁定する。**ここが一番負荷が高い** |
| **B** | 見守る |
| **C** | 見守る |
| **評価** | **議論を返す** ＋ **模範アプローチを示す** |

**★A の前に「聞かれたら何と答えるか」を用意しておく。** 用意していないと、研修生の質問で講師が止まる。
