# 通しの流れ

## 目的

> ### AIに書かせたコードの品質を、自分で担保できるようにする。

対象は**3か月目の新人**。題材は**2か月目と同じ Todo API**（Java 21 / Spring Boot 3.4.1 / MyBatis）。
**実装するのはAI。研修生がやるのは、コンテキストを整えて、委任して、検証すること。**

---

## 全体

```
【前提】 ガバナンス ── 理解度テストに合格 → 本編

【本編】
  入口（自分）        →      中（AI）      →     出口（自分）
  A 入力を整える            B 任せる           C 確かめる
   （半日）                 （半日）           （半日）
```

| 段 | やること | 提出物 |
|---|---|---|
| **⓪ ガバナンス** | 客先ルール・渡してよいもの・記録・PRでの明示 | **理解度テスト合格** |
| **A 入力を整える** | 配られたものを、AIに渡せる状態にする | **設計書リポの差分／`確認事項.md`／`受入条件.md`** |
| **B 任せる** | 1コミットずつ、4手を回す | **作業ブランチ（7コミット）／増えた `確認事項.md`** |
| **C 確かめる** | 動いた、ではなく正しいと言える形にする | **`検証記録.md`／PR（セルフレビュー済み）** |
| **評価** | 議論を返す。そのあと模範アプローチを示す | — |

**各段の提出物が、次の段の入力になる。**

⚠ **A・B・C で 1.5日。1週間のうち残りの配分は未決**（`13_議事録/` の未決参照）。

## ⓪ ガバナンス — 前提

**答えがあるので、教えて、測って、終わらせる。**

1. 客先のルールを確認する
2. 渡してはいけないものを渡さない
3. 何を渡したか記録する
4. AIに書かせた部分を PR で明示する

**理解度テストに合格して、次に進む。**

---

## A 入力を整える（半日）

**課題で配られるもの**と、**AIに最終的に渡すもの**は別物。**その差分を作るのが A。**

### 達成しておくこと — 5つ

**道具の話の前に、これが目的。**

| | 達成しておくこと | 種別 |
|---|---|---|
| **1** | **合格の基準**（何が満たされれば正しいか ＋ 期待値をどこから取るか） | **あとから作ると汚染される** |
| **2** | **範囲**（やらないこと・触ってよい場所） | **あとから作ると汚染される** |
| **3** | **書けなくなる未決の決着。矛盾は設計書を直して消す** | **決まらないと書けない** |
| **4** | **決まらなかったことの一覧** | **あとから作ると汚染される** |
| **5** | **制約が、AIが読む場所にある**（一般解から外れるところだけ） | **決まらないと書けない** |

> **実装前の作業は「早くやるため」ではなく、「汚染される前に固定するため」。**

### 手順

| | 何をするか |
|---|---|
| **A-1** | **配られたものを確認する**（設計書一式・`CLAUDE.md`・雛形2つ） |
| **A-2** | **AIに渡す形に更新する**（矛盾・未決は仕様管理者に確認し、**設計書を直す**） |
| **A-3** | **AIに聞いて、決まっていない箇所を洗う**（＝**B に進んでよいかの判定**） |

**★やり方は指定しない。** アプローチは無数にある。**どう辿ったかを、あとで議論する。**

### A-3 でやること

1. **「実装するとして、あなたが独断で決めることになる事項を列挙して。実装はしないで」**
2. **新しいセッションで、渡すものだけを見せて実装計画を出させる**
   （4節: **変更するファイル／作業の順序／リスク／証明**）
3. **3つ詰問する** — **「何が壊れうるか／どの手が一番危ないか／捨てた代替案は何か」**
4. **AIが自分で決めた箇所を、1つずつ処理する**

### B に進んでよい状態

> ### **配ったものだけを見た別のAIが、実装計画を書ききれる。**
> ### **そのとき、AIが自分で決めた箇所を、全部把握している。**

| | 何が言えればよいか |
|---|---|
| **計画** | **4節が埋まり、「証明」の各行が受入条件のどれかを指している** |
| **決めた箇所** | **全部挙がり、それぞれ「聞いて設計書を直した」か「決まらないと知って進む」になっている** |

**「決まらないと知って進む」に入るのは2つだけ** — **その場で決まらなかったもの**（研修では稀）と、**時間切れ**。
**矛盾はここに入れない。聞いて設計書を直して消す。**

**時間はゴールではなく歯止め。** 半日で届かなければ、残りを全部「決まらないと知って進む」にして B に行く。

### 何が揃った状態になるか

| 問い | 置き場 | 配られた状態 | **B開始時** |
|---|---|---|---|
| **何を作るか** | 設計書 | 矛盾・未決あり | **矛盾が消え、答えが書き戻されている** |
| **どう作るか** | `CLAUDE.md` | 規約・DoD の雛形 | **意図を理解し、足りない前提を足した** |
| **どこまでやるか** | `受入条件.md` の「対象外」節 | 空 | **やらないことが書いてある** |
| **どうなれば完了か** | `受入条件.md` | 空の雛形 | **埋まっている。検証手段付き** |

**そして本人が「渡していないものは何か」を言える**（`確認事項.md`）。

**提出物: 設計書リポの差分 ＋ `確認事項.md` ＋ `受入条件.md`**

---

## B 任せる（半日）

**A-3 で実装計画は承認済み。** B は**1コミットずつ、4手を回すだけ。**

|     | やること | 誰が |
| --- | --- | --- |
| ① | **そのコミットで満たす受入条件を、テストに書く**（実装ではなく仕様から書く） | AI |
| ② | **実装前に `mvn test` を走らせ、①のテストが失敗する出力を見せる** | AI |
| ③ | **実装する。①のテストは変えない**（変えたいときは変えずに理由を報告） | AI |
| ④ | **`mvn test` と `mvn checkstyle:check` を通してコミットする** | AI |

**7コミット**: 土台（Entity・Form・Query）→ Tag（CRUD 5本）→ Todo（`POST` → `GET(1件)` → `GET(一覧)` → `PUT` → `DELETE`）

- **auto は禁止。** ステップごとに承認させる（流れを見せるため）
- **4手は `CLAUDE.md` に書いて渡す。** 研修生から見える手数を増やさない
- **リモートはまだ足さない。** 提出は C-5

### 設計から逸れたら、設計書に書き戻す

> **設計書と違う実装にしたら、設計書を直し、`確認事項.md` に1行足してから報告してください（いつ＝B）。**

**「いつ＝B」の行が、そのまま「AIが設計から逸れた箇所」。**
**⚠ 逸れたものは全部上げる。「自分で決めてよい逸脱」は無い。**

**提出物: 作業ブランチ（7コミット）＋ 増えた `確認事項.md`**

---

## C 確かめる（半日）

| | 何をするか |
|---|---|
| **C-1** | **`git diff` で変更範囲を確認する**（`受入条件.md` の「対象外」節が参照点） |
| **C-2** | **受入条件と突き合わせる**（「目視」行が作業リスト）＋**「テスト」行を1〜2件、実装を壊して赤になるか確かめる** |
| **C-3** | **問いに答える**（AIが仕様に無いことを独自に決めた箇所はどこか、など） |
| **C-4** | **別セッションのAIに自分の成果物をレビューさせ**、正しい／的外れ／判断できない に仕分ける |
| **C-5** | **リモートを足して push → PR を作り、セルフレビューする** |

**⚠ C-4 は C-5 より先。** 逆にすると、**セルフレビューのコメントをAIが読んだ状態**になる。
**⚠ C-4 は検証手段に数えない。** 同じ資料を読むので同じ誤読をするし、**渡していない情報は原理的に見えない**。

### テストコードは読ませない。壊して確かめる

> **受入条件の「テスト」行から1〜2件選び、対応する実装を1行壊して `mvn test` を走らせる。**
> **赤にならなければ、そのテストは何も検証していない。**

**新しい道具はゼロ**（`mvn test` と `git checkout .` だけ）。**判定は機械的**（赤か緑か）。

### A で印をつけた行と突き合わせる

| | 意味 |
|---|---|
| **A で「未回答」にした穴に、B の逸脱が当たっていた** | **認識できていた** |
| **印をつけていない箇所で AI が決めていた** | **A で見えていなかった穴** |

**提出物: `検証記録.md` ＋ PR（セルフレビュー済み）**

---

## 評価

| | 測り方 |
|---|---|
| **ガバナンス** | **理解度テスト。合格が必要** |
| **A** | **アプローチを議論する。**成果物の正しさは測らない |
| **B** | 逸れた箇所を全部上げたか（`確認事項.md` の「いつ＝B」の行） |
| **C** | **検証記録とPRを読んで、議論を返す** |

**添削はしない／評価はする／議論はする。**

**議論の材料は C で数として出る。**

| A が甘いと | どこに出るか |
|---|---|
| **何を作るかが曖昧** | `確認事項.md` の「いつ＝B」が増える |
| **完了条件が曖昧** | 検証手段の無い受入条件が出る |
| **渡し漏れがある** | C-4 の「的外れ」が増える |

**議論のあとに、模範アプローチ（一例）を示す。** 事前に配ればなぞるだけになる。
