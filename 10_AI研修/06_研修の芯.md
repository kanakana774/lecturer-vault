## 目的（一文）

> ### AIで作ったものを、自分の名前で出せるようにする。

SES では客先に**自分の名前で**成果物を出す。AIが書いたものでも変わらない。

---

## なぜ品質が落ちるか — 理解モデル

```
L1  仕様（入力）                    ← 仕様管理者が持つ
 │                                        ↑
 │ 読む                     考慮漏れ・矛盾を上げる／自分で決めたことを返す
 ↓                                        │
L2  変換 ──→ 実装（出力）            ← ジュニアが持つ
     誤読 / 独断 / 読み漏らし
```

**L1 は「仕様書」ではなく、与えられたもの全部。** 既存コード・DDL・実行基盤の既定も入力。

| どこ | 何が起きるか | 誰が担保するか |
|---|---|---|
| **L1 の欠陥** | **考慮漏れ**（実装しないと気づかない）／**矛盾**（資料どうしが食い違う） | 仕様管理者。**だが本人は気づいていない** |
| **L2 の変換** | **誤読**（書いてあるのに違う意味に取った）／**独断**（書いていないことを勝手に決めて足した）／**読み漏らし**（そこにあるのに読まなかった） | 実装者 |

**SESでは L2 がジュニアの担当。だが L1 に返す責任も本人にある。**

| 返すもの | 返さないとどうなるか |
|---|---|
| **L1 の欠陥** | **仕様管理者は、自分の仕様に穴があることを知らないまま** |
| **L2 で自分が決めたこと** | **仕様管理者は、自分の仕様が実質変わったことを知らないまま** |

**上位者は設計を把握しているが、そこから逸れたことは把握していない。** 説明を求められるのも、そもそも上げるかどうかを決めるのも本人。

### 決めなければ、フレームワークが決める

**L1 の考慮漏れは「決まらないまま」では終わらない。必ず何かが決める。そして誰も担保していない。**

実測で出た5件は、**すべて「仕様が決めていなかった」ことの現れ方**だった——重複行の畳み込み（MyBatis の既定）／レスポンスに全フィールドが出る（Jackson の既定）／「30文字」の数え方（Java の既定）／型不一致で 500（既存の共通例外）／空白1文字が通る（バリデーションの既定）。

### AIに任せると、実装者の内心が聞ける

**誤読か独断かは、実装したAIに聞けば分かる。** 人間より判定しやすい。
**ただし聞かなければ言わない。** だから「聞く」が作業として要る。

## 構造 — A 決める / B 任せる / C 確かめる

```
入口（自分）      →      中（AI）      →      出口（自分）
 A 決める                B 任せる            C 確かめる
```

| | 到達した状態 | 代表語 |
|---|---|---|
| 前提 **⓪ ガバナンス** | **使ってよいかを、自分で判断できる** | NDAと第三者開示／コピーレフト |
| **入口 A 決める** | **何が決まっていないかを分かっていて、決めることと聞くことを着手前に仕分けている** | 確認事項／受入条件／完了の定義（DoD） |
| 中 **B 任せる** | **任せた仕事の流れが、見えている** | ステップ承認／テストを仕様から書く |
| **出口 C 確かめる** | **動いた、ではなく、正しいと言える。出せない部分は、出せないと言える** | 動いた≠正しい／説明責任／エスカレーション |

実装が速くなった分、価値は**入口（何を作るか）と出口（保証できるか）**に移った。
**新人の仕事が上流に「昇格」するのではなく、同じ職位・同じ担当のまま、仕事の中身が入口と出口に寄る。** だから配属直後の新人にこそ先に来る。

| **3か月（この研修が狙う）** | **チケット1本を、AIを使って、自分で確認して出せる。** 保証できない部分を「判断できないので確認したい」と**言える**。**独断しないことが合格条件**で、判断の広さは求めない |

## 設計原則

1. **目的は「到達した状態」で書く。作業を書かない。** そのまま評価の文になる。「〜する」で書くと達成したか判定できない
2. **答えを配らない。** 検証に唯一の答えは無く、**講師にも無い**。だから **添削はしない／評価はする／議論はする** の3つを分ける
3. **失敗を仕込まない。** わざと情報を抜いて失敗させる演習は作らない。作為的で、AIが賢くなると成立しなくなる
4. **陳腐化するものを軸にしない。** ツール操作・プロンプト技法・モデル比較は**触るだけ**
5. **新しく教える技術をゼロにする。** 道具は全部既習（`git diff`・テスト仕様書・レビュー観点・PR）。**新規はAIへの一文だけ**
6. **提出して終わる成果物を作らない。** 各段の提出物が次の段の入力になる
7. **実装するのはAI。研修生がやるのは委任。** だから B を「実装」と呼ばない

---

## 軸にしないもの

| | 扱い |
|---|---|
| ツールの操作 | 触るだけ（半年で陳腐化する） |
| プロンプトの工夫 | **講師が配る。**研修生に考えさせない |
| コンテキストの与え方 | **経験の中で自得させる。**教える項目にしない |
| モデル比較・コスト最適化 | 扱わない（新人の裁量外） |
| **「AIはここができない」** | **軸にしない。**モデルが変われば崩れる。軸は**誰が担保するか**（`08` §10） |
| **自分の成長を守る判断**（任せる／自分でやる） | **演習にしない。**最後に一言で伝える。本人の判断だが、面接で語れる強い材料 |

---

## この構成が崩れない理由

- **理解モデルが責任の所在で切れている** — AIの能力を1つも使っていない。**AIが変換を正確にやるほど、残るのは「L1に返す仕事」だけになる**。賢くなるほど主張が強くなる
- **フェーズ非依存** — ガバナンスと検証は陳腐化しない。委任は「一周回した」事実が残る
- **ツール非依存** — 伝え方は抽象、触るのは具体。**「これはツール固有／これは普遍」をその場で言い分ける**
- **既存カリキュラムに接続** — Git（差分）／PR・レビュー（明示）／テスト仕様書からのケース洗い出し（突き合わせ）
- **AI禁止の現場でも残る** — 客先ルールの確認・仕様を読む力は、AIの可否と無関係
- **講師のAI習熟度に品質が依存しない** — 答えを配らない設計の帰結。講師の知識更新に研修の質が依存しない
