## 3. 段① 把握

**到達点**: 何が決まっていないかを、分かっている。
**目的（研修生に言う形）**: **AIに渡してよいことと、人に聞くべきことを、渡す前に分けられる。**

| | 内容 | 目安 |
|---|---|---|
| **1-1** | 環境を確認する（コードと設計書の2つが見えているか） | 10分 |
| **1-2** | **要件定義書とアーキテクチャ図を通読** → そのまま**何も渡さずAIに叩かせる** | 25分 |
| **1-3** | **「確認しないと決められないこと」をAIにリストアップさせる**（根拠つき） | 60分 |
| **1-4** | **リストを1件ずつ資料に当たって確かめ、4判定に仕分ける** | 90分 |

### 通読と参照

| | 中身 | いつ読むか |
|---|---|---|
| **通読するもの** | 要件定義書・アーキテクチャ図 | **前に読む**（全体像がないと 1-4 で判定できない） |
| **参照するもの** | DB定義書・OpenAPI・エラーコード表・プログラム設計 | **必要になったときに開く**（1-4 で根拠を書かせるので必然的に開く） |

### 提出物: Q&A票（4判定）

| 判定 | 意味 | 書かせるもの | 行き先 |
|---|---|---|---|
| **① 書いてあった** | AIの誤検出 | 資料名と場所 | 却下 |
| **② 自分で決められる** | 書かれておらず、判断してよい | こう決めた＋理由 | **2-1 で書き戻す** |
| **③ 自分では決められない** | 書かれておらず、権限や背景が要る | 誰に何を聞くか | **2-1 で聞いて回答を得る** |
| **未判定** | 手をつけていない | その理由 | — |

**迷ったら③。** 実務で困るのは、③にすべきものを②にしたとき。
**⚠ 研修生に必ず言う**: 制約が無いこと・書かれていないことを、「許可」や「決定済み」として読まない。

## 4. 段② 決定

**到達点**: 何を作るか・どうなれば完了かを、AIに触る前に確定させている。

| | 内容 | 目安 | 提出物 |
|---|---|---|---|
| **2-1** | **③を聞いて回答を得る** → **`決定事項.md` に書き戻す** → **AIに受入条件を出させる** → **自分が渡したものと照合する** | 45分 | `決定事項.md`／受入条件 |
| **2-2** | **AIに計画を出させ、5つの観点で判定してから着手させる** | 20分 | 承認した計画 |

**2-1 は「何ができたら終わりか」、2-2 は「どの順で・どのファイルを触り・どこで区切るか」。**

### 書き戻しの行き先（3種類）

| 中身 | 行き先 |
|---|---|
| **決めたこと** | **`決定事項.md`**（出所「自分の判断」） |
| **決められないこと** | **聞いて回答を得る** → `決定事項.md`（出所「確認済み」） |
| **やってはいけないこと** | **`CLAUDE.md`**（1行で「実装の前に `決定事項.md` を読むこと」も足す） |

**③の返し方は3つ**: 仕様として決まる／**「自分で決めてよい」（実務で一番多い）**／「今は決まっていない」（暫定を記録）。
**聞き方は丸投げにしない**: ①見立て ②理由 ③どこを見て無いと判断したか。

### 受入条件は3層

| 層 | 中身 | 誰が出すか |
|---|---|---|
| **DoD**（全変更に共通） | N+1を作らない／例外メッセージを外に出さない／層構成を維持／lint通す | **講師が配る**（`09_配布物/DoD.md`） |
| **受入条件**（機能ごと） | 正常系・境界値・異常系 | **AIが出す** |
| **追加分** | 決定事項から導かれる不変条件 ＋ DoDのこの機能での具体形 | **人が足す** |

### 照合の観点（2-1）

> **自分が渡した決定とDoDが、受入条件に全部反映されているか。**
> **反映されていないなら、渡し漏れか、AIの落としか。**

**受入条件を全部読まない。** 自分が渡したもの（決定事項＋DoD）を1件ずつ引く。

### 計画のレビュー観点（2-2・5つ）

① 層の順序（Entity→Mapper→Service→Controller）／② 触るファイル一覧が妥当か／③ 設計書に無い判断が混ざっていないか／④ 確認方法が書かれているか／⑤ 後戻りできる単位に割れているか

**2-2 だけが持つもの**: plan モードの体験／**触るファイル一覧＝独断の検知**／**コミット粒度＝後戻りできる単位**。

### 受入基準・DoD・品質ゲートの置き場

| | 単位 | 誰が決める | 研修での扱い |
|---|---|---|---|
| **受入基準** | 機能ごと | 仕様を持つ人＋実装者 | **AIが出し、研修生が照合して足す** |
| **完了の定義（DoD）** | 全変更に共通 | チーム | **講師が配る** |
| **品質ゲート** | CI | 組織 | `mvn checkstyle:check` と `mvn test` |

用語の整理は `08_ギャップ` 付録C。

## 5. 段③ 委任

| | 内容 | 目安 |
|---|---|---|
| **3-1** | 環境確認・課題説明・プロンプト配布 | 20分 |
| **3-2** | **仕様からテストを書かせる**（実装を書かせる前に） | 40分 |
| **3-3** | **実装させる**（ステップ承認・7コミット） | 120分 |

**流れ**: 受入条件を確定（段②）→ **テストにする** → **通るまで回す** → テストにできない条件は段④で人が見る。
**AIが実装を見てテストを書くと、実装のバグをテストが追認する。** 防ぐのは **「実装ではなく仕様からテストを書け」の一文**。
**E2Eはやらない**（フロントを触っていない）。DBUnit + JUnit の既習範囲。

### 何を用意するか（2026-08-21 に実機で確認）

| | 中身 | 状態 |
|---|---|---|
| **リポジトリ** | **AI研修用に独立させた `todo-app-api`**。出発点は空フォルダ＋例外処理・util の雛形 | ローカルに作成済み |
| **設計書** | 別リポジトリ `todo-app-api-docs`（**課題の区切りを畳んで平坦化済み**） | 同上 |
| **コーディングガイド／環境構築手順** | `04.開発資料` / `00.環境構築` | 既存 |
| **AI向け指示ファイル** | `todo-app-api/CLAUDE.md` | **未**（P3 のものを持ち込む） |
| **DoD** | `09_配布物/DoD.md` | **作成済み** |
| **テストの参照実装1本** | `testTools` はあるがテスト本体が**1本も無い**。**Controller 層で講師が書く** | **未** |
| **テスト用DBを分ける** | `main` と `test` が同じ `todo` DB を指しており、**テスト実行で動作確認データが壊れる** | **未（全員が踏む）** |
| **`pom.xml` に CheckStyle plugin** | 現状 plugin は `spring-boot-maven-plugin` のみ。**DoDが要求するので必須** | **未** |
| **テスト仕様書（ケース一覧）／DB** | 3か月目の既習資産／2か月目の環境 | 既存 |

**渡す pom は Spring Boot 3.4.1 / Java 21。** 実験（P1）でAIが書いたのは 4.0.7。**段④の「バージョン不一致」の実物。**

### 配るプロンプト

```
todo-app-api の課題ブランチに、Todo 管理 REST API の実装を追加してください。
空のフォルダに実装を埋める形です。

添付の設計書に従ってください。
- 01.要件定義/
- 02.DB設計/（DB定義書と DDL）
- 03.API設計/（OpenAPI・エラー設計書・プログラム設計）

既存のコードとフォルダ構成を確認し、それに合わせて実装してください。
設計書に書かれていないことは、書かれていないと明示してください（勝手に決めないでください）。
テストは実装ではなく仕様から書いてください。
```

### コミット粒度 — 7コミット

| # | コミット | 中身 |
|---|---|---|
| 1 | **土台** | Entity / Form / Query / Mapper インタフェース / 共通部分 |
| 2 | **Tag 5本** | Tag の CRUD（紐づけを含まないのでまとめてよい） |
| 3〜7 | **Todo 1本ずつ** | `POST` → `GET(1件)` → **`GET(一覧)`** → `PUT` → `DELETE` |

**Tag を先に置く**: Todo の登録・更新が Tag の存在チェックを要求する。
**`GET(一覧)` を5番目に置く**: **N+1がその1コミットの差分だけで見える**（設計書が「ループで取得」と明記しているので素直に書くとN+1になる）。
**ブランチは課題ブランチ1本。**「捨ててよい実験ブランチ」だけ一言触れる。

### auto は禁止

**ステップごとに承認させる。** 目的は「開発フローをイメージできるようになること」で、**auto だと流れが見えない**（実験では一度も確認を挟まず完走した）。

### ガードレールは不要（2026-08-21 解決）

**教材を2か月目リポジトリから独立させたので、模範解答も過去研修生の実装も存在しない。** カンニング経路そのものが無い。
**実務での構造の話は段⓪で使う**: 「指示ファイルで意図を伝え、レビューとCIで落とす。**強制力は権限側にしかない**」。

## 6. 段④ 検証

**答えを配らない。問いだけ渡す。**

| | 内容 | 目安 |
|---|---|---|
| **4-1** | 何を任せたか把握する（AIが読んだものと変えたものを自分で見る） | 60分 |
| **4-2** | 確かめる（**段②で確定した受入条件**と突き合わせる） | 90分 |
| **4-3** | どこまでやるかを決める | 30分 |

### 使う道具 — 新規はAIへの一文だけ

| 道具 | いつ習ったか | 何に使うか |
|---|---|---|
| `git diff` | 1か月目 | 頼んでいないファイルが変わっていないか（**コミット単位で**） |
| Postman / ThunderClient | 2か月目 | 動かして叩く |
| CheckStyle / SonarLint | 2か月目 | 規約違反。**CheckStyle は AI にも回させる** |
| レビュー観点（N+1・Service層の責務・トランザクション境界・DTO/Entity分離・`SELECT *`禁止） | 2か月目 | 設計上の問題 |
| DBUnit + JUnit、テスト仕様書からのケース洗い出し | 3か月目 | **AIが書いたテストと受入条件を突き合わせる** |
| **AIへの一文**（「勝手に決めた箇所を明示せよ」＋その報告を読む） | **新規。これだけ** | AIが黙って決めたこと |

### 突き合わせの読み方

| | 意味 | どうするか |
|---|---|---|
| 受入条件にあるが、AIのテストに無い | **テスト漏れ** | 追加する |
| AIのテストにあるが、受入条件に無い | AIの過剰 or 自分の漏れ | どちらか判定する |
| **両方にあるが期待値が違う** | **仕様解釈の相違。★一番価値がある** | 設計書に戻る。決着しなければQ&A票へ |

### 渡す「問い」

```
□ AIは何を勝手に決めたか。それは正しいか。
□ 頼んでいないファイルが変わっていないか。なぜ変えたのか。
□ 動いた。では正しいのか。何をもって正しいと言うのか。
□ 段②で確定した受入条件を、実装は満たしているか。とくに 自分が足した条件 はどうか。
□ 外に出してはいけない情報が出ていないか（例外メッセージ・スタックトレース・設定値）。
□ 使われている依存のバージョンは、渡した pom と合っているか。
□ AIが足した依存はあるか。そのライセンスは使ってよいものか。
□ このコードを客先のレビューに出して「なぜこう書いたのか」と聞かれたら答えられるか。
□ どこまで自分で確認し、どこからレビューを頼むか。その線をどこに引いたか。なぜそこか。
```

**提出物**: 検証記録 —「何を確認したか」「何を疑ったか」「判断できなかったこと」。

**レビュー観点は全量を見せた上で仕分けさせる**（`08_ギャップ` 付録A・15カテゴリ約60項目）。新人が出すのは6カテゴリだけ。**残りは「自分では判定できないのでレビューを頼む」と言えるための材料。**
**必ず言うこと**: 「実務でも答えは与えられない。基準は現場ごとに違う。だから考え続ける」
**落とさないこと**: 新人が判断すべきは**「基準を持っている人に確認すること」まで**。

### AIレビューの仕分け（4列）

| 列 | 中身 |
|---|---|
| ① 正しい指摘 | 直す |
| ② **的外れな指摘** | **なぜ的外れなのか理由を書く** |
| ③ 判断できない | レビューで聞く |
| ④ ②の理由の分類 | **大半が「AIが知らない前提」に落ちる** |

**④まで書かせると1周が閉じる。**「なぜAIはこれを的外れに言ったのか」＝「**自分が渡していない情報は何か**」で、2-1（書き戻し）に戻る。
**「AIでAIを検証する」限界の体験。**「レビューbotを入れれば安心」という誤解を先に潰せる。**教材はゼロ**（自分の成果物を使う）。

### 5-4 最後の一言（演習にしない）

> 今これは、自分でやるべきか、任せるべきか。
> **学習機会は自分でしか守れない。** AIが賢くなるほど、任せる誘惑は強くなる。
> 配属後1年の伸びを決めるのはここ。

**もう1行**: **AIは既存に合わせる。だから既存が古いと、古いまま増える。** 気づいても、まず合わせるのが実務。**おかしいと思ったら、直すのではなく聞く。**

## 10. 設計判断の記録

**「なぜそう決めたか」を1行ずつ。** 詳細な根拠は右列の場所にある。

| | 決めたこと | 理由 | 根拠 |
|---|---|---|---|
| 1 | **段①は設計書の穴に依存しない** | 依存先を「設計書の不完全さ」から「**AIの出力の不確かさ**」に移した。穴が0件でも成立する | 04 §2.3 |
| 2 | **AIに根拠（どこを読んだか）を書かせる** | 誤検出は減るが（実測2回とも0件）、**研修生が90分で判定できる形**を優先 | 10_シミュレーション/02 |
| 3 | **答えの一覧（模範解答）は作らない** | 3回の実測で全部に出たのは1件だけ。**講師は既知の全量を持ち、出てきたものを判定する** | 04 §2.3 |
| 4 | **Q&A票に「未判定」を置く** | 空欄だと見落としと区別できない。しかも**未判定は聞き逃しになる**（③に振れば聞けた） | 10_シミュレーション/03 |
| 5 | **③は聞いて回答を得る**（投げっぱなしにしない） | 聞かなければ実装できず、勝手に埋めれば独断。**仕様の質問には答える／検証の基準には答えない** | — |
| 6 | **決定は `決定事項.md` に置く**（指示ファイルに書かない） | 規約と決定は別物。**設計書に直接書くと、上流の決定と自分の決定が混ざり出所が残らない**。ADRと同じ形 | — |
| 7 | **受入条件はAIに出させる**（白紙から書かせない） | 実務がそう。実測でも**AIの方が網羅的**（`version=0`・大文字小文字・ロールバック確認まで） | 10_シミュレーション/03 |
| 8 | **人の仕事は照合（渡し漏れの発見）** | 実測で**渡し漏れ0件**。決定とDoDを渡せばAIが全部条件にする。人は追加より照合 | 同上 |
| 9 | **受入条件はAIに渡す**（旧「渡さない」を撤回） | 合格条件をゴールにして回すには渡さないと成立しない | — |
| 10 | **通読は要件＋図だけ** | 読み方が**通読と参照**に分かれる。参照物は 1-4 で根拠を書かせれば必然的に開く | — |
| 11 | **素で叩く比較相手は「自分の理解」** | 段③の出力と比べると時間が離れる。通読直後に見ると鋭く入る | — |
| 12 | **auto は禁止** | 成果物は出るが、何が起きたかが見えない | 02_実験 |
| 13 | **コミットは土台→Tag→Todo の7つ** | `GET(一覧)` を5番目にすると**N+1が1コミットの差分で見える** | — |
| 14 | **ガードレールは不要** | 教材を独立させたので経路が存在しない。浅いcloneは「偶発は塞げるが故意は塞げない」 | 09_配布物/README |
| 15 | **教材の不備は「作業を止めるもの」だけ直す** | **実装判断に効く不備は段①の題材**。由来（実務／研修）では切らない | 04 §2.2 |
