| **0-2** | AIはなぜ間違えるか | 確率的な仕組み。**ハルシネーションを実際に踏ませる** |

## 3. 段① 把握

**到達点**: 何が決まっていないかを、分かっている。
**目的（研修生に言う形）**: **AIに渡してよいことと、人に聞くべきことを、渡す前に分けられる。**

| | 内容 |
|---|---|
| **1-1** | 環境を確認する（コードと設計書の2つが見えているか） |
| **1-2** | **要件定義書とアーキテクチャ図を通読** → そのまま**何も渡さずAIに叩かせる** |
| **1-3** | **「確認しないと決められないこと」をAIにリストアップさせる**（根拠つき） |
| **1-4** | **リストを1件ずつ資料に当たって確かめ、4判定に仕分ける** |

### 通読と参照

| | 中身 | いつ読むか |
|---|---|---|
| **通読するもの** | 要件定義書・アーキテクチャ図 | **前に読む**（全体像がないと 1-4 で判定できない） |
| **参照するもの** | DB定義書・OpenAPI・エラーコード表・プログラム設計 | **必要になったときに開く**（1-4 で根拠を書かせるので必然的に開く） |

### 提出物: Q&A票（4判定）

| 判定 | 意味 | 書かせるもの | 行き先 |
|---|---|---|---|
| **① 書いてあった** | AIの誤検出 | 資料名と場所 | 却下 |
| **② 自分で決められる** | 書かれておらず、判断してよい | こう決めた＋理由 | **2-1 で書き戻す** |
| **③ 自分では決められない** | 書かれておらず、権限や背景が要る | 誰に何を聞くか | **2-1 で聞いて回答を得る** |
| **未判定** | 手をつけていない | その理由 | — |

**迷ったら③。** 実務で困るのは、③にすべきものを②にしたとき。
**⚠ 研修生に必ず言う**: 制約が無いこと・書かれていないことを、「許可」や「決定済み」として読まない。

### 講師がやること

| | |
|---|---|
| 1-1 | 2つのディレクトリが見える状態で配る。**何を見せているかを明示する** |
| 1-2 | 素の出力を**捨てさせない** |
| 1-3 | プロンプトを配る。**研修生に考えさせない** |
| 1-4 | **①の判定を見る。** AIが「未定義」と言った項目が実は書かれているのに②③に振っていたら、読んでいない |

## 4. 段② 決定

**到達点**: 何を作るか・どうなれば完了かを、AIに触る前に確定させている。

| | 内容 | 提出物 |
|---|---|---|
| **2-1** | **③を聞いて回答を得る** → **`決定事項.md` に書き戻す** → **AIに受入条件を出させる** → **自分が渡したものと照合する** | `決定事項.md`／受入条件 |
| **2-2** | **AIに計画を出させ、5つの観点で判定してから着手させる** | 承認した計画 |

**2-1 は「何ができたら終わりか」、2-2 は「どの順で・どのファイルを触り・どこで区切るか」。**

### 書き戻しの行き先（3種類）

| 中身 | 行き先 |
|---|---|
| **決めたこと** | **`決定事項.md`**（出所「自分の判断」） |
| **決められないこと** | **聞いて回答を得る** → `決定事項.md`（出所「確認済み」） |
| **やってはいけないこと**（実装中に踏んだ地雷） | **`docs/決定事項.md`** の末尾（出所「自分の判断」）。**`CLAUDE.md` は配られる側なので研修生は書き換えない** |

**③の返し方は3つ**: 仕様として決まる／**「自分で決めてよい」（実務で一番多い）**／「今は決まっていない」（暫定を記録）。
**聞き方は丸投げにしない**: ①見立て ②理由 ③どこを見て無いと判断したか。

### 受入条件は3層

| 層 | 中身 | 誰が出すか |
|---|---|---|
| **DoD**（全変更に共通） | **9項目。**N+1を作らない／例外の中身を外に出さない／層構成を維持／見せてはいけない情報を返さない／`SELECT *` 禁止／頼んでいないファイルを変えない／依存を変えない／**トランザクション境界が Service にある**／**テストが実質を見ている** | **講師が配る**（`CLAUDE.md` の「完了の定義」節。正本は `09_配布物/DoD.md`）。**この9項目が段④の目視チェックリスト**（`11` §8） |
| **受入条件**（機能ごと） | 正常系・境界値・異常系 | **AIが出す** |
| **追加分** | 決定事項から導かれる不変条件 ＋ DoDのこの機能での具体形 | **人が足す** |

### 照合の観点（2-1）

> **自分が渡した決定とDoDが、受入条件に全部反映されているか。**
> **反映されていないなら、渡し漏れか、AIの落としか。**

**受入条件を全部読まない。** 自分が渡したもの（決定事項＋DoD）を1件ずつ引く。

### 計画のレビュー観点（2-2・5つ）

① 層の順序（Entity→Mapper→Service→Controller）／② 触るファイル一覧が妥当か／③ 設計書に無い判断が混ざっていないか／④ 確認方法が書かれているか／⑤ 後戻りできる単位に割れているか

**2-2 だけが持つもの**: plan モードの体験／**触るファイル一覧＝独断の検知**／**コミット粒度＝後戻りできる単位**。

### 受入基準・DoD・品質ゲートの置き場

| | 単位 | 誰が決める | 研修での扱い |
|---|---|---|---|
| **受入基準** | 機能ごと | 仕様を持つ人＋実装者 | **AIが出し、研修生が照合して足す** |
| **完了の定義（DoD）** | 全変更に共通 | チーム | **講師が配る** |
| **品質ゲート** | CI | 組織 | `mvn checkstyle:check` と `mvn test` |

用語の整理は `08_ギャップ` 付録C。

### 講師がやること

| | |
|---|---|
| 2-1 | **③への回答を返す**（仕様の持ち主役）。`決定事項.md` の雛形と **DoD** を配る。**受入条件の中身は添削しない** |
| 2-2 | **観点5つを配る。**「なぜその線を引いたのか」を聞く（＝議論。**これが実質のフィードバック**） |

## 5. 段③ 委任

| | 内容 |
|---|---|
| **3-1** | 環境確認・課題説明・プロンプト配布 |
| **3-2** | **委任する** — コミット1で土台、**コミット2〜7は「テストを書く → 赤を確認 → 実装 → 緑」を1コミットずつ**（ステップ承認・auto禁止） |

**流れ**: 受入条件を確定（段②）→ **コミットごとに Red → Green** → テストにできない条件は段④で人が見る。
**AIが実装を見てテストを書くと、実装のバグをテストが追認する。** 「実装ではなく仕様からテストを書け」の一文だけでは**守ったか確認できない**ので、**赤を見せさせる**。
**「落ちなかったテストを列挙し、なぜ落ちなかったかを書く」まで書く。** 赤が出ないテストは、何もアサートしていないか、実装を写しているか、**もともと通る振る舞いを叩いている**（実測では `notFound` を期待するテストが該当。→ §10-20）。
**⚠ Red は「落ちうる」ことしか証明しない。** 期待値が仕様と違っていても落ちる。**そこは段④の仕事として残る。**
**E2Eはやらない**（フロントを触っていない）。DBUnit + JUnit の既習範囲。

### `CLAUDE.md` を実務に寄せると段①が痩せる — 補うかは再実測で決める（**保留**）

**`CLAUDE.md` に層の役割と設計書の参照を書くと、1-3 でAIが挙げる件数が減る**（実測10件のうち `queryCondition` の役割・テストの層・トランザクション境界が消える見込み）。

**順序は「まず入れて測る」。** **既存の食い違いだけで段①が成立するなら、何も足さない。**
**足りなかったときに限り**、実務に実在する状態を足す。（判断は **§12-9** ／ 理由は §10-16）

| 足りなかったときの候補 | なぜ実務的か |
|---|---|
| **指示ファイルと設計書の食い違い** | **指示ファイルは腐る。**現場で最も普通に起きる（例: `CLAUDE.md` が `query`、プログラム設計が `queryCondition`）。**5-4 の「AIは既存に合わせる」と直結する** |
| **表記ゆれ** | 上流の書き手が複数いれば必ず出る（要件定義「タグ」／OpenAPI `tag`／DB定義 `tag_name`／プログラム設計「タグ名称」） |
| **数値の不一致** | **既に実在した**（`content` 30 vs 100）ので、同種を1つ残す判断でよい |

**⚠ 矛盾は足してよい。情報は抜かない。** 抜くと 1-4 で辿り着けなくなり、設計原則3に触れる。
**足したものの一覧は `04_教材見直しの材料.md` が正本。**（07 には書かない。講師の手元の答えは1箇所に置く）

### §12-9 の測り方（実測3回分から）

**既に加えた教材修正（`content` 30→100・`tag.yaml`・`Tag機能.md` 追加・研修生向け資料52ファイル削除）は、段①の実測2回目に織り込まれている。** 測り直す差分は無い。
**次の3つが揃ってから、1回だけ測る。** どれも段①の題材を直接消すので、揃う前に測っても無効になる。

| 揃えるもの | 消える題材 |
|---|---|
| **`CLAUDE.md`（実務版）** | ⑲ トランザクション境界 ／ ⑳ `queryCondition` の役割 |
| **テスト参照実装1本** | ⑮ テストの層（04 §2.4 が「**削除だけでは足りず、参照実装1本＋DoDが必須**」と結論） |
| **`pom.xml` の checkstyle** | §2.1-④「plugin が無い」そのもの |

**⚠ 総数で判断しない。** 04 §2.3 の通り**3回とも全部に出たのは1件だけ**で、**3件直しても10件のまま**だった（6件が新しく出た）。
**見るのは2つ** — ①**上の3つが実際に消えたか** ②**残りが 1-4 に収まるか**。
**過去実測は「足さなくてよい」側の証拠**でもある（直しても減らなかったので、`CLAUDE.md` でも別の空白が前に出ると予想できる）。

| 3〜7 | **Todo 1本ずつ** | `POST` → `GET(1件)` → **`GET(一覧)`** → `PUT` → `DELETE` |

**Tag を先に置く**: Todo の登録・更新が Tag の存在チェックを要求する。
**`GET(一覧)` を5番目に置く**: **旧「N+1がその1コミットの差分で見える」は撤回**（→ §10-22）。**DoDを渡すとAIはN+1を作らない**（実測）。位置は「検索条件を含むので後ろ」以上の意味を持たない。
**ブランチは課題ブランチ1本。**「捨ててよい実験ブランチ」だけ一言触れる。

### auto は禁止

**ステップごとに承認させる。** 目的は「開発フローをイメージできるようになること」で、**auto だと流れが見えない**（実験では一度も確認を挟まず完走した）。

### ガードレールは不要（2026-08-21 解決）

**教材を2か月目リポジトリから独立させたので、模範解答も過去研修生の実装も存在しない。** カンニング経路そのものが無い。
**実務での構造の話は段⓪で使う**: 「指示ファイルで意図を伝え、レビューとCIで落とす。**強制力は権限側にしかない**」。

## 6. 段④ 検証

**答えを配らない。問いだけ渡す。**

| | 内容 |
|---|---|
| **4-1** | 何を任せたか把握する（AIが読んだものと変えたものを自分で見る） |
| **4-2** | 確かめる（**段②で確定した受入条件**と突き合わせる） |
| **4-3** | どこまでやるかを決める |

### 使う道具 — 新規はAIへの一文だけ

| 道具 | いつ習ったか | 何に使うか |
|---|---|---|
| `git diff` | 1か月目 | 頼んでいないファイルが変わっていないか（**コミット単位で**） |
| Postman / ThunderClient | 2か月目 | 動かして叩く |
| CheckStyle / SonarLint | 2か月目 | 規約違反。**CheckStyle は AI にも回させる** |
| レビュー観点（N+1・Service層の責務・トランザクション境界・DTO/Entity分離・`SELECT *`禁止） | 2か月目 | 設計上の問題 |
| DBUnit + JUnit、テスト仕様書からのケース洗い出し | 3か月目 | **AIが書いたテストと受入条件を突き合わせる** |
| **AIへの一文**（「勝手に決めた箇所を明示せよ」＋その報告を読む） | **新規。これだけ** | AIが黙って決めたこと |

### 突き合わせの読み方

| | 意味 | どうするか |
|---|---|---|
| 受入条件にあるが、AIのテストに無い | **テスト漏れ** | 追加する |
| AIのテストにあるが、受入条件に無い | AIの過剰 or 自分の漏れ | どちらか判定する |
| **両方にあるが期待値が違う** | **仕様解釈の相違。★一番価値がある** | 設計書に戻る。決着しなければQ&A票へ |

### 渡す「問い」

```
□ AIは何を勝手に決めたか。それは正しいか。
□ 設計書と DoD が食い違っている箇所はあるか。AIはどちらに従ったか。
   それを報告してきたか、黙って決めたか。
□ 設計書は「ループして取得する」と書いてある。実装はどうなっているか。
   違っていたら、それは設計書違反か、正しい最適化か。誰が決めてよいことか。
□ 頼んでいないファイルが変わっていないか。なぜ変えたのか。
□ 動いた。では正しいのか。何をもって正しいと言うのか。
□ 段②で確定した受入条件を、実装は満たしているか。とくに 自分が足した条件 はどうか。
□ 外に出してはいけない情報が出ていないか（例外メッセージ・スタックトレース・設定値）。
□ Entity をそのままレスポンスに返している。DBにカラムを1本足したら、APIの
   レスポンスは何が変わるか。それは誰の許可が要るか。
□ 使われている依存のバージョンは、渡した pom と合っているか。
□ AIが足した依存はあるか。そのライセンスは使ってよいものか。
□ このコードを客先のレビューに出して「なぜこう書いたのか」と聞かれたら答えられるか。
□ どこまで自分で確認し、どこからレビューを頼むか。その線をどこに引いたか。なぜそこか。
```

**提出物**: 検証記録 —「何を確認したか」「何を疑ったか」「判断できなかったこと」。

**レビュー観点は全量を見せた上で仕分けさせる**（`08_ギャップ` 付録A・15カテゴリ約60項目）。新人が出すのは6カテゴリだけ。**残りは「自分では判定できないのでレビューを頼む」と言えるための材料。**
**必ず言うこと**: 「実務でも答えは与えられない。基準は現場ごとに違う。だから考え続ける」
**落とさないこと**: 新人が判断すべきは**「基準を持っている人に確認すること」まで**。
