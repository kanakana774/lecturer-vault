## 1. 全体像 — A 決める / B 任せる / C 確かめる

```
入口（自分）      →      中（AI）      →      出口（自分）
 A 決める                B 任せる            C 確かめる
```

| | 何をする段か | 講師が渡すもの | 研修生が出すもの |
|---|---|---|---|
| **A 決める** | **何を作るか・どうなれば完了かを、AIに触る前に確定させる** | 設計書・既存コード・配布プロンプト・`仕様確定.md` の雛形・DoD | **`docs/仕様確定.md`**（確認事項／決定事項／受入条件） |
| **B 任せる** | **任せた仕事の流れが見えている状態で回す** | 作業ブランチ・コミット規約 | **7コミット（実装＋テスト）** |
| **C 確かめる** | **動いた、ではなく、正しいと言える** | 検証記録の雛形（**問い記入済み**） | **`検証記録.md`** |

**ガバナンスは前提として先に置く**（→ §2）。実装の軸から外れるので A・B・C に番号を持たせない。

**各段の提出物が次の段の入力になる。提出して終わる成果物を作らない。**
**A→B が背骨。** Aで決め、Bで任せ、**Cで「決めたこと」と突き合わせる。**

### この研修が持って帰らせるもの

> **AIは結果を出す。結果は良い。だから根拠の欠落が見逃される。**

**そして記録はコミットメッセージにしか残っていなかった。**

## 4. `docs/仕様確定.md` — 研修生が書く唯一のドキュメント

**3つの節を持つ。** 埋めるのは A の全部と、B で設計から逸れたとき。

```markdown
# 仕様確定

## §1 確認事項
| 項目 | 区分 | 根拠 / 確認先 | 反映 |
|---|---|---|---|
| content の最大文字数が文書間で違う | 記載あり | 要件定義 4.2 / DB定義書 | — |
| Tag削除時に todo_tag をどうするか | 要確認 | 仕様管理者へ | §2 |
| 同名のTagを登録できるか | 自己判断 | 記載なし | §2 |
| 部分一致の % _ の扱い | 未着手 | 時間切れ | — |

## §2 決定事項
| 決めたこと | 理由 | 出所 | 上位者へ |
|---|---|---|---|
| content は最大100文字 | DB定義とOpenAPIが100。要件定義だけ30 | 確認済み | — |
| Tag削除時に todo_tag の行も消す | 孤児レコードが残る | 確認済み | — |
| 同名のTagを登録できる | tag に UNIQUE 制約が無い | 自分の判断 | — |
| 一覧取得を JOIN 1本にした | 設計書は「ループして取得」だが DoD の for内SQL 禁止と衝突 | 実装中 | ○ |

## §3 受入条件
| # | 条件 | 出所 | 検証手段 |
|---|---|---|---|
| 1 | POST /todos content 空文字は 400 | AI | テスト |
| 2 | version 不一致で 409 | AI | テスト |
| 3 | content 101文字は 400 | §2 | テスト |
| 4 | 例外の内部情報を body に返さない | DoD | テスト |
| 5 | 一覧取得で N+1 を発生させない | DoD | 目視（SQLログ） |
| 6 | 3層構成を維持する | DoD | 目視 |
| 7 | SELECT * を使わない | DoD | checkstyle |
```

### 語は実務語で揃える

| 研修語 | 使う語 |
|---|---|
| 判定ログ | **確認事項** |
| ① 書いてあった | **記載あり** |
| ② 自分で決められる | **自己判断** |
| ③ 自分では決められない | **要確認** |
| 未判定 | **未着手** |
| 講師へ／講師回答 | **仕様管理者へ／確認済み** |
| 課題ブランチ | **作業ブランチ** |

### §1 と §2 を1つの表にしない

**対応が 1:1 にならない。**「記載あり」「未着手」は決定を持たず、**実装中に決めたことは §1 に元行が無い**。列の性質も違う（§1は「根拠・確認先」、§2は「出所」）。
**代わりに §1 の右端に「反映」列を1つだけ置く。** これで対応関係は追えて、表は汚れない。**書き戻し漏れは実測で起きている**（→ §10-27）。

### ★§2 の「出所＝実装中」と「上位者へ」列（**この研修の芯**）

**設計から逸れた瞬間、それを知りうるのは委任した本人だけになる。**

| | |
|---|---|
| 上位者 | **設計は把握している。逸れたことは把握していない** |
| AI | **聞かなければ言わない**（実測。講師が明示的に聞いて初めて報告した） |
| **本人** | **把握していなければ、組織の誰もその逸脱を知らない** |

**エスカレーションするかどうかの判断も本人がする。** そのためには**まず逸れたことを知っていないと始まらない。**

**実測で起きたこと**: `distinct()` が設計書の「404を返す」分岐を **201** に変え、`JOIN` が「ループして取得」を上書きした。**動作はどちらも妥当で、テストは51件すべて緑。記録はコミットメッセージにしか無かった。**

**だから網を2枚張る。**

| | 誰が | いつ |
|---|---|---|
| **1枚目** | **AIに書かせる** | B-2 の各コミットで「設計書と違う実装にしたら §2 に1行足してから報告する」 |
| **2枚目** | **人が探す** | C-3 の問い2。**1枚目の書き漏れを拾う** |

**「上位者へ」は ○ / — の2値でよい。** 判断そのものが提出物になる。

### 受入条件は「AIに出させて、人が照合する」

**AIは非機能も出す**（実測: `§2＋DoD` を渡した状態で24件を自分で挙げ、**DoD から N+1 の項目を外しても N+1 を作らなかった**）。
**だから §2 と DoD を渡す理由は「出させるため」ではなく、照合の基準を1箇所に固定するため。**

> **AIが満たしていても、確かめたのが人でなければ担保にならない。**

**「検証手段」列を必須にする。** 理由は2つ。

1. **受入条件のうちテストにできるのは半分程度。** 列が無いと C-2 で「テストが無い＝漏れ」と誤判定する
2. **「目視」の行が、そのまま C の作業リストになる**（`11` §8 の停止条件が、受入条件から自動で立ち上がる）

| 検証手段 | 誰が確かめるか |
|---|---|
| テスト | AIが書き、研修生が突き合わせる |
| checkstyle | `mvn checkstyle:check` |
| **目視** | **研修生（＝Cの実体）** |

## 5. A 決める

| | 作業 | 入力 | 出力 |
|---|---|---|---|
| **A-1** | 要件定義書とアーキテクチャ図を**通読** | 設計書 | — |
| **A-2** | **そのまま何も渡さずAIに叩かせ、自分の理解と比べる** | 素で叩くプロンプト | 素の出力（捨てさせない） |
| **A-3** | AIに**未確定事項を根拠つきで出させる** | 配布プロンプト | §1 の素案 |
| **A-4** | **1件ずつ資料に当たり、4区分に仕分ける** | §1素案＋設計書 | **§1 確認事項** |
| **A-5** | **「要確認」を投げ、回答を書き戻す** | §1 の要確認行 | **§2 決定事項** |
| **A-6** | **§2 と DoD を渡して受入条件を出させ、渡し漏れを照合し、検証手段を付ける** | §2＋DoD | **§3 受入条件** |

**通読するのは要件定義書とアーキテクチャ図だけ。** DB定義書・OpenAPI・エラーコード表・プログラム設計は**必要になったときに開く**（A-4 で根拠を書かせるので必然的に開く）。

**迷ったら「要確認」。** 実務で困るのは、要確認にすべきものを自己判断にしたとき。
**⚠ 必ず言う**: 制約が無いこと・書かれていないことを、「許可」や「決定済み」として読まない。

### 講師がやること

| | |
|---|---|
| A-2 | 素の出力を**捨てさせない**。**比べる相手は B の出力ではなく、通読直後の自分の理解** |
| A-3 | **プロンプトを配る。研修生に考えさせない** |
| A-4 | **「記載あり」の判定を見る。** AIが「未定義」と言った項目が実は書かれているのに要確認に振っていたら、読んでいない |
| A-5 | **回答を返す**（仕様の持ち主役）。**締切を切って一括セッションで返す**（人数分がバラバラに飛ぶと講師側が崩れる） |
| A-6 | **受入条件の中身は添削しない。** 照合したかだけ見る |

## 6. B 任せる

| | 作業 | 出力 |
|---|---|---|
| **B-1** | `仕様確定.md` を渡して**計画を出させ、触るファイル一覧だけ見て承認** | 承認した計画 |
| **B-2** | **コミット1=土台／2=Tag／3〜7=Todo。各コミットで テストを書く → 赤を確認 → 実装 → 緑** | 7コミット |

### コミット規約（配る）

| # | コミット | 中身 |
|---|---|---|
| 1 | **土台** | Entity / Form / Query / Mapper インタフェース / Mapper XML の枠。**テストは書かない** |
| 2 | **Tag 5本** | Tag の CRUD |
| 3〜7 | **Todo 1本ずつ** | `POST` → `GET(1件)` → `GET(一覧)` → `PUT` → `DELETE` |

**Tag を先に置く**: Todo の登録・更新が Tag の存在チェックを要求する。
**土台にテストを書かない**: Java では Entity が無いとテストがコンパイルできない。**土台が入ってから Red → Green が回る。**

### B-2 で渡す指示（要点だけ）

```
1コミットずつ、次に進む前に必ず確認を取ってください。各コミットで:

1. そのコミットで満たす受入条件をテストにする
   - テストは実装ではなく仕様から書いてください
   - 参照実装に合わせてください（統合テスト。モックは使わず、
     HTTPリクエストから実DBまで通す）
2. mvn test を実行し、落ちることを確認して出力を見せてください
   - 落ちなかったテストがあれば列挙し、なぜ落ちなかったかを書いてください
3. 実装してください。1 で書いたテストは変更しないでください
   変更が必要だと思ったら、変更せずに理由を報告してください
4. mvn test と mvn checkstyle:check を通してからコミットしてください

★設計書と違う実装にしたら、docs/仕様確定.md §2 に1行足してから
  報告してください（出所は「実装中」）。
頼んでいないファイル・テーブル・依存（pom.xml）は変更しないでください。
```

### auto は禁止

**ステップごとに承認させる。** 目的は**開発フローをイメージできるようになること**で、auto だと流れが見えない（実験では一度も確認を挟まず完走した）。

### ⚠ 赤を見せさせることの限界

**「テストは仕様から書け」は守ったか確認できないが、「赤を見せろ」は機械的に検証できる。** ただし2つ抜ける。

| | |
|---|---|
| **偶然一致** | **404 を期待するテストは、そのパスにハンドラが無いと実装前に通る。** 最初のコミットほど Red が弱い |
| **アサートの一部しか走らない** | `@ExpectedDatabase` は成功時のみ検証。**「赤を見た」≠「全アサートを通した」** |

**そして根本的に**——**テストは実装と同じ仕様解釈から生まれる。だから仕様の読み間違いを検出できない。固定する。**
**「51件green」が保証するのは「実装が、実装者の解釈どおりに動く」ことだけ。** ここが C の存在理由。

## 7. C 確かめる

**答えを配らない。問いだけ渡す。講師も答えを持っていない。**

| | 作業 | 入力 | 出力 |
|---|---|---|---|
| **C-1** | **`git diff` で変更範囲を見る**（コミット単位で） | コミット | 検証記録 §1 |
| **C-2** | **§3 と突き合わせる**（**「目視」行が作業リスト**） | §3＋実装 | 検証記録 §2 |
| **C-3** | **問いに答える** | 実装 | 検証記録 §3 |
| **C-4** | **AIに成果物をレビューさせ、仕分ける** | 実装 | 検証記録 §4 |

### 検証記録の雛形（**AIに渡さない**）

```markdown
# 検証記録（AIに渡さないこと）

## §1 変更範囲
頼んでいないファイルが変わっていないか（コミット単位で確認）
→

## §2 受入条件との突き合わせ
| # | 手段 | 結果 | 判断 |
|---|---|---|---|
| 1 | テスト | あり・通過 | OK |
| 5 | 目視 | LEFT JOIN 1本 | OK |

## §3 問い
1. AIが勝手に決めたことは何か。それは正しいか。
   →
2. 設計書と違う実装になっている箇所はあるか。違反か、正しい最適化か。
   誰が決めてよいことか。上位者に上げるべきか。
   →
3. 外に出してはいけない情報が出ていないか。
   →
4. 動いた。では正しいと言える根拠は何か。
   →
5. Entity をそのまま返している。DBにカラムを1本足したら、レスポンスは
   何が変わるか。それは誰の許可が要るか。
   →
6. どこまで自分で確認し、どこからレビューを頼むか。なぜそこか。
   →

## §4 AIに自分の成果物をレビューさせた結果
| 指摘 | 判定 | 理由 |
|---|---|---|
|  | 正しい / 的外れ / 判断できない |  |
的外れの理由は何に分類できたか →
```

**問いは正解のない、きっかけ。** 実測では**問いを渡さなくても12本中7本は出た**ので、問いは「AIに出させるための呼び水」ではなく**人が自分で見るための足場**（→ §10-25）。
**問い5（カラムを1本足したら）は、実測で問いを渡して初めて出た3本のうちの1本**なので残す。

**⚠ 「分かりません」が2種類ある。** 実測で、検証役が**「自分では決められない」と「自分では思いつかなかった」を同じ袋に入れていた**。

> **前者は正直な報告。後者は確認漏れを謙虚さの言葉で包んだだけ。**

**線を引く基準はこれ。**

> **自分の観測で決着するものは、全部自分側。他人の同意が要るものは、全部相手側。**
> **難しいかどうか、時間がかかるかどうかでは切らない。**

### C で使う道具 — 新規はAIへの一文だけ

| 道具 | いつ習ったか | 何に使うか |
|---|---|---|
| `git diff` | 1か月目 | 頼んでいないファイルが変わっていないか |
| **Postman / ThunderClient** | 2か月目 | **動かして叩く。★テストで出ない継ぎ目はここでしか出ない** |
| CheckStyle | 2か月目 | 規約違反 |
| レビュー観点（N+1・Service層の責務・トランザクション境界・DTO/Entity分離・`SELECT *`禁止） | 2か月目 | 設計上の問題 |
| DBUnit + JUnit、テスト仕様書からのケース洗い出し | 3か月目 | AIが書いたテストと受入条件を突き合わせる |
| **AIへの一文**（「勝手に決めた箇所を明示せよ」＋その報告を読む） | **新規。これだけ** | AIが黙って決めたこと |

**⚠ 「動かして叩く」を1行で済ませると届かない。** 実測では、**捨てDBを立ててアプリを起動し `curl` で12パターン叩いて初めて**、51件greenをすり抜けたバグ（**一覧と1件取得が、同じデータで違う `tags` を返す**）が出た。**手順の具体が要る**（→ §12-19）。

### 停止条件

**目視の量はコード量ではなく、チェックリストの項目数で決まる。一巡したら終わり。**（`11` §8）

**⚠ チェックリストは1本ではない。** 実測で、検証役が「DoD の7項目は一巡した」で閉じかけ、自分で訂正した。

> **チェックリストは少なくとも3本あった —— DoD、コーディングガイド、受入条件。1本だけ一巡して「一巡した」と言った。**

**停止条件の手前に「渡された規約書を全部並べる」を置く。**

**終わったときに言うのはこれ。**

> **「このリストは見た。これ以外は自分では分からないので、レビューを頼みたい」**
