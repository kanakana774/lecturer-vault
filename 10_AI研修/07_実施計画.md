## 1. 全体像 — A 決める / B 任せる / C 確かめる

```
入口（自分）      →      中（AI）      →      出口（自分）
 A 決める                B 任せる            C 確かめる
```

| | 何をする段か | 講師が渡すもの | 研修生が出すもの |
|---|---|---|---|
| **A 決める** | **何を作るか・どうなれば完了かを、AIに触る前に確定させる** | 設計書・既存コード・配布プロンプト・`仕様確定.md` の雛形・DoD | **`docs/仕様確定.md`**（確認事項／決定事項／受入条件） |
| **B 任せる** | **任せた仕事の流れが見えている状態で回す** | 作業ブランチ・コミット規約 | **7コミット（実装＋テスト）** |
| **C 確かめる** | **動いた、ではなく、正しいと言える** | 検証記録の雛形（**問い記入済み**） | **`検証記録.md`** |

**ガバナンスは前提として先に置く**（→ §2）。実装の軸から外れるので A・B・C に番号を持たせない。
**各段の提出物が次の段の入力になる。提出して終わる成果物を作らない。**

### この研修が持って帰らせるもの

> **エージェントに実装させた人は、設計書に無いことを実装時に決めた箇所を、自分で把握していないといけない。**

**上位者は設計を把握しているが、そこから逸れたことは把握していない。** AIは**聞かなければ言わない**。だから**本人が把握していなければ、組織の誰もその逸脱を知らない。**
上位者に説明を求められるのも、**そもそも上げるかどうかを決めるのも本人**。

**実測で起きたこと**: 設計書が「ループして取得」と書いている箇所が `JOIN` 1本で実装され、設計書が「404を返す」と書いている分岐が **201** になった。**動作はどちらも妥当で、テストは51件すべて緑。記録はコミットメッセージにしか残っていなかった。**

## 2. ⓪ ガバナンス（前提）

**答えがある。教えて、測って、終わらせる。**

| 内容 | 材料 |
|---|---|
| なぜ今これをやるか | 業界動向。**SESの現実**＝申請制・指定ツール・全面禁止の幅がある（金融系調査） |
| AIはなぜ間違えるか | 確率的な仕組み。**ハルシネーションを実際に踏ませる** |
| **ガバナンス4項目** | 下記 |
| AIから見える範囲は設定で決まる | **`.claude/settings.json` の現物**（deny に何が並ぶかを見る。**キー名は解説しない**）＋**平文パスワードの実物**（`spring.datasource.password=todo`。「客先ならこれが deny の筆頭」）。**MCPは一言だけ** |
| **理解度テスト → 合格でアカウント発行** | LINEヤフーコミュニケーションズ方式（100点合格制） |

### ガバナンス4項目

| | 中身 | 教材 |
|---|---|---|
| 1 | **客先のルールを確認する** | FISC第13版でAI項目が新設・金融庁・FDUA／「申請しても即座には通らない」現場の証言 |
| 2 | **渡してはいけないものを渡さない** | 客先コードの外部送信は **NDA上「第三者への開示」に当たりうる**／個人アカウントの持ち込みは原則NG／**Web検索は自分が投げた文字列が社外に出る**／**著作権とライセンス（コピーレフト）** |
| 3 | **何を渡したか記録する** | 申請制の現場で説明できる |
| 4 | **AIに書かせた部分を PR で明示する** | 3か月目までのPR運用に接続 |

**社長の要望**: ガバナンスは **Q&A集の形**で用意する。

## 3. 手元にあるもの

**研修生に見えているのは2つのリポジトリだけ。** A-1 で開き、最後まで増えない。
**★ = AI研修のために足すもの**（2か月目の環境には無い）。

```
todo-app-api/                        ← 書き換える唯一の場所
├── ★ CLAUDE.md                       読むだけ。DoD 9項目を含む
├── ★ .claude/settings.json           AIに許す操作の範囲。触らない
├── ★ docs/仕様確定.md                ★空の雛形。研修生が埋める
├──   pom.xml ／ todo_checks.xml      Spring Boot 3.4.1 / Java 21 ＋ ★checkstyle
└──   src/                            ↓下記
todo-app-api-docs/                   ← 読むだけ・書き換えさせない
（別配布・リポジトリの外）検証記録.md  ★問い記入済みの雛形。AIに渡さない
```

### `src/` の中身 — **2か月目の雛形そのまま ＋ 参照実装1本**

| | 中身 |
|---|---|
| **雛形**（2か月目と同じ） | `.gitkeep` の空フォルダ（`app/controller` `logic/service` `mapper` `entity` `form` `query` `queryCondition`）／**`core/exception` 一式9本**／`config/SecurityConfig`／`util/LocationUtil` 他3本／**`testTools` 3本**／**空の Mapper XML 2本** |
| **★参照実装1本** | **Todo 1件取得の完成品**（Controller・Service・Mapper・Entity ＋ **統合テスト1本** ＋ dataset）／`testTools` を2本追加 |

**参照実装1本を配る理由**: **テストの層と書き方は、例が無いと揃わない**（実測。ただし例だけでも半分は揃わない → §10-26）。

### `docs/仕様確定.md` を**コード側**に置く理由

**内容は仕様なので `todo-app-api-docs` に置きたくなるが、コード側に置く。**

1. **`todo-app-api-docs` は上流の資産で、実装者が書き換えるものではない**（実務でも設計書リポにPRを出すのは別プロセス）。**「読むだけ」を徹底できる**
2. **`CLAUDE.md` から読ませる導線が同一リポの方が確実**
3. **受入条件は実装に紐づく**ので、同じブランチで履歴が追える

### `検証記録.md` をリポジトリに置かない理由

`docs/` に置くと `CLAUDE.md` 経由でAIが読み、**C-4（AIレビュー）で自分の答えをAIが読んだ状態**になる。**手渡しで配り、記入して提出させる。**

## 4. `docs/仕様確定.md` — 研修生が書く唯一のドキュメント

**配るのは空の雛形。** どう埋まっていくかは §5・§6 で追う。

```markdown
# 仕様確定

## §1 確認事項
| 項目 | 区分 | 根拠 / 確認先 | 反映 |
|---|---|---|---|
|  | 記載あり / 自己判断 / 要確認 / 未着手 |  |  |

## §2 決定事項
| 決めたこと | 理由 | 出所 | 上位者へ |
|---|---|---|---|
|  |  | 確認済み / 自分の判断 / 実装中 |  |

## §3 受入条件
| # | 条件 | 出所 | 検証手段 |
|---|---|---|---|
|  |  | AI / §2 / DoD | テスト / checkstyle / 目視 |
```

**§1 と §2 を1つの表にしない。** 対応が 1:1 にならないため（「記載あり」「未着手」は決定を持たず、**実装中に決めたことは §1 に元行が無い**）。代わりに **§1 の右端に「反映」列**を置く。**書き戻し漏れは実測で起きている**（→ §10-27）。

### ★「出所＝実装中」と「上位者へ」列（**この研修の芯**）

**設計から逸れた瞬間、それを知りうるのは委任した本人だけになる。**

**網を2枚張る。**

| | 誰が | いつ |
|---|---|---|
| **1枚目** | **AIに書かせる** | B-2 の各コミットで「設計書と違う実装にしたら §2 に1行足してから報告する」 |
| **2枚目** | **人が探す** | C-3 の問い2。**1枚目の書き漏れを拾う** |

**「上位者へ」は ○ / — の2値。** 判断そのものが提出物になる。

### ★「検証手段」列を必須にする

**AIは非機能も出す**（実測: `§2＋DoD` を渡した状態で受入条件24件を自分で挙げ、**DoD から N+1 の項目を外しても N+1 を作らなかった**）。
**だから §2 と DoD を渡す理由は「出させるため」ではなく、照合の基準を1箇所に固定するため。**

> **AIが満たしていても、確かめたのが人でなければ担保にならない。**

| 検証手段 | 誰が確かめるか | なぜ列が要るか |
|---|---|---|
| テスト | AIが書き、研修生が突き合わせる | **受入条件のうちテストにできるのは半分程度。**列が無いと C-2 で「テストが無い＝漏れ」と誤判定する |
| checkstyle | `mvn checkstyle:check` | 同上 |
| **目視** | **研修生（＝Cの実体）** | **この行がそのまま C の作業リストになる**（`11` §8 の停止条件が受入条件から自動で立ち上がる） |

## 5. A 決める

| | 作業 | 出力 |
|---|---|---|
| **A-1** | 要件定義書とアーキテクチャ図を**通読** | — |
| **A-2** | **何も渡さずAIに叩かせ、自分の理解と比べる** | 素の出力（捨てさせない） |
| **A-3** | AIに**未確定事項を根拠つきで出させる** | §1 の素案 |
| **A-4** | **1件ずつ資料に当たり、4区分に仕分ける** | **§1 確認事項** |
| **A-5** | **「要確認」を投げ、回答を書き戻す** | **§2 決定事項** |
| **A-6** | **§2 と DoD を渡して受入条件を出させ、渡し漏れを照合し、検証手段を付ける** | **§3 受入条件** |

**通読するのは要件定義書とアーキテクチャ図だけ。** DB定義書・OpenAPI・エラーコード表・プログラム設計は**必要になったときに開く**（A-4 で根拠を書かせるので必然的に開く）。

### 4区分

| 区分 | 意味 | 書くこと | 行き先 |
|---|---|---|---|
| **記載あり** | **AIの誤検出。**実は書いてある | 資料名と場所 | 却下 |
| **自己判断** | 書かれておらず、判断してよい | こう決めた ＋ 理由 | **§2 へ** |
| **要確認** | 書かれておらず、権限や背景が要る | 誰に何を聞くか | **A-5 で聞く → §2 へ** |
| **未着手** | 手をつけていない | その理由（**空欄にしない**） | — |

**迷ったら「要確認」。** 実務で困るのは、**要確認にすべきものを自己判断にしたとき**。
**⚠ 必ず言う**: 制約が無いこと・書かれていないことを、「許可」や「決定済み」として読まない。

### `仕様確定.md` はこう埋まっていく

**A-4 の直後** — §1 だけが埋まる

```markdown
## §1 確認事項
| 項目 | 区分 | 根拠 / 確認先 | 反映 |
| content の最大文字数が文書間で違う | 要確認 | 要件定義は30、DB定義とOpenAPIは100 | |
| Tag削除時に todo_tag をどうするか   | 要確認 | 仕様管理者へ | |
| 同名のTagを登録できるか             | 自己判断 | tag に UNIQUE 制約が無い | |
| 進捗状況という項目が要件にある      | 記載あり | 要件定義 3.1（DB設計に対応物なし） | |
| 部分一致の % _ の扱い               | 未着手 | 時間切れ | |
```

**A-5 の直後** — 聞いた答えが §2 に落ち、§1 の「反映」が埋まる

```markdown

| content の最大文字数が文書間で違う | 要確認   | …… | §2 |

| 決めたこと | 理由 | 出所 | 上位者へ |
| content は最大100文字            | 3対1で100。要件定義だけ30 | 確認済み   | — |
| Tag削除時に todo_tag の行も消す  | 孤児レコードが残る        | 確認済み   | — |
| 同名のTagを登録できる            | UNIQUE 制約が無い         | 自分の判断 | — |
```

**A-6 の直後** — §3 が埋まる。**「出所」で §2 と DoD が引ける**

```markdown
## §3 受入条件
| # | 条件 | 出所 | 検証手段 |
| 1 | POST /todos content 空文字は 400        | AI  | テスト |
| 2 | content 101文字は 400                    | §2  | テスト |
| 3 | Tag削除時に todo_tag の行が残らない      | §2  | テスト |
| 4 | 例外の内部情報を body に返さない          | DoD | テスト |
| 5 | 一覧取得で N+1 を発生させない             | DoD | 目視（SQLログ） |
```

**B-2 のあと** — **設計書から逸れた分が §2 に増える**

```markdown
## §2 決定事項
```

## 6. B 任せる

| | 作業 | 出力 |
|---|---|---|
| **B-1** | `仕様確定.md` を渡して**計画を出させ、触るファイル一覧だけ見て承認** | 承認した計画 |
| **B-2** | **コミット1=土台／2=Tag／3〜7=Todo。各コミットで テストを書く → 赤を確認 → 実装 → 緑** | 7コミット |

### コミット規約（配る）

| # | コミット | 中身 |
|---|---|---|
| 1 | **土台** | Entity / Form / Query / Mapper インタフェース / Mapper XML の枠。**テストは書かない** |
| 2 | **Tag 5本** | Tag の CRUD |
| 3〜7 | **Todo 1本ずつ** | `POST` → `GET(1件)` → `GET(一覧)` → `PUT` → `DELETE` |

**Tag を先に置く**: Todo の登録・更新が Tag の存在チェックを要求する。

**土台もAIに作らせる。テストは書かせない。**
**テストが参照する型（Entity・Form・Query）は先に置く**のが TDD でも普通で、**中身は空でよい**。Java では型が無いとテストがコンパイルできず、`mvn test` そのものが回らない。**土台が入ってから Red → Green が回る。**

### B-2 で渡す指示（要点だけ）

```
1コミットずつ、次に進む前に必ず確認を取ってください。各コミットで:

1. そのコミットで満たす受入条件（仕様確定.md §3）をテストにする
   - テストは実装ではなく仕様から書いてください
   - 参照実装に合わせてください（統合テスト。モックは使わず、
     HTTPリクエストから実DBまで通す）
2. mvn test を実行し、落ちることを確認して出力を見せてください
   - 落ちなかったテストがあれば列挙し、なぜ落ちなかったかを書いてください
3. 実装してください。1 で書いたテストは変更しないでください
   変更が必要だと思ったら、変更せずに理由を報告してください
4. mvn test と mvn checkstyle:check を通してからコミットしてください

★設計書と違う実装にしたら、docs/仕様確定.md §2 に1行足してから
  報告してください（出所は「実装中」）。
頼んでいないファイル・テーブル・依存（pom.xml）は変更しないでください。
```

### auto は禁止

**ステップごとに承認させる。** 目的は**開発フローをイメージできるようになること**で、auto だと流れが見えない（実験では一度も確認を挟まず完走した）。

### ★テストで何が担保できて、何が残るか

**2つの軸が独立している。**

| | **機械で判定できる** | **目視でしか判定できない** |
|---|---|---|
| **仕様を読めていた** | **B で終わる**（テストが緑になる） | **C-2**（受入条件の「目視」行） |
| **読み漏らした／誤読した** | **テストが書かれないので緑のまま。C で設計書に戻って初めて気づく** | **一番出にくい。C-3 の問いと C-4** |

**左下に注意。**「読めた**つもり**で誤読していた」場合、**テストはその誤読を固定する**。

> **テストは実装と同じ仕様解釈から生まれる。だから仕様の読み間違いを検出できない — 固定する。**

実測では、**設計書の文言なら404のものを「201が正しい」とアサートするテスト**が書かれ、緑になっていた。
**「51件green」が保証するのは「実装が、実装者の解釈どおりに動く」ことだけ。** ここが C の存在理由。

### ⚠ 赤を見せさせることの限界

**「テストは仕様から書け」は守ったか確認できないが、「赤を見せろ」は機械的に検証できる。** ただし2つ抜ける。

| | |
|---|---|
| **偶然一致** | **404 を期待するテストは、そのパスにハンドラが無いと実装前に通る。** 最初のコミットほど Red が弱い |
| **アサートの一部しか走らない** | `@ExpectedDatabase` は成功時のみ検証。**「赤を見た」≠「全アサートを通した」** |

## 7. C 確かめる

**答えを配らない。問いだけ渡す。講師も答えを持っていない。**

| | 作業 | 出力 |
|---|---|---|
| **C-1** | **`git diff` で変更範囲を見る**（コミット単位で） | 検証記録 1 |
| **C-2** | **受入条件（`仕様確定.md` §3）と突き合わせる**（**「目視」行が作業リスト**） | 検証記録 2 |
| **C-3** | **問いに答える** | 検証記録 3 |
| **C-4** | **AIに成果物をレビューさせ、仕分ける** | 検証記録 4 |

### C-4 で何をさせるか

**自分の成果物を、同じAIにレビューさせる。** 追加の教材はゼロ。

```
このブランチの実装をレビューしてください。
設計書・docs/仕様確定.md・CLAUDE.md を読んだうえで、
問題がある箇所を挙げてください。
```

**出てくるのは10〜20件の指摘。それを3つに仕分ける。**

| 指摘の例（実測より） | 判定 | 理由 |
|---|---|---|
| `TagController.getTags` に `@Valid` が無い | **正しい** | 付け忘れ。`TodoController` には有る |
| Entity をそのままレスポンスに返している | **的外れ** | **アーキテクチャ図が「今回アーキテクチャを省略し、1つのクラスにまとめています」と明記している。AIはその注記を読んでいない** |
| Tag削除の順序が FK の不在に依存している | **判断できない** | DB定義書は複合PK、DDLは制約なし。**どちらが正本かは仕様管理者にしか決められない** |

**★4列目に「的外れの理由」を分類させる。** ここが本題。

> **的外れの理由をまとめると、「自分が渡していない情報は何か」が出てくる。**

実測での分類例: **アーキ図の注記／`仕様確定.md` に書いていない決定／2か月目の教材の文脈**。
**「AIでAIを検証する」限界がここで体験できる。**「レビューbotを入れれば安心」という誤解を先に潰せる。

### 検証記録の雛形（**AIに渡さない**）

```markdown
# 検証記録（AIに渡さないこと）

## 1. 変更範囲
頼んでいないファイルが変わっていないか（コミット単位で確認）
→

## 2. 受入条件との突き合わせ（仕様確定.md §3 の番号で引く）
| §3 の # | 検証手段 | 結果 | 判断 |
|---|---|---|---|
| 1 | テスト | あり・通過 | OK |
| 5 | 目視 | LEFT JOIN 1本。SQLログで確認 | OK |

## 3. 問い
1. AIが勝手に決めたことは何か。それは正しいか。
   →
2. 設計書と違う実装になっている箇所はあるか。違反か、正しい最適化か。
   誰が決めてよいことか。上位者に上げるべきか。
   →
3. 外に出してはいけない情報が出ていないか。
   →
4. 動いた。では正しいと言える根拠は何か。
   →
5. Entity をそのまま返している。DBにカラムを1本足したら、レスポンスは
   何が変わるか。それは誰の許可が要るか。
   →
6. どこまで自分で確認し、どこからレビューを頼むか。なぜそこか。
   →

## 4. AIに自分の成果物をレビューさせた結果
| 指摘 | 判定 | 理由 |
|---|---|---|
|  | 正しい / 的外れ / 判断できない |  |

的外れの理由は何に分類できたか（＝自分が渡していない情報は何か）
→
```

**問いは正解のない、きっかけ。** 実測では**問いを渡さなくても12本中7本は出た**ので、問いは「AIに出させるための呼び水」ではなく**人が自分で見るための足場**（→ §10-25）。
**問い5（カラムを1本足したら）は、問いを渡して初めて出た3本のうちの1本**なので残す。

**⚠ 「分かりません」が2種類ある。** 実測で、検証役が**「自分では決められない」と「自分では思いつかなかった」を同じ袋に入れていた**。

> **前者は正直な報告。後者は確認漏れを謙虚さの言葉で包んだだけ。**

**線を引く基準はこれ。**

> **自分の観測で決着するものは、全部自分側。他人の同意が要るものは、全部相手側。**
> **難しいかどうか、時間がかかるかどうかでは切らない。**

### C で使う道具 — 新規はAIへの一文だけ

| 道具 | いつ習ったか | 何に使うか |
|---|---|---|
| `git diff` | 1か月目 | 頼んでいないファイルが変わっていないか |
| **Postman / ThunderClient** | 2か月目 | **動かして叩く。★テストで出ない継ぎ目はここでしか出ない** |

**⚠ 「動かして叩く」を1行で済ませると届かない。** 実測では、**捨てDBを立ててアプリを起動し `curl` で12パターン叩いて初めて**、51件greenをすり抜けたバグ（**一覧と1件取得が、同じデータで違う `tags` を返す**）が出た。**手順の具体が要る**（→ §12-19）。

### 停止条件

**目視の量はコード量ではなく、チェックリストの項目数で決まる。一巡したら終わり。**（`11` §8）

**⚠ チェックリストは1本ではない。** 実測で、検証役が「DoD の7項目は一巡した」で閉じかけ、自分で訂正した。

> **チェックリストは少なくとも3本あった —— DoD、コーディングガイド、受入条件。1本だけ一巡して「一巡した」と言った。**

**停止条件の手前に「渡された規約書を全部並べる」を置く。**

**終わったときに言うのはこれ。**

> **「このリストは見た。これ以外は自分では分からないので、レビューを頼みたい」**
