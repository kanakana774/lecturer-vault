# 模範アプローチ — A 入力を整える

## これは何か

| | |
|---|---|
| **示すもの** | **唯一の正解ではなく、アプローチの一例** |
| **示すタイミング** | **本人が自分のやり方を出しきったあと。**議論のあと |
| **何のために** | **自分のやり方と比べる材料。**比較があって初めて議論になる |
| **⚠ 置き場** | **リポジトリに置かない**（`03_研修環境とガードレール.md` §8。AIが勝手に読みに行く） |

**「答えを配らない」は破っていない。** 配るのは答えではなく議論の材料。

## Playbook のどこを使ったか

**Playbook は6ステージ（01 Plan / 02 Design / 03 Build / 04 Test / 05 Deploy / 06 Maintain）に分かれ、各ステージが「プレイ」を持つ。**

> **"Each play covers: What changes; Getting started; Concrete steps for implementation; Governance considerations; and How you measure whether it worked."**

**A に効くのは4つのプレイだけ。ステージはまたいでいる**（A は Playbook の1ステージに対応しない）。

| Playbook のプレイ（見出しのまま）                                   | ステージ      | 研修の手                |
| ------------------------------------------------------- | --------- | ------------------- |
| **Requirements and design**                             | 02 Design | **手1〜3**（設計書を精緻化する） |
| **The CLAUDE.md**                                       | 03 Build  | **手4**              |
| **Give Claude a feedback loop**                         | 04 Test   | **手5**（**考え方だけ。**受入条件という一覧は Playbook に無い） |
| **Claude Code plan mode as the default starting point** | 03 Build  | **手6**（着手判定）        |

**★手3（フレームワークの既定を挙げさせる）に対応するプレイは Playbook に無い。** こちらの実測から起こしたもの。

> [!warning]- 出典の精度について（2026-09-01）
> **初稿では「Stage 3 に `Before Delegating to Claude` という4項目がある」と書いていたが、これは誤り。**
> **そのような見出しはページに存在しない。**要約を経由して読んだときに、要約側が作った区分だった。
> **見出しを取り直して差し替えた。**以降、この文書に `"..."` で囲んだ英文は**ページからの逐語引用**。

|---|---|---|
| `intent.md`（何がしたいか） | **無し。**課題として与えられる | — |
| **`spec.md`（要件＋設計）** | **配られた設計書一式** | 仕様管理者（講師）。**研修生が書き戻す** |
| **`plan.md`（実装計画）** | **手6 で出させる計画** | 研修生が承認する |

| `REVIEW.md`（レビュー方針） | 2か月目のレビュー観点で代用 | — |
| Skills / Hooks | **使わない**（後述） | — |
| **（対応なし）** | **`受入条件.md`** | **★研修固有。**下記 |

### ★ `受入条件.md` は Playbook に対応物が無い

**"acceptance criteria" も "definition of done" も、ページに一度も出てこない。**
**Playbook は完了の基準を2箇所に分けて置き、独立した一覧を持たない。**

| | どこ | 例（逐語） |
|---|---|---|
| **変更ごと** | **`plan.md` の Proof 節**（インライン。別文書を参照しない） | **"test_status.py covers the four claim states; screenshot matches the approved mock."** |
| **常に守る** | **`CLAUDE.md` の検証ブロック** | **"Test: make test (all green; never skip or delete a failing test)"** |

> **"Commit the approved plan as `plan.md`. The plan joins the audit trail, and the PR review play checks the eventual diff against it."**
> **完了の基準は `plan.md` 自身が持つ。**

**なぜ研修では1枚にまとめるか**

| | |
|---|---|
| **7コミットに分かれる** | **変更ごとの Proof だけだとコミットごとに散る。**C で全体を突き合わせられない |
| **DoD 由来の常時条件がある** | N+1・3層構成。**`plan.md` 側にも `CLAUDE.md` 側にも収まりが悪い** |
| **C-2 の作業リストになる** | **「目視」の行がそのまま作業になる。**1枚で見たい |

**★「証明」節を受入条件への参照として使うのも、こちらの決めごと。** Playbook の Proof はテストを名指しするだけ。

## 6手

### ① 材料を集める

#### 手1 棚卸し — 何が配られたか、AIに一覧させる

> **「このリポジトリにある資料を全部挙げて、それぞれ何を決めている文書か1行で説明して」**

**出てくるもの:** 6つの設計書（要件定義書・アーキ図・DB定義書・OpenAPI・エラーコード表・プログラム設計）＋ `CLAUDE.md` ＋ 雛形2つ。

**なぜ効くか:** **読まずに済ませる資料を決められる。** `12` で「通読するのは要件定義書とアーキ図だけ」としているのは、**残りは必要になったときに開くほうが速い**から。何があるかを知らずには、その判断ができない。

**⚠ ここでアーキ図の「今回アーキテクチャを省略する」という注記を拾えるかが、後で効く。**
拾えていないと、C-4 で「Entity をそのまま返している」という**的外れな指摘**を正しいと誤判定する。

#### 手2 資料間の矛盾を洗い出させる

> **「6つの資料を突き合わせて、食い違っている箇所と、どこにも書いていない箇所を、根拠つきで全部挙げて。推測で埋めないで」**

**出てくるもの（実測ベース）**

| 出るもの | 根拠 |
|---|---|
| content の最大文字数が違う | 要件定義は30、DB定義は100 |
| Tag削除時の `todo_tag` の扱い | DB定義書に記載なし |
| 同名のTagを登録できるか | UNIQUE 制約が無い |
| 進捗状況という項目 | 要件定義 3.1 にあるが DB設計にない |
| Tag削除の順序が FK の不在に依存 | DB定義書は複合PK、DDLは制約なし |
| 部分一致の `%` `_` の扱い | どこにも無い |

**★ここは AI が得意。人が6資料を突き合わせるより速く、漏れない。**
**「AIを使った効率的な仕様把握」の実体はここ。**

**⚠「推測で埋めないで」が要る。** 言わないと、AIは**もっともらしい答えを書いて矛盾を消してしまう**。

---

#### 手3 ★フレームワークの既定が決めてしまう箇所を挙げさせる

> **「設計書に書いていないせいで、MyBatis / Jackson / Bean Validation / 既存の共通例外の既定が"決めてしまう"箇所を挙げて」**

**★これが一番差がつく手。** 手2 では出ない。**資料を突き合わせても出てこないから。**

**実測で出た5件は、全部この形だった。**

| 何が起きたか | 誰が決めたか |
|---|---|
| 重複行が畳み込まれた | **MyBatis の既定** |
| レスポンスに全フィールドが出た | **Jackson の既定** |
| 「30文字」の数え方 | **Java の既定**（サロゲートペア） |
| 型不一致で 500 が返った | **既存の共通例外** |
| 空白1文字が通った | **バリデーションの既定** |

> **`06_研修の芯.md`「決めなければ、フレームワークが決める」**
> **L1 の考慮漏れは「決まらないまま」では終わらない。必ず何かが決める。そして誰も担保していない。**

**この手を打たないと、5件は B で実装されるまで表に出ない。** 打てば、**A の時点で「未回答」として印をつけられる。**

**★A の良し悪しは、ほぼここで決まる。**

### ② 制約を書く

#### 手4 `CLAUDE.md` を仕上げる

**プレイ「The CLAUDE.md」の "How to execute it" は5手。うち3手が研修に効く。**

> - **"Cut the generated file down to what a new joiner would need on day one."**
> - **"When Claude makes a mistake twice, the correction goes into `CLAUDE.md`."**
> - **"Keep it under a page, because Claude reads all of it at the start of a session and anything stale is taking up context for no benefit."**

**★1つめが「新入社員が初日に必要なものまで削れ」。** 研修そのものの読み手と一致する。
**★3つめの「1ページに収めろ」が、skill 化を保留した判断の裏付けになる**（→ 後述の「あえて外したもの」）。

> [!note]- 2つめは研修では回らない
> **"When Claude makes a mistake twice"** は**同じ失敗を2回見て初めて足す**という手なので、**1週間・1周では回らない。**
> これは `06_研修の芯.md` の到達ライン **「1年 — 渡すコンテキストを育てられる」** の内容。**最後に一言で触れるだけにする。**

**配った時点であるもの:** DoD 9項目、3層構成、B の4手、`mvn` コマンド。

**研修生が足すもの（この課題で効くのは3行）**

| 足す行 | なぜ要るか |
|---|---|
| **「自分のローカルPCで動かす前提。デプロイ・スケール・監視は考慮しない」** | **書かないと考慮が無限に終わらない。**「デプロイ環境は？」と聞いてくる |
| **「足りない情報があれば、推測せず全部聞いてください」** | **`06`「AIは聞かなければ言わない」。**言わないと黙って決める。**手6 の前提** |
| **「参照するのはこのリポジトリと `todo-app-api-docs/` だけ。他のブランチは見ないでください」** | **`03` §8。**AIは渡していない情報源を自分から探しに行く |

**⚠ 3行目は保険。** 本体の対策は「**リモートを C-5 まで足さない**」（`12` 参照）。

### ③ 完了を数える

#### 手5 受入条件を、検証手段まで書く

**プレイ「Give Claude a feedback loop」の "How to execute it" は7手。研修に効くのは3つ。**

> - **"State a target and make it quantifiable so Claude can check the work without asking you."**
> - **"Make verification part of 'done.'"**
> - **"Finally, the loop itself needs protecting, because an agent fixing code must not be able to weaken the check."**

**★1つめが「検証手段」列そのもの。** 数えられる形にしないと、AIが自分で確かめられない。
**★3つめが B-2 ③「①のテストは変えない」の裏付け。** 直す側が検査を弱められてはいけない。
**Playbook はここを hook で機械的に塞ぐが、研修では `CLAUDE.md` の1行にしている**（新規技術を増やさないため）。

**この手でAIに言うこと**

> **「決定した仕様から、受入条件を洗い出して。それぞれ、テストで機械的に確かめられるか、人が目で見るしかないかを分けて」**

**★「検証手段」列まで書かせるのが肝。** 条件だけ並べても、C で何をすればいいか決まらない。

```markdown
| # | 条件                                | 出所   | 検証手段       |
|---|-------------------------------------|--------|----------------|
| 1 | POST /todos content 空文字は 400    | AI     | テスト         |
| 2 | content 101文字は 400               | 設計書 | テスト         |
| 5 | 一覧取得で N+1 を発生させない       | DoD    | 目視（SQLログ）|
| 6 | 3層構成を維持する                   | DoD    | 目視           |
```

**テストにできるのは半分程度。** 残りは人が目で見るしかない。**「目視」の行が、そのまま C の作業リストになる。**

**⚠ DoD 9項目から漏らさない。** AIは設計書からしか条件を出さないので、**DoD 由来の行は自分で足す**。

**★同じ紙に「対象外（やらないこと）」を書く。** これは**AIに聞かない。自分で書く。**

```markdown
## 対象外（やらないこと）
- 認証・認可の実装（2か月目の SecurityConfig をそのまま使う）
- デプロイ・スケール・監視（ローカルPCで動けばよい）
- 画面（APIのみ）
- 触ってよいのは src/ と docs/ だけ。pom.xml は依存を足さない
```

**なぜ要るか:** **C-1 の「頼んでいないファイルが変わっていないか」は、頼んだ範囲を書いていないと言えない。**
**事後に「どこを見ていないか」を数えるには、先に地図が要る。**
**AIに聞かないのは、対象外は仕様ではなく本人の宣言だから。**

### ④ 計画で確かめる

#### 手6 インタビューさせて実装計画を出させる（＝着手判定）

**プレイ「Claude Code plan mode as the default starting point」がそのまま使える。**

**何を出させるか（"How to execute it" より）**

> **"The engineer gives Claude the `intent.md` and the `spec.md` and asks for an implementation plan that names the files that change, the order of the work, and the tests that prove it."**
> （**変わるファイル／作業の順序／それを証明するテスト**を挙げさせる）

**どこまで往復するか — ★これが着手基準の言い換え**

> **"Iterate until an engineer who has never seen the conversation could implement the change from the plan alone."**
> （**その会話を一度も見ていないエンジニアが、計画だけで実装できる**ところまで往復する）

**「渡したものだけで実装が一意に決まる」＝「会話を見ていない人が、計画だけで実装できる」。**
**★研修生への説明は、この言い方のほうが伝わる。**

> [!note]- Playbook の前提と、研修の前提の違い
> Playbook は plan mode の **Prerequisites** をこう書いている。
> **"The intent artifact (`intent.md` or `spec.md`) if one exists, and the `CLAUDE.md` file helps."**
> **"if one exists"** ——**無くても始められる**前提。**研修では設計書が必ず配られる**ので、ここは研修のほうが条件が良い。
> **だから研修の焦点は「spec を作る」ではなく「配られた spec を、渡せる状態まで精緻化する」**になる。

**やること — 4手**

**(0) ★ まず、決めることになる事項を直接列挙させる**

> **「実装するとして、あなたが独断で決めることになる事項を列挙して。実装はしないで」**

**AIは生成が得意で、自分から止まるのが苦手。** その性質を逆に使う。
**「不明なら聞け」という指示は効果が薄い**（何が不明かをAI自身が判定できないため）。**列挙させるほうが直接的。**
**列挙された項目に自分が即答できなければ、準備不足。**

**⚠ 列挙ゼロは準備完了の証拠にならない。** 網羅性は保証されない。**だから (1)〜(3) も要る。**

**(1) 新しいセッションを開き、渡すものだけを見せて実装計画を出させる**

> **「実装計画を出して。下の4節で書いて。足りない情報があれば推測せず全部聞いて」**

```markdown
## 変更するファイル
## 作業の順序
## リスク
## 証明          ← どの受入条件を、どのテストで満たすか
```

**★4節目「証明」を落とさない。** 「作る計画」だけ出させると、**完了の判定が計画に入らない。**

**⚠ Playbook の `Proof` はテストを名指しするだけで、別文書を参照しない。**
**「どの受入条件を満たすか」まで書かせるのは研修の決めごと**（→ 上の「`受入条件.md` は Playbook に対応物が無い」）。
**7コミットに分かれるので、ここで紐づけておかないと C で全体を突き合わせられない。**

> [!note]- Playbook の `plan.md` の実物
> ```
> ## Files that change
> portal/src/claims/StatusPanel.tsx (new), claims-api/routes/status.py, ...
> ## Order of work
> 1. Add the status endpoint behind existing auth. ...
> ## Risks
> The claims-core API rate-limits at 50 rps; the panel must cache.
> ## Proof
> test_status.py covers the four claim states; screenshot matches the approved mock.
> ```

**(2) 計画を詰問する**

**Playbook の "How to execute it" の2手目。3つ聞く。**

> **"Interrogate the plan by asking what could break, which step is riskiest, and what alternatives were rejected"**

| 聞くこと | なぜ効くか |
|---|---|
| **何が壊れうるか** | 計画が触っていない範囲への影響が出る |
| **どの手が一番危ないか** | 順序の妥当性が確かめられる |
| **★捨てた代替案は何か** | **AIが黙って決めたことを吐かせる**（`06`「聞かなければ言わない」） |

**★3つめが本命。** 「捨てた代替案」を聞かないと、**選ばれなかった方は永久に見えない。**

**(3) AIが自分で決めた箇所を、1つずつ処理する**

| 印 | 意味 | どうする |
|---|---|---|
| **聞いて設計書を直した** | 仕様管理者に聞いて答えが出た | **設計書に書き戻す** |
| **決まらないと知って進む** | 下の2つだけ | **`確認事項.md` に「未回答」で残す** |

**「決まらないと知って進む」に入ってよいのは2つだけ**

| | 例 |
|---|---|
| **聞いても決まらなかった** | Tag削除の順序が FK の不在に依存。**DB定義書は複合PK、DDLは制約なし。どちらが正本かは仕様管理者しか決められない** |
| **時間切れで聞けなかった** | 部分一致の `%` `_` の扱い |

**★「聞けば決まる」ものがここに並んでいたら、A が甘い。**
content の最大文字数（要件定義は30、DB定義は100）は**聞けば答えが出る**ので、ここには入らない。**評価の議論はそこを突く。**

**⚠ 新しいセッションでやる。** 同じセッションだと、**会話の中で口頭で埋めた情報がAIに残っている**ので判定にならない。**渡したファイルだけで成立するかを見たい。**

> [!warning]- Playbook の `answered or carried forward` をそのまま持ち込まないこと（2026-09-01）
> Design のゲートに **"are the open questions from `intent.md` answered or carried forward?"** とあるが、
> **これは `intent.md` の open questions に掛かっている。発案者の疑問なので機能単位。**
> **実装者が聞きたい粒度とは違う**（「content は30文字か100文字か」を product owner が次に先送りすることはない）。
>
> **Build 段階の停止条件は別物で、こちら。**
> **"Iterate until an engineer who has never seen the conversation could implement the change from the plan alone."**
> **質問が片付いたか、ではなく、計画が実装できるか。**だから研修も「質問の仕分け」ではなく
> **「AIが自分で決めた箇所を把握しているか」**にした。

### 実装計画の雛形は配らない

**節の名前を `CLAUDE.md` に1行書くだけにする。**

> **実装計画は「変更するファイル／作業の順序／リスク／証明」の4節で書いてください。**

**配布物を増やさない**（8/31 指摘1）。**AIに出させるものなので、雛形を配ると「埋める作業」に見えてしまう。**

### 用語 — 個有名以外は日本語にする

**研修生に渡す言葉は日本語。** Playbook の引用は出典なので原文のまま（この文書は講師用）。

| Playbook | 研修での名前 |
|---|---|
| `plan.md` | **実装計画** |
| Files that change / Order of work / Risks / **Proof** | **変更するファイル／作業の順序／リスク／証明** |
| `spec.md` | **配られた設計書** |
| Open questions | **`確認事項.md`** |
| **`CLAUDE.md` / `.claude/settings.json`** | **変えられない。**Claude Code が読むファイル名 |

**★「受入条件」「証明」「テスト」は3段に分かれる。名前を混ぜない。**

| | 何を持つか | いつ |
|---|---|---|
| **受入条件** | **何が満たされれば完了か** | A（手5） |
| **実装計画の「証明」節** | **どの受入条件を、どのテストで満たすか** | A（手6） |
| **テストコード** | ケースと期待値 | B |

**2か月目の「テスト仕様書」とは別物**として置ける（2026-09-01 決着。`13_議事録/2026-08-31_水谷さん.md` の未決「雛形の名前」への答え）。

## この一例が「良い」と言える根拠

**A の良し悪しは C で数として出る**（`12` の評価節）。**この6手を打つと、こう減る。**

| C で出るもの | どの手が効くか |
|---|---|
| **`確認事項.md` の「いつ＝B」の行**（AIが勝手に決めた箇所） | **手3**（既定の洗い出し）が最も効く |
| **検証手段の無い受入条件** | **手5** |
| **C-4 の「的外れ」** | **手1**（アーキ図の注記）・**手4**（前提を書く） |
| **A で印をつけていなかった穴** | **手3・手6** |

**議論では、この4つの数を材料にする。**
「あなたのアプローチはどうだったか」だけだと感想戦になるが、
**「B で AI が勝手に決めた箇所が7件あった。どこを渡していれば減ったか」なら具体になる。**

## 付録 — 「実装までに達成しておくこと」を素で洗い直した（2026-09-01）

**Playbook を読み込む過程で、道具の話が先に立ち、目的が見えにくくなった。**
**そこで、この検討の文脈を一切渡さない状態で3つの視点から洗い直した。**

| 視点 | 問い |
|---|---|
| **一般論** | 他人が書いた設計書一式を渡された新人が、着手前に達成しておくべきことは（ソフトウェア工学の一般論として） |
| **AI特有** | AIに実装をまるごと任せる場合、人が書く場合と比べて追加で要るもの／不要になるもの |
| **品質逆算** | 実装後に「担保できた範囲／できない範囲」を線引きするには、実装前に何が決まっている必要があるか |

### 3つとも同じ理由に行き着いた

> **事後に作った基準は実装に合わせて曲がる。**（一般論）
> **出てきてから決めると、出てきたコードの構造に引きずられて観点自体が汚染される。**（AI特有）
> **参照点を実装から作れば差分は定義上ゼロになる。**（品質逆算）

**実装前の作業は「早くやるため」ではなく、「汚染される前に固定するため」。**

### 結論 — 2種類・5つ

| | 何が起きるか | どれ |
|---|---|---|
| **決まらないと書けないもの** | **止まる。**あるいは勝手に決まる | **3・5** |
| **あとから作ると汚染されるもの** | **書けるが、根拠として使えなくなる** | **1・2・4** |

**5つの本体は `12_研修の流れ_説明用.md` の A 章冒頭。**

### 洗い直しで見つかった抜け

| | どう埋めたか |
|---|---|
| **範囲（やらないこと）が無かった** | **`受入条件.md` に「対象外」節を足した。**C-1 の「頼んでいないファイルが変わっていないか」は、**頼んだ範囲を書いていないと言えない** |
| **矛盾の扱いが曖昧だった** | **矛盾は聞いて設計書を直して消す。**「決まらないと知って進む」に入れない |

> [!note]- 「正本の優先順位を先に合意する」案は採らなかった
> 一般論の視点からは、**「型は DB定義書が正、項目名は API仕様が正」といった優先順位を先に合意しておけば、**
> **軽微な矛盾は自力で裁定でき都度止まらずに済む**、という案が出た。大規模なら有効。
> **採らない理由:** 資料6つ・矛盾数件で**直せる規模**。そして優先順位ルールは**矛盾を残す前提**なので、
> **「実装と設計をずらさない」（8/31 水谷さん）と逆を向く。**仕組みが2つになるのも避けたい。
