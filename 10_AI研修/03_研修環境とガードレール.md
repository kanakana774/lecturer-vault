## 1. 期ごとに用意するもの

| | 誰が | 頻度 |
|---|---|---|
| **研修用リポジトリを1本作る**（テンプレートから） | 講師 | **期ごと1回** |
| **研修生の Team に write を付ける** | 講師 | **期ごと1回** |
| **Claude Code のシート**（法人契約） | 会社 | 契約は1回・人数分 |
| **`gh auth login`** | 研修生 | **1人1回・1〜2分** |

**新しい開発環境は用意しない**（→ §4）。**PAT の発行も、研修生ごとのリポジトリ作成も要らない**（→ §5）。

### `gh auth login` の手順

1. `gh auth login` → **GitHub.com** → **HTTPS**
2. **「Authenticate Git with your GitHub credentials?」は No。**
   **Yes にすると git の認証が gh 経由に切り替わり、GCM と二重管理になる**
3. ブラウザでデバイスコードを入力

**`gh` は GCM の資格情報を使わない。**git の push が通っていても、`gh` は別にログインが要る。
**既定スコープは `repo`** なので、**技術的にはそのアカウントが見える全リポジトリに届く。スコープでは絞れない**（→ §5）。

## 2. リポジトリは1本

**21人が同じ1本のリポジトリに、それぞれのブランチで PR を出す。**設計書も同梱する。

```
todo-training-YYYY/                  ← 期ごとに1本。private
├── CLAUDE.md                        AIへの指示。DoD 9項目・B の4手を含む
├── .claude/
│   ├── settings.json                allow / ask / deny（→ §5）
│   └── hooks/block-remote-read.ps1  ガードの実体（→ §5）
├── pom.xml ／ todo_checks.xml       2か月目と同じ ＋ checkstyle
├── src/                             2か月目の雛形 ＋ 参照実装1本
└── docs/                            ★設計書一式 ＋ 確認事項.md ／ テストケース一覧.md の空雛形
```

**分けない理由:** 「配られたものと渡したものの差分」は **`git diff main...task -- docs/`** でサブディレクトリ単位に出る。
**リポジトリを分ける必要は無く、運用が半分になる。**

> [!note]- 同梱すると、AIが設計書を読める状態が既定になる
> **試走で一番効いた発見は「AIは渡していない仕様には届かない」だった**（`%` `_` のエスケープに一言も触れなかった）。
> **同梱はその発見を弱める方向に効く。**
> ただし**実務では設計書もリポジトリにあるのが普通**で、何を渡すかは結局プロンプトの問題として残る。
> **実務に寄せる判断として同梱を選んだ**（2026-09-14）。

**`振り返り.md` だけはリポジトリの外で配る。**中に置くと `CLAUDE.md` 経由でAIが読む（試走で実証済み）。

## 3. AIアカウントは法人契約（譲れない）

**個人アカウントは不可。**

- 無料・個人プランは**入力がモデルの学習に使われる**設定のことがある。会社のコードを投げる場に使えない
- **監査ログが残らない**ため、誰が何を投げたか後から追えない
- メンバー管理・SSOがなく、退職・異動時に止められない

**ライセンス数＝研修生数＋講師分。**

> **SES固有の注意:** 研修で使う法人アカウントは**自社契約**であって、配属後に客先へ持ち込めるとは限らない。
> **「研修と現場は別」を最初に言っておく**（→ §6）。

## 4. 開発環境は2か月目のまま

研修生は**2か月目に自分で環境を構築している** — Maven・PostgreSQL・Postman/ThunderClient・CheckStyle・SonarLint。
**3か月目の最終週なら手元にある。**

**新しい環境を用意しない。**1週間しかないのに環境構築で1日溶けるのが最悪の失敗。
**追加で要るのは Claude Code のアカウントと `gh auth login` だけ。**

## 5. ガードレール — フック1本で塞ぐ

**塞ぐ相手は3つ。**

| 経路 | 中身 |
|---|---|
| **同じリポジトリの他の研修生のPR** | **21人が同じ1本に出すので、read があれば全員分見える** |
| **2か月目の `todo-app-api`** | **21人分の完成ブランチと `answer-sample`。いちばん危ない** |
| 過去期の研修リポジトリ | 前年の完成品 |

**GitHub に「PR単位の可視性制御」は無い。**リポジトリの read があれば全PRが見える。
**コマンドの allow/deny でも絞れない** —— `gh pr view -R owner/repo 1` で他リポジトリに届くため。

### 原則: PR番号を指定させない

**`gh pr view` / `gh pr diff` / `gh pr comment` は、番号を省くと「現在のブランチのPR」を対象にする。**
研修生は自分のブランチで作業しているので、**番号なしの形だけ許せば、対象は必ず自分のPR。**

| 形 | |
|---|---|
| `gh pr view --comments` ／ `gh pr diff` ／ `gh pr comment -b "..."` ／ `gh pr create` | **許可** |
| **`gh pr view 3`**（番号あり） | **ブロック** |
| **`gh pr view -R owner/repo 1`**（リポジトリ指定） | **ブロック** |
| `gh pr list` / `gh pr checkout` / `gh api` / `gh repo` / `gh search` / `gh browse` / `gh auth` | **ブロック** |
| **`git fetch` / `git ls-remote` / `git clone` / `git pull`** | **ブロック**（`refs/pull/*/head` で他人のPRを直接取れる） |

**これで自分のPRのコメントは読める。**「レビュアーの指摘をAIに渡して直させる」という実務どおりの使い方が残る。

### フックの実体

`.claude/hooks/block-remote-read.ps1`（PreToolUse / matcher は `Bash`、終了コード2でブロック）

```powershell
$in = [Console]::In.ReadToEnd() | ConvertFrom-Json
$cmd = $in.tool_input.command
if (-not $cmd) { exit 0 }

$deny = @(
  'gh\s+(api|repo|search|browse|auth|release|gist)',
  'gh\s+pr\s+(list|checkout)',
  'gh\s+pr\s+\w+.*(\s-R\s|\s--repo\s)',
  'gh\s+pr\s+(view|diff|comment)\s+\d',
  'git\s+(fetch|clone|ls-remote|pull)',
  'api\.github\.com'
)
foreach ($p in $deny) {
  if ($cmd -match $p) {
    [Console]::Error.WriteLine("研修環境ではブロックされています（他の研修生のPRに到達しうるため）。自分のPRは番号を付けずに gh pr view / gh pr diff で参照してください。")
    exit 2
  }
}
exit 0
```

**判定はハーネス側で行われるので、モデルの善意には依存しない。**

### 前提と、許容する穴

- **リポジトリが private であること。**未認証の `curl` では 404 になる。**public だとこの構成は崩れる**
- **フックは起動時に読み込まれる。**`.claude/settings.json` を書き換えて再起動すれば外せる。
  **研修生に悪意は無い前提で、ここは許容する**（2026-09-14 判断）
- **研修生自身がブラウザで他人のPRを見ることは止めない。**元から org にアクセスできるので、
  **AIに混ぜられるのとは危険度が違う。**注意もしない
- **カンニングの価値自体が低い。**評価は成果物の正しさではなくアプローチの議論なので、
  **他人のケース一覧を写しても、根拠を聞かれた時点で説明できない**

## 6. ⓪ガバナンスの根拠

**⓪で教える4点**（客先のルールを確認する／渡してはいけないものを渡さない／何を渡したか記録する／AIに書かせた部分を PR で明示する）には、**一次情報の裏がある。**

| | |
|---|---|
| **経産省「AIの利用・開発に関する契約チェックリスト」**（2025年2月） | 秘密保持・第三者提供・知財侵害のリスク |
| **IPA「テキスト生成AIの導入・運用ガイドライン」**（2024年7月） | 同上 |
| **客先常駐の契約上の整理** | **常駐先の情報管理規程の順守が前提。客先コードを生成AIに入力すると第三者提供とみなされ得る**（法務・人材系メディア複数で一致） |

**AI利用の開示は、OSS では必須化が進んでいる**（MicroPython は全PRで開示必須。Python・NumPy・Django・Kubernetes・Linux カーネルも**AI支援は許可、開示は必須**）。
**ただし `Co-Authored-By` でAIを共著者にするのは避ける方向**で、`Assisted-by:` 等の専用トレーラーを使う例が複数（attrs・pip）。
**粒度と方法は会社ごとに割れているので、「開示すること」だけを作法として教え、粒度は客先のルールに従わせる。**

**「テストに合格してから解禁」は LINEヤフーコミュニケーションズの形をそのまま採っている**（全社共通テストを100点で合格してからAI利用を許可）。
他社も**触らせる前に「なぜ間違えるか」を理解させる**順序で揃っている（ベリサーブ・サイバーエージェント）。

### AIレビューボットを置かない理由

**費用ではなく運用の都合。**

| | |
|---|---|
| **GitHub Copilot code review** | **Copilot のシート課金に含まれる**（追加のAPI従量課金は不要） |
| **CodeRabbit** | **自社SaaSのシート課金**。LLM費用はベンダー持ち |
| **Actions で `@claude` を回す** | **`claude setup-token` の OAuth トークンでサブスク枠を使える**が、**トークンは個人のサブスクに紐づく。21人分のPRを講師のトークンで捌く運用は公式に想定されていない** |

→ **ローカルで走らせて、結果を自分でPRにコメントする。**実務との違いは**起動が手動なだけ**。
**日本でのAIレビュー導入は先進企業から始まっている段階**で、業界全体の導入率を示す統計は見つからなかった（日経新聞社・TIS・スパイダープラス・SalesNow の個別事例のみ）。

## 8. 模範解答・他人の成果物への経路（旧版からの継続論点）

**AIは「渡していない情報源」を自分から探しに行く。** P2 の実験中、渡していない `04.開発資料`（コーディングガイド）や
`05.講義資料` を勝手に読みに行った（`02_実験_プロンプト差の検証.md` §統制）。**カンニングが事故として発生しうる。**

| 経路 | 現在の扱い |
|---|---|
| **2か月目リポジトリの `answer-sample*` ブランチ** | **§5 のフックでブロック**（`git fetch` / `gh` 経由の両方） |
| **他の研修生の `task/*` ブランチ・PR** | **同上。番号指定とリポジトリ指定を塞ぐ** |
| **過去期の完成品** | **期ごとにリポジトリを作り直す。旧リポジトリの権限を外す** |
| **講師の模範アプローチ・見本** | **リポジトリに置かない**（`14_模範アプローチ.md` / `16_見本_Aの1周.md` / `17_見本_PR.md` は vault 内に置く） |

**旧版では「A（模範解答を別リポジトリに分離）＋ D（プロンプトログの事後検査）」を推奨としていた。**
**いまは §5 のフックが主で、A は「期ごとに新しいリポジトリを1本作る」という形で自然に満たされている。**

> これは **AI研修だけの問題ではない。**既存の3か月カリキュラムでも、研修生が個人的にAIを使えば同じことが起きる。
> **いま「AI禁止」で成立している安全性が、解禁と同時に崩れる**という構造。
