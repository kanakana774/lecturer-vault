## ★★18 B-1「動いた。では正しいのか」— テストが仕様の読み間違いを固定する

**検証役の言葉がそのまま結論。**

> **テストは実装と同じパスで、同じ仕様解釈から同時に生まれている。だから仕様の読み間違いを検出できない — 読み間違いを固定する。**

| 実例 | |
|---|---|
| `TodoPostTest.sameTagIdTwice` | **設計書の文言なら 404 のはずのものを、テストが「201 が正しい」とアサートしている。** テストは解釈を**検証していない、追認している** |
| 期待値の作り方 | `assertEquals(TestUtil.convertJSON(expected), actual)` の `expected` は**実装と同じ `TodoEntity` を直列化して**作る。**レスポンス構造の変化に原理的に盲目** |
| `@ExpectedDatabase` の期待XML | 同じ人が同じ理解で書いている |

**「51件green」が保証しているのは「実装が、実装者の解釈どおりに動く」ことだけ。**

**★これが `07 §5` の「⚠ Red は落ちうることしか証明しない」の一段深い説明。** 段③をどう組んでも、**テストと実装が同じ解釈から生まれる限り、仕様との一致は段④で人が手で突き合わせるしかない。**

検証役が置いた3段が使える。

| | 何で示せるか |
|---|---|
| (a) 実装が解釈どおり動く | **テストで示せる** |
| (b) 解釈が資料と合っている | **設計書を読み直して手で突き合わせるしかない** |
| (c) 資料が仕様と合っている | **判定不能**（DDL と DB定義書が矛盾している時点で「資料が正しい」の前提が壊れている） |

## ★★19 B-2「カラムを1本足したら」— 守っているのは Entity の設計ではなく隣の規約

**実測**（捨てDBにカラムを足してアプリを起動し、`SECRET-DO-NOT-LEAK` を grep）。

| やったこと | 結果 |
|---|---|
| `internal_memo` を tag と todo に追加して値を入れる | **4本のレスポンスすべてに出現0件。漏れない** |
| `owner_id integer NOT NULL`（default なし）を tag に追加 | GET は 200、**POST が 500** |

**なぜ漏れないか。Entity 直返しなのに漏れないのは、すべての SELECT が列を明示列挙していて `SELECT *` が1つも無いから。**

> **このコードを守っているのは Entity の設計ではなく、DoD の「`SELECT *` を使わない」という別の項目。** Entity 直返しは無防備なのに、たまたま隣の規約が防いでいる。

**★本当の露出は逆向き。** DB にカラムを足しても漏れないが、**Entity にフィールドを足すと Jackson が全レスポンスに載せる**。止めるものが無い。

- レスポンス専用の DTO が無い（`04 ㊶` の結論の帰結）
- `@JsonIgnore` も `@JsonInclude` も1つも無い
- **そしてテストが止めない** — 期待値が同じ Entity の直列化なので、**フィールドを足すと期待値にも同じフィールドが増え、テストは緑のまま通る**（★18 と同じ構造）

> **「OpenAPI に無いフィールドがレスポンスに出る」変更が、CI を1本も落とさずにマージできる。**

**誰の許可が要るか**も分かれた。**DBのカラム追加は DB/仕様担当。レスポンスの形が変わることは API仕様の所有者。厄介なのは後者が前者の許可だけで起きうること** — Entity にフィールドを足す作業は誰の許可も要らないように見えて、結果は API の契約変更。

**→ `07 §6` の問い8（Entity 直返し／カラムを1本足したら）は残す。** B として実際に機能した。
