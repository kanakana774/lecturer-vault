### ⚠ 土台コミットを 3-2 の前に置く（07 §5 との差）

**Java では「テストを先に書く」が単体で成立しない。**
`Entity` / `Form` / `Query` / `Mapper` インタフェースが無いとテストがコンパイルできず、**`mvn test` そのものが回らない**（`src/main/java` は `.gitkeep` だけの空フォルダで渡している）。

→ **7コミットの1番目（土台）を、テストを書かせる前に置く。** コミットの順序は変えない。

| 07 §5 の書き方 | 実際に回す順 |
|---|---|
| 3-2 テストを書かせる → 3-3 実装させる（コミット1が土台） | **3-2a 土台（コミット1）→ 3-2b テスト → 3-3 実装（コミット2〜7）** |

**この差は 07 §5 に反映する。**（→ `07 §5` の作業表）

### ★テストは統合テストにする（yafh は踏襲しない）

**`yafh-app-api` のテストは全てユニットテスト。** Controller層は Service をモックし（`standaloneSetup`）、Service層は実DBを使うが HTTP を通らない。**HTTPからDBまで通す統合テストは1本も無い。**

**それでは `決定事項.md` が受入条件にならない。**

| 決定事項 | Controller層ユニット（Serviceモック） | 統合テスト（HTTP→実DB） |
|---|---|---|
| 1 カラムは `title` ／ 3 登録時 `version = 0` ／ 9 `%` `_` をエスケープしない | **✗** | **○** |
| 2 同じ `tagId` で2行登録 ／ 4 Tag削除時に `todo_tag` も削除 ／ 5 同名Tagを登録できる | **✗** | **○**（`@ExpectedDatabase`） |
| 6 `name` は1〜30文字 | ○ | ○ |

**10件のうち6件がDBを通さないと検証できない。**「決定 → 受入条件 → テスト」の鎖が切れるので、**yafh に合わせるより自然さを取る**。

**参照実装の作り**（実物: `Desktop/ai-sim/todo-app-api`）

```java
@SpringBootTest
@AutoConfigureMockMvc
@TestExecutionListeners(
        value = TransactionDbUnitTestExecutionListener.class,
        mergeMode = TestExecutionListeners.MergeMode.MERGE_WITH_DEFAULTS)
@DatabaseSetup(value = "classpath:META-INF/dbunit/app/controller/todo/"
        + "todoGetByIdTest/setup.xml")
public class TodoGetByIdTest {
    @Autowired
    private MockMvc mockMvc;   // モックは使わない。実際のDIコンテナから取る
```

**yafh から引き継ぐもの**: `testTools`（`TestUtil` / `DatasourceConfig` に `TestMockMvcSetupUtil` と `ExceptionTester` を移植）、DBUnit の `setup.xml` / `expected*.xml` の命名、**アサーションは JUnit5 の `Assertions` のみ（AssertJ は使わない）**。
**変えるもの**: モックを使わない。**HTTPから実DBまで1本で通す。**

**実測**: `mvn test` で3件成功（`tagsExist` / `tagsEmpty` / `notFound`）。`mvn checkstyle:check` も通る。**開発用DB（`todo`）は触らず `todo_test` だけが更新される**ことを確認済み。

## 3-2b テストを書かせるプロンプト

```
段②で確定した受入条件をもとに、Todo と Tag、および両者の紐づけの
テストを書いてください。実装（Controller / Service）はまだ書かないでください。

- 設計書・決定事項.md と、CLAUDE.md の「完了の定義」を読んでください。
- テストは実装ではなく仕様から書いてください。
- 既存の testTools と、参照実装 TodoGetByIdTest の書き方に合わせてください。
  統合テストです。モックは使わず、HTTPリクエストから実DBまで通してください。
  事前データは DBUnit の dataset(setup.xml) で投入してください。
  dataset の置き場は、テストクラスのパッケージ＋クラス名の鏡写しにしてください。
- アサーションは JUnit5 の Assertions を使ってください（AssertJ は使いません）。
- 受入条件のうち「目視でしか判定できない」ものはテストにしないでください。
  代わりに、テストにできなかった条件を一覧で出してください。
```

**「テストは実装ではなく仕様から書いてください」がこの段の全部。**
この一文が無いと、AIは実装を読んでテストを書き、**実装のバグをテストが追認する**（`07 §5`）。

**「テストにできなかった条件の一覧」を出させるのが 3-2b の隠れた提出物。** これが段④で人が見るものの正体になる。

## 3-3 実装のプロンプト

```
承認した計画のとおり、コミット2から順に実装してください。

- 1コミットずつ進めてください。次に進む前に、必ず確認を取ってください。
- 各コミットで mvn test と mvn checkstyle:check を通してください。
- 3-2b で書いたテストは変更しないでください。
  変更が必要だと思ったら、変更せずに理由を報告してください。
- 頼んでいないファイル・テーブル・依存（pom.xml）は変更しないでください。
- 設計書と決定事項に書かれていないことは、書かれていないと明示してください。
```

**★「テストは変更しないでください」の3行が新規。** 07 §5 には無い。
**理由**: テストを先に書かせた以上、**実装を通すためにテストを緩める**逃げ道を塞がないと 3-2b が無意味になる。**変更させないのではなく、変更したいと言わせる**（言ってきた内容が仕様解釈の相違そのもの）。
