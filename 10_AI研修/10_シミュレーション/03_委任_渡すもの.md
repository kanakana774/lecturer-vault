## 3-1 環境

**段②を終えた状態のリポジトリ。** 段①の環境（`01_把握_渡すもの.md`）から増えるのは★の4つ。

| | 状態 |
|---|---|
| `決定事項.md` | **研修生が段②で埋めたもの**（決定10件 ＋「やってはいけないこと」） |
| `CLAUDE.md` | **完了の定義を内包**。「実装の前に `決定事項.md` を必ず読むこと」の1行つき |

| ★ `src/test/resources/application.properties` | **`todo_test` DB を指す。** 段①時点では `main` と同じ `todo` を指しており、テスト実行で動作確認データが壊れる |
| ★ **参照実装1本**（`GET /todos/{todoId}`） | **完成品を配る。** Entity / Mapper（＋XML）/ Service / Controller ＋ **Controller層の統合テスト1本**。`src/test/java/.../app/controller/todo/TodoGetByIdTest.java`、dataset は `META-INF/dbunit/app/controller/todo/todoGetByIdTest/setup.xml`。**テストの層と書き方をこれで固定する** |

### ★1コミットの中で Red → Green を回す（07 §5 との差）

**テストを全部先に書かせる形は破綻する。** 理由が2つある。

| | |
|---|---|
| **コンパイルできない** | `Entity` / `Form` / `Mapper` インタフェースが無いとテストが型を参照できず、**`mvn test` そのものが回らない**（`src/main/java` は `.gitkeep` だけの空フォルダで渡している） |
| **途中のコミットが全部赤になる** | 実装がコミット2〜7で徐々に入るので、**「各コミットで `mvn test` を通す」と両立しない** |

→ **コミットごとに「テストを書く → 赤を確認 → 実装 → 緑」を回す。** 作業の分割は要らなくなる。

| コミット | テスト |
|---|---|
| **1 土台** | **無し**（テストする振る舞いがまだ無い） |
| **2〜7** | **そのコミットの中で Red → Green** |

**これは TDD の Red-Green そのもの。**「**見たことのない失敗を信じるな**」——赤を一度も見ていないテストは、①何もアサートしていない ②実装を写している（トートロジー） ③もともと通る振る舞いを叩いている、のどれかである可能性を排除できない。

**★AIに対して特別に効く。**「テストは実装ではなく仕様から書け」は**お願い**なので守ったか確認できないが、**「まず赤になるのを見せろ」は機械的に検証できる**。
**赤が出ないこと自体が発見になる。** しかも赤の出力は**そのまま提出物**になり、段④の材料になる。

**⚠ 限界**: Red は「**落ちうる**」ことしか証明しない。期待値が仕様と違っていても落ちる。**そこは段④で受入条件と突き合わせる仕事として残る。**

**この差は 07 §5 に反映する。**（3-2a/3-2b/3-3 の3分割は廃止し、**3-1 環境と課題説明 / 3-2 委任** の2つにする）

### ★テストは統合テストにする（yafh は踏襲しない）

**`yafh-app-api` のテストは全てユニットテスト。** Controller層は Service をモックし（`standaloneSetup`）、Service層は実DBを使うが HTTP を通らない。**HTTPからDBまで通す統合テストは1本も無い。**

**それでは `決定事項.md` が受入条件にならない。**

| 決定事項 | Controller層ユニット（Serviceモック） | 統合テスト（HTTP→実DB） |
|---|---|---|
| 1 カラムは `title` ／ 3 登録時 `version = 0` ／ 9 `%` `_` をエスケープしない | **✗** | **○** |
| 2 同じ `tagId` で2行登録 ／ 4 Tag削除時に `todo_tag` も削除 ／ 5 同名Tagを登録できる | **✗** | **○**（`@ExpectedDatabase`） |
| 6 `name` は1〜30文字 | ○ | ○ |

**10件のうち6件がDBを通さないと検証できない。**「決定 → 受入条件 → テスト」の鎖が切れるので、**yafh に合わせるより自然さを取る**。

**参照実装の作り**（実物: `Desktop/ai-sim/todo-app-api`）

```java
@SpringBootTest
@AutoConfigureMockMvc
@TestExecutionListeners(
        value = TransactionDbUnitTestExecutionListener.class,
        mergeMode = TestExecutionListeners.MergeMode.MERGE_WITH_DEFAULTS)
@DatabaseSetup(value = "classpath:META-INF/dbunit/app/controller/todo/"
        + "todoGetByIdTest/setup.xml")
public class TodoGetByIdTest {
    @Autowired
    private MockMvc mockMvc;   // モックは使わない。実際のDIコンテナから取る
```

**yafh から引き継ぐもの**: `testTools`（`TestUtil` / `DatasourceConfig` に `TestMockMvcSetupUtil` と `ExceptionTester` を移植）、DBUnit の `setup.xml` / `expected*.xml` の命名、**アサーションは JUnit5 の `Assertions` のみ（AssertJ は使わない）**。
**変えるもの**: モックを使わない。**HTTPから実DBまで1本で通す。**

**実測**: `mvn test` で3件成功（`tagsExist` / `tagsEmpty` / `notFound`）。`mvn checkstyle:check` も通る。**開発用DB（`todo`）は触らず `todo_test` だけが更新される**ことを確認済み。

## 3-2 委任のプロンプト（2本）

### ① 土台（コミット1）

```
承認した計画のとおり、コミット1「土台」だけを実装してください。

- Entity / Form / Query / queryCondition / Mapper インタフェース と、
  MyBatis の Mapper XML の枠だけです。
- Controller と Service はまだ書かないでください。テストも書きません。
- 設計書・決定事項.md・CLAUDE.md に書かれていないことは、
  書かれていないと明示してください（勝手に決めないでください）。
- 既存の core/exception・util・testTools・参照実装のコードと構成に
  合わせてください。
```

**`queryCondition` と `query` の使い分けは資料に無い**（段①の題材⑳）。**決定事項 #8「`queryCondition` は使わない」に従うか**を見る。

### ② コミット2〜7（Red → Green を1コミットずつ）

```
承認した計画のとおり、コミット2から順に実装してください。
1コミットずつ、次に進む前に必ず確認を取ってください。

各コミットで、この順に進めてください。

1. そのコミットで満たす受入条件を、テストにする
   - 設計書・決定事項.md と、CLAUDE.md の「完了の定義」を読んでください
   - テストは実装ではなく仕様から書いてください
   - 参照実装 TodoGetByIdTest に合わせてください。統合テストです。
     モックは使わず、HTTPリクエストから実DBまで通してください
   - 事前データは DBUnit の dataset(setup.xml) で投入し、DBの状態を
     確かめるものは @ExpectedDatabase で検証してください
   - dataset の置き場は、テストクラスのパッケージ＋クラス名の鏡写しに
     してください
   - アサーションは JUnit5 の Assertions を使ってください
     （AssertJ は使いません）

2. mvn test を実行し、そのテストが落ちることを確認して結果を見せてください
   - 落ちなかったテストがあれば、それを列挙し、なぜ落ちなかったかを
     書いてください

3. 実装してください
   - 1 で書いたテストは変更しないでください。変更が必要だと思ったら、
     変更せずに理由を報告してください

4. mvn test と mvn checkstyle:check を通してからコミットしてください

- 頼んでいないファイル・テーブル・依存（pom.xml）は変更しないでください。
- 設計書と決定事項に書かれていないことは、書かれていないと明示してください。
```

**★2 と、3 の「テストは変更しない」が新規。** 07 §5 には無い。

| | なぜ入れるか |
|---|---|
| **2（赤を見せる）** | 「テストは仕様から書け」は**お願い**なので守ったか確認できない。**赤を見せるのは機械的に検証できる。**落ちなかったテストが**自己申告される** |
| **3（テストを変更しない）** | 先に書かせた以上、**実装を通すためにテストを緩める**逃げ道を塞ぐ。**変更させないのではなく、変更したいと言わせる**（言ってきた内容が仕様解釈の相違そのもの） |

**赤の出力は提出物にする。** 段④で「何を任せたか」を見るときの材料になる。

**⚠ 「落ちなかったら実装せずに報告」ではなく「列挙して理由を書く」にした（2026-08-25 の実測で訂正）。**
コミット2の実測で、**24件中3件が実装前に通った**（`notFound` を期待するテスト。**エンドポイントが無いので404が返り、期待した404と偶然一致した**）。
**止めさせると1件でもコミット全体が止まる**ので運用できない。**列挙させて、止めるかどうかは研修生が判定する。**
**この「404の一致」自体が段④の題材になる** — 存在しないパスの404と、存在するリソースが無い404が区別できない。
