## ★1 「落ちなかったら実装せずに報告」が構造的に効かないケースがある

**24件のうち3件（`TagGetByIdTest.notFound` / `TagPutByIdTest.notFound` / `TagDeleteByIdTest.notFound`）は、実装前の時点で通っていた。**

**エンドポイントが存在しないので 404 が返り、期待した 404 と偶然一致した。**

> **存在しないパスの404と、存在するリソースが無い404が区別できない。**

AIはこれを**自分から申告した**（「この3件はこの段階では何も検証できていません」）が、**指示どおりなら実装を止めるべきところで続行した**。

| | |
|---|---|
| **指示の欠陥** | 「落ちなかった場合は実装せずに報告」は、**24件中3件だと運用できない**（コミット全体が止まる） |
| **直し方** | **「落ちなかったテストを列挙し、なぜ落ちなかったかを書く」に変える。**止めるかどうかは研修生が判定する |
| **★教材としての価値** | **404を期待するテストは Red-Green が効かない**、というのは実務でそのまま通用する話。**段④の題材になる**（「このテストは何を証明しているか」） |

## ★2 死んでいると判断した `flyway` が、テストで実害を出した

**`@ExpectedDatabase` の既定 assertionMode はDB全体のテーブル数まで一致を要求する。** そのため `flyway_schema_history` が存在するだけで落ちる。

```
[ERROR] TagPutByIdTest.notFound » DbComparisonFailure[table count expected:<1> but was:<4>]
```

AIは `assertionMode = NON_STRICT_UNORDERED` に直して**実装前に**再実行した（期待するDBの中身は変えていない）。

**→ `04 §2.5` の判断を訂正する。** ㉛（flyway-core が依存にあるのに migration が無い）を「**死んでいるだけで作業を止めない**」としたが、**止めた**。
**ただし直す先は flyway ではない。** `assertionMode` を明示するのが正しい対処で、**参照実装 `TodoGetByIdTest` に `@ExpectedDatabase` の例が無かったことが原因**。

| 直すもの | 内容 |
|---|---|
| **参照実装** | `@ExpectedDatabase` を1つ入れ、**`assertionMode = NON_STRICT_UNORDERED` を既定として見せる** |
| `DoD.md` か `CLAUDE.md` | 1行「`@ExpectedDatabase` は `NON_STRICT_UNORDERED` を使う」 |

## ★3 DoD と参照実装が矛盾している（**講師側の欠陥**）

AIの指摘（報告 5-6）:

> `DoD` の「Entity とレスポンス用のクラスを混ぜない」と参照実装が食い違う。`TodoController` は `TodoEntity` をそのまま返しており、要件定義のアーキテクチャ図の注記も「今回アーキテクチャを省略し、1つのクラスにまとめています」と書いている。

**正しい指摘。参照実装を作った講師の側の欠陥。**

| | |
|---|---|
| 教材の実態 | 要件定義のアーキ図が「**アーキテクチャを省略し、1つのクラスにまとめています**」と明記 |
| `DoD.md` | 「**Entity とレスポンス用のクラスを混ぜない**」 |
| 参照実装 | `TodoController` が `TodoEntity` を返す＝**DoD違反** |

**AIは参照実装に合わせた**（＝`TagEntity` をそのまま返した）。**「AIは既存に合わせる。だから既存が古いと、古いまま増える」（`07 §7` の 5-4）の実例が出た。**

**要対応（どちらかに寄せる）**

| | 案 |
|---|---|
| **A** | **`DoD.md` からこの1項目を外す。** 教材がアーキ省略を明言しているので、DoDが教材と矛盾している |
| B | 参照実装にレスポンス専用クラスを入れ、**教材のアーキ省略を上書きする** |
