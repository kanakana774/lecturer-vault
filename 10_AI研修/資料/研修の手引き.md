# AI研修の手引き

> **研修生だけが読む資料です。**リポジトリに置かず、Claude にも貼らないでください。

## この研修のゴール

> ### AIに書かせたコードの品質を、自分で担保できるようにする。

客先には自分の名前で成果物を出します。AIが書いたコードでも同じです。

題材は2か月目と同じ Todo API。**Todo と Tag の CRUD と、Todo への Tag の紐づけ**を Claude Code に作らせます（Todo の1件取得だけは実装済みで、テストの見本になっています）。

---

## 研修の流れ

| 段 | やること | 出すもの |
|---|---|---|
| **前提** | ガバナンス講義と Claude Code の説明を聞く | — |
| **A 入力を整える** | 設計書を読んで仕様を把握する。`実装計画.md` を作らせ、中身を確認して合意する | `実装計画.md` |
| **B 任せる** | 機能ごとにテスト → 実装 → コミットを任せる。終わったら push して PR を作る | 作業ブランチ・PR |
| **C 確かめる** | AIにレビューさせ、自分でも確かめる。直すものは直し、PR本文を仕上げる | PR |
| **D 振り返る** | `振り返り.md` の問い5つに答える | `振り返り.md` |

- **A の終わりは「`実装計画.md` に合意できた」とき。**半日たっても決まらないものは、「未決」と書いて B に進んでかまいません
- 決められているのは**何を作るか**と、**AIに任せてよいか**だけです。どう作らせるかは自由です
- **仕様で迷ったら講師に聞いてください。**講師が仕様管理者です。決まったことは設計書に書き戻します

### 判断の軸 — 迷ったらここに戻る

1. **根拠が書けないテストケースは、一覧に残さない。**期待する結果を断定できないなら、仕様がまだ決まっていません
2. **テストが緑でも、正しいとは限らない。**「このテストは効いている」と言える根拠は、自分で作ります
3. **自分で確かめて決着するものは自分で決める。他人の同意が要るものは相談に上げる。**難しいかどうかでは分けません

## はじめる準備

PowerShell で、自分の手で実行します。

**1. GitHub にログインする**（1人1回）

```powershell
gh auth login
```

**GitHub.com** → **HTTPS** の順に選びます。「Authenticate Git with your GitHub credentials?」には **No**。最後にブラウザでデバイスコードを入力します。

**2. リポジトリを取ってきて、ブランチを切る**

```powershell
git clone https://github.com/aevic-education/ai-training.git
cd ai-training
git switch -c feature/<社員番号>-<氏名>
git push -u origin feature/<社員番号>-<氏名>
git switch -c task/<社員番号>-<氏名>
```

例: `feature/129999-TanakaTaro` → `task/129999-TanakaTaro`。作業は `task` で行い、PR は `task` から `feature` に出します。**`feature` を先に push しておかないと、PR が作れません。**

**3. DB を作る**

`docs/00.環境構築/05.DB環境構築/DB環境構築手順書.md` のとおりに、データベース `todo` とロール `todo` を作ります。**2か月目の `todo` は作り直します。**

**⚠ `mvn test` を回すとテーブルの中身が入れ替わります。**手で入れた確認用のデータは残りません。

**4. 動くことを確かめる**

```powershell
mvn test
mvn checkstyle:check
```

**5. Claude Code を起動する**

```powershell
claude
```

## Claude Code の使い方

| 機能 | 何ができるか | 使う場面 |
|---|---|---|
| **`CLAUDE.md`** | 起動時に毎回読まれる指示書 | B の進め方はここに書いてある。毎回言わなくてよい |
| **許可の確認** | 実行前に「実行してよいか」を聞く。講義の Human-in-the-loop | commit・push・ファイル削除。**読んでから答える** |
| **auto** | 確認を減らして任せる | B。ただし取り消せない操作は承認する |
| **plan モード** | 手を動かす前に計画だけを出させる | B。実装の進め方を先に確かめたいとき |
| **`/clear`** | 会話を捨て、コンテキストを空にする | 作業の区切りで。渡しすぎると効きが落ちる |
| **`/model`** | モデルを切り替える | 講義で説明する |

**`Shift+Tab`** で plan モードと auto を切り替え、**`Esc`** で作業を止められます。

## 止めてあること

`.claude/` の設定で、Claude からは次ができません。

| | 理由 |
|---|---|
| 他の人の PR・他のリポジトリを読む（`git pull`・`gh pr view 番号` など） | 全員が同じリポジトリで作業するため |
| `.env` などの秘密ファイルを読む | 講義の「秘密を渡さない」 |

**自分の PR は、番号を付けなければ Claude も読めます**（`gh pr view`）。止められた操作は自分の手で実行してください。**おかしな止まり方をしたら、設定を触らずに講師へ。**

## レビュー観点9項目 — C で見るところ

**項目そのものは `CLAUDE.md` にあります。**ここは、この課題での見どころです。

**一巡したら終わりです。**終わったときに言うのは「全部見ました」ではなく、
**「このリストは見た。これ以外は自分では分からないので、レビューを頼みたい」**。

| # | 見どころ |
|---|---|
| **1 N+1** | **Todo一覧に紐づく Tag を取るところが典型。**`for` だけでなく `stream` や MyBatis の遅延ロードでも起きます。**ログに出る SQL の本数を数える**のが早い |
| **2 内部由来の文字列** | **⚠「例外メッセージを返すな」ではありません。**共通例外が返す `title`/`status`/`code`/`message` は正しい。見るのは**その仕組みを迂回していないか**——`catch` して自前で組む、`@ControllerAdvice` を足す、`message` に DB 由来の文言が混ざる |
| **3 層の責務** | Controller から Mapper を直接呼んでいないか。**Service に HTTP の都合**（ステータス・`ResponseEntity`）**が漏れていないか** |
| **4 レスポンスの中身** | **判定は OpenAPI との突き合わせだけ。**`todo.yaml` / `tag.yaml` に無いフィールドが混ざっていないか。**⚠ `version` は OpenAPI が返すと定義しているので返します。**カラムの見た目では決めません |
| **5 `SELECT *`** | Mapper の XML でカラムを列挙する。**`COUNT(*)` は当たりません** |
| **6 範囲外の変更** | **`git diff --stat` を `実装計画.md` の §1・§2 と突き合わせる。**「テーブルを変更しない」は**テーブル定義（DDL）**のこと。テストがデータを入れ直すのは当たりません |
| **7 依存** | `pom.xml` の差分がゼロか。**「便利なライブラリを入れておきました」が起きます** |
| **8 トランザクション** | `@Transactional` が Service にあるか。**削除は子（`todo_tag`）→ 親の順**か。**「いまは外部キー制約が無いから、どの順でも動く」に頼っていないか** |
| **9 テストが仕様を検証しているか** | **DB を見ているか**（`@ExpectedDatabase` があるか）／**期待値が設計書から来ているか**／**実行順に依存していないか**。**⚠ `assertionMode = NON_STRICT_UNORDERED` は厳密さを下げる指定で、DB を見ている証拠にはなりません** |

## 出すもの

### `実装計画.md`（A）

テストケースは1件ごとに、**入力・事前状態・期待する結果**と、**設計書のどこから来たか**を書きます。

### PR（C）

**AIのレビューは、Claude 自身に `gh pr comment` で投稿させます。**そのうえで自分でも確かめ、見つけたことは該当行にコメントします。

AIの指摘は3つに分けます。

| 判定 | どうするか |
|---|---|
| **正しい** | 自分で確かめてから直す。仕様に関わるなら講師に確認し、設計書も直す |
| **的外れ** | 理由を返信して閉じる |
| **判断できない** | 本文の「相談したいこと」に上げる |

**直しに戻るのは1周まで。**本文の雛形は PR を作ると出てきます。**書くのは「いまの状態とその根拠」で、経緯は書きません。**

**PR はマージしません。**

### `振り返り.md`（D）

思い出せる範囲で書けば十分です。**Claude には渡しません。**これをもとに講師と話します。
