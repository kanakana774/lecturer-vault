# AI研修の流れ

## 目的

> ### AIに書かせたコードの品質を、自分で担保できるようにする。

SES では客先に**自分の名前で**成果物を出す。AIが書いたものでも変わらない。

対象は**3か月目の新人**。題材は**2か月目と同じ Todo API**（Java 21 / Spring Boot 3.4.1 / MyBatis）。

- Todo API概要
	- todoのCRUD機能
	- tagのCRUD機能
	- todoの登録/更新時にtagを紐づけることができる機能

---

## 見てほしいところ

- **冒頭の「達成したいこと3点」が、配属後に必要なものとして妥当か。抜けは無いか**
- **各工程のやり方が、実務のやり方として妥当か**

---

## 研修生に達成してもらいたいこと — 3点

|       |             | 到達した状態                          | どこで     |
| ----- | ----------- | ------------------------------- | ------- |
| **1** | **コンテキスト**  | **何を渡し、何を渡さなかったかを、理由とともに説明できる** | **A**   |
| **2** | **逸脱の把握**   | **AIが設計から逸れた箇所を、説明できる**         | **B・C** |
| **3** | **線引き**     | **担保できた範囲と、できない範囲を言える**         | **C**   |

**3点とも「独断しないこと」が合格条件で、判断の広さは求めない。また、研修はあくまで考えるきっかけにしてもらい、上記は願わくばという感じ**
**配属直後の新人が、客先で最初に問われるのはこの3つだけ（と仮定）。**

> [!note]- 「決めてよいことと聞くべきことを分ける」を目標から外した理由（2026-09-01）
> **3点のうち、ここだけがAIで変質していない。**紙とペンの時代から同じ能力なので、**AI研修の目的にならない。**
> さらに判定の実体が薄い —— 決まっていないことは**AIに実装させれば必ず表に出る**し、
> **設計書に書いていないことは「逸れる」と言えない**ので、上げるか決めるかの分岐が立たない。
> **工程には残すが、測らない**（`06_研修の芯.md`「軸にしないもの」）。

---

## 流れ

```
【前提】
  ガバナンス  ──  理解度テストに合格  →  本編

【本編】
  入口（自分）      →      中（AI）      →      出口（自分）
   A 入力を整える          B 任せる            C 確かめる
```

**実装するのはAI。研修生がやるのは、コンテキスト整えて、委任して、その検証。**
**各段の提出物が、次の段の入力になる。**

---

## ガバナンス（前提）

**答えがあるので、教えて、測って、終わらせる。**

1. 客先のルールを確認する
2. 渡してはいけないものを渡さない
3. 何を渡したか記録する
4. AIに書かせた部分を PR で明示する

**理解度テストに合格して、次に進む。**

---

## A 入力を整える — AIに渡すものを、配られたものから作る（半日）

**課題で配られるもの**と、**AIに最終的に渡すもの**は別物。**その差分を作るのが A。**

### ★ 実装までに達成しておくこと — 5つ

**道具の話の前に、これが目的。**

| | 達成しておくこと | なぜ実装前でないとダメか |
|---|---|---|
| **1** | **合格の基準**（何が満たされれば正しいか ＋ **期待値をどこから取るか**） | **実装を見てから作ると、実装に寄る。**独立性は一度失うと再現できない |
| **2** | **範囲**（**やらないこと**・触ってよい場所） | **事後に「どこを見ていないか」を数えるには、先に地図が要る** |
| **3** | **書けなくなる未決の決着。矛盾は設計書を直して消す** | **型・スキーマ・DB制約・権限の後付けは「担保」ではなく「改修」** |
| **4** | **決まらなかったことの一覧** | **実装が出てからでは「AIが決めた」のか「決まっていた」のか区別できない** |
| **5** | **制約が、AIが読む場所にある**（**一般解から外れるところだけ**） | **頭の中の制約は、AIには存在しないのと同じ** |

**実装前の作業は「早くやるため」ではなく、「汚染される前に固定するため」。**

| | 何が起きるか | どれ |
|---|---|---|
| **決まらないと書けないもの** | **止まる。**あるいは勝手に決まる | **3・5** |
| **あとから作ると汚染されるもの** | **書けるが、根拠として使えなくなる** | **1・2・4** |

### 手順は3つ

|         | 何をするか                                             |
| ------- | ------------------------------------------------- |
| **A-1** | **配られたものを確認する**（設計書一式・`CLAUDE.md`・雛形）            |
| **A-2** | **AIに未決事項を列挙させ、仕様管理者に聞き、設計書を直す**                 |
| **A-3** | **AIにテストケース一覧を作らせ、抜け漏れを見る**                       |

**★やり方は指定しない。** アプローチは無数にある。**どう辿ったかを、あとで議論する**（→ 評価）。

### なぜ設計書に書き戻すか

**実装と設計がずれると困るから。** 決まったことは設計書に書く。**A・B・C の全段で同じ動作。**

| 段 | 何が起きたら | どこに書き戻すか |
|---|---|---|
| **A** | 矛盾・未決を確認して答えが出た | **設計書** |
| **B** | 実装が設計から逸れた | **設計書** |
| **C** | B で書き漏らした逸脱を拾った | **設計書** |

**「配られた設計書」と「渡した設計書」の差分が A の成果物。`git diff` でそのまま出る。**

### 渡すものは4つの問いに畳める

| 問い | 5つのどれか | 置き場 | 配られた状態 | **B開始時の状態** |
|---|---|---|---|---|
| **何を作るか** | 3 | **設計書** | 矛盾・未決あり | **矛盾が消え、答えが書き戻されている** |
| **どう作るか** | 5 | **`CLAUDE.md`** | 規約・DoD の雛形 | **意図を理解した** |
| **どこまでやるか** | 2 | **`CLAUDE.md` の「前提」** | 配布済み | **確認した** |
| **何をテストするか** | 1 | **`テストケース一覧.md`** | 空の雛形 | **埋まっている。根拠つき** |

**そして本人が「渡していないものは何か」を言える**（`確認事項.md` ＝ 5つの 4）。**ここが C-3 の土台になる。**

> [!note]- 「どこまでやるか」の置き場を変えた（2026-09-04）
> **以前は `受入条件.md` に「対象外（やらないこと）」節を置いていた。**
> **受入条件をやめたので、前提（画面なし・デプロイ不要・認証は既存・依存を足さない）は `CLAUDE.md` に移した。**
> **配布時点で入っているので、研修生は確認するだけ。**
>
> **「触ってよい場所」は、`実装計画.md` の「変更するファイル」との差で見る。**
> **★試走で実際に効いたのは、AIが自発的に書いた「既存で変更しないもの」のリストだった。**
> **否定形のほうが機械的に判定できる。**

### ★ B に進んでよい状態

> ## **テストケース一覧に合意できている。**

**「何をテストするか」が実装の前に決まっていれば、B に進んでよい。**
**合意した時点が着手基準。**研修生が自分でその場で確かめられる。

**そこへ至る手は2つ。**

**1. ★ 決めることになる事項を、直接列挙させる**

> **「実装するとして、あなたが独断で決めることになる事項を列挙して。実装はしないで」**

**AIは生成が得意で、自分から止まるのが苦手。** その性質を逆に使う。
**列挙された項目に自分が即答できなければ、準備不足。**
**⚠ 列挙ゼロは準備完了の証拠にならない。** 網羅は保証されない。

**★これを打たないと出ないものがある。**
**未決の出どころは3つあり、3つ目（フレームワークの既定が決めてしまうもの）は資料を突き合わせても出ない。**
**設計書に書いていないので、突き合わせようがないから。**

**2. ケース一覧を作らせ、抜け漏れを見る**

**★期待する結果が断定できないものは、ケースにしない。** → **`確認事項.md` に戻して手1へ。**

**模範アプローチの一例:** **別のAIにケース一覧をレビューさせる。**
**ただし仕分けまでで1セット**にする——**試走では7件の指摘のうち3件に対応し、残り4件を捨てた理由が残らなかった。**

> [!warning]- ⚠ 別AIレビューは、痕跡のあるものしか拾えない（2026-09-08・試走）
> **設計書に矛盾の材料があった1件は拾い、どこにも書いていない2件は0件だった。**
> **→ 手1（独断で決めることの列挙）の代わりにはならない。**

### ★ 矛盾は「決まらない」に入れない。直して消す

**資料が食い違っているものは、聞けば決まる。** 聞いて、**設計書を直す**。
**優先順位のルール**（「型は DB定義書が正」など）**は作らない。**矛盾を残す前提になるので、
**「実装と設計をずらさない」と逆を向く**（2026-09-01 判断）。

**だから「決まらないと知って進む」に入るのは、実質2つだけ。**

**⏸ ここから下は後回し**（2026-09-01）。**上手くいった1周では、全部聞けて設計書に落ちる。**
**先に漏れの想定を組むと、決まるものも決まらない。**理想形が固まってから戻る。

| | 例 |
|---|---|
| **聞いたが、その場で決まらなかった** | 仕様管理者が持ち帰った。**研修では稀**（講師が決める） |
| **時間切れで聞けなかった** | 部分一致の `%` `_` の扱い |

**★「聞けば決まる」ものがここに並んでいたら、A が甘い。**
Todo名の物理名（DB定義書は `NAME`、DDL は `title`）は**矛盾なので直して消す**。ここには入らない。**評価の議論はそこを突く。**

### 歯止め

| | |
|---|---|
| **その場で判定できる** | **ケース一覧に合意できたか**。研修生が自分で確かめられる |
| **形式を満たすだけでは通らない** | **根拠の書けないケースは残せない。**雛形を埋めただけでは通過できない |
| **新しい道具はゼロ** | 新しいセッションを開いて一言聞くだけ |
| **時間はゴールではなく歯止め** | **半日で届かなければ、残りを全部「決まらないと知って進む」にして B に行く。**それも正しい終わり方で、**C で答え合わせされる** |

**★これは必要条件であって、十分条件ではない。** 満たせば良いA、ではない。**A の質が分かるのは C**（→ 評価）。
**⚠ 完璧にはならない。**抜けは残る。**残りは B のコードには出る。ただし報告されるとは限らない。**

> [!note]- 潰し切れない分は「刻み」で買う
> **どれだけ準備しても、掘れば出てくる。**言語化できていない前提は、定義上、事前準備の対象にならない。
> だから**ゲートを「一発で当てる準備ができたか」ではなく「外したときに安く捨てられるか」に置く。**
> **B をエンドポイント単位に刻んでいるのは、これをやっている。**準備の不足は**周回数で買う**。

⚠ **AIは聞かなければ言わない。**「足りなければ推測せず全部聞いて」を**明示的に渡す**（`CLAUDE.md` に書く）。

### 配る雛形は2つ（＋ワークスペースの外に1つ）

**どちらも設計書リポに置く。** 決まったことは**設計書本体**へ書き戻し、**雛形には「聞いた事実」だけが残る。**

**`確認事項.md`** — 何を確認し、どう答えが出たか。**A・B・C の全段で行が増える**

```markdown
| いつ | 項目                        | 根拠 / 確認先             | 回答       | 反映     |
|------|-----------------------------|---------------------------|------------|----------|
| 着手前 | Todo名の物理名が違う        | DB定義書は NAME、DDLは title | title | 設計書へ |
| 着手前 | Tag削除時の todo_tag の扱い | DB定義書に記載なし        | 一緒に消す | 設計書へ |
| 着手前 | 同名のTagを登録できるか     | UNIQUE 制約が無い         | 登録できる | 設計書へ |
| 着手前 | Tag削除の順序が FK に依存   | DB定義書は複合PK、DDLは制約なし | DDLが正 | 設計書へ |
| 着手前 | 部分一致の % _ の扱い       | 時間切れ                  | **未回答** | 進む     |
```

**上4行は矛盾・記載漏れなので、聞いて設計書を直した。** 最後の1行だけが**「決まらないと知って進む」**。
**「未回答」の行が、C で答え合わせされる**（→ C-3）。

**`テストケース一覧.md`** — 何をテストするか。**実装が始まる前に決める**

```markdown
| # | 対象         | 入力・事前状態              | 期待する結果                  | 根拠 |
|---|--------------|-----------------------------|-------------------------------|------|
| 2 | Todo一覧取得 | limit=1、Todoが2件以上存在  | 200。先頭1件のみ返却          | todo.yaml `limit`「取得上限件数」 |
| 6 | Todo一覧取得 | limit=0                     | 400、badRequest.invalid-field | Todo機能.md「limitが1未満の場合400」 |
```

**★「根拠」列が肝。** **根拠が書けないケースは、仕様がまだ決まっていない。**
→ **ケースにせず、`確認事項.md` に戻す。**A-2 と A-3 の往復そのもの。

> [!note]- 「受入条件」をやめた（2026-09-04）
> **同じ情報が3段あった** —— 受入条件 → 実装計画の「証明」節 → テストコード。**2段に畳んだ。**
>
> - **受入条件は実務で使わない。**2か月目で書いているのは「テスト仕様書」。**新規概念を1つ減らせる**
> - **粒度が定まらず、研修生が混乱する。**ケースなら「入力・事前状態・期待する結果」で決まる
> - **抜け漏れの指摘がしやすい。**「この受入条件は妥当か」より「このケースが足りない」のほうが言える
> - **Playbook にも `acceptance criteria` は一度も出てこない**（確認済み）
>
> **「対象外（やらないこと）」の節も落とした。**「触ってよい場所」は **`実装計画.md` の「変更するファイル」との差**で見る。

> [!note]- 「目視」の欄も作らない（2026-09-04・実測）
> **試走でAIが出した61件は、全部「機械」だった。**「DoD 9項目以外に目視が要るものだけ書け」と指示しても**1件も書かない。**
>
> **理由は構造的。**Controller層の統合テストは「HTTPリクエスト →（レスポンス, DBの行）」という関数を検証する。
> **仕様が定めているのは全部その関数の値なので、判定は機械比較になる。**
> 人の目が要るのは**「同じ振る舞いを実現する実装のうちどれを選んだか」**で、
> **それは DoD 9項目（N+1・層構成・`SELECT *`・トランザクション境界）がすでに埋めている。**

**もう1枚、ワークスペースの外に `振り返り.md`**（問い5つ）。**評価の場に出す。**
**AIに渡さない。**渡すと問いへの答えを作られる。

**提出物: 設計書の差分 ＋ `テストケース一覧.md` ＋ `確認事項.md`**

## B 任せる — 任せた仕事の流れが見えている状態で回す（半日）

**A でケース一覧に合意している。** B は**計画を1枚書いてから、1コミットずつ4手を回すだけ。**

**B-0 — ブランチを切って、実装計画を書く**

> **配布時点から `feature` を切り、そこから `task` を切って作業する。`main` には直接コミットしない。**
> **実装の前に、`実装計画.md` に3節（変更するファイル／作業の順序／リスク）を書く。承認するまで実装しない。**

**★ブランチの指示を言わないと `main` に直接入る**（試走でそうなった）。
**★plan モードは使わない。** 保存先が研修生のローカルで、**提出物にならない。**C の参照点なのでリポジトリに置く。

|     | やること                                               | 誰が  |
| --- | -------------------------------------------------- | --- |
| ①   | **そのコミットで満たすケースを、`テストケース一覧.md` からテストに書く**（実装ではなく仕様から書く） | AI  |
| ②   | **実装前に `mvn test` を走らせ、①のテストが失敗する出力を見せる**          | AI  |
| ③   | **実装する。①のテストは変えない**（変えたいときは変えずに理由を報告）              | AI  |
| ④   | **`mvn test` と `mvn checkstyle:check` を通してコミットする** | AI  |

**②が要る理由: 実装前に通ってしまうテストは、何も検証していない。**
実装のあとに書いたテストは、実装に合わせて書ける。**②は機械的に確認できる**（出力を見せさせればよい）。

**コミットはエンドポイント単位で刻む**（試走では9本）。**Tag を先に、Todo を後に。**
Todo登録がTagの存在チェックを要し、削除のトランザクションの型を Tag で先に確立できるため。

**auto を使ってよい。ただし取り消しがきかない操作（コミット・ファイル削除・DB操作）では承認を取る。**
**`settings.json` の `ask` がその線を引いている。**

**★4手は `CLAUDE.md` に書いて渡す。** 研修生から見える手数を増やさない。

### 設計から逸れたら、設計書に書き戻す

**★AIへの指示に1行入れる。**

> **設計書と違う実装にしたら、設計書を直し、`確認事項.md` に1行足してから報告してください（「いつ」列は `実装中`）。**

**B-2 のあと** — **AIが**書く。**設計書から逸れた分が増える**

```markdown
| いつ | 項目                         | 根拠 / 確認先                    | 回答         | 反映     |
|------|------------------------------|----------------------------------|--------------|----------|
| 実装中 | 一覧取得を JOIN 1本にした    | 設計書は「ループして取得」だが、 | 講師に確認   | 設計書へ |
|      |                              | DoD の for内SQL 禁止と衝突       |              |          |
| 実装中 | tags に同じIDが2つ来ても 201 | 存在チェックを重複を除いて数えた | 講師に確認   | 設計書へ |
|      |                              | 設計書の文言なら404              |              |          |
```

**「いつ」が `実装中` の行が、そのまま「AIが設計から逸れた箇所」**（→ 達成目標2）。

> **上位者は設計を把握しているが、そこから逸れたことは把握していない。**
> **AIは聞かなければ言わない。だから本人が把握していなければ、組織の誰もその逸脱を知らない。**

**⚠ 逸れたものは全部上げる。** 設計書に書いてあることと違うことをしたなら、それは**必ず**仕様管理者の領分。
**「自分で決めてよい逸脱」は無い**（書いていないことについては、そもそも「逸れた」と言えない）。

**リモートはまだ足さない。** 提出は C-2。**足すのは講師。**

> ### AIが書いたコードを、問題ないと自分で説明できる状態にする。

**答えは配らず、考える機会だけ与える**

| 段 | やること | 誰が |
|---|---|---|
| **C-1 機械チェックの妥当性を確かめる** | **ケース一覧 ↔ テストの対応を見る。「このテストは効いている」と言える根拠を出す** | **AIにやらせてよい** |
| **C-2 コードレビューをする** | **変更範囲**（`実装計画.md` が参照点）・**DoD 9項目**・その他気になるところ。**結果を PR に書く** | **★AIを使わない** |
| **C-3 AIにもレビューさせ、仕分ける** | **正しい／的外れ／判断できない に分け、処置を決めて PR に書く** | AI ＋ 自分 |

**★C-2 だけは AI を使わない。**
**C-2 と C-3 は同じ作業を別の主体がやるもので、差そのものが材料になる。**
**C-2 で AI を使うと C-3 が空になる。**そして**研修全体で、自分の目でコードを読む工程はここだけ。**

**★DoD 9項目はコードレビューに畳んである。** 別枠にすると「人のコードレビュー」になるので。

### ★ なぜ自分の目で読ませるのか

**人の手抜きは荒れて見えるが、AIの取り違えは自然で一貫して見える。**
**「読んで違和感がない」は、正しさの証拠にならない。**

**だから「テストが79件あって全部緑」も、そのままでは根拠にならない。**

> [!warning]- 実測: 裁定を壊しても、79件が緑のまま通った（2026-09-11・試走）
> **`TodoService.delete` から `todoMapper.deleteTodoTagsByTodoId(todoId);` を1行消して `mvn test`。**
> **Tests run: 79, Failures: 0, Errors: 0 — BUILD SUCCESS。**
>
> **A で一番手間をかけた裁定（FK・削除順序）を壊しても、1つも落ちない。**
> **原因はテストデータ。**正常系のテストが**紐づきなしの Todo** を消しており、FK に当たらない。
>
> **★「ケースがある」「テストがある」「名前も対応している」——3つ揃っても、fixture が違えば何も検証していない。**

### ★ 機械チェックの妥当性は、どう示すか

**証明の仕方は研修生に委ねる。****何をもって「効いている」と言えるのか**——そこを見る。

**模範アプローチの一例は、敵対的にテストを検査させること**（**ミューテーションテスト**）。
実装を機械的に変異させて、テストが落ちるかを見る。**「テストのテスト」。**

**Java の定番ツールは PIT（pitest）**だが、**`pom.xml` に依存を足す**ので課題の前提と衝突する。
**→ 別セッションのAIに「`mvn test` が緑のまま通る変更を探せ」と投げる。**道具を増やさずに同じことができる。

**★講師は1回実演する。**「79件全部緑なのに壊れている」を**全員が同時に見る**ほうが、各自でやるより効く。

### C-3 — 指摘を受けて、直して、また見せる

| 判定 | 処置 |
|---|---|
| **正しい** | **直す → コミット → push → 再レビュー。**直すときも **B の4手** |
| **的外れ** | **理由を書いて閉じる。**直さない |
| **判断できない** | **★消さない。**仕様なら `確認事項.md`（確認時）→ 仕様管理者へ。技術なら**そのままPRに書いてレビュアーに上げる** |

> ### ★「判断できない」を消す必要はない。そのまま出すのが正しい。
> **分かったふりをして閉じるほうが悪い。**

**★再レビューは1周で切る。** 2周目の新しい指摘は仕分けるだけ。
**Claude Code の Code Review が「nit が無限に積み上がる／再レビューのたびに新しい nit が増える」を
既知のノイズ源として公式に挙げている。****収束しない。どこで切るかは人が決める。**

**終わりの条件: 3分類すべてに処置が決まったら終わり。**
**「正しい」を全部直した、ではない。**——**直さないと決めて理由を書いた**ものも、処置済み。

### ★ C-3 は検証ではなく、A の答え合わせ

**★検証手段には数えない。** 同じ資料を読むので**同じ誤読をする**し、**渡していない情報は原理的に見えない**。
**ただし拾い漏れの受け皿にはなる。**

> [!warning]- 実測: 人とAIで、見つけたものの重なりがゼロだった（2026-09-11・試走）
> | | 件数 |
> |---|---|
> | 自分だけが見つけた | **3** |
> | AIだけが見つけた | **4** |
> | **両方が見つけた** | **★0** |
> | 的外れ | **0** |
>
> **人は「仕様との対応」を見ていた**（裁定した内容・ケース一覧・fixture の中身）。
> **AIは「コードの構造」を見ていた**（並行性・HTTPの作法・入力の型）。**見ているものが違う。**
>
> **⚠ AIは、A で裁定した `%` `_` のエスケープに一言も触れなかった。**
> 差分に4箇所あり、**3352行を最後まで読んだうえで**。**設計書を渡していないので、仕様として決めたことには届かない。**
>
> **⚠ さらに「境界値テストの網羅性は問題なし」と締めくくった。**——**穴がそこにあるのに。**
> **「指摘が無い」ではなく「問題ない」と書く。**誤った安心を与える。
>
> **★「的外れの数＝渡し漏れた情報の量」は指標として機能しなかった。**
> **代わりに効いたのは「AIが触れなかったもの」。出たものより、出なかったもののほうが情報だった。**

### ★ AIにリモートを触らせない

### `確認事項.md` は C でも増える

**C-3 のあと** — **自分が**書く。**AIが書き漏らした逸脱を拾う。判断できないものは残す**

```markdown
| いつ   | 項目                             | 根拠 / 確認先                     | 回答       | 反映 |
```

**A の質が C で数として出るので、議論が感想戦にならない。**

## 評価

|           | 測り方                                              |
| --------- | ------------------------------------------------ |
| **ガバナンス** | **理解度テスト。合格が必要**                                 |
| **A**     | **アプローチを議論する。**成果物の正しさは測らない（下記）                  |
| **B**     | 逸れた箇所を全部上げたか（`確認事項.md` の「いつ＝実装中」の行）            |
| **C**     | **PR と `振り返り.md` を読んで、議論を返す**                          |

**添削はしない／評価はする／議論はする。** 3つ目が実質のフィードバック。

### A は「どう辿ったか」を議論する

**A の完了時点では、良し悪しは測れない。** 実装と突き合わせるまで分からないので、**線を2本引く。**

| | いつ | 誰が | 性質 |
|---|---|---|---|
| **着手基準**（B に進んでよいか） | **A の終わり** | **研修生が自分で** | **形式的。その場で判定できる** |
| **評価** | **C のあと** | **講師と議論** | **事後にしか分からない** |

**★着手基準は必要条件であって、十分条件ではない。** 満たせば良いA、ではない。
**十分条件にすると、雛形を埋めて終わりになり、アプローチの探索が止まる。**

**議論の材料は C で数として出る。**

| A が甘いと | どこに出るか |
|---|---|
| **入力の確定が甘い** | **B で AI が勝手に決める**（`確認事項.md` の「いつ＝実装中」が増える） |
| **ケース一覧が甘い** | **根拠の書けないケースが残る／`確認事項.md` に戻せていない** |
| **渡し漏れがある** | **C-3 で「AIだけが見つけた」が増える** |

**「あなたのアプローチはどうだったか」だけだと感想戦になる。**
**「AIだけが見つけた指摘が4件あった。どこを渡していれば自分で気づけたか」なら具体になる。**

### 模範的なアプローチは、やりきったあとに示す

**議論のあとに、講師が用意した一例を見せる。**

| | |
|---|---|
| **示すもの** | **唯一の正解ではなく、アプローチの一例** |
| **示すタイミング** | **本人が自分のやり方を出しきったあと**。事前に配ればなぞるだけになる |
| **⚠ 置き場** | **リポジトリに置かない**（`03_研修環境とガードレール.md` §8） |

**「答えを配らない」（`06_研修の芯.md` 設計原則2）は破っていない。** 配るのは答えではなく**議論の材料**。

**★ = AI研修のために足すもの**（2か月目の環境には無い）。

```

└──   src/

todo-app-api-docs/                   ← ★研修生が書き戻す（読むだけではない）
├──   要件定義書・アーキ図・DB定義書・OpenAPI・エラーコード表・プログラム設計
├── ★ 確認事項.md                    ★空の雛形。A・B・C で行が増える（提出物）

└──   実装計画.md                    ★配らない。B の頭でAIが書く（提出物）


（リポジトリの外・別配布）振り返り.md   ★問い5つだけの雛形。AIに渡さない（提出物）

（リモートは C-2 で講師が足す）        ★AIには最後まで触らせない
```

> [!note]- なぜこの置き方にしたか
> **現物は `Desktop/配布見本/` にある**（研修生に渡した直後の状態）。
>
> | | なぜそうしたか |
> |---|---|
> | **設計書リポを書き換えさせる** | **実装と設計がずれると困る。**決まったことは設計書に書き戻す（2026-09-01 変更。以前は「上流の資産なので書き換えさせない」としていた） |
> | **設計書を別リポジトリにする** | **配られたものと渡したものの差分**が、リポジトリ単位で `git diff` に出る |
> | **雛形を設計書リポに置く** | **「決まったことは設計書」で1本に通すため。**コード側と分けると「どっちに書くんだっけ」が起きる |
> | **`振り返り.md` はリポジトリの外** | 設計書リポに置くと **`CLAUDE.md` 経由でAIが読む。****試走で実証済み**——仕分けをAIに投稿させようとして、読めずに止まった |
> | **リモートは講師が足す** | **`gh` を全面的に許すと org のリポジトリが全部見える。**2か月目のリポに**21人分の完成品**がある |
> | **参照実装を1本だけ配る** | **テストの層と書き方は、例が無いと揃わない** |
