# AI研修の流れ

## 目的

> ### AIに書かせたコードの品質を、自分で担保できるようにする。

SES では客先に**自分の名前で**成果物を出す。AIが書いたものでも変わらない。

対象は**3か月目の新人**。期間は**1週間**。
題材は**2か月目と同じ Todo API**（Java 21 / Spring Boot 3.4.1 / MyBatis）。
Todo と Tag の CRUD ＋ Todo の登録／更新時に Tag を紐づける機能。

# 作業の一覧

```
【前提】
  ⓪ ガバナンス  ──  理解度テストに合格  →  本編

【本編】
  入口（自分）      →      中（AI）      →      出口（自分）
   A 入力を整える          B 任せる            C 確かめる
      半日                 半日                 半日
        ↑                    ↑                   │
        └────────────────────┴───────────────────┘
             対応が要るものは戻して直す（最大1周）
```

**実装するのはAI。研修生がやるのは、入力を整え、任せ、確かめること。**

|  | 段 | 研修生がやること | 出るもの |
|---|---|---|---|
| **1** | **⓪** | ルールを学び、**理解度テストに合格する** | — |
| **2** | **A** | プロジェクトの中身を確認し、仕様を把握する（設計書一式・`CLAUDE.md`・雛形） | — |
| **3** | **A** | **仕様書から未決/矛盾を洗い出し、仕様管理者（講師）に聞いて、設計書を整える** | **直した設計書** ／ `確認事項.md` |
| **4** | **A** | **AIにテストケース一覧を作らせ、過不足を確認する** | `テストケース一覧.md` |
|  |  | **▶ テストケース一覧に合意できたら B へ** |  |
| **5** | **B** | ブランチを切り、**AIに実装計画を書かせて承認する** | `実装計画.md` |
| **6** | **B** | **1コミットずつ4手を回す**（テストを書く → 失敗を見せる → 実装 → 通してコミット） | 作業ブランチ |
|  |  | **▶ push して PR を作る** | **PR** |
| **7** | **C** | **AIにレビューさせる** | PRのコメント |
| **8** | **C** | **自分でも確かめ、AIの指摘の妥当性も見る**（下の7観点） | 指摘の仕分け |
| **9** | **→ A・B** | **対応が要るものは、A（確認と設計書）と B（実装）に戻して直す。最大1周** | `確認事項.md` ／ コミット |
| **10** | **C** | **もう一度確かめ、PR本文を4欄で仕上げる** | **PR** |
| **11** | **通し** | **振り返りを書く**（問い5つ） | `振り返り.md` |

**8 の7観点**

|  |  |
|---|---|
| **仕様どおりか** | ケース一覧とテストが対応しているか |
| **★設計に無い判断が入っていないか** | **AIが勝手に決めた箇所。見つけたら `確認事項.md` に足して聞き、設計書に書き戻す** |
| **テストは効いているか** | **緑であることが、正しさの証拠になっているか** |
| **触った範囲は宣言どおりか** | `実装計画.md` との差 |
| **DoD 9項目** | N+1・層構成・`SELECT *`・トランザクション境界 ほか |
| **どこまで見るか** | **非機能をどこまで見るかは、自分で決めて宣言する** |
| **AIが触れなかったもの** | **AIの指摘に出てこなかったものを、自分で探す** |

**各段の出るものが、次の段の入力になる。**

# 詳細

## 研修生に達成してもらいたいこと — 3点

|       |            | 到達した状態                          | どこで     |
| ----- | ---------- | ------------------------------- | ------- |
| **1** | **コンテキスト** | **何を渡し、何を渡さなかったかを、理由とともに説明できる** | **A**   |
| **2** | **AIが決めたことの把握** | **設計に無いことをAIが決めた箇所を、説明できる** | **C** |
| **3** | **線引き**    | **担保できた範囲と、できない範囲を言える**         | **C**   |

**3点とも「独断しないこと」が合格条件。判断の広さは求めない。**

---

## 作らせるもの — 6点

| 作らせるもの | どこで | AIの扱い | 何のために |
|---|---|---|---|
| **直した設計書（差分）** | **A →（C で増える）** | **自由** | **矛盾と未決を、実装より前に消す** |
| **`確認事項.md`** | **A →（C で増える）** | **自由** | **確認した事実と、決まらなかったことを残す** |
| **`テストケース一覧.md`** | **A** | **★AIに作らせ、過不足を人が見る** | **合格の基準を、実装より前に固定する** |
| **`実装計画.md`** | **B** | **★AIに書かせ、承認してから実装** | **触る範囲を、先に宣言させる** |
| **PR（本文とコメント）** | **C** | **自由**（AIにレビューさせてよい） | **担保できた範囲と、できない範囲を示す** |
| **`振り返り.md`** | **通し** | **★AIに渡さない** | **何を渡し、何を渡さなかったかを言わせる** |

**上の4つは、実装より前に作らせる。早くやるためではなく、汚染される前に固定するため。**

### ★ が指示。無印は自由

**指示は「何を作るか」と「AIに任せてよいか」まで。「どう作らせるか」は縛らない。**
どう渡し、どう確かめたかは研修生が決める。**そこが評価の材料になる**（→ 評価）。

**指示には2種類ある。研修生にはどちらかを言う。**

|  | どういうものか | どれ |
|---|---|---|
| **実務の作法** | **やり方が実務でほぼ1つに決まっている。必ず踏ませる** | **テストケース一覧をAIに作らせる／実装計画を承認してから実装する／B の4手** |
| **研修の都合** | **外すと到達点3点が測れなくなる。「実務の作法ではない」と断って渡す** | **AIの指摘と仕分けをPRに貼る／`振り返り.md` をAIに渡さない／`実装計画.md` をファイルで残す** |

**やり方が決まっていないものは指示にしない。**講師の案は**模範アプローチ**として、本人がやりきったあとに見せる。

---

## ⓪ ガバナンス（前提）

1. 客先のルールを確認する
2. 渡してはいけないものを渡さない
3. 何を渡したか記録する（**実体は `振り返り.md` の問い1。正確なログは取らせない**）
4. AIに書かせた部分を PR で明示する

**根拠は一次情報にある**（経産省の契約チェックリスト／IPA のガイドライン／客先常駐の契約上の整理）。
**→ `03_研修環境とガードレール.md` §6。**

**あわせて B の4手も、ここで説明しておく。**先に失敗するテストを書かせ、通してコミットする——
**`CLAUDE.md` に書いてあるので、説明さえすれば勝手に回る。**

**理解度テストに合格して、次に進む。**

## A 入力を整える（半日）

**課題で配られるものと、AIに最終的に渡すものは別物。その差分を作るのが A。**

- **ケースは1件ごとに「入力・事前状態・期待する結果」＋ 設計書のどこから来たかの根拠を書く**
- **期待する結果を断定できないものは、ケースにしない。**`確認事項.md` に戻して聞く
- **やり方は指定しない。**どう辿ったかを、あとで議論する

### B に進んでよい状態

> ## **テストケース一覧に合意できている。**

**合意した時点が着手基準。**研修生が自分でその場で確かめられる。
**半日で届かなければ、残りを「決まらないと知って進む」に落として B に行く。それも正しい終わり方。**

---

## B 任せる（半日）

**計画を1枚書いてから、1コミットずつ4手を回す。**

### 実装計画

> **配布時点から `feature` を切り、そこから `task` を切って作業する。`main` には直接コミットしない。**
> **実装の前に、`実装計画.md` に3節（変更するファイル／作業の順序／リスク）を書く。承認するまで実装しない。**
> **plan モードを使ってよい。ただし計画はリポジトリに残らないので、承認のあとに同じ内容を `実装計画.md` へ書かせる。**

### コミットごとの4手

|     | やること                                               | 誰が  |
| --- | -------------------------------------------------- | --- |
| ①   | **そのコミットで満たすケースを、`テストケース一覧.md` からテストに書く**（実装ではなく仕様から書く） | AI  |
| ②   | **実装前に `mvn test` を走らせ、①のテストが失敗する出力を見せる**          | AI  |
| ③   | **実装する。①のテストは変えない**（変えたいときは変えずに理由を報告）              | AI  |
| ④   | **`mvn test` と `mvn checkstyle:check` を通してコミットする** | AI  |

- **コミットはエンドポイント単位で刻む**（試走では9本）。**Tag を先に、Todo を後に**
- **4手は `CLAUDE.md` に書いて渡す。**研修生から見える手数を増やさない
- **auto を使ってよい。ただし取り消しがきかない操作（コミット・ファイル削除・DB操作）では承認を取る**

### 設計に無いことをAIが決めても、B では止めない

**その場で報告させる仕組みは置かない。**止めどころを増やすと B が進まないため。
**C の観点「設計に無い判断が入っていないか」で拾い、そこで `確認事項.md` に足して聞く**（→ A に戻る）。

> [!warning]- 拾えないことがある（2026-09-11・試走）
> **A で「エスケープする」と裁定したのに設計書へ書き戻さなかった1件は、全工程を素通りした。**
> **AIレビューは設計書を渡していないので仕様の話には届かない**（差分に4箇所あり、最後まで読んで一言も触れなかった）。
> **→ この観点は、人が見るしかない。**

---

## C 確かめる（半日）

> ### AIが書いたコードを、問題ないと自分で説明できる状態にする。

**B が終わったら push して PR を作り、C はすべて PR の上で回す。**
**段には分けない。確認する観点だけ渡し、アプローチは任せる。**

### 確認する観点

**→ 上の「8 の7観点」。**

**AIを使ってよい。順序も使い方も指定しない。**
**★「AIが触れなかったもの」だけは外せない。**指摘リストの中を見ている限り、**そこに無いものは見えない。**

### 回し方 — push してから直す

**push → PR → AIにレビューさせる → 自分でも確かめる → 対応が要るものを直す → push。**
**指摘も対応もコミットも、PR に時系列で残る。**

**仕様に関わる指摘は、C で閉じない。**`確認事項.md` に足して仕様管理者に聞き、**設計書を直してから実装を直す**
——**A と B に戻る。**直すときも **B の4手。**

**実務との違いは、ボットが自動で走るか、自分で走らせて貼るかだけ。**
**★ボットを置かないのは費用ではなく運用の都合**（→ `03_研修環境とガードレール.md` §6）。研修生にはそう言う。

| 判定 | 処置 |
|---|---|
| **正しい** | **直す → コミット → push。**仕様に関わるなら **A から回す** |
| **的外れ** | **理由を書いて閉じる。**直さない |
| **判断できない** | **消さない。**仕様なら `確認事項.md`（「いつ」列は `確認時`）→ 仕様管理者へ。技術ならPRに書いてレビュアーへ |

**戻るのは最大1周。**2周目の新しい指摘は仕分けるだけ。
**終わりの条件: 3分類すべてに処置が決まったら終わり。**「正しい」を全部直した、ではない。

### PR に何を書くか

**本文は4欄。実務のPRと同じ形にする**（見本 → `17_見本_PR.md`）。

|  | 中身 |
|---|---|
| **概要・背景** | 何を作ったか。着手前に何件確認して設計書を直したか |
| **変更点** | 差分の規模・実装したエンドポイント・テスト件数・コミットの刻み方 |
| **確認したこと** | **何をどう確かめ、その結果をなぜ信じてよいか** |
| **判断を仰ぎたいこと** | **見たが自分では決められないもの。回答待ちの確認事項** |
| **AIの利用** | **開示する。粒度と方法は客先のルールによる**（→ ⓪ の1番） |

> **書くのは「現在の状態と根拠」。「足りなかったので足した」という経緯は書かない。**
> **経緯はコミット履歴に残る。**レビュアーが要るのは、**いまのテストをどこまで信じてよいか**のほう。

**★AIの指摘と仕分けは、本文ではなくコメントとして貼る。**実務ではボットの指摘がスレッドに残るので、形を合わせる。

### 終わりの形

**自分で確かめた範囲と、仕様管理者に問い合わせる範囲を、線を引いて言えること。**

> **自分の観測で決着するものは、全部自分側。他人の同意が要るものは、全部相手側。**
> **難しいかどうか、時間がかかるかどうかでは切らない。**

## 配布物

**リポジトリは1本。期ごとに作り直す。★ = AI研修のために足すもの**（2か月目の環境には無い）。

```
todo-training-YYYY/                  ← private。21人が同じ1本にブランチで入る
├── ★ CLAUDE.md                      AIへの指示ファイル。DoD 9項目・B の4手を含む
├── ★ .claude/
│   ├── settings.json                AIに許す操作の範囲。触らない
│   └── hooks/                       ★他の研修生のPRに届く経路を塞ぐ
├──   pom.xml ／ todo_checks.xml     2か月目と同じ ＋ ★checkstyle
├──   src/
│    ├── 2か月目の雛形そのまま      空フォルダ・共通例外・SecurityConfig・testTools
│    └── ★参照実装1本               Todo 1件取得の完成品 ＋ 統合テスト1本
└──   docs/                          ← ★研修生が書き戻す（読むだけではない）
     ├── 要件定義書・アーキ図・DB定義書・OpenAPI・エラーコード表・プログラム設計
     ├── ★ 確認事項.md               ★空の雛形。A・B・C で行が増える（提出物）
     ├── ★ テストケース一覧.md       ★空の雛形。A で埋める（提出物）
     └──   実装計画.md               ★配らない。B の頭でAIが書く（提出物）

（リポジトリの外・別配布）振り返り.md   ★問い5つだけの雛形。AIに渡さない（提出物）
```

**設計書を同梱しても、「配られたものと渡したもの」の差分は `git diff main...task -- docs/` で出る。**
**環境・権限・ガードレールは `03_研修環境とガードレール.md`。**
