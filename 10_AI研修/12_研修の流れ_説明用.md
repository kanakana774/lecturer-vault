# AI研修の流れ

## 目的

> ### AIに書かせたコードの品質を、自分で担保できるようにする。

SES では客先に**自分の名前で**成果物を出す。AIが書いたものでも変わらない。

対象は**3か月目の新人**。題材は**2か月目と同じ Todo API**（Java 21 / Spring Boot 3.4.1 / MyBatis）。

---

## 流れ

```
【前提】
  ガバナンス  ──  理解度テストに合格  →  アカウント発行

【本編】
  入口（自分）      →      中（AI）      →      出口（自分）
   A 決める                B 任せる            C 確かめる
```

**実装するのはAI。研修生がやるのは、コンテキスト整えて、委任して、その検証。**
**各段の提出物が、次の段の入力になる。**

## 配布物

**リポジトリは2つだけ。最後まで増えない。**
**★ = AI研修のために足すもの**（2か月目の環境には無い）。

```
todo-app-api/                        ← 書き換える唯一の場所
├── ★ CLAUDE.md                      AIへの指示ファイル。読むだけ。DoD 9項目を含む
├── ★ .claude/settings.json          AIに許す操作の範囲。触らない。ガバナンスで説明しておく
├── ★ docs/仕様確定.md               ★空の雛形。研修生が埋める（提出物）
├──   pom.xml ／ todo_checks.xml     2か月目と同じ ＋ ★checkstyle
└──   src/
     ├── 2か月目の雛形そのまま      空フォルダ・共通例外・SecurityConfig・testTools
     └── ★参照実装1本               Todo 1件取得の完成品 ＋ 統合テスト1本

todo-app-api-docs/                   ← 読むだけ・書き換えさせない
     要件定義書・アーキ図・DB定義書・OpenAPI・エラーコード表・プログラム設計

（リポジトリの外・別配布）検証記録.md   ★問い記入済みの雛形。AIに渡さない（提出物）
```

> [!note]- なぜこの置き方にしたか
> **現物は `Desktop/AI研修/配布見本/` にある**（研修生に渡した直後の状態）。
>
> | | なぜそうしたか |
> |---|---|
> | **設計書を別リポジトリにする** | 上流の資産なので**書き換えさせない**。実務でも設計書リポにPRを出すのは別プロセス |
> | **`仕様確定.md` はコード側に置く** | 受入条件が実装に紐づくので、**同じブランチで履歴が追える** |
> | **`検証記録.md` はリポジトリの外** | `docs/` に置くと **AIが読んでしまう**（C-4 で自分の答えをAIが読んだ状態になる） |
> | **参照実装を1本だけ配る** | **テストの層と書き方は、例が無いと揃わない** |

## ガバナンス（前提）

**答えがあるので、教えて、測って、終わらせる。**

1. 客先のルールを確認する
2. 渡してはいけないものを渡さない
3. 何を渡したか記録する
4. AIに書かせた部分を PR で明示する

**理解度テストに合格して、次に進む。**

---

## A 決める — AIに実装させる前に、何を作るかを確定させる

| | 何をするか |
|---|---|
| **A-1** | 要件定義書とアーキテクチャ図を**通読する** |
| **A-2** | **コンテキストを整えずにAIに実装させ**、自分の要件の理解と比べる |
| **A-3** | AIに**設計上の未決事項や矛盾を、根拠つきで挙げさせる** |
| **A-4** | 1件ずつ資料に当たり、**記載あり／自己判断／要確認／未着手**に仕分ける |
| **A-5** | **「要確認」を仕様管理者（講師）にエスカレーションし、回答を書き戻す** |
| **A-6** | **受入条件をAIに挙げさせ**、渡し漏れが無いか照合する |

**通読するのは要件定義書とアーキテクチャ図だけ。**
DB定義書・OpenAPI・エラーコード表・プログラム設計は、**A-4 で必要になったときに開く。AIで設計書を効率的に参照する体験をここでさせる。**

### `docs/仕様確定.md` がどう埋まっていくか

**配るのは空の雛形。** 3節あり、**AIが素案を出し、自分が確定させる。**

| 節 | 何を持つ節か | 素案を出すのは | 確定させるのは |
|---|---|---|---|
| **§1** | **確認事項** — 決まっていないこと | **AI**（A-3） | **自分**（A-4） |
| **§2** | **決定事項** — 決めたことと、その出所 | — | **自分**（A-5）／**実装中はAIが足す**（B-2） |
| **§3** | **受入条件** — どうなれば完了か | **AI**（A-6） | **自分**（A-6 で照合し、検証手段を付ける） |

**配る時点** — 空の雛形

```markdown
## §1 確認事項
| 項目 | 区分                                 | 根拠 / 確認先 | 反映 |
|------|--------------------------------------|---------------|------|
|      | 記載あり / 自己判断 / 要確認 / 未着手 |               |      |

## §2 決定事項
| 決めたこと | 理由 | 出所                            | 上位者へ |
|------------|------|---------------------------------|----------|
|            |      | 確認済み / 自分の判断 / 実装中 |          |

## §3 受入条件
| #  | 条件 | 出所           | 検証手段                    |
|----|------|----------------|-----------------------------|
|    |      | AI / §2 / DoD | テスト / checkstyle / 目視 |
```

**A-3 のあと** — **AIが**項目と根拠を挙げる。**「区分」はまだ空**

```markdown
## §1 確認事項
| 項目                        | 区分 | 根拠 / 確認先             | 反映 |
|-----------------------------|------|---------------------------|------|
| content の最大文字数が違う  |      | 要件定義は30、DB定義は100 |      |
| Tag削除時の todo_tag の扱い |      | DB定義書に記載なし        |      |
| 同名のTagを登録できるか     |      | UNIQUE 制約が無い         |      |
| 進捗状況という項目がある    |      | 要件定義 3.1              |      |
```

**A-4 のあと** — **自分が**1件ずつ資料に当たり、**区分を埋める。ここが人の仕事**

```markdown
## §1 確認事項
| 項目                        | 区分     | 根拠 / 確認先             | 反映 |
|-----------------------------|----------|---------------------------|------|
| content の最大文字数が違う  | 要確認   | 要件定義は30、DB定義は100 |      |
| Tag削除時の todo_tag の扱い | 要確認   | DB定義書に記載なし        |      |
| 同名のTagを登録できるか     | 自己判断 | UNIQUE 制約が無い         |      |
| 進捗状況という項目がある    | 記載あり | 要件定義 3.1（DB設計になし）|    |
| 部分一致の % _ の扱い       | 未着手   | 時間切れ                  |      |
```

**迷ったら「要確認」。** 実務で困るのは、**要確認にすべきものを自己判断にしたとき**。

**A-5 のあと** — 聞いた答えが §2 に落ち、§1 の「反映」が埋まる（**どちらも自分が書く**）

```markdown
## §2 決定事項
| 決めたこと                      | 理由                      | 出所       | 上位者へ |
|---------------------------------|---------------------------|------------|----------|
| content は最大100文字           | 3対1で100。要件定義だけ30 | 確認済み   | —        |
| Tag削除時に todo_tag の行も消す | 孤児レコードが残る        | 確認済み   | —        |
| 同名のTagを登録できる           | UNIQUE 制約が無い         | 自分の判断 | —        |
```

**A-6 のあと** — **AIが**条件を挙げ、**自分が**渡し漏れを照合して**検証手段を付ける**

```markdown
## §3 受入条件
| # | 条件                                | 出所 | 検証手段       |
|---|-------------------------------------|------|----------------|
| 1 | POST /todos content 空文字は 400    | AI   | テスト         |
| 2 | content 101文字は 400               | §2  | テスト         |
| 3 | Tag削除時に todo_tag の行が残らない | §2  | テスト         |
| 4 | 例外の内部情報を body に返さない    | DoD  | テスト         |
| 5 | 一覧取得で N+1 を発生させない       | DoD  | 目視（SQLログ）|
| 6 | 3層構成を維持する                   | DoD  | 目視           |
```

**★「検証手段」列がこの後の作業を決める。**
**受入条件のうち、テストにできるのは半分程度。**残りは人が目で見るしかない。
**「目視」の行が、そのまま C の作業リストになる。**

**提出物: `docs/仕様確定.md`**

---

## B 任せる — 任せた仕事の流れが見えている状態で回す

| | 何をするか |
|---|---|
| **B-1** | `仕様確定.md` を渡して**実装計画を出させ、触るファイル一覧を見て承認する** |
| **B-2** | **1コミットずつ、下の4手を回す** |

**B-2 の4手**

| | やること | 誰が |
|---|---|---|
| ① | **そのコミットで満たす受入条件を、テストに書く**（実装ではなく仕様から書く） | AI |
| ② | **実装前に `mvn test` を走らせ、①のテストが失敗する出力を見せる** | AI |
| ③ | **実装する。①のテストは変えない**（変えたいときは変えずに理由を報告） | AI |
| ④ | **`mvn test` と `mvn checkstyle:check` を通してコミットする** | AI |

**②が要る理由: 実装前に通ってしまうテストは、何も検証していない。**
実装のあとに書いたテストは、実装に合わせて書ける。**②は機械的に確認できる**（出力を見せさせればよい）。

**7コミット**: 土台（テストに必要な Entity・Form・Query）→ Tag（CRUD 5本）→ Todo（`POST` → `GET(1件)` → `GET(一覧)` → `PUT` → `DELETE`）

**auto は禁止。** ステップごとに承認させる（流れを見せるため）。

**★AIへの指示に1行入れる。**

> **設計書と違う実装にしたら、`docs/仕様確定.md` §2 に1行足してから報告してください（出所は「実装中」）。**

### `仕様確定.md` がもう一度増える

**B-2 のあと** — **AIが**書く。**設計書から逸れた分が §2 に増える**

```markdown
## §2 決定事項
| 決めたこと                   | 理由                             | 出所   | 上位者へ |
|------------------------------|----------------------------------|--------|----------|
| 一覧取得を JOIN 1本にした    | 設計書は「ループして取得」だが、 | 実装中 | ○        |
|                              | DoD の for内SQL 禁止と衝突       |        |          |
| tags に同じIDが2つ来ても 201 | 存在チェックを重複を除いて数えた。| 実装中 | ○       |
|                              | 設計書の文言なら404              |        |          |
```

**「上位者へ」列が ○ / — の2値。** ここの判断そのものが提出物になる。

> **上位者は設計を把握しているが、そこから逸れたことは把握していない。**
> **AIは聞かなければ言わない。だから本人が把握していなければ、組織の誰もその逸脱を知らない。**

**提出物: 作業ブランチ（7コミット）**

## C 確かめる — 動いた、ではなく、正しいと言える

**答えは配らない。問いだけ渡す。**

| | 何をするか |
|---|---|
| **C-1** | **`git diff` で変更範囲を確認する**（頼んでいないファイルが変わっていないか） |
| **C-2** | **受入条件と突き合わせる**（`仕様確定.md` §3 の「目視」行が作業リスト） |
| **C-3** | **問いに答える**（AIが仕様に無いことを独自に決めた箇所はどこか、など） |
| **C-4** | **AIに自分の成果物をレビューさせ**、正しい／的外れ／判断できない に仕分ける |

### `仕様確定.md` は C でも増える

**C-3 のあと** — **自分が**書く。**B-2 でAIが書き漏らした逸脱を拾い、判断できないものは §1 に戻す**

```markdown
## §2 決定事項
| 決めたこと                     | 理由                            | 出所   | 上位者へ |
|--------------------------------|---------------------------------|--------|----------|
| 一覧取得の tags を distinct した | 重複行が出たため。設計書に記載なし | 実装中 | ○      |

## §1 確認事項

|----------------------------------|--------|------------------------------|------|
| Tag削除の順序が FK の不在に依存  | 要確認 | DB定義書は複合PK、DDLは制約なし |   |
```

**★C で §1 に戻る行が出る。** これが**エスカレーションの実体**。

### `検証記録.md` はこう埋まる

**リポジトリの外。全部自分で書く。AIに書かせる欄はひとつも無い。**

```markdown
## 2. 受入条件との突き合わせ（C-2）
| §3 の # | 検証手段 | 何をして確かめたか            | 結果 |
|----------|----------|-------------------------------|------|
| 1        | テスト   | TodoPostTest#blankContent 緑  | OK   |
| 5        | 目視     | SQLログで LEFT JOIN 1本を確認 | OK   |
| 6        | 目視     | Controller に業務判断が無い    | OK  |

## 3. 問い
1. AIが仕様に無いことを独自に決めた箇所はどこか。それは正しいか。
   → 一覧取得の distinct。重複が出るのは事実だが、
     「重複をどう扱うか」は設計書に無い。§1 に上げた
...

## 5. 終わりの形
**自分で確かめた範囲** → 受入条件6件（テスト4・目視2）と DoD 9項目
**レビューを頼む範囲** → Tag削除の順序。DB定義書とDDLのどちらが正本か決められない
```

### C-4 は「検証」ではなく「渡し漏れの可視化」

**AIに自分の成果物をレビューさせると10〜20件出る。それを3つに仕分ける。**

| 指摘の例 | 判定 | 理由 |
|---|---|---|
| `TagController` に `@Valid` が無い | **正しい** | 付け忘れ。`TodoController` には有る |
| Entity をそのままレスポンスに返している | **的外れ** | **アーキ図が「今回アーキテクチャを省略する」と明記している。AIはその注記を読んでいない** |
| Tag削除の順序が FK の不在に依存している | **判断できない** | どちらの資料が正本かは仕様管理者しか決められない |

**★4列目に「的外れの理由」を分類させる。ここが本題。**

> **的外れの理由をまとめると、「自分がAIに渡していない情報は何か」が出てくる。**

**検証手段としては弱い。** 同じ資料を読むので**同じ誤読をする**し、**渡していない情報は原理的に見えない**。
**だから C-4 は「レビューbotを入れれば安心」という誤解を先に潰す装置として置いている。**

### 終わりの形

**自分で確かめた範囲と、レビューを頼む範囲を、線を引いて言えること。**

**線を引く基準はこれ。**

> **自分の観測で決着するものは、全部自分側。他人の同意が要るものは、全部相手側。**
> **難しいかどうか、時間がかかるかどうかでは切らない。**

**提出物: `検証記録.md`**

## 押さえるべきところ

**AIエージェントでの開発で品質が落ちる原因を、モデルにした。**

```
  L1  入力 ── 仕様書 / 既存コード / DDL / 実行基盤の既定     ← 仕様管理者が持つ
  │ ▲
  │ │  ↓ 読む      ↑ 返す（考慮漏れ・矛盾を上げる／自分で決めたことを返す）
  ▼ │
  L2  変換 ── ジュニア ──①─▶ AI ──②─▶ 実装（出力）        ← ジュニアが持つ
              ①② どちらでも 誤読 / 独断 / 読み漏らし が起きる
```

**L1 の入力は仕様書だけではない。** 既存コード・DDL・実行基盤の既定も入力。
**これはAI固有ではない。** 人に任せても同じ構造で、変わったのは量と速度だけ。

**この原因ひとつずつに、工程を割り当てた。**

| 押さえるべきところ | どの工程で押さえるか |
|---|---|
| **L1 矛盾**（資料どうしが食い違う） | **A-3 → A-4 → A-5。紙 ⟷ 紙 なので実装前に出る** |
| **L1 考慮漏れ**（読めば気づく分） | A-3 → A-4 → A-5 |
| **L1 考慮漏れ**（実装しないと気づかない分） | **B-2 でAIが報告 ＋ C-3 で人が探す** → §2「実装中」 |
| **誤読** | **C-2**（受入条件と突き合わせる）。**テストでは拾えない** |
| **独断** | **B-2 の★指示 ＋ C-3** → §2「実装中」＋「上位者へ ○」 |
| **読み漏らし** | **C の停止条件**（渡された規約書を全部並べてから閉じる） |
| **① ジュニアの渡し漏れ** | **C-4**（的外れ指摘の理由を分類する） |

**★誤読をテストでは拾えないのが要点。** テストは実装と同じ仕様解釈から生まれるので、**読み間違いを検出せず、固定する。**
だから **A-6（受入条件を実装より先に作る）**と **C-2** が誤読の足場になる。

## 見てほしいところ

- **上の「押さえるべきところ」に抜けは無いか。原因の立て方そのものが妥当か**
- **各工程のやり方が、実務のやり方として妥当か**
  （とくに **C-4 の「AIに自分の成果物をレビューさせる」** — 検証手段としては弱いと書いたが、置く価値があるか）
