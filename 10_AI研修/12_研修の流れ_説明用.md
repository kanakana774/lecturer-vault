# AI研修の流れ

## 目的

> ### AIに書かせたコードの品質を、自分で担保できるようにする。

SES では客先に**自分の名前で**成果物を出す。AIが書いたものでも変わらない。

対象は**3か月目の新人**。期間は**1週間**で、**本編の作業は2〜3日**を見込む。
題材は**2か月目と同じ Todo API**（Java 21 / Spring Boot 3.4.1 / MyBatis）。
Todo と Tag の CRUD ＋ Todo の登録／更新時に Tag を紐づける機能。

# 作業の一覧

```
【前提】
  ガバナンス  ──  ルールを学ぶ  →  本編

【本編】
  入口（自分）      →      中（AI）      →      出口（自分）
   A 入力を整える          B 任せる            C 確かめる
      半日                 半日                 半日

【締め】
   D 振り返る  ──  問い5つ。AIに渡さない
```

**各段の「半日」は仮置き。**試走から置いた目安で、**研修生の速度に合わせて動かす。**

| Step  | フェーズ   | 研修生がやること                                                      | 出るもの                    |
| ----- | ------ | ------------------------------------------------------------- | ----------------------- |
| **1** | **前提** | **AIの基本的な講義を受け、ルールを学ぶ**                          | —                       |
| **2** | **A**  | **配布プロジェクトを確認し、仕様を把握する**                                      | —                       |
| **3** | **A**  | **plan モードで `実装計画.md` を作らせ、テストケース一覧ごと過不足を確認して承認する**           | **`実装計画.md`**（ケース一覧を含む） |
|       |        | **▶ 実装計画に合意できたら B へ**                                         |                         |
| **4** | **B**  | **機能ごとに、テストを先に書かせ、失敗を確認してから実装させ、テストと Checkstyle を通してコミットさせる** | 作業ブランチ                  |
|       |        | **▶ push して PR を作る**                                          | **PR**                  |
| **5** | **C**  | **AIにレビューさせ、PR にコメントさせる**                                     | **PRのコメント**（AIが投稿）      |
| **6** | **C**  | **自分でも確かめ、AIの指摘の妥当性も見る**                                      | **PRの行コメント**            |
| **7** | **C**  | （**対応が要るものは、A・B に戻して直す**）                                     | コミット                    |
|       |        | **▶ PR本文を仕上げて提出**                                             | **PR**                  |
| **8** | **D**  | **振り返りを書く**（問い5つ）                                             | `振り返り.md`               |

**通して守るルール**

- **質問はいつでも投げてよい。**仕様管理者は講師
- **設計に無いこと・確認が要ることは、仕様管理者に確認してから設計書に書き戻す。**タイミングは問わない

**Step 6 の観点 — 問いは1つ**

> ### **仕様どおりに実装できたと、なぜ言えるのか。**

**下の3つは、その根拠の作り方。**どれか1つで言い切れるものではない。

|  |  |
|---|---|
| **設計に無い判断が入っていないか** | **AIが勝手に決めた箇所。確認して、設計書に書き戻す** |
| **テストは妥当だったか** | **緑であることが、正しさの証拠になっているか**（詳細はレビュー観点9） |
| **レビュー観点9項目** | **チーム共通で、機能が変わっても変わらない。**見どころは `09_配布物/DoD.md` |

**観点はガイドとして配る。**確認した結果は、**該当箇所への行コメントとして PR に残す**（＝人間レビュー）。
**まとめは PR本文の「確認したこと」へ。**

**PR本文**

|  |  |
|---|---|
| **概要** | 何を作ったか。着手前に何件確認して設計書を直したか |
| **確認したこと** | **ケース件数とテスト件数・`mvn test` の結果・観点チェック** |
| **相談したいこと（自分の見解つき）** | **自分で確認してもなお決められなかったもの ＋ 回答待ち。AIの指摘をそのまま置かない。1件ごとに見解を添える** |

**★PR に書く作業は3つだけ。**（実物は下の折りたたみ）

|           | やること                                        | 何のために                     |
| --------- | ------------------------------------------- | ------------------------- |
| **数える**   | テスト件数・ケース件数・欠番の有無                           | **いまのテストをどこまで信じてよいかを示す**  |
| **印を付ける** | 観点に `[x]` か `[ ]`                           | **担保できた範囲と、できない範囲を線引きする** |
| **絞る**    | AIの指摘のうち、**自分で確認しても決められなかったものだけ** ／ 回答待ちのもの | **レビュアーの認知負荷を下げる**        |

# 詳細

## 研修生に達成してもらいたいこと — 3点

|       |                | 到達した状態                                          | どこで   |
| ----- | -------------- | ----------------------------------------------- | ----- |
| **1** | **コンテキストの重要性** | **何を渡し、何を渡さなかったかを、理由とともに説明できる。**渡さなかった側も同じ重さで語れる | **A** |
| **2** | **仕様充足の証明**    | **仕様どおりに実装できたと、根拠をもって言える**（設計に無い判断が入っていないことを含む）。**テストで何をどこまで証明できたかを、品質の言葉で言える** | **C ／ D** |
| **3** | **品質保証の線引き**   | **担保できた範囲と、できない範囲を言える**                         | **C** |

**1 には「渡しすぎない」も入る。**
**要らないものを渡さない／`/clear` で切る**——コンテキストウィンドウの管理も、「何を渡すか」の一部。
**渡す量が増えるほど効きが落ちる**ので、長い作業ではここで差が出る。

**2 は、言葉を持っていないと語れない。**
「テストが緑だから正しい」で止まるのは、**QA・内部品質・外部品質**といった語を持っていないため。
**★語はこちらから渡す。定義は自分でAIに調べさせ、振り返りのフィードバックでもできるだけ説明する。**
（→ `11_品質特性と検証の分担.md` §6）

> **3点は到達点であって、手順ではない。**作業中にこれを確認する場は置かない。
> **主に振り返りで、本人が実際にとったアプローチを材料に話し合う。**
> **★将来は「前提」の講義に入れ、着手前に指標を渡した状態で始めたい。**初回は振り返りだけで回す。

## 作らせるもの — 4点

| 作らせるもの | どこで | AIの扱い | 何のために |
|---|---|---|---|
| **`実装計画.md`**（テストケース一覧を含む） | **A** | **★AIに作らせ、過不足を人が見て承認する** | **合格の基準を、実装より前に固定する** |
| **直した設計書（差分）** | **通し** | **自由** | **確認して決まったことを、AIが読む場所に戻す** |
| **PR（本文とコメント）** | **C** | **自由**（AIにレビューさせてよい） | **担保できた範囲と、できない範囲を示す** |
| **`振り返り.md`** | **D** | **★AIに渡さない** | **何を渡し、何を渡さなかったかを言わせる** |

### `実装計画.md` は、実装より前に作らせる

**汚染される前に固定するため。**早くやるためではない。
**実装を見てから作ると、テストが実装に寄る。**

### ★ が指示。無印は自由

**指示は「何を作るか」と「AIに任せてよいか」まで。「どう作らせるか」は縛らない。**
**やり方が決まっていないものは指示にしない。**講師の案は **`18_模範アプローチ_説明用.md`** にある。

> [!note]- 指示には2種類ある。研修生にはどちらかを言う
> |  | どういうものか | どれ |
> |---|---|---|
> | **実務の作法** | **やり方が実務でほぼ1つに決まっている。必ず踏ませる** | **ケース一覧を含む実装計画をAIに作らせる／承認してから実装する／テストを先に書かせる** |
> | **研修の都合** | **外すと到達点3点が測れなくなる。「実務の作法ではない」と断って渡す** | **`振り返り.md` をAIに渡さない** |
>
> **どう渡し、どう確かめたかは研修生が決める。そこが評価の材料になる**（→ 評価）。

## 前提 — ガバナンス

1. 客先のルールを確認する
2. 渡してはいけないものを渡さない
3. 何を渡したか記録する（**実体は `振り返り.md` の問い1。正確なログは取らせない**）
4. AIに書かせた部分を開示する（**粒度と方法は客先のルールによる**）。**この研修ではコミットのトレーラーで残す**

**根拠は一次情報にある**（経産省の契約チェックリスト／IPA のガイドライン／客先常駐の契約上の整理）。
**→ `03_研修環境とガードレール.md` §6。**

**あわせて B の進め方も、ここで説明しておく。**先に失敗するテストを書かせ、通してコミットする——
**`CLAUDE.md` に書いてあるので、説明さえすれば勝手に回る。**

### 併せてやる「AIの基本的な講義」

| | |
|---|---|
| **モデルの違い** | **Opus / Sonnet など。どれをいつ使うか** |
| **スラッシュコマンド** | **`/clear` でコンテキストを切る**（→ 到達点1） |
| **skill** | **手順を再利用する形。毎回プロンプトに書かない** |

**講義は対話で進める。**手順を一方的に配らず、**AIと共存する姿勢そのものを見せる。**

**★講義を受けたら本編に進む。合否の判定は置かない**（→ `03_研修環境とガードレール.md` §6）。

## A 入力を整える（半日）

**課題で配られるものと、AIに最終的に渡すものは別物。その差分を作るのが A。**

**`実装計画.md` のケース一覧の基準は2つだけ。**

- **1件ごとに「入力・事前状態・期待する結果」＋ 設計書のどこから来たかの根拠を書く**
- **期待する結果を断定できないケースは、一覧に残さない。**根拠が書けないなら、**それは仕様がまだ決まっていない**

**基準を満たそうとすれば、未決と矛盾は自然に表に出る。**

### B に進んでよい状態

> ## **`実装計画.md`（ケース一覧を含む）に、合意できている。**

**plan モードの承認が、そのまま着手基準。**研修生が自分でその場で確かめられる。
**半日で届かなければ、残りを「決まらないと知って進む」に落として B に行く。それも正しい終わり方。**

---

## B 任せる（半日）

**計画に合意したら、機能ごとに刻んで任せるだけ。**

**B に固有の到達点は置かない。**流れを一度通す段で、**研修生がやるのは見守ること。**
**1コミットの中身（下の①〜④）は `CLAUDE.md` に書いてあり、前提で説明する**ので、
**研修生は「いま何が起きているか」が分かった状態で B に入る。**

> **`develop` から `feature/<社員番号>-<氏名>` を切り、そこから `task/<社員番号>-<氏名>` を切って作業する。**
> **例: `feature/126013-KawauchiKota` → `task/126013-KawauchiKota`。**
> **既定ブランチは `develop`。2か月目と同じ形で、直接コミットはしない。**

**1コミットの中身は4つ。`CLAUDE.md` に書いて渡すので、研修生から見える手数は増えない。**

|     | やること                                               | 誰が  |
| --- | -------------------------------------------------- | --- |
| ①   | **そのコミットで満たすケースを、`実装計画.md` のケース一覧からテストに書く**（実装ではなく仕様から書く） | AI  |
| ②   | **実装前に `mvn test` を走らせ、①のテストが失敗する出力を見せる**          | AI  |
| ③   | **実装する。①のテストは変えない**（変えたいときは変えずに理由を報告）              | AI  |
| ④   | **`mvn test` と `mvn checkstyle:check` を通してコミットする** | AI  |

**②が要る理由: 実装前に通ってしまうテストは、何も検証していない。**

- **コミットはエンドポイント単位で刻む**（試走では9本）
- **auto を使ってよい。ただし取り消しがきかない操作（コミット・ファイル削除・DB操作）では承認を取る**

### 設計に無いことをAIが決めても、B では止めない

**その場で報告させる仕組みは置かない。**止めどころを増やすと B が進まないため。
**C の観点「設計に無い判断が入っていないか」で拾い、確認してから設計書に書き戻す。**

---

## C 確かめる（半日）

> ### AIが書いたコードを、問題ないと自分で説明できる状態にする。

**B が終わったら push して PR を作り、C はすべて PR の上で回す。**
**段には分けない。観点だけ渡し、アプローチは任せる**（→ 上の「Step 6 の観点」）。

**AIを使ってよい。順序も使い方も指定しない。**

### 回し方 — push してから直す

**push → PR → AIにレビューさせる → 自分でも確かめる → 対応が要るものを直す → push。**
**指摘も対応もコミットも、PR に時系列で残る。**

**実務との違いは、ボットが自動で走るか、自分で走らせるかだけ。**指摘はAI自身が PR に投稿する。

| 判定 | 処置 |
|---|---|
| **正しい** | **なぜ正しいのかを自分で確かめてから**、直す → コミット → push。仕様に関わるなら**確認を取り、設計書も直す** |
| **的外れ** | **そのコメントに理由を返信して閉じる。**直さない |
| **判断できない** | **消さない。本文の「相談したいこと」に上げる。**仕様なら仕様管理者へ |

> **「正しい」に入れる前に、必ず自分で確かめる。**確かめずに直すのは、AIに判断を預けたのと同じ。
> **3つ目に残ってよいのは、確かめたうえでなお決められないものだけ。**
> **指摘を全部3つ目に流すと、自分では何も決めていないPRになる。**

**戻るのは最大1周。**2周目の新しい指摘は仕分けるだけ。

### PR に何を書くか

**本文は3欄**（→ 上の表と折りたたみ）。

> **書くのは「現在の状態と根拠」。「足りなかったので足した」という経緯は書かない。**
> **経緯はコミット履歴に残る。**レビュアーが要るのは、**いまのテストをどこまで信じてよいか**のほう。

**★AIの指摘は、AI自身に `gh pr comment` で投稿させる。**実務のボットと同じ場所に残る（→ 上の折りたたみ）。

### 終わりの形

**自分で確かめた範囲と、仕様管理者に問い合わせる範囲を、線を引いて言えること。**

> **自分の観測で決着するものは、全部自分側。他人の同意が要るものは、全部相手側。**
> **難しいかどうか、時間がかかるかどうかでは切らない。**

## D 振り返る

**問い5つに答える。`振り返り.md` はAIに渡さない**（→ 作らせるもの）。
**正確さは求めない。**思い出して書ける範囲でよく、記録を取りながら進める必要はない。

| | 問い | 何を見るか |
|---|---|---|
| **1** | **AIに何を渡し、何を渡さなかったか**（渡さなかったものは、なぜ渡さなかったかも） | **到達点1** |
| **2** | **AIが設計から逸れた箇所に、どうやって気づいたか**（気づけなかったかもしれないものも） | **到達点2** |
| **3** | **自分で確かめて決着したものと、仕様管理者に上げたものを、何で分けたか** | **到達点3** |
| **4** | **「テストが緑」以外に、テストが効いていると言える根拠は何か** | **到達点2** |
| **5** | **AIのレビューに出てこなかったもののうち、自分が見つけたものは何か**（なぜAIには出なかったと思うか） | **到達点3** |

**雛形は `09_配布物/振り返り.md`。**

**ここが到達点3点を話す場。**本人が実際にとったアプローチを材料に、
**何を渡し何を渡さなかったか／テストで何をどこまで証明できたか／どこから先は担保していないか**を議論する。
**正解を配る場ではない。**模範アプローチを見せるのは、この議論のあと。

## 評価

| フェーズ        | 測り方                                   |
| ----------- | ------------------------------------- |
| **前提**      | **測らない。**講義で扱うだけ                      |
| **A**       | **アプローチを議論する。**成果物の正しさは測らない           |
| **B**       | **テストが先に書かれ、機能単位で刻まれているか**（作業ブランチ）    |

**添削はしない／評価はする／議論はする。** 3つ目が実質のフィードバック。
**模範アプローチは、本人がやりきったあとに一例として見せる。**

## 配布物

**リポジトリは `ai-training` 1本。期をまたいで使い続ける**（→ `03_研修環境とガードレール.md` §2）。
**★ = AI研修のために足すもの**（2か月目の環境には無い）。

```
ai-training/                         ← private。21人が同じ1本にブランチで入る
├── ★ CLAUDE.md                      AIへの指示ファイル。レビュー観点9項目・1コミットの4つを含む
├── ★ .claude/
│   ├── settings.json                AIに許す操作の範囲。触らない
│   └── hooks/                       ★他の研修生のPRに届く経路を塞ぐ
├──   pom.xml ／ todo_checks.xml     2か月目と同じ ＋ ★checkstyle
├──   src/
│    ├── 2か月目の雛形そのまま      空フォルダ・共通例外・SecurityConfig・testTools
│    └── ★参照実装1本               Todo 1件取得の完成品 ＋ 統合テスト1本
└──   docs/                          ← ★研修生が書き戻す（読むだけではない）
     ├── 要件定義書・アーキ図・DB定義書・OpenAPI・エラーコード表・プログラム設計
     └── ★ 実装計画.md              ★空の雛形。A で埋める（テストケース一覧を含む・提出物）

（リポジトリの外・別配布）
  DoD.md         ★レビュー観点9項目の見どころ。研修生だけが読む（中に置くとAIが先回りして直す）
  振り返り.md     ★問い5つだけの雛形。AIに渡さない（提出物）
```

**設計書を同梱しても、「配られたものと渡したもの」の差分は `git diff develop...task -- docs/` で出る。**
**研修生の PR はマージしない。**`develop` を配布時点で固定しないと、次の期の研修生に「もう直っている設計書」が渡る。
**環境・権限・ガードレールは `03_研修環境とガードレール.md`。**
