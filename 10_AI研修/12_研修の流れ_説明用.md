# AI研修の流れ

## 目的

> ### AIに書かせたコードの品質を、自分で担保できるようにする。

SES では客先に**自分の名前で**成果物を出す。AIが書いたものでも変わらない。

対象は**3か月目の新人**。題材は**2か月目と同じ Todo API**（Java 21 / Spring Boot 3.4.1 / MyBatis）。

- Todo API概要
	- todoのCRUD機能
	- tagのCRUD機能
	- todoの登録/更新時にtagを紐づけることができる機能

---

## 見てほしいところ

- **冒頭の「達成したいこと3点」が、配属後に必要なものとして妥当か。抜けは無いか**
- **各工程のやり方が、実務のやり方として妥当か**

---

## 研修生に達成してもらいたいこと — 3点

|       |             | 到達した状態                          | どこで     |
| ----- | ----------- | ------------------------------- | ------- |
| **1** | **コンテキスト**  | **何を渡し、何を渡さなかったかを、理由とともに説明できる** | **A**   |
| **2** | **逸脱の把握**   | **AIが設計から逸れた箇所を、説明できる**         | **B・C** |
| **3** | **線引き**     | **担保できた範囲と、できない範囲を言える**         | **C**   |

**3点とも「独断しないこと」が合格条件で、判断の広さは求めない。また、研修はあくまで考えるきっかけにしてもらい、上記は願わくばという感じ**
**配属直後の新人が、客先で最初に問われるのはこの3つだけ（と仮定）。**

> [!note]- 「決めてよいことと聞くべきことを分ける」を目標から外した理由（2026-09-01）
> **3点のうち、ここだけがAIで変質していない。**紙とペンの時代から同じ能力なので、**AI研修の目的にならない。**
> さらに判定の実体が薄い —— 決まっていないことは**AIに実装させれば必ず表に出る**し、
> **設計書に書いていないことは「逸れる」と言えない**ので、上げるか決めるかの分岐が立たない。
> **工程には残すが、測らない**（`06_研修の芯.md`「軸にしないもの」）。

## 流れ

```
【前提】
  ガバナンス  ──  理解度テストに合格  →  本編

【本編】
  入口（自分）      →      中（AI）      →      出口（自分）
   A 入力を整える          B 任せる            C 確かめる
```

**実装するのはAI。研修生がやるのは、コンテキスト整えて、委任して、その検証。**
**各段の提出物が、次の段の入力になる。**

---

## ガバナンス（前提）

**答えがあるので、教えて、測って、終わらせる。**

1. 客先のルールを確認する
2. 渡してはいけないものを渡さない
3. 何を渡したか記録する
4. AIに書かせた部分を PR で明示する

**理解度テストに合格して、次に進む。**

---

## A 入力を整える — AIに渡すものを、配られたものから作る（半日）

**課題で配られるもの**と、**AIに最終的に渡すもの**は別物。**その差分を作るのが A。**

### ★ 実装までに達成しておくこと — 5つ

**道具の話の前に、これが目的。**

| | 達成しておくこと | なぜ実装前でないとダメか |
|---|---|---|
| **1** | **合格の基準**（何が満たされれば正しいか ＋ **期待値をどこから取るか**） | **実装を見てから作ると、実装に寄る。**独立性は一度失うと再現できない |
| **2** | **範囲**（**やらないこと**・触ってよい場所） | **事後に「どこを見ていないか」を数えるには、先に地図が要る** |
| **3** | **書けなくなる未決の決着。矛盾は設計書を直して消す** | **型・スキーマ・DB制約・権限の後付けは「担保」ではなく「改修」** |
| **4** | **決まらなかったことの一覧** | **実装が出てからでは「AIが決めた」のか「決まっていた」のか区別できない** |
| **5** | **制約が、AIが読む場所にある**（**一般解から外れるところだけ**） | **頭の中の制約は、AIには存在しないのと同じ** |

**実装前の作業は「早くやるため」ではなく、「汚染される前に固定するため」。**

| | 何が起きるか | どれ |
|---|---|---|
| **決まらないと書けないもの** | **止まる。**あるいは勝手に決まる | **3・5** |
| **あとから作ると汚染されるもの** | **書けるが、根拠として使えなくなる** | **1・2・4** |

### 手順は3つ

|         | 何をするか                                             |
| ------- | ------------------------------------------------- |
| **A-1** | **配られたものを確認する**（設計書一式・`CLAUDE.md`・雛形）            |
| **A-2** | **AIに渡す形に更新する**（矛盾・未決は仕様管理者に確認し、**設計書を直す**）       |
| **A-3** | **AIに聞いて、決まっていない箇所を洗う**（＝**B に進んでよいかの判定**）        |

**★やり方は指定しない。** A-2 のアプローチは無数にある。**どう辿ったかを、あとで議論する**（→ 評価）。

### なぜ設計書に書き戻すか

**実装と設計がずれると困るから。** 決まったことは設計書に書く。**A・B・C の全段で同じ動作。**

| 段 | 何が起きたら | どこに書き戻すか |
|---|---|---|
| **A** | 矛盾・未決を確認して答えが出た | **設計書** |
| **B** | 実装が設計から逸れた | **設計書** |
| **C** | B で書き漏らした逸脱を拾った | **設計書** |

**「配られた設計書」と「渡した設計書」の差分が A の成果物。`git diff` でそのまま出る。**

### 渡すものは4つの問いに畳める

| 問い | 5つのどれか | 置き場 | 配られた状態 | **B開始時の状態** |
|---|---|---|---|---|
| **何を作るか** | 3 | **設計書** | 矛盾・未決あり | **矛盾が消え、答えが書き戻されている** |
| **どう作るか** | 5 | **`CLAUDE.md`** | 規約・DoD の雛形 | **意図を理解し、足りない前提を足した** |
| **どこまでやるか** | 2 | **`受入条件.md` の「対象外」節** | 空 | **やらないことが書いてある** |
| **どうなれば完了か** | 1 | **`受入条件.md`** | 空の雛形 | **埋まっている。検証手段付き** |

**そして本人が「渡していないものは何か」を言える**（`確認事項.md` ＝ 5つの 4）。**ここが C-4 の土台になる。**

> [!note]- 「どこまでやるか」を足した理由（2026-09-01）
> **C-1 で「頼んでいないファイルが変わっていないか」を見るのに、何を頼んだかを書いていなかった。**
> **事後に「どこを見ていないか」を数えるには、先に地図が要る。**
> 新しいファイルは増やさない。**受入条件の裏面が「対象外」なので、同じ紙に置く。**

### ★ B に進んでよい状態

> ## **配ったものだけを見た別のAIが、実装計画を書ききれる。**
> ## **そのとき、AIが自分で決めた箇所を、全部把握している。**

**「別のAI」は新しいセッション。** 会話の中で口頭で埋めた情報が残っていないので、**渡したファイルだけで成立するか**が見える。

**やること**

**1. ★ まず、決めることになる事項を直接列挙させる**

> **「実装するとして、あなたが独断で決めることになる事項を列挙して。実装はしないで」**

**AIは生成が得意で、自分から止まるのが苦手。** その性質を逆に使う。
**列挙された項目に自分が即答できなければ、準備不足。**
**⚠ 列挙ゼロは準備完了の証拠にならない。** 網羅は保証されない。

**2. 実装計画を出させる**（4節: **変更するファイル／作業の順序／リスク／証明**）

**3. 3つ詰問する** — **「何が壊れうるか／どの手が一番危ないか／捨てた代替案は何か」**

**4. AIが自分で決めた箇所を、1つずつ処理する**

**★4節目「証明」に、どの受入条件をどのテストで満たすかを書かせる。** ここで A の成果物と繋がる。
**7コミットに分かれるので、ここで紐づけないと C で全体を突き合わせられない。**
**★詰問の3つめが本命。** 聞かないと、**AIが選ばなかった方は永久に見えない。**

**具体的には、この2つが言えればよい**

| | 何が言えればよいか |
|---|---|
| **計画** | **4節が埋まり、「証明」の各行が受入条件のどれかを指している** |
| **決めた箇所** | **AIが自分で決めた箇所が全部挙がり、それぞれ「聞いて設計書を直した」か「決まらないと知って進む」になっている** |

### ★ 矛盾は「決まらない」に入れない。直して消す

**資料が食い違っているものは、聞けば決まる。** 聞いて、**設計書を直す**。
**優先順位のルール**（「型は DB定義書が正」など）**は作らない。**矛盾を残す前提になるので、
**「実装と設計をずらさない」と逆を向く**（2026-09-01 判断）。

**だから「決まらないと知って進む」に入るのは、実質2つだけ。**

| | 例 |
|---|---|
| **聞いたが、その場で決まらなかった** | 仕様管理者が持ち帰った。**研修では稀**（講師が決める） |
| **時間切れで聞けなかった** | 部分一致の `%` `_` の扱い |

**★「聞けば決まる」ものがここに並んでいたら、A が甘い。**
content の最大文字数（要件定義は30、DB定義は100）は**矛盾なので直して消す**。ここには入らない。**評価の議論はそこを突く。**

### 歯止め

| | |
|---|---|
| **その場で判定できる** | **別のAIが計画を書ききれるか**。研修生が自分で確かめられる |
| **形式を満たすだけでは通らない** | **中身が足りなければ計画が書けない。**雛形を埋めただけでは通過できない |
| **新しい道具はゼロ** | 新しいセッションを開いて一言聞くだけ |
| **時間はゴールではなく歯止め** | **半日で届かなければ、残りを全部「決まらないと知って進む」にして B に行く。**それも正しい終わり方で、**C で答え合わせされる** |

**★これは必要条件であって、十分条件ではない。** 満たせば良いA、ではない。**A の質が分かるのは C**（→ 評価）。

> [!note]- 潰し切れない分は「刻み」で買う
> **どれだけ準備しても、掘れば出てくる。**言語化できていない前提は、定義上、事前準備の対象にならない。
> だから**ゲートを「一発で当てる準備ができたか」ではなく「外したときに安く捨てられるか」に置く。**
> **B を7コミットに刻んでいるのは、これをやっている。**準備の不足は**周回数で買う**。

⚠ **AIは聞かなければ言わない。**「足りなければ推測せず全部聞いて」を**明示的に渡す**（`CLAUDE.md` に書く）。

### 配る雛形は2つ

**どちらも設計書リポに置く。** 決まったことは**設計書本体**へ書き戻し、**雛形には「聞いた事実」だけが残る。**

**`確認事項.md`** — 何を確認し、どう答えが出たか。**A・B・C の全段で行が増える**

```markdown
| いつ | 項目                        | 根拠 / 確認先             | 回答       | 反映     |
|------|-----------------------------|---------------------------|------------|----------|
| A    | content の最大文字数が違う  | 要件定義は30、DB定義は100 | 100        | 設計書へ |
| A    | Tag削除時の todo_tag の扱い | DB定義書に記載なし        | 一緒に消す | 設計書へ |
| A    | 同名のTagを登録できるか     | UNIQUE 制約が無い         | 登録できる | 設計書へ |
| A    | Tag削除の順序が FK に依存   | DB定義書は複合PK、DDLは制約なし | DDLが正 | 設計書へ |
| A    | 部分一致の % _ の扱い       | 時間切れ                  | **未回答** | 進む     |
```

**上4行は矛盾・記載漏れなので、聞いて設計書を直した。** 最後の1行だけが**「決まらないと知って進む」**。
**「未回答」の行が、C で答え合わせされる**（→ C-3）。

**`受入条件.md`** — どうなれば完了か ＋ **どこまでやるか**

```markdown
## 対象外（やらないこと）
- 認証・認可の実装（2か月目の SecurityConfig をそのまま使う）
- デプロイ・スケール・監視（ローカルPCで動けばよい）
- 画面（APIのみ）
- 触ってよいのは src/ と docs/ だけ。pom.xml は依存を足さない

## 受入条件
| # | 条件                                | 出所   | 検証手段       |
|---|-------------------------------------|--------|----------------|
| 1 | POST /todos content 空文字は 400    | AI     | テスト         |
| 2 | content 101文字は 400               | 設計書 | テスト         |
| 3 | Tag削除時に todo_tag の行が残らない | 設計書 | テスト         |
| 4 | 例外の内部情報を body に返さない    | DoD    | テスト         |
| 5 | 一覧取得で N+1 を発生させない       | DoD    | 目視（SQLログ）|
| 6 | 3層構成を維持する                   | DoD    | 目視           |
```

**★「検証手段」列がこの後の作業を決める。**
**受入条件のうち、テストにできるのは半分程度。**残りは人が目で見るしかない。
**「目視」の行が、そのまま C の作業リストになる。**

**★「対象外」節が C-1 の参照点になる。** 「頼んでいないファイルが変わっていないか」は、**頼んだ範囲を書いていないと言えない。**

**提出物: 設計書リポの差分 ＋ `確認事項.md` ＋ `受入条件.md`**

---

## B 任せる — 任せた仕事の流れが見えている状態で回す（半日）

**A-3 で実装計画は承認済み。** B は**1コミットずつ、下の4手を回すだけ。**

|     | やること                                               | 誰が  |
| --- | -------------------------------------------------- | --- |
| ①   | **そのコミットで満たす受入条件を、テストに書く**（実装ではなく仕様から書く）           | AI  |
| ②   | **実装前に `mvn test` を走らせ、①のテストが失敗する出力を見せる**          | AI  |
| ③   | **実装する。①のテストは変えない**（変えたいときは変えずに理由を報告）              | AI  |
| ④   | **`mvn test` と `mvn checkstyle:check` を通してコミットする** | AI  |

**②が要る理由: 実装前に通ってしまうテストは、何も検証していない。**
実装のあとに書いたテストは、実装に合わせて書ける。**②は機械的に確認できる**（出力を見せさせればよい）。

**7コミット**: 土台（テストに必要な Entity・Form・Query）→ Tag（CRUD 5本）→ Todo（`POST` → `GET(1件)` → `GET(一覧)` → `PUT` → `DELETE`）

**auto は禁止。** ステップごとに承認させる（流れを見せるため）。

**★4手は `CLAUDE.md` に書いて渡す。** 研修生から見える手数を増やさない。

### 設計から逸れたら、設計書に書き戻す

**★AIへの指示に1行入れる。**

> **設計書と違う実装にしたら、設計書を直し、`確認事項.md` に1行足してから報告してください（いつ＝B）。**

**B-2 のあと** — **AIが**書く。**設計書から逸れた分が増える**

```markdown
| いつ | 項目                         | 根拠 / 確認先                    | 回答         | 反映     |
|------|------------------------------|----------------------------------|--------------|----------|
| B    | 一覧取得を JOIN 1本にした    | 設計書は「ループして取得」だが、 | 講師に確認   | 設計書へ |
|      |                              | DoD の for内SQL 禁止と衝突       |              |          |
| B    | tags に同じIDが2つ来ても 201 | 存在チェックを重複を除いて数えた | 講師に確認   | 設計書へ |
|      |                              | 設計書の文言なら404              |              |          |
```

**「いつ＝B」の行が、そのまま「AIが設計から逸れた箇所」**（→ 達成目標2）。

> **上位者は設計を把握しているが、そこから逸れたことは把握していない。**
> **AIは聞かなければ言わない。だから本人が把握していなければ、組織の誰もその逸脱を知らない。**

**⚠ 逸れたものは全部上げる。** 設計書に書いてあることと違うことをしたなら、それは**必ず**仕様管理者の領分。
**「自分で決めてよい逸脱」は無い**（書いていないことについては、そもそも「逸れた」と言えない）。

**リモートはまだ足さない。** 提出は C（→ C-5）。

**提出物: 作業ブランチ（7コミット）＋ 増えた `確認事項.md`**
---

## C 確かめる — 動いた、ではなく、正しいと言える（半日）

**答えは配らず、考える機会だけ与える**

|         | 何をするか                                                                 |
| ------- | --------------------------------------------------------------------- |
| **C-1** | **`git diff` で変更範囲を確認する**（頼んでいないファイルが変わっていないか）                        |
| **C-2** | **受入条件と突き合わせる**（`受入条件.md` の「目視」行が作業リスト）＋**「テスト」行を1〜2件、実装を壊して赤になるか確かめる** |
| **C-3** | **問いに答える**（AIが仕様に無いことを独自に決めた箇所はどこか、など）                                |
| **C-4** | **別セッションのAIに自分の成果物をレビューさせ**、正しい／的外れ／判断できない に仕分ける（**検証手段には数えない**）       |
| **C-5** | **リモートを足して push → PR を作り、セルフレビューする**                                  |

**⚠ C-4 は C-5 より先。** 順序を逆にすると、**セルフレビューのコメントをAIが読んだ状態**になる。

### ★テストコードは読ませない。壊して確かめる

**受入条件を入力に整えたので、「テストが何を検証すべきか」は担保できている。**
**担保できていないのは「テストが実際にそれを検証しているか」。** 受入条件をどれだけ整えても防げない。

| 実測で出たもの | なぜ受入条件では防げないか |
|---|---|
| 設計書の文言なら404のところを、**201 をアサート**していた | **誤読がテストに固定された。**受入条件との対応はある |
| 期待値を**実装と同じ Entity から**組み立てていた | レスポンス形が変わっても落ちない。**構造的に盲目** |
| DBを検証する設定の**付け忘れ**（`assertionMode`） | **DB検証が空振り**。緑だが何も見ていない |

**テストコードを全部読ませない。** 51本あり、量が破綻し、**AIに任せた意味も消える**。代わりに1手だけ。

> **受入条件の「テスト」行から1〜2件選び、対応する実装を1行壊して `mvn test` を走らせる。**
> **赤にならなければ、そのテストは何も検証していない。**

| | |
|---|---|
| **新しい道具** | **ゼロ。** `mvn test` と `git checkout .` だけ |
| **判定** | **機械的**（赤か緑か）。講師の主観が入らない |
| **量** | **受入条件の数で決まる。**コード量に比例しない |
| **正体** | **ミューテーションテストの手動版**（実務では PIT などの道具でやる） |

**「51件greenは何も保証しない」を、言葉ではなく赤／緑で研修生自身に証明させる手。**

### ★ AIに GitHub を見せない — リモートは C-5 で足す

| 段 | リモート | AIから見えるもの |
|---|---|---|
| **A・B** | **無し（ローカルのみ）** | **GitHub は見えない** |
| **C-5** | **ここで `git remote add` して push → PR** | PR は見えるが、**もう実装は終わっている** |

**これで2つ同時に塞げる。**

- **セルフレビューのコメントをAIに読ませない**（C-4 を先にやるのと合わせて）
- **`answer-sample` ブランチ・他の研修生のブランチをAIが見に行く経路**（`03_研修環境とガードレール.md` §8）

**PR提出の動線は壊れない。** 「最初から外す」ではなく「**あとで足す**」だから。

### `確認事項.md` は C でも増える

**C-3 のあと** — **自分が**書く。**B で AI が書き漏らした逸脱を拾う。判断できないものは「未回答」で残す**

```markdown
| いつ | 項目                             | 根拠 / 確認先                   | 回答       | 反映     |
|------|----------------------------------|---------------------------------|------------|----------|
| C    | 一覧取得の tags を distinct した | 重複行が出たため。設計書に記載なし | 講師に確認 | 設計書へ |
| C    | Tag削除の順序が FK の不在に依存  | DB定義書は複合PK、DDLは制約なし  | **未回答** | —        |
```

**★C で「未回答」が出る。** これが**エスカレーションの実体**。

**そして A で「未回答」と印をつけた行と突き合わせる。**

| | 意味 |
|---|---|
| **A で印をつけた穴に、B の逸脱が当たっていた** | **認識できていた** |
| **印をつけていない箇所で AI が決めていた** | **A で見えていなかった穴** |

**これが達成目標3「担保できた範囲と、できない範囲を言える」の実体。**
**A の質が C で数として出るので、議論が感想戦にならない。**

### `検証記録.md` はこう埋まる

**リポジトリの外。全部自分で書く。AIに書かせる欄はひとつも無い。**

```markdown
# 検証記録（AIに渡さないこと）

## 1. 変更範囲
頼んでいないファイルが変わっていないか（コミット単位で確認）
→pom.xmlが変更されてる

## 2. 受入条件との突き合わせ（C-2）
| 受入条件の # | 検証手段 | 何をして確かめたか            | 結果 |
|--------------|----------|-------------------------------|------|
| 1            | テスト   | TodoPostTest#blankContent 緑  | OK   |
| 5            | 目視     | SQLログで LEFT JOIN 1本を確認 | OK   |
| 6            | 目視     | Controller に業務判断が無い   | OK   |

## 3. 問い
1. AIが仕様に無いことを独自に決めた箇所はどこか。それは正しいか。
   → 一覧取得の distinct。重複が出るのは事実だが、
     「重複をどう扱うか」は設計書に無い。`確認事項.md` に上げた
2. 設計書と違う実装になっている箇所はあるか。全部上げたか。
   →
3. 外に出してはいけない情報が出ていないか。
   →
4. 動いた。では正しいと言える根拠は何か。
   →
5. Entity をそのまま返している。DBにカラムを1本足したら、レスポンスは
   何が変わるか。それは誰の許可が要るか。
   →
6. どこまで自分で確認し、どこから先は聞かないと決まらないか。なぜそこか。
   →
...

## 5. 終わりの形
**自分で確かめた範囲** → 受入条件6件（テスト4・目視2）と DoD 9項目
**仕様管理者に問い合わせる範囲** → Tag削除の順序。DB定義書とDDLのどちらが正本か決められない
```

### C-4 は検証ではなく、A の答え合わせ

**別のセッションで、AIに自分の成果物をレビューさせると10〜20件出る。それを3つに仕分ける。**

| 指摘の例 | 判定 | 理由 |
|---|---|---|
| `TagController` に `@Valid` が無い | **正しい** | 付け忘れ。`TodoController` には有る |
| Entity をそのままレスポンスに返している | **的外れ** | **アーキ図が「今回アーキテクチャを省略する」と明記している。AIはその注記を読んでいない** |
| Tag削除の順序が FK の不在に依存している | **判断できない** | どちらの資料が正本かは仕様管理者しか決められない |

**★4列目に「的外れの理由」を分類させる。ここが本題。**

> **的外れの理由をまとめると、「自分がAIに渡していない情報は何か」が出てくる。**

**★検証手段には数えない。** 同じ資料を読むので**同じ誤読をする**し、**渡していない情報は原理的に見えない**。
**C-4 が実際に拾っているのは、B の出力の欠陥ではなく「A で渡し漏れた情報」＝ A の成果物の欠陥。**

> **だから C-4 は「ここまでやってもカバーできない範囲」を体験で示す装置。**
> 「レビューbotを入れれば安心」という誤解を先に潰せる。

### 終わりの形

**自分で確かめた範囲と、仕様管理者に問い合わせる範囲を、線を引いて言えること。**

**線を引く基準はこれ。**

> **自分の観測で決着するものは、全部自分側。他人の同意が要るものは、全部相手側。**

**提出物: `検証記録.md` ＋ PR（セルフレビュー済み）**

## 評価

|           | 測り方                                              |
| --------- | ------------------------------------------------ |
| **ガバナンス** | **理解度テスト。合格が必要**                                 |
| **A**     | **アプローチを議論する。**成果物の正しさは測らない（下記）                  |
| **B**     | 逸れた箇所を全部上げたか（`確認事項.md` の「いつ＝B」の行）                |
| **C**     | **検証記録とPRを読んで、議論を返す**                            |

**添削はしない／評価はする／議論はする。** 3つ目が実質のフィードバック。

### A は「どう辿ったか」を議論する

**A の完了時点では、良し悪しは測れない。** 実装と突き合わせるまで分からないので、**線を2本引く。**

| | いつ | 誰が | 性質 |
|---|---|---|---|
| **着手基準**（B に進んでよいか） | **A の終わり** | **研修生が自分で** | **形式的。その場で判定できる** |
| **評価** | **C のあと** | **講師と議論** | **事後にしか分からない** |

**★着手基準は必要条件であって、十分条件ではない。** 満たせば良いA、ではない。
**十分条件にすると、雛形を埋めて終わりになり、アプローチの探索が止まる。**

**議論の材料は C で数として出る。**

| A が甘いと | どこに出るか |
|---|---|
| **何を作るかが曖昧** | **B で AI が勝手に決める**（`確認事項.md` の「いつ＝B」が増える） |
| **完了条件が曖昧** | **C で確かめようがない**（検証手段の無い受入条件が出る） |
| **渡し漏れがある** | **C-4 で「的外れ」が増える**（理由が全部「渡していないから」になる） |

**「あなたのアプローチはどうだったか」だけだと感想戦になる。**
**「B で AI が勝手に決めた箇所が7件あった。どこを渡していれば減ったか」なら具体になる。**

### 模範的なアプローチは、やりきったあとに示す

**議論のあとに、講師が用意した一例を見せる。**

| | |
|---|---|
| **示すもの** | **唯一の正解ではなく、アプローチの一例** |
| **示すタイミング** | **本人が自分のやり方を出しきったあと**。事前に配ればなぞるだけになる |
| **⚠ 置き場** | **リポジトリに置かない**（`03_研修環境とガードレール.md` §8） |

**「答えを配らない」（`06_研修の芯.md` 設計原則2）は破っていない。** 配るのは答えではなく**議論の材料**。

> [!note]- なぜこの置き方にしたか
> **現物は `Desktop/配布見本/` にある**（研修生に渡した直後の状態）。
>
> | | なぜそうしたか |
> |---|---|
> | **設計書リポを書き換えさせる** | **実装と設計がずれると困る。**決まったことは設計書に書き戻す（2026-09-01 変更。以前は「上流の資産なので書き換えさせない」としていた） |
> | **設計書を別リポジトリにする** | **配られたものと渡したものの差分**が、リポジトリ単位で `git diff` に出る |
> | **雛形2つを設計書リポに置く** | **「決まったことは設計書」で1本に通すため。**コード側と分けると「どっちに書くんだっけ」が起きる |
> | **`検証記録.md` はリポジトリの外** | `docs/` に置くと **AIが読んでしまう**（C-4 で自分の答えをAIが読んだ状態になる） |

> | **参照実装を1本だけ配る** | **テストの層と書き方は、例が無いと揃わない** |
