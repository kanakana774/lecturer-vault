# AI研修の流れ

## 目的

> ### AIに書かせたコードの品質を、自分で担保できるようにする。

SES では客先に**自分の名前で**成果物を出す。AIが書いたものでも変わらない。

対象は**3か月目の新人**。期間は**1週間**。
題材は**2か月目と同じ Todo API**（Java 21 / Spring Boot 3.4.1 / MyBatis）。
Todo と Tag の CRUD ＋ Todo の登録／更新時に Tag を紐づける機能。

# 作業の一覧

```
【前提】
  ⓪ ガバナンス  ──  理解度テストに合格  →  本編

【本編】
  入口（自分）      →      中（AI）      →      出口（自分）
   A 入力を整える          B 任せる            C 確かめる
      半日                 半日                 半日
```

**実装するのはAI。研修生がやるのは、入力を整え、任せ、確かめること。**

|  | 段 | 研修生がやること | 出るもの |
|---|---|---|---|
| **1** | **⓪** | ルールを学び、**理解度テストに合格する** | — |
| **2** | **A** | **配布プロジェクトを確認し、仕様を把握する** | — |
| **3** | **A** | **AIにテストケース一覧を作らせ、過不足を確認する** | `テストケース一覧.md` |
| **4** | **A** | **plan モードで実装計画を立てさせ、承認する** | — |
|  |  | **▶ ケース一覧と実装計画に合意できたら B へ** |  |
| **5** | **B** | **機能ごとに、テストを先に書かせ、失敗を確認してから実装させ、テストと Checkstyle を通してコミットさせる** | 作業ブランチ |
|  |  | **▶ push して PR を作る** | **PR** |
| **6** | **C** | **AIにレビューさせる** | PRのコメント |
| **7** | **C** | **自分でも確かめ、AIの指摘の妥当性も見る** | **PRの行コメント** |
| **8** | **C** | （**対応が要るものは、A・B に戻して直す**） | コミット |
|  |  | **▶ PR本文を仕上げて提出** | **PR** |
| **9** | **通し** | **振り返りを書く**（問い5つ） | `振り返り.md` |

**手順ではないが、通して守るルール**

- **質問はいつでも投げてよい。**仕様管理者は講師
- **設計に無いこと・確認が要ることは、仕様管理者に確認してから設計書に書き戻す。**タイミングは問わない

**7 の観点 — 問いは1つ**

> ### **仕様どおりに実装できたと、なぜ言えるのか。**

**下の4つは、その根拠の作り方。**どれか1つで言い切れるものではない。

|  |  |
|---|---|
| **設計に無い判断が入っていないか** | **AIが勝手に決めた箇所。確認して、設計書に書き戻す** |
| **テストは妥当だったか** | **緑であることが、正しさの証拠になっているか** |
| **編集したファイルは妥当だったか** | その変更は、仕様のために必要だったか |
| **DoD 9項目について** | N+1・層構成・`SELECT *`・トランザクション境界 ほか |

**観点はガイドとして配る。**確認した結果は、**該当箇所への行コメントとして PR に残す**（＝人間レビュー）。
**まとめは PR本文の「確認したこと」へ。**

**PR本文の5欄**

|  |  |
|---|---|
| **概要・背景** | 何を作ったか |
| **変更点** | 差分の規模・実装したエンドポイント・テスト件数 |
| **確認したこと** | **何をどう確かめ、その結果をなぜ信じてよいか** |
| **判断を仰ぎたいこと** | **見たが自分では決められないもの。回答待ちのもの** |
| **AIの利用** | **開示する。粒度と方法は客先のルールによる** |

# 詳細

## 研修生に達成してもらいたいこと — 3点

|       |                 | 到達した状態                          | どこで   |
| ----- | --------------- | ------------------------------- | ----- |
| **1** | **コンテキストの重要性**  | **何を渡し、何を渡さなかったかを、理由とともに説明できる** | **A** |
| **2** | **AIが決めたことの把握** | **設計に無いことをAIが決めた箇所を、説明できる**     | **C** |
| **3** | **品質保証の線引き**    | **担保できた範囲と、できない範囲を言える**         | **C** |

---

## 作らせるもの — 4点

| 作らせるもの | どこで | AIの扱い | 何のために |
|---|---|---|---|
| **`テストケース一覧.md`** | **A** | **★AIに作らせ、過不足を人が見る** | **合格の基準を、実装より前に固定する** |
| **直した設計書（差分）** | **通し** | **自由** | **確認して決まったことを、AIが読む場所に戻す** |
| **PR（本文とコメント）** | **C** | **自由**（AIにレビューさせてよい） | **担保できた範囲と、できない範囲を示す** |
| **`振り返り.md`** | **通し** | **★AIに渡さない** | **何を渡し、何を渡さなかったかを言わせる** |

**`テストケース一覧.md` だけは、実装より前に作らせる。**早くやるためではなく、**汚染される前に固定するため**。
**実装を見てから作ると、テストが実装に寄る。**

### ★ が指示。無印は自由

**指示は「何を作るか」と「AIに任せてよいか」まで。「どう作らせるか」は縛らない。**
**やり方が決まっていないものは指示にしない。**講師の案は **`18_模範アプローチ_説明用.md`** にある。

> [!note]- 指示には2種類ある。研修生にはどちらかを言う
> |  | どういうものか | どれ |
> |---|---|---|
> | **実務の作法** | **やり方が実務でほぼ1つに決まっている。必ず踏ませる** | **テストケース一覧をAIに作らせる／計画を承認してから実装する／テストを先に書かせる** |
> | **研修の都合** | **外すと到達点3点が測れなくなる。「実務の作法ではない」と断って渡す** | **AIの指摘をPRに貼る／`振り返り.md` をAIに渡さない** |
>
> **どう渡し、どう確かめたかは研修生が決める。そこが評価の材料になる**（→ 評価）。

## ⓪ ガバナンス（前提）

1. 客先のルールを確認する
2. 渡してはいけないものを渡さない
3. 何を渡したか記録する（**実体は `振り返り.md` の問い1。正確なログは取らせない**）
4. AIに書かせた部分を PR で明示する

**根拠は一次情報にある**（経産省の契約チェックリスト／IPA のガイドライン／客先常駐の契約上の整理）。
**→ `03_研修環境とガードレール.md` §6。**

**あわせて B の進め方も、ここで説明しておく。**先に失敗するテストを書かせ、通してコミットする——
**`CLAUDE.md` に書いてあるので、説明さえすれば勝手に回る。**

**理解度テストに合格して、次に進む。**

## A 入力を整える（半日）

**課題で配られるものと、AIに最終的に渡すものは別物。その差分を作るのが A。**

**ケース一覧の基準は2つだけ。**

- **1件ごとに「入力・事前状態・期待する結果」＋ 設計書のどこから来たかの根拠を書く**
- **期待する結果を断定できないケースは、一覧に残さない。**根拠が書けないなら、**それは仕様がまだ決まっていない**

**★2つ目が効く。**基準を満たそうとすれば、**未決と矛盾は自然に表に出る。**
**「洗い出せ」と手順で指示しなくても、同じ結果になる**（洗い出し方は → `18_模範アプローチ_説明用.md`）。

### B に進んでよい状態

> ## **ケース一覧と実装計画に、合意できている。**

**plan モードの承認が、そのまま着手基準。**研修生が自分でその場で確かめられる。
**半日で届かなければ、残りを「決まらないと知って進む」に落として B に行く。それも正しい終わり方。**

---

## B 任せる（半日）

**計画に合意したら、機能ごとに刻んで任せるだけ。**

> **配布時点から `feature` を切り、そこから `task` を切って作業する。`main` には直接コミットしない。**

**1コミットの中身は4つ。`CLAUDE.md` に書いて渡すので、研修生から見える手数は増えない。**

|     | やること                                               | 誰が  |
| --- | -------------------------------------------------- | --- |
| ①   | **そのコミットで満たすケースを、`テストケース一覧.md` からテストに書く**（実装ではなく仕様から書く） | AI  |
| ②   | **実装前に `mvn test` を走らせ、①のテストが失敗する出力を見せる**          | AI  |
| ③   | **実装する。①のテストは変えない**（変えたいときは変えずに理由を報告）              | AI  |
| ④   | **`mvn test` と `mvn checkstyle:check` を通してコミットする** | AI  |

**②が要る理由: 実装前に通ってしまうテストは、何も検証していない。**

- **コミットはエンドポイント単位で刻む**（試走では9本）
- **auto を使ってよい。ただし取り消しがきかない操作（コミット・ファイル削除・DB操作）では承認を取る**

### 設計に無いことをAIが決めても、B では止めない

**その場で報告させる仕組みは置かない。**止めどころを増やすと B が進まないため。
**C の観点「設計に無い判断が入っていないか」で拾い、確認してから設計書に書き戻す。**

> [!warning]- 拾えないことがある（2026-09-11・試走）
> **A で「エスケープする」と裁定したのに設計書へ書き戻さなかった1件は、全工程を素通りした。**
> **AIレビューは設計書を渡していないので仕様の話には届かない**（差分に4箇所あり、最後まで読んで一言も触れなかった）。
> **→ この観点は、人が見るしかない。**

---

## C 確かめる（半日）

> ### AIが書いたコードを、問題ないと自分で説明できる状態にする。

**B が終わったら push して PR を作り、C はすべて PR の上で回す。**
**段には分けない。観点だけ渡し、アプローチは任せる**（→ 上の「7 の観点」）。

**AIを使ってよい。順序も使い方も指定しない。**

### 回し方 — push してから直す

**push → PR → AIにレビューさせる → 自分でも確かめる → 対応が要るものを直す → push。**
**指摘も対応もコミットも、PR に時系列で残る。**

**実務との違いは、ボットが自動で走るか、自分で走らせて貼るかだけ。**
**★ボットを置かないのは費用ではなく運用の都合**（→ `03_研修環境とガードレール.md` §6）。研修生にはそう言う。

| 判定 | 処置 |
|---|---|
| **正しい** | **直す → コミット → push。**仕様に関わるなら**確認を取り、設計書も直す** |
| **的外れ** | **理由を書いて閉じる。**直さない |
| **判断できない** | **消さない。**仕様なら仕様管理者へ。技術なら**そのままPRに書いてレビュアーへ** |

**戻るのは最大1周。**2周目の新しい指摘は仕分けるだけ。
**終わりの条件: 3分類すべてに処置が決まったら終わり。**「正しい」を全部直した、ではない。

### PR に何を書くか

**本文は5欄**（→ 上の表。見本 → `17_見本_PR.md`）。

> **書くのは「現在の状態と根拠」。「足りなかったので足した」という経緯は書かない。**
> **経緯はコミット履歴に残る。**レビュアーが要るのは、**いまのテストをどこまで信じてよいか**のほう。

**★AIの指摘と仕分けは、本文ではなくコメントとして貼る。**実務ではボットの指摘がスレッドに残るので、形を合わせる。

### 終わりの形

**自分で確かめた範囲と、仕様管理者に問い合わせる範囲を、線を引いて言えること。**

> **自分の観測で決着するものは、全部自分側。他人の同意が要るものは、全部相手側。**
> **難しいかどうか、時間がかかるかどうかでは切らない。**

| ----------- | ------------------------------------- |
| **ガバナンス**   | **理解度テスト。合格が必要**                      |

## 配布物

**リポジトリは1本。期ごとに作り直す。★ = AI研修のために足すもの**（2か月目の環境には無い）。

```
todo-training-YYYY/                  ← private。21人が同じ1本にブランチで入る
├── ★ CLAUDE.md                      AIへの指示ファイル。DoD 9項目・1コミットの4つを含む
├── ★ .claude/
│   ├── settings.json                AIに許す操作の範囲。触らない
│   └── hooks/                       ★他の研修生のPRに届く経路を塞ぐ
├──   pom.xml ／ todo_checks.xml     2か月目と同じ ＋ ★checkstyle
├──   src/
│    ├── 2か月目の雛形そのまま      空フォルダ・共通例外・SecurityConfig・testTools
│    └── ★参照実装1本               Todo 1件取得の完成品 ＋ 統合テスト1本
└──   docs/                          ← ★研修生が書き戻す（読むだけではない）
     ├── 要件定義書・アーキ図・DB定義書・OpenAPI・エラーコード表・プログラム設計
     └── ★ テストケース一覧.md       ★空の雛形。A で埋める（提出物）

（リポジトリの外・別配布）振り返り.md   ★問い5つだけの雛形。AIに渡さない（提出物）
```

**設計書を同梱しても、「配られたものと渡したもの」の差分は `git diff main...task -- docs/` で出る。**
**環境・権限・ガードレールは `03_研修環境とガードレール.md`。**
