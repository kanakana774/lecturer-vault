### 設計書を書き換えてよい条件

**設計書は読むだけのものではない。**確認して決まったことは、ここに書き戻す。

- **書き戻すのは、仕様管理者の確認が取れたものだけ。**
- **自分の判断で書き換えない。**設計書に書かれていないことに気づいたら、**書き換えずに報告する。**
  決めるのは仕様管理者であって、実装者ではない

## 層構成

| 層 | 場所 | 責務 |
|---|---|---|
| Controller | `app/controller/` | リクエストの受け取りとレスポンスの組み立て |
| Service | `logic/service/` | 業務ロジック。**`@Transactional` はここに置く** |
| Mapper | `mapper/` ＋ `resources/.../mapper/*.xml` | SQL |

`entity/` `form/` `query/` `queryCondition/` `core/exception/` `util/` は既存のものに従う。

## テスト

**参照実装 `src/test/java/jp/aevic/todo/app/controller/todo/TodoGetByIdTest.java` に合わせる。**

- **Controller層の統合テスト。** モックは使わず、HTTPリクエストから実DBまで通す
- DBUnit（`@DatabaseSetup` / `@ExpectedDatabase`）を使う
- **`@ExpectedDatabase` には `assertionMode = DatabaseAssertionMode.NON_STRICT_UNORDERED` を必ず付ける**
- dataset は `src/test/resources/META-INF/dbunit/` 以下に、テストクラスと同じ階層で置く

# 実装の進め方

## 実装より前に `docs/実装計画.md` を作る

**何を作るか・どう作るか・どこまでやるか・どうなれば完了かを、実装を書く前に固定する。**
**テストケース一覧もここに含める。**

**ケース1件ごとに書くもの。**

- **入力・事前状態・期待する結果**
- **設計書のどこから来たかの根拠**

**期待する結果を断定できないケースは、一覧に残さない。**
根拠が書けないなら、**それは仕様がまだ決まっていない。**勝手に決めず、報告する。

> **実装を見てからケースを作ると、テストが実装に寄る。**
> 実装が正しいことの確認ではなく、実装の追認になる。だから順序を逆にしない。

## 1コミットの中身は4つ

**承認された `docs/実装計画.md` に沿って、機能ごとに刻む。**

|  | やること |
|---|---|
| **①** | **そのコミットで満たすケースを、`docs/実装計画.md` のケース一覧からテストに書く**（実装ではなく仕様から書く） |
| **②** | **実装前に `mvn test` を走らせ、①のテストが失敗する出力を見せる** |
| **③** | **実装する。①のテストは変えない。**変えたいときは、**変えずに理由を報告する** |
| **④** | **`mvn test` と `mvn checkstyle:check` を通してコミットする** |

**②を飛ばさない。実装前に通ってしまうテストは、何も検証していない。**

- **コミットはエンドポイント単位で刻む。**複数のエンドポイントを1コミットに混ぜない
- **取り消しがきかない操作**（コミット・ファイル削除・DB操作）**では、必ず承認を取る**

## コミットメッセージ

**AIが書いた部分は、トレーラーで残す。**

```
Assisted-by: Claude Code
```

**実務では開示の粒度と方法は客先のルールによる。この研修ではトレーラーで統一する。**

# 完了の定義（DoD）

**すべての変更に共通の最低ライン。** 機能ごとに変わるもの（`docs/実装計画.md` のケース一覧）とは別に、**必ず満たす**。

> **これはチームが配るもの。** 決めるのはケース一覧で、この一覧は与えられる側。
> 実務でも同じで、DoD はチームが持ち、参画者は渡される。

## 機械が判定する

- `mvn test` が通る
- `mvn checkstyle:check` が通る

## 人が見る

- **for 文の中で SQL を呼び出していない**（件数分のクエリを発行しない）
- **例外メッセージ・スタックトレース・SQL・設定値を外に出さない**
- **層構成を維持する**（Controller / Service / Mapper の責務を越えない）
- **見せてはいけない情報をレスポンスに含めない**（内部ID・設定値・DB都合のカラム）
- **`SELECT *` を使わない**
- **頼んでいないファイル・テーブルを変更しない**
- **依存（`pom.xml`）を勝手に追加・変更しない**
- **トランザクション境界が Service にある**（`@Transactional` の位置。同一トランザクション内の削除・更新の順序が、制約の不在に暗黙依存していない）
- **テストが実質を見ている**（assert が body と DB を見ている／期待値が実装ではなく仕様から来ている／実行順に依存しない）

---

> **「人が見る」の9項目は、2か月目のレビュー観点そのまま。** 新しく覚えるものはない。
> **この9項目が、目視の停止条件になる。** 一巡したら終わり。
> **各項目の見どころは `docs/DoD.md`。**
