# 完了の定義（DoD）

**すべての変更に共通の最低ライン。**機能ごとに変わるものは `テストケース一覧.md` が持つ。**こちらは機能が変わっても変わらない。**

> **これは講師（チーム）が配るもの。**研修生が決めるのは**テストケース一覧**で、この一覧は与えられる側。
> 実務でも同じで、DoD はチームが持ち、参画者は渡される。

**2つに分かれている。**

| | | いつ |
|---|---|---|
| **完了の条件** | **機械が判定する。**満たさなければ PR を出さない | **コミットのたび** |
| **レビュー観点** | **人が見る9項目。**PR を出したあと、自分で一巡する | **C（確かめる）** |

## 完了の条件 — 機械が判定する

- `mvn test` が通る
- `mvn checkstyle:check` が通る

## レビュー観点 — 人が見る

- **for 文の中で SQL を呼び出していない**（件数分のクエリを発行しない）
- **例外メッセージ・スタックトレース・SQL・設定値を外に出さない**
- **層構成を維持する**（Controller / Service / Mapper の責務を越えない）
- **見せてはいけない情報をレスポンスに含めない**（内部ID・設定値・DB都合のカラム）
- **`SELECT *` を使わない**
- **頼んでいないファイル・テーブルを変更しない**
- **依存（`pom.xml`）を勝手に追加・変更しない**
- **トランザクション境界が Service にある**（`@Transactional` の位置。**同一トランザクション内の削除・更新の順序が、制約の不在に暗黙依存していない**）
- **テストが実質を見ている**（assert が body と DB を見ている／**期待値が実装ではなく仕様から来ている**／実行順に依存しない）

---

> **上の7項目は、2か月目のレビュー観点そのまま。** 新しく覚えるものはない。
> **8つめ（トランザクション境界）も2か月目の観点**だが、DoD から漏れていたので足した（2026-08-26）。
> **9つめ（テストが実質を見ている）だけがこの研修の新規**。「実装を見て書いたテストは、実装のバグを追認する」。
> 参照実装1本では足りないことが実測で出ている——**参照実装の Javadoc が「必ず付ける」と書いた `assertionMode` が、
> 後から書かれたテストで16箇所欠けていた。** 流儀は例で伝わるが、**守られたかは目視でしか拾えない**。
>
> **この9項目が、目視の停止条件になる。** 一巡したら終わり。
> 終わったときに言うのは「全部見ました」ではなく、**「このリストは見た。これ以外は自分では分からないので、レビューを頼みたい」**。
> **項目を減らすと停止条件が痩せる**（`11_品質特性と検証の分担.md` §8・07 §10-24）。

# レビュー観点9項目 — 見どころ

**項目名だけでは何を見ればよいか分からないので、この課題での具体を書いておく。**

## 1. for 文の中で SQL を呼び出していない

**Todo一覧に紐づく Tag を取るところが典型。**Todo を1件ずつループして「この Todo の Tag を取る」SQL を呼ぶと、
**Todoが100件あればクエリが101本走る。**JOIN 1本、または `IN` でまとめて取る。

## 2. 例外メッセージ・スタックトレース・SQL・設定値を外に出さない

**エラー時のレスポンスの話。**雛形の `core/exception/MyErrorAttributes` が既に対策を持っていて、
**返すのは `title` / `status` / `code` / `message` の4つだけ**（Spring の既定では例外クラス名・例外メッセージ・
スタックトレース・発生パスまで出る）。**見るのは「その仕組みを迂回していないか」。**

| 見るところ | 何が危ないか |
|---|---|
| **`catch` して自前でレスポンスを組んでいないか** | **`e.getMessage()` をそのまま body に入れる**のが典型 |
| **`@ExceptionHandler` / `@ControllerAdvice` を勝手に足していないか** | 共通例外を通らない経路ができる |
| **`message` に DB 由来の文言が混ざっていないか** | **制約名・テーブル名・SQL 断片**が漏れる |

**AIは「親切なエラーメッセージ」を作りたがるので、実際に起きる。**

## 3. 層構成を維持する

**Controller はリクエストを受けて返すだけ。SQL は Mapper。判断は Service。**
**Controller から Mapper を直接呼んでいないか、Service に HTTP の都合（ステータスコード）が漏れていないか。**

## 4. 見せてはいけない情報をレスポンスに含めない

**正常系レスポンスの話。**判定は1つ——**OpenAPI（`todo.yaml`）に定義されていないフィールドが混ざっていないか。**

| | |
|---|---|
| **中間テーブルの内部ID** | **`todo_tag` の行のID。**紐づきの実装都合なので、APIには出さない |
| **DB都合のカラム** | 作成日時・更新日時など、**仕様が返すと言っていないもの** |
| **エンティティをそのまま返す** | `TagEntity` は `tagId`/`name`/`version` だけなので**この課題では偶然一致している**が、**フィールドを足した瞬間にレスポンスへ漏れる** |

**`version` は「見せてはいけない情報」ではない。**楽観ロックで**クライアントが送り返す必要がある**ので、仕様が返すと決めている。

## 5. `SELECT *` を使わない

**Mapper の XML を見る。**カラムを列挙する。`*` だと、**DBにカラムが増えた瞬間にレスポンスが変わる。**

## 6. 頼んでいないファイル・テーブルを変更しない

**`git diff --stat` を、実装計画で宣言した範囲と突き合わせる。**
既存クラス・DDL・`testTools` に手が入っていないか。

## 7. 依存（`pom.xml`）を勝手に追加・変更しない

**`pom.xml` の差分がゼロかを見るだけ。**「便利なライブラリを入れておきました」が起きる。

## 8. トランザクション境界が Service にある

**`@Transactional` の位置を見る。**Controller や Mapper に付いていない。

**あわせて削除の順序を見る。**子（`todo_tag`）→ 親（`todo`）の順で消しているか。
**「いまは外部キー制約が無いから、どの順でも動く」に頼っていないか**——制約が付いた瞬間に壊れる。

## 9. テストが実質を見ている

**この研修で新しく足した観点。**「実装を見て書いたテストは、実装のバグを追認する」。

- **assert が body と DB の両方を見ている**か（`@ExpectedDatabase` があるか、`assertionMode` が付いているか）
- **期待値が実装ではなく仕様から来ている**か（設計書のどこから来た値か言えるか）
- **実行順に依存していない**か
