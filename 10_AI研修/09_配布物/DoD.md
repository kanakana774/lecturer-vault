# 完了の定義（DoD）

> **リポジトリの外で配る。**中に置くと AI が読み、指摘される前に先回りで直してしまう。
> **9項目そのものは `CLAUDE.md` にある**（AIへの制約として）。こちらはその**見どころ**で、読むのは研修生。
> **項目名は `CLAUDE.md` と揃えてある。**PR の `[x]` はそちらの順番で付く。

**すべての変更に共通の最低ライン。**機能ごとに変わるものは `実装計画.md` のケース一覧が持つ。**こちらは機能が変わっても変わらない。**

> **これは講師（チーム）が配るもの。**研修生が決めるのは**ケース一覧（`実装計画.md`）**で、こちらは与えられる側。
> 実務でも同じで、DoD はチームが持ち、参画者は渡される。

**2つに分かれている。**

| | | いつ |
|---|---|---|
| **完了の条件** | **機械が判定する。**満たさなければ PR を出さない | **コミットのたび** |
| **レビュー観点** | **人が見る9項目。**PR を出したあと、自分で一巡する | **C（確かめる）** |

## 完了の条件 — 機械が判定する

- `mvn test` が通る
- `mvn checkstyle:check` が通る

## レビュー観点 — 人が見る9項目

1. **件数に比例してクエリが増えない**（N+1）
2. **内部由来の文字列をレスポンスに載せない**
3. **層の責務を越えない**
4. **OpenAPI に定義のないフィールドを返さない**
5. **SQL はカラムを列挙する**
6. **宣言した範囲の外を変更しない**
7. **依存（`pom.xml`）を追加・変更しない**
8. **トランザクション境界と削除の順序**
9. **テストが仕様を検証している**

> **1〜8 は、2か月目のレビュー観点そのまま。** 新しく覚えるものはない。
> **8（トランザクション境界）も2か月目の観点**だが、DoD から漏れていたので足した（2026-08-26）。
> **9（テストが仕様を検証している）だけがこの研修の新規**。「実装を見て書いたテストは、実装のバグを追認する」。

> 後から書かれたテストで16箇所欠けていた。** 流儀は例で伝わるが、**守られたかは目視でしか拾えない**。
>
> **この9項目が、目視の停止条件になる。** 一巡したら終わり。

# レビュー観点9項目 — 見どころ

**項目名だけでは何を見ればよいか分からないので、この課題での具体を書いておく。**

## 1. 件数に比例してクエリが増えない（N+1）

**Todo一覧に紐づく Tag を取るところが典型。**Todo を1件ずつ「この Todo の Tag を取る」SQL に渡すと、
**Todoが100件あればクエリが101本走る。**JOIN 1本、または `IN` でまとめて取る。

**`for` 文だけを見ても足りない。**同じことは次の形でも起きる。

| | |
|---|---|
| **`stream()` の中の呼び出し** | **`list.stream().map(t -> mapper.selectTags(t.getId()))`。**AIはこの書き方をよく選ぶ |
| **MyBatis の遅延ロード** | `collection` / `association` で、1件ずつ後から引く設定になっていないか |
| **Service 層のループ** | Mapper の中だけ見ても出てこない |

**見るのは「発行されるクエリの本数が、入力の件数に比例していないか」。**
**ログに出る SQL を数えるのがいちばん早い**（`TodoMapper.getOne` の行が何本出るか）。

## 2. 内部由来の文字列をレスポンスに載せない

**⚠ 「例外メッセージを返すな」ではない。**雛形の `core/exception/MyErrorAttributes` は
**`title` / `status` / `code` / `message` の4つを返す設計**で、**`message` は返すのが正しい**
（Spring の既定では、例外クラス名・例外メッセージ・スタックトレース・発生パスまで出る。それを絞ったのがこの4つ）。

**見るのは「その仕組みを迂回して、内部の文字列が混ざっていないか」。**

| 見るところ | 何が危ないか |
|---|---|
| **`catch` して自前でレスポンスを組んでいないか** | **`e.getMessage()` をそのまま body に入れる**のが典型 |
| **`@ExceptionHandler` / `@ControllerAdvice` を勝手に足していないか** | 共通例外を通らない経路ができる |
| **`message` に DB 由来の文言が混ざっていないか** | **制約名・テーブル名・SQL 断片**が漏れる |

**AIは「親切なエラーメッセージ」を作りたがるので、実際に起きる。**

## 3. 層の責務を越えない

**Controller はリクエストを受けて返すだけ。SQL は Mapper。判断は Service。**
**見るのは2つ。**

- **Controller から Mapper を直接呼んでいないか**
- **Service に HTTP の都合（ステータスコード・`ResponseEntity`）が漏れていないか**

## 4. OpenAPI に定義のないフィールドを返さない

**正常系レスポンスの話。**判定は1つ——**`todo.yaml` / `tag.yaml` に定義されていないフィールドが混ざっていないか。**

| よく混ざるもの | |
|---|---|
| **中間テーブルの内部ID** | **`todo_tag` の行のID。**紐づきの実装都合なので、APIには出さない |
| **DB都合のカラム** | 作成日時・更新日時など、**仕様が返すと言っていないもの** |
| **エンティティをそのまま返す** | `TagEntity` は `tagId`/`name`/`version` だけなので**この課題では偶然一致している**が、**フィールドを足した瞬間にレスポンスへ漏れる** |

**⚠ 「DB都合のカラムは全部ダメ」ではない。**`version` は楽観ロックで**クライアントが送り返す必要がある**ので、
**OpenAPI が返すと定義している。**判定はあくまで OpenAPI との突き合わせで、カラムの見た目ではない。

## 5. SQL はカラムを列挙する

**Mapper の XML を見る。**`SELECT *` だと、**DBにカラムが増えた瞬間にレスポンスが変わる**（→ 観点4）。
**`COUNT(*)` は別物なので、これには当たらない。**

## 6. 宣言した範囲の外を変更しない

**`git diff --stat` を、`実装計画.md` の §1「作るもの」・§2「やらないこと」と突き合わせる。**
既存クラス・`testTools`・DDL に手が入っていないか。

**テーブルの「変更」はテーブル定義（DDL）のこと。**テストがデータを入れ直すのは当然なので、これには当たらない。

## 7. 依存（`pom.xml`）を追加・変更しない

**`pom.xml` の差分がゼロかを見るだけ。**「便利なライブラリを入れておきました」が起きる。

## 8. トランザクション境界と削除の順序

**`@Transactional` の位置を見る。**Controller や Mapper に付いていない。

**あわせて削除の順序を見る。**子（`todo_tag`）→ 親（`todo`）の順で消しているか。
**「いまは外部キー制約が無いから、どの順でも動く」に頼っていないか**——制約が付いた瞬間に壊れる。

## 9. テストが仕様を検証している

**この研修で新しく足した観点。**「実装を見て書いたテストは、実装のバグを追認する」。

| 見るところ | |
|---|---|
| **DB を見ているか** | **`@ExpectedDatabase` が付いているか。**レスポンスだけ見て通るテストは、DB の状態を1つも保証しない |
| **期待値の出どころ** | **設計書のどこから来た値か言えるか。**実装を動かして出た値を貼っていないか |
| **実行順** | 他のテストが入れたデータに依存していないか |

**⚠ `assertionMode = NON_STRICT_UNORDERED` は、厳密さを下げる指定。**
**期待データセットに書いていないテーブル・カラムを無視し、行の順序も無視する。**
**「付いているから DB を見ている」という証拠にはならない。**
参照実装に合わせる**流儀の規約**であって、検証の強さとは別の話（→ `CLAUDE.md` のテスト節）。
