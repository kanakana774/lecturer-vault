# AI研修の手引き

> **研修生だけが読む資料です。**リポジトリに置かず、Claude にも貼らないでください。

## この研修のゴール

> ### AIに書かせたコードの品質を、自分で担保できるようにする。

客先には自分の名前で成果物を出します。AIが書いたコードでも、責任を負うのは採用したあなたです。

題材は2か月目と同じ Todo API です。今回は **Tag の CRUD と、Todo への Tag の紐づけ**を Claude Code に作らせます。

---

## 1週間の流れ

| 段 | やること | 出すもの |
|---|---|---|
| **前提** | ガバナンス講義とClaude Code の説明を聞く | — |
| **A 入力を整える** | 設計書を読んで仕様を把握する。plan モードで `実装計画.md` を作らせ、中身を確認して承認する | `実装計画.md` |
| **B 任せる** | 機能ごとにテスト → 実装 → コミットを任せる。終わったら push して PR を作る | 作業ブランチ・PR |
| **C 確かめる** | AIにレビューさせ、自分でも確かめる。直すものは直し、PR本文を仕上げる | PR |
| **D 振り返る** | `振り返り.md` の問い5つに答える | `振り返り.md` |

- **A の終わりは「`実装計画.md` に合意できた」とき**です。半日たっても決まらないものは、「未決」と書いて B に進んでかまいません
- 決められているのは**何を作るか**と、**AIに任せてよいか**だけです。どう作らせるかは自由です
- **仕様で迷ったら、講師に聞いてください。**講師が仕様管理者です。決まったことは設計書に書き戻します

### 判断の軸 — 迷ったらここに戻る

1. **根拠が書けないテストケースは、一覧に残さない。**期待する結果を断定できないなら、仕様がまだ決まっていません。講師に聞きます
2. **テストが緑でも、正しいとは限らない。**「このテストは効いている」と言える根拠は、自分で作ります
3. **自分で確かめて決着するものは自分で決める。他人の同意が要るものは相談に上げる。**難しいかどうかでは分けません

## はじめる準備

PowerShell で、自分の手で実行します。

**1. GitHub にログインする**（1人1回）

```powershell
gh auth login
```

**GitHub.com** → **HTTPS** の順に選びます。「Authenticate Git with your GitHub credentials?」には **No** と答え、最後にブラウザでデバイスコードを入力します。

**2. リポジトリを取ってきて、ブランチを切る**

```powershell
git clone https://github.com/aevic-education/ai-training.git
cd ai-training
git switch -c feature/<社員番号>-<氏名>
git switch -c task/<社員番号>-<氏名>
```

例: `feature/126013-KawauchiKota` → `task/126013-KawauchiKota`。作業は `task` で行い、PR は `task` から `feature` に出します。

**3. Claude Code を起動する**

```powershell
claude
```

## Claude Code の使い方

ガバナンス講義で言う「エージェント」です。ファイルを読み、コマンドを実行し、コードを書きます。

| 機能 | 何ができるか | この研修で使う場面 |
|---|---|---|
| **plan モード** | 手を動かす前に計画だけを出させる。承認するまで実装しない | A。`実装計画.md` を作らせる |
| **`CLAUDE.md`** | 起動時に毎回読まれる指示書 | B の進め方はここに書いてある。こちらから毎回言わなくてよい |
| **許可の確認** | 実行前に「実行してよいか」を聞いてくる。講義の Human-in-the-loop | commit・push・ファイル削除などは毎回聞かれる。**読んでから答える** |
| **auto** | 確認を減らして任せる | B で使ってよい。ただし取り消せない操作は承認する |
| **`/clear`** | 会話を捨て、コンテキストを空にする | 作業の区切りで。渡しすぎると効きが落ちる |
| **`/model`** | モデルを切り替える | 講義で説明する |

**`Shift+Tab`** で plan モードと auto を切り替えられます。**`Esc`** で作業を止められます。

## 止めてあること

`.claude/` の設定で、Claude から次の操作ができないようにしてあります。

| 止めてあること | 理由 |
|---|---|
| 他の人の PR・他のリポジトリを読む（`git pull`・`gh pr view 番号` など） | 全員が同じリポジトリで作業するため |
| `.env` などの秘密ファイルを読む | 講義の「秘密を渡さない」 |

止められたら、**自分の手で PowerShell から実行**してください（`git pull` など）。自分の PR は、番号を付けなければ Claude も読めます（`gh pr view`）。
**おかしな止まり方をしたら、設定を触らずに講師へ。**

## 出すもの

### `実装計画.md`（A）

テストケースは1件ごとに**入力・事前状態・期待する結果**と、**設計書のどこから来たか**を書きます。

### PR（C）

**AIのレビューは、Claude 自身に `gh pr comment` で投稿させます。**そのうえで自分でも確かめ、見つけたことは該当行にコメントします。

AIの指摘は3つに分けます。

| 判定 | どうするか |
|---|---|
| **正しい** | 自分で確かめてから直す。仕様に関わるなら講師に確認し、設計書も直す |
| **的外れ** | 理由を返信して閉じる |
| **判断できない** | 本文の「相談したいこと」に上げる |

直しに戻るのは1周までです。本文は次の3欄で書きます。**書くのは「いまの状態とその根拠」で、経緯は書きません。**

```markdown
## 概要
<!-- 何を作ったか。着手前に何件確認して設計書を直したか -->

## 確認したこと
<!-- ケース件数・テスト件数・欠番の有無。mvn test の結果。手で叩いた範囲 -->
- [ ] 設計に無い判断が入っていないか
- [ ] レビュー観点9項目
- [ ] ケース一覧そのものの網羅性
- [ ] 性能・セキュリティ

## 相談したいこと（自分の見解つき）
<!-- 自分で確認しても決められなかったものだけ。AIの指摘をそのまま並べない。
     1件ごとに「何を確かめたか」「自分はどう考えるか」「相手に決めてほしいこと」 -->
```

PR はマージしません。

### `振り返り.md`（D）

思い出せる範囲で書けば十分です。**Claude には渡しません。**これをもとに講師と話します。
