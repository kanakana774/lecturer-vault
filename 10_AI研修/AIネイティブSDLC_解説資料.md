## 1. 前提知識: SDLC とは何か

### 1-1. 定義

**SDLC（Software Development Life Cycle / ソフトウェア開発ライフサイクル）**
= アイデアが「動く本番システム」になるまでの一連の工程のこと。

多くの組織は次の6段階で回しています。

| # | ステージ | 日本語 | やること |
|---|---|---|---|
| 1 | Plan | 計画 | 何を作るか決める |
| 2 | Design | 設計 | どう作るか決める |
| 3 | Build | 実装 | 実際にコードを書く |
| 4 | Test | テスト | 正しく動くか確かめる |
| 5 | Deploy | リリース | 本番環境に出す |
| 6 | Maintain | 運用保守 | 動いているものを見守り、直す |

### 1-2. 伝統的な SDLC の特徴

各段階は**別の役割の人が持ち場として担当**します。

```
プロダクトマネージャ → 要件を書く
    ↓ ドキュメント / チケット / 承認
アーキテクト → 設計に落とす
    ↓
エンジニア → 実装する
    ↓
QAチーム → 検証する
    ↓
リリースチーム → 出す
    ↓
運用チーム → 監視する
```

段階の間は**ドキュメント・チケット・サインオフ（承認）**で受け渡されます。

🔰 なぜこんなに重いのか？
→ **説明責任（accountability）とコントロール**のためです。誰が何を承認したかを残す必要があります。特に金融・医療のような規制業種では、これが監査で問われます。

### 1-3. 伝統的 SDLC の設計思想

原文の重要な指摘:

> 伝統的な SDLC は「**コードを書く工程が一番時間もお金もかかる**」時代に最適化された設計である。

PRD（Product Requirements Document / 製品要件書）、見積り儀式、セキュリティレビュー — これらはすべて、**数週間〜数四半期かかる開発作業の前に、認識を強制的に揃えるため**に存在していました。

さらに、伝統的 SDLC のコントロールは「**すべての工程を人間がやる**」ことを前提に組まれています。

## 2. 中心主張: コードはもうボトルネックではない

### 2-1. 何が起きたか

- AI（Claude Code などのエージェント型コーディングツール）により、コードを書く速度が1年前には考えられなかったレベルになった
- しかし**コードの周りのプロセスは同じ速度で変わっていない**
- 承認ゲート、レビュー、引き継ぎ、ポリシーがそのまま残り、生産性の向上を潰している

### 2-2. Build が速くなると起きる3つのこと

原文が挙げる3点:

**① ボトルネックが左右に移動する**

```
[Plan] [Design] → [Build] → [Test] [Deploy] [Maintain]
 人間速度のまま     数時間に      人間速度のまま
                    圧縮
```

Build だけが数時間に縮み、その前後（計画・レビュー/テスト・リリース）は人間の速度のまま残る。結果、そこが新しい詰まりになります。

**② コントロールが現実に合わなくなり、実行不能になる**

「レビュアーが1行ずつ手で読む」は、**人間が書いていた頃は妥当**でした。差分（diff）の大半をエージェントが書くようになると、この方式は追いつきません。

**③ ガバナンスのコストが上がる**

例外承認が、週次・月次でしか開かれない会議や委員会を経由し続けるため。

### 2-3. 具体例: セキュリティのボトルネック

セキュリティチームの人数は「**人間の出力量**」に合わせて決められています。エージェントがコード出力を何倍にすると:

- レビュー待ち行列が積み上がる、**または**
- 十分レビューされないままコードが出荷される

規制業種の組織はどちらも受け入れられません。**したがってセキュリティとポリシーのチェック自体がエージェントの速度に追いつく必要がある**、というのが原文の論理です。

🔰 **ここが記事全体の出発点です。** 「AIで速く書けるようになった」ではなく「速く書けるようになったせいで、周りの仕組みが壊れた。だから周りも作り直す」という話です。

## 3. AI ネイティブ SDLC の全体像

### 3-1. 定義

> **古いコントロール目的（control objectives）を、新しい強制手段（enforcement）で実現し直したプロセス。**

- 「何をコントロールしたいか」（例: 承認されていないものが本番に出ない）は**変えない**
- 「どうやってそれを強制するか」（例: 人が会議で承認 → フックがスクリプトでブロック）を**変える**

🔰 これが記事の一番大事な発想です。ガバナンスを捨てるのではなく、**実装手段を差し替える**。

### 3-2. 直線からループへ

伝統的 SDLC は**直線**（Plan → ... → Maintain で終わり）。
AI ネイティブ SDLC は**ループ**で、各ポイントに AI が埋め込まれます。

```
   ┌──────────────────────────────────────┐
   │                                      │
   ↓                                      │
[1 Plan] → [2 Design] → [3 Build] → [4 Test] → [5 Deploy] → [6 Maintain]
intent.md    spec.md      plan.md    テスト結果   PR・レビュー   異常検知
                          diff                                  ↓
                                                          新しい intent.md
```

Maintain で検知した異常が、そのまま次の Plan の入力（`intent.md`）になって回り続けます。

🔰 別名: agentic SDLC / AI SDLC / agentic software development。呼び方が違うだけで同じものです。

### 3-3. 6ステージの対比表（原文の中核テーブル）

| ステージ | 伝統的 SDLC | AI ネイティブ SDLC |
|---|---|---|
| **Plan** | 委員会で要件収集、ワークショップと承認を経て、人手で文書化 | Claude が現場の課題を情報源から直接まとめ、`intent.md` に記録。人が読めて、機械が処理できる形 |
| **Design** | アナリストが仕様を書き、デザイナーがそれを解釈 | 要件と設計を1回の作業セッションに圧縮。組織の標準は skill として与え、git でバージョン管理 |
| **Build** | テストとコードは手書き、ドキュメントは開発後に書く | テストとコードは AI が生成。組織知は `CLAUDE.md` と skill として機械可読な形で保守 |
| **Test** | 各段階の境界に QA ゲート | 実装の中に評価（eval）が織り込まれ、継続的に走る |
| **Deploy** | 人が全行レビュー、ガバナンスはレビューサイクル中に（しばしば不揃いに）行われる | エージェントによる多層レビュー。人のレビューは規制対象・重要コードに限定。ガバナンスはエージェントが動く瞬間にフックで強制 |
| **Maintain** | 人が本番を見張ってバグを見つける | エージェントが稼働環境を監視。管理帯（control band）を超えたら診断し、新しい `intent.md` としてループに書き戻す |

### 3-4. 全体を貫く1本の糸: 「コミットされた成果物」

**これが記事全体を理解する鍵です。**

各ステージは**バージョン管理システムに1つの成果物を書いて終わり、次のステージはそれを読んで始まる**。

| ステージ | 出力される成果物 |
|---|---|
| Plan | `intent.md` |
| Design | `spec.md` |
| Build | `plan.md` + diff + テスト |
| Test | テスト実行結果・eval 結果 |
| Deploy | PR とレビュー指摘 |
| Maintain | インシデント記録 → 新しい `intent.md` |

- **前半のステージが `.md`（Markdown）ファイルなのはなぜか** → プロダクトオーナー（非エンジニア）とエージェントの**両方が同じファイルを読んで動ける**から
- **Build 以降はコードとその記録**が成果物になる
- **コミットの連鎖がそのまま監査証跡（audit trail）になる** — 誰が何を依頼し、エージェントが何を出し、誰が承認したか

そして:

> **判断が必要な決定については、人間が引き続き全責任を負う。**
> エージェント型 SDLC では、レビュー対象となる成果物とともに、人間の注意の向き先が移動する。

🔰 「人間が消える」話ではありません。「**人間が見るものが、コードの1行1行から、成果物とゲートに移る**」話です。

### 3-5. プレイ（play）とは

「プレイ」= 実践パターン。6ステージにグループ分けされ、各プレイは以下を含みます。

1. 何が変わるか
2. 始め方（前提条件・必要なインフラ）
3. 実装の具体手順
4. ガバナンス上の考慮点
5. うまくいったかの測り方

**重要**: プレイはモジュール式で、**ステージ順に導入する必要はありません**。各プレイには「前提条件（Prerequisites）」があり、前提が「なし」のプレイからどこでも始められます。

## 4. Stage 1 — Plan（計画）

> アイデアが「誰かが文書化してくれるのを待つ」ことをやめる。発案者自身の言葉で、一度だけ、バージョン管理された成果物として記録される。

### 4-1. プレイ: intent.md として捕捉する

**`intent.md` の入り口は3種類**

1. 人がアイデアを思いつく
2. チケットが起票される
3. インシデントがアラートで表面化する（← Stage 6 からの戻り）

### 4-2. 何が変わるか

| | 内容 |
|---|---|
| **伝統的** | アイデアはバックログ登録 → ユーザーストーリー → ストーリーポイント → リファインメント会議、を経てようやく着手可能に。各引き継ぎで所有権が移るため、**エンジニアに届く頃には発案者の意図から何段階も離れている** |
| **AIネイティブ** | 発案者が Claude とブレストし、結果を `intent.md` として書き出す。発案者自身の言葉によるプロトスペック（proto-spec / 仮仕様）。「何が欲しいか」「なぜか」「どんな制約下でか」を含む。繰り返し発生する手順は skill として符号化する |

🔰 **プロトスペック**: まだ正式な仕様書ではないが、次工程がそのまま使える下書き。

### 4-3. 始め方

**前提条件**: なし（ここから始められる）

**必要なインフラ**:
- 非エンジニアも使える Claude アクセス（claude.ai または Cowork）
- 合意された `intent.md` テンプレート
- プロダクトオーナーが見張る、共有・バージョン管理された置き場
  - 単一プロダクトなら**製品リポジトリ内の `intent/` フォルダが一番シンプル**
  - 専用リポジトリは、intent が複数リポジトリにまたがる場合のみ割に合う
  - モノレポならディレクトリ1つ

**セットアップは一度きりの作業**で、プラットフォームチームまたはエンジニアリングチームが担当。技術メンバーが置き場を立ち上げ、**誰が書き込めるかを決める**（組織横断で多数の貢献者が来るため）。

🔰 **git を知らない人はどうする？**
→ バージョン管理システム（GitHub など）へのコネクタを使えば、claude.ai や Cowork から Claude が代理でコミットしてくれます。貢献者は git を直接触りません。

### 4-4. 実行手順

1. **発案者が自分の言葉で問題を Claude に説明する**
   - 「今日できないこと」「誰が困っているか」「良い状態とは何か」「スコープ外は何か」
   - **形式的な言葉づかいは不要**
2. **アイデアが具体的になるまでブレストする**
   - Claude はアナリストが聞くであろう質問をする: スコープ、ユーザー、制約、成功の定義
3. **組織のテンプレートで `intent.md` を書かせる**
   - テンプレートは skill として符号化でき、技術メンバーが用意しリードが承認する
   - 含める内容: 問題 / 提案する成果 / 影響を受けるユーザーとシステム / 制約 / 未解決の問い
4. **発案者が誤解を訂正する**
5. **共有の置き場にコミットする**
   - 著者とタイムスタンプが記録に加わり、プロダクトオーナーがそこから拾う

### 4-5. intent.md の例

```markdown
# Intent: 保険金請求ステータスのセルフサービス化
著者: J. Ortiz（請求業務部） ステータス: draft

## 問題
顧客が請求の進捗を電話で問い合わせてくる。
オペレータの通話時間のおよそ1/3がステータス確認だけに費やされている。

## 提案する成果
顧客がポータル上で、請求ステータス・次のステップ・見込み日を確認できる。

## 影響を受けるユーザーとシステム
請求オペレータ、ポータルチーム、claims-core API

## 制約
ポータルセッションに新たな個人情報を持ち込まない。既存の認証のみを使う。

## 未解決の問い
第三者の損害査定人にもアクセスが必要か？
```

🔰 見てわかる通り、**技術的な記述がまったくありません**。業務担当者が書けるレベルに保たれています。

### 4-6. ガバナンス

- **証拠となるもの**: コミットされた `intent.md`（著者・タイムスタンプ・全改訂履歴を含む）
- **記録場所**: intent 置き場の git 履歴
- **承認者**: プロダクトオーナー
- Stage 2 へ進める/却下する判断は、**マージまたはレビューのクローズとして記録される**

### 4-7. 測定

| 種類 | 指標 |
|---|---|
| **先行指標** (leading indicator) | 最初の会話から `intent.md` のコミットまでの時間。git 履歴から読み取れる。**数週間の要件抽出サイクルから数時間へ**落ちることが期待値 |
| **遅行指標** (lagging indicator) | **生存率**: プロダクトオーナーが Stage 2 へ受け入れた `intent.md` の割合。加えて、同じ変更の最初の `spec.md` コミット後に `intent.md` に加えられた変更の数 |

🔰 **先行指標 / 遅行指標**: 先行指標は「今うまくいっているか」をすぐ教えてくれる数字、遅行指標は「結果として良かったか」を後から教えてくれる数字。

## 5. Stage 2 — Design（設計）

> 要件定義と設計が1セッションに統合される。ポリシーは**仕様を書いている最中に適用される**。数週間後のレビューで発覚するのではなく。

### 5-1. プレイ: 要件と設計

プロダクトオーナーが承認した `intent.md` を Claude が受け取り、**要件・設計仕様書**を生成します。これは組織の **skill**（ブランド、セキュリティ、コンプライアンス、UX）によってガイドされます。

**プロダクトオーナーは仕様をレビューするが、書かない。**
ゴールは「エンジニアリングチームが計画を立てられる仕様書 + 懸念点のフラグ付き」を作ること。

### 5-2. 何が変わるか

| | 内容 |
|---|---|
| **伝統的** | 要件定義と設計は別チームが担当する別フェーズ。アナリストがアイデアを要件に形式化し、デザイナーがそれを設計に読み戻す。**分離は説明責任のためだが、遅く、情報が失われる（lossy）** |
| **AIネイティブ** | 両フェーズが1回のセッションで起きる。Claude が `intent.md` を受け取り、組織の skill を制約として要件・設計仕様を生成、懸念点にフラグを立てる |

### 5-3. フロントエンドの場合

原文が「最も分かりやすい例」として挙げるフロー:

```
intent.md 承認
  → プロダクトオーナーが Claude Design（ベータ）でモックを起こす
  → モックを反復して詰める
  → Claude Code にエクスポートして実装
```

### 5-4. 始め方

**前提条件**:
- `intent.md` が書かれていること
- ブランド、セキュリティ、コンプライアンス、UX の各ポリシーが **skill として書かれていること**

**必要なインフラ**: Claude にアクセスできるプロダクトオーナー1名。**エンジニアリングスキルは不要**。

### 5-5. 実行手順

1. プロダクトオーナーが、組織の skill を利用可能な状態でセッションを開き、`intent.md` を添付する
2. プロンプトで `intent.md` を指し、制約を挙げ、**懸念点のフラグ立てを要求する**
   - 最初は手で実行 → 慣れたら組織レベルのスラッシュコマンドに固める
   - さらに進めると: **intent 置き場での `intent.md` 受け入れをトリガーにする**。マージで発火する非対話ジョブが、組織の skill を読み込んだ状態でこのパスを走らせ、`spec.md` をプルリクエストとしてコミットする
   - この段階になると、プロダクトオーナーの最初の関与は**レビューから**になる
3. 同じプロダクトオーナーが、仕様をアイデアと突き合わせてレビューする
   - 「仕様は述べられた問題を解決しているか」「`intent.md` の未解決の問いは答えられたか、持ち越されたか」
4. **フラグの立った懸念点から先に処理する**
   - これらはアナリストならエスカレーションしていたはずの点
   - プロダクトオーナーが**各ポリシーの所有者と1つずつ解決する** — エンジニアが仕様を見る前に
5. `spec.md` を `intent.md` の隣にコミットする
   - **このファイルのペアが「何が求められたか」と「何が決められたか」を記録する**
6. プロダクトオーナーが、仕様と intent を Build に進めるか判断する
   - 組織が高リスクと分類するものについてはテクニカルリードに相談
   - **この判断は必ず人間が下す**
   - 仕様の受け入れが Stage 3 のプランモードのプレイを開始させる

### 5-6. 実際のプロンプト（要約）

> 添付の `intent.md` を読み、既存コードベースへ統合するための要件・設計仕様を作ってください。利用可能な skill を適用し、ブランドガイドライン・セキュリティポリシー・UX標準に適合させてください。仕様は `spec.md` として完全に文書化し、エンジニアリングチームに渡せる状態にしてください。**懸念のある箇所、特に矛盾するポリシーを同時に満たせない箇所は明確に記述してください。**

🔰 最後の一文が肝です。「矛盾があったら黙って片方を選ぶな、報告しろ」という指示になっています。

### 5-7. ガバナンス

- ポリシーが**仕様を書いている最中に読まれ適用される**（数週間後のレビューで発見されるのではなく）
- 組織の skill が仕様に対する制約として適用される
- **仕様・それを生成したプロンプト・適用された skill のバージョン、すべてがバージョン管理に記録される**
- プロダクトオーナーが仕様を承認し、フラグの立った懸念点を指名されたポリシー所有者にルーティングする

### 5-8. 測定

| 種類 | 指標 |
|---|---|
| **先行指標** | 同一変更の `intent.md` コミットと `spec.md` コミットの間の経過時間（gitのタイムスタンプ2つ）。従来の「要件定義+設計」サイクルとの比較 |
| **遅行指標** | **Build 開始後の要件手戻り**。同一変更の最初の `plan.md` コミットより後の日付を持つ `spec.md` コミット数。git log で直接取れる |

---

## 6. Stage 3 — Build（実装）

> 承認された計画なしには何も実装されない。組織知はエージェントが読むファイルになり、ガードレールは「習慣」ではなく「コード」として動く。

このステージには**5つのプレイ**があります。

### 6-1. プレイ①: Claude Code のプランモードを既定の出発点にする

**プランモード（plan mode）** = Claude がコードベースを**読めるが変更できない**モード。

エンジニアは Claude Code をプランモードで開始し、Stage 2 の承認済み `spec.md` を渡し、**Claude に自分をインタビューさせながら**計画を反復します。

| | 内容 |
|---|---|
| **伝統的** | エンジニアが設計を読み、コードを書き始める。「どのファイルを、どの順で、どのテストで」という**変更の進め方はエンジニアの頭の中**（よくてチケットのコメント）にとどまる。**誰もレビューできない**。レビュアーが最初に見るのは完成した差分で、その時点では手戻りが遅い |
| **AIネイティブ** | 作業は**書かれた計画**から始まる。エンジニアがコードを書く前に計画を修正し、承認版を `plan.md` としてコミット。後続ステージがこれと照合する |

**実行手順**

1. プランモードでセッション開始
2. `intent.md` と `spec.md` を渡し、**「変更されるファイル」「作業の順序」「それを証明するテスト」を名指しした実装計画**を求める
3. **計画を尋問する**: この変更で何が壊れうるか / 一番リスクの高いステップはどれか / 採用しなかった他の選択肢は何か
4. **この会話を見たことのないエンジニアが、計画だけで実装できるレベルまで**反復する
5. 承認した計画を `plan.md` としてコミット（監査証跡に加わり、Stage 5 のPRレビューが最終差分と照合する）
6. 計画を受け入れ、Claude に実装させる。**しっかりした計画があれば、実装は多くの場合1パスで済む**
7. 実装が計画から逸れたら、**同じコミットで `plan.md` を更新する**。両者の同期をフックで強制することも検討

**plan.md の例**

```markdown
# Plan: 請求ステータスのセルフサービス化（intent.md 2026-06-02 より）

## 変更するファイル
portal/src/claims/StatusPanel.tsx（新規）
claims-api/routes/status.py
claims-api/tests/test_status.py

## 作業の順序
1. 既存認証の背後にステータス取得エンドポイントを追加
2. そのエンドポイントに対してパネルを実装
3. ポータルのナビゲーションに組み込む

## リスク
claims-core API は 50 rps でレート制限される。パネルはキャッシュ必須。

## 証明方法
test_status.py が4つの請求ステータスを網羅。スクリーンショットが承認済みモックと一致。
```

**ガバナンス**
- **設計レビューがコード生成前に起きる** — 方針転換がまだ「文書を編集するだけ」で済む段階で
- **プランモード自体がこれを強制する**（計画を受け入れるまで Claude はファイルを編集できない）
- 計画とその改訂、および誰が承認したかが記録される
- 通常の変更はエンジニアが承認、高リスクはテックリードまたはアーキテクトへ

**測定**
- 先行指標: 最初の実装パスでマージされる変更の割合、計画承認からPRマージまでの時間
- 遅行指標: 変更あたりの手戻り回数、マージされた差分がコミット済み `plan.md` と一致している頻度

### 6-2. プレイ②: オートモード

**オートモード（auto mode）** = エンジニアが計画を承認したあと、Claude が**編集1つごとの確認を求めずに**変更を適用していくモード。

後続プレイのガードレールが成熟するにつれ、**定型作業ではオートモードが既定になる**:
- チューニングされた `CLAUDE.md`
- ポリシーを符号化した skill
- 危険な操作をブロックするフック
- Claude が実行できるテストスイート

適した条件: **引き締まった `spec.md` / 影響範囲（blast radius）が小さい / テストが既にカバーしているコード**。

変化の本質:

```
【旧】ユーザーがエージェントの編集を見守り、アクションをレビューする
              ↓
【新】長い自律セッションの後、成果物をレビューする
```

さらにオートモードは、**worktree と併用することで個人・チーム横断の並列実行を可能にし**、Stage 6 の「ループを閉じる」ための基盤になります。

### 6-3. サイドバー: レガシーシステムと「信頼できる唯一の情報源」

🔰 **これは実務上とても重要な節です。** 「全部 Markdown にしろ」ではありません。

現実には既に成果物が管理されています:
- 作業項目 → Jira
- 要件 → 規制トレーサビリティ機能つきの要件管理ツール
- デザイン → Figma
- 変更承認 → 変更管理委員会

これらは**監査人・規制当局が既に受け入れており、他チームも依存しているため、置き換えは困難**です。だから AI ネイティブ SDLC は**既存のものに合わせて作る**必要があります。

**原則**: プロセスが生む成果物ごとに、**1つのシステムを source of truth（信頼できる唯一の情報源）に指名する**。他はすべてコピーかリンクを持つだけ。

**3つの構成パターン**

| 構成 | 内容 | 向いている組織 |
|---|---|---|
| **リポジトリが source of truth** | Markdown 成果物が正式記録。レガシー側がコミット内のファイルを参照する | エンジニアリング主導の組織。**すべての記録が1つのツール・1つのタイムスタンプ権威に集まるため最もクリーン** |
| **レガシーシステムが source of truth** | Jira / ServiceNow / 要件ツールが正式記録。Markdown は作業用コピー。Claude はセッション開始時に記録を読み、**MCP コネクタ経由で同じセッション内に結果を書き戻す** | 規制対応で既存ツールを外せない組織 |
| **リンクを最低ラインとする** | 全成果物がレコードIDを記載し、全レガシーレコードが Markdown ファイルのコミットSHAを持つ | **移行の出発点として良い**。source of truth が2つあることを許容する |

両者は共存できます。ただし**リンクがあるか、どちらかが source of truth と宣言されている**ことが条件。

### 6-4. プレイ③: CLAUDE.md

**`CLAUDE.md`** = 新しく入ったメンバーが必要とする文脈を Claude に与えるファイル。

含めるもの: **規約 / コマンド / アーキテクチャ / チームが最もよく踏む地雷**。

> 人の頭の中や wiki にあった知識が、**セッション開始のたびにエージェントが読むファイル**になる。チーム全体で保守し、ミスがあるたびに更新する。

**実行手順**

1. リポジトリで `/init` を実行 → Claude が見つけたものから `CLAUDE.md` の叩き台を生成
2. **生成されたファイルを「新人が初日に必要なもの」まで削る**。ビルド/テスト/lint コマンド、重要な規約、Claude が繰り返し間違えることを残す
3. リポジトリルートに git でチェックインし、チーム全員が同じ版を共有、変更はコードと同様にレビューされる
4. **運用ルール: Claude が同じミスを2回したら、その訂正を `CLAUDE.md` に入れる**
5. **1ページ以内に保つ** — Claude はセッション開始時に全文を読むため、古い記述は無駄にコンテキストを食う

**CLAUDE.md の例**

```markdown
# 決済サービス

## コマンド
- ビルド: make build
- テスト: make test（単体） / make itest（結合、docker必要）
- Lint: make lint（CIでも走る。push前に直すこと）

## 規約
- Java 21, Spring Boot 3。Lombok の新規使用は禁止。
- 金額は必ず BigDecimal。double は使わない。
- 全エンドポイントに src/itest 配下の結合テストが必要。

## アーキテクチャ
- api/ = RESTコントローラ、core/ = ドメインロジック、adapters/ = 外部連携
- Kafka イベントは schemas/ で定義。生成クラスは絶対に編集しない。

## Claude がよく間違えること
- 依存バージョンを上げないこと。プラットフォームチームの管轄。
- レガシーの v1/ パッケージは凍結。変更は v2/ に入れる。
```

🔰 Satoshi さんの研修文脈だと、この「Claude がよく間違えること」セクションが特に示唆的です。**AIの誤りを個人の経験知ではなく、リポジトリの共有資産に変換する**仕組みになっています。

**ガバナンス**: `CLAUDE.md` はバージョン管理されるため、**エージェントが従う指示そのものがレビュー可能・監査可能**になる。変更は git 履歴に残り、コードオーナーが PR レビューで承認する。

**測定**
- 先行指標: `CLAUDE.md` が防ぐべきだったミスを Claude が繰り返す頻度
- 遅行指標: 新メンバーの初回PRマージまでの時間

### 6-5. プレイ④: 組織知としての Skill

**Skill** = 組織が institutional knowledge（組織に蓄積された知識）を**運用可能にする**手段。

特徴: 指示が明示的 / バージョン管理される / 広く適用される / ポリシー変更時に中央で更新される。

> **経験則**: 一貫して適用されなければならない組織知には skill を書く。`CLAUDE.md` やプロンプトに属するものには skill を書かない。

**実行手順**

1. **今日、不揃いに運用されている知識を1つ選ぶ**（セキュリティ標準、API設計規約、ブランドルールなど）
2. skill として書く = `SKILL.md` を含むフォルダ。**フロントマターに「いつ発火するか」、本文に「何をするか」**
   - エンジニアがポリシー所有者の source of truth から、Claude の助けを借りて書く
3. `.claude/skills/<name>/` に置いてコードと一緒に配布するか、**プラグイン経由で組織全体に配布する**
4. **skill が発火することをテストする** — 該当タスクを異なる言い方で依頼し、毎回ロードされることを確認
5. ポリシーが変わったら skill を変更し、**ポリシー所有者が変更を承認する**
6. エンジニアは次のセッションで自動的に新版を取得する

**SKILL.md の例（構造）**

```markdown
---
name: secure-api-review
description: APIセキュリティ標準を適用する。外部公開エンドポイントの作成・変更、
  APIコードのレビュー、OpenAPI仕様の生成のときに使用。
---
# セキュアAPIレビュー

エンドポイントを作成・変更するとき:
1. 認証: 全エンドポイントにゲートウェイJWTが必要。/health 以外に匿名ルートを作らない。
2. 入力検証: リクエストボディを OpenAPI スキーマで検証し、未知のフィールドは拒否する。
3. 監査: 状態を変えるエンドポイントは、実行者・操作・対象・時刻を含む監査イベントを発行する。
4. データ分類: スキーマで pii とタグ付けされたフィールドは、ログやエラーメッセージに絶対に出さない。

scripts/check-endpoints.sh を実行し、その出力をサマリに含めること。
```

**ガバナンス — ここが最重要**

> **skill はコントロールではあるが、あくまで advisory（助言的）なコントロールである。**
> skill は「コードを書いている最中に Claude がポリシーを適用する可能性を高める」が、**セッションがそれに従うことを強制する仕組みはない**。

したがって:

> **常に成立しなければならないポリシーには、skill の背後に決定論的（deterministic）な何かが必要**。
> 具体的には、**その操作をブロックするフック**、または **PR時にポリシーを再チェックするレビューパス**。
>
> **skill が違反をまれにし、フックが違反をほぼ不可能にする。**

🔰 **この一文が Deploy ステージの設計思想につながります。** 「AIに指示を書けば守る」ではなく、「指示（確率的）+ 強制（決定論的）の二層」です。

**測定**
- 先行指標: ポリシー所有者がポリシー変更を承認してから、更新された skill がマージされるまでの時間
- 遅行指標: **そのポリシーを引用するPRレビュー指摘の数**。skill が機能していればゼロに近づくはず。**落ちない場合は、skill が発火していないか、skill の記述が公式ポリシーからずれている**

### 6-6. プレイ⑤: ビルド時ガードレールとしてのフック

**フック（hook）** = skill の背後にある**決定論的な層**。

Claude のアクションの大半は実装中のファイル編集とシェルコマンドなので、**フックが最も頻繁に発火するのは Build フェーズ**です。

**ビルドフェーズのフックができること**:
- 保護対象パスへの編集をブロックする（生成クラス、凍結パッケージなど）
- ファイル編集後にフォーマッタと lint を走らせ、ずれが蓄積しないようにする
- **認証情報が差分に混入しないようにする**

**注意点**:
- **例外なく成立すべきポリシーを持つ skill には、必ずフックを背後に置く**
- フックはマッチする各アクションごとに走るため、**ビルドフェーズのフックは高速で、変更されたファイルにスコープを絞るべき**
- テストスイート全体のような重い検査は、コミット時またはPR時に置く
- **人間の承認を求めるフックは Stage 5 に属する** — ビルド中に承認プロンプトを出すと、**並行実行中の全セッションのクリティカルパスに人間を戻してしまう**から

### 6-7. プレイ⑥: 並列セッションとサブエージェント

1人のエンジニアが複数の作業ストリームを同時に進める方法です。

**2つの概念を区別する**

| | 並列セッション (parallel session) | サブエージェント (subagent) |
|---|---|---|
| 実体 | **別個の Claude Code インスタンス** | **1セッション内で動くスコープ限定のヘルパー** |
| 隔離 | 各自の git worktree で別タスク | 独自のコンテキストウィンドウとツール制限を持つ |
| 相互認識 | **互いを一切知らない**。共有するのは操縦するエンジニアだけ | 親セッションの一部 |
| 用途 | 独立したタスクを同時に進める | 複数タスクで繰り返される仕事（例: アプリが期待通り動くか検証する） |
| 効果 | **同時進行できるタスク数が増える** | **各セッションを自分のタスクに集中させる** |

🔰 **git worktree**: 同じリポジトリから、別ブランチの独立したチェックアウトを作る git の機能。ディレクトリが分かれるのでファイル衝突が起きません。

**何が変わるか**

| | 内容 |
|---|---|
| **伝統的** | 1人が1タスク。1日/1週の相当部分をビルド、テスト、レビュー待ちに費やす。待ち時間にタスクを切り替えることは可能だが、**コンテキストスイッチが疲れるので実際にやる人は少ない** |
| **AIネイティブ** | 1人が複数の Claude セッションを同時に動かす。各セッションは自分の worktree で自分のタスクを持つ。繰り返しの仕事はサブエージェントになる。**エンジニアの仕事はオーケストレーション（統率）へ、そして最終的にはループの構築と監視へ移る** |

**実行手順**

1. **異なるファイルに触れるタスクに分割する**。プランモードで作った計画を見て、どこが独立しているか判断する。**同じファイルを触るタスクは1セッションで順番に処理する**
2. 並列タスクごとに worktree を割り当てる
   ```
   claude --worktree feature-auth      # ターミナル1
   claude --worktree fix-rate-limit    # ターミナル2
   ```
3. **2〜3セッションが妥当な出発点**。実務上の上限は「**1人がきちんとレビューできるストリーム数**」。**レビューが追いついている間だけセッションを増やす**
4. 繰り返しの仕事をサブエージェント化する。`.claude/agents/` 内の Markdown ファイルで定義（名前、使うべきタイミングの説明、触れてよいツール）
   - 例: メインエージェント終了後に不要な複雑さを削る **code simplifier**
   - アプリを実行して挙動を確認する **verifier**
   - コードベースを調査して報告し、メインのコンテキストを汚さない **researcher**
   - **定義を git にチェックインしてチーム全体で共有する**

**サブエージェント定義の例（verifier）**

```markdown
---
name: verifier
description: セッションが完了報告する前に、アプリを実行して変更が動くか確認する
tools: Bash, Read
---
make run でアプリを起動する。変更された挙動と、最も近い2つの周辺フローを実行する。
何を実行し、何を観察したか、plan.md と一致しない挙動を報告する。
何も修正しないこと。報告のみ。
```

🔰 最後の「**Do not fix anything; report only.（修正するな、報告のみ）**」が重要です。検証役が修正までしてしまうと、検証の独立性が失われます。

**ガバナンス**: セッションが増えれば出力も増えるため、**コントロールはリポジトリ内の設定から来る必要がある**。そこに置かれたフックと権限設定は全セッションに適用され、セッションの動作は**それを実行したエンジニアに紐づけてログされる**。

**測定**
- 先行指標: レビュー品質を保ったままのエンジニアあたり同時セッション数（OpenTelemetry エクスポートから集計）、および1日のうち「待ち」ではなく「操縦」に使った割合
- 遅行指標: エンジニアあたり週次マージ数を**手戻り率と並べて読む**

---

## 7. Stage 4 — Test（テスト）

> すべてのセッションが、人間が見る前に自分の仕事を検査する。そしてエージェントを操縦する設定自体が、コードと同じようにリグレッションテストされる。

### 7-1. プレイ①: Claude にフィードバックループを与える

**原則**: **Claude には常に、自分の仕事を検証する手段を与えること。** テスト、ビルド、スクリーンショット差分など。

セッションが自分で自分の仕事をチェックし、**エンジニアが見る前に自分のミスを直す**。

**フィードバックループ ≠ verifier サブエージェント**（混同注意）

| | フィードバックループ | verifier サブエージェント |
|---|---|---|
| 実行タイミング | **タスク全体を通じて、作業の必要な回数だけ**走る | セッションが「完了した」と考えた時点で**1回** |
| 目的 | 作業中の自己修正 | 最終チェック |
| 特徴 | — | **新しいコンテキストウィンドウで走る**ため、**コードを生み出した思い込みに判定が汚染されない** |

**何が変わるか**

| | 内容 |
|---|---|
| **伝統的** | 「コードが動く」という信号が遅れて届く。CIなら数分後、テスターなら数日後、本番なら数週間後。**エージェントがコードを生産している状況で信号が遅いと、人間がその全出力をチェックする羽目になり、その人がボトルネックになる** |
| **AIネイティブ** | セッションに、人が見る前に自分の仕事を確認する手段を与える。テストを走らせ、ビルドし、スクリーンショットを撮る。Claude がチェックに通るまで反復するので、**エンジニアに届く時点で既にチェックを通過している** |

**実行手順**

1. **今日、作業の確認に複数のコマンドと環境知識が要るなら、`make test` や `npm test` のような単一ターゲットに包む**。失敗時は非ゼロ終了コードを返すこと
2. `CLAUDE.md` の Commands セクションに、各コマンドと**正常時の出力例**を書く
3. **目標を述べ、それを定量的にする**（Claude が人に聞かずに確認できるように）
   - 「test_status.py のテストが全部通る」
   - 「スクリーンショットが添付のモックと一致する」
   - 「エンドポイントが新フィールド付きで 200 を返す」
4. **バグ修正では、失敗するテストを先に書く**
   - Claude にバグをテストとして再現させ、実行し、**期待した理由で失敗することを確認する**
   - **そのテストをコミットする**
   - **その後にはじめて**、テストを編集せずに通るようにさせる（テストファイル編集禁止フックで強制）
   - > **修正前から存在し、エージェントが書き換えられなかったテストこそが、バグが消えた証拠になる**
5. **UI作業は視覚チェックでループを閉じる**。ブラウザまたはスクリーンショットツールとモックを与えて反復させる。**実装 → スクショ → 比較 → 調整。2〜3ラウンドが普通で、毎回良くなるはず**
6. **検証を「完了」の定義に含める**。指示は `CLAUDE.md` に置く。タスク完了報告の前にテストを実行し、出力を提示する
7. **ループ自体を保護する**
   > **コードを修正しているエージェントが、そのコードに対するチェックを弱められてはならない。**
   - 修正タスク中のテストファイル編集をブロックするフックがこれを実現する
   - 代替案: レビューで差分をチェックし、テストに触れる変更を却下する

🔰 Satoshi さんの研修設計にある「**red before green を明示的に強制する**」がまさにここです。原文も同じ結論に到達しています。

**CLAUDE.md の検証ブロック例**

```markdown
## 作業の検証方法

- ビルド: make build（"Build succeeded" で終わること）
- テスト: make test（全部グリーン。失敗するテストをスキップ・削除しない）
- Lint: make lint（警告ゼロ）

タスク完了を報告する前に3つすべてを実行し、出力を貼り付けること。
テストが落ちたら、テストではなくコードを直すこと。
```

**ガバナンス**

| 項目 | 内容 |
|---|---|
| **何が強制されるか** | タスク完了報告前の検証、および修正タスク中のテストファイル編集禁止。組織が保証を求める場合はフックとして実装 |
| **証拠は何か** | `make test` の実際の出力、ビルドログ、Claude が実行して貼ったスクリーンショット差分。**証拠はツールチェーンから来る**（AIの自己申告ではない） |
| **どこに記録されるか** | セッションのトランスクリプト（OpenTelemetry エクスポートが組織の可観測性基盤へ転送）、およびPRのチェック実行結果 |
| **誰が承認するか** | PRをレビューするコードオーナー。**機械的な証拠は既に添付されているため、意図とリスクに集中できる** |

**測定**
- 先行指標: エージェントが書いた変更の**初回CI成功率**
- 遅行指標: PRあたりのレビュー時間（レビュアーが拾っていたものをテストが拾うようになれば下がるはず）、インシデント管理からの変更失敗率

### 7-2. プレイ②: CI での継続的 eval

**eval（評価）** = AI ネイティブ版の「ステージゲート QA」。

**エージェントの設定が変わるたびに走るスイート**です。新しいモデルに差し替えたとき、プロンプトを書き直したとき、**エージェントが同じ水準で仕事をできているか**を eval が答えます。

> **eval は生きたスイートとして扱うこと。** モデルが良くなるにつれ、かつては差がついたケースが差をつけなくなる。継続的な監視から生まれる新しいケースを追加し続けなければならない。

🔰 ユースケースによっては、変更のたびではなく**決まった周期でオフライン実行**する方が良いチームもある、と原文は補足しています。

**前提条件**: `CLAUDE.md` とフィードバックループ

**必要なインフラ**: Claude Code を非対話で実行できる CI、eval 実行予算のある API キー

**実行手順**

1. **プラットフォームエンジニアが、直近の実作業から20〜50件のタスクを、期待される/受け入れ可能な結果とともに収集する**
2. 各タスクを eval として書く = **プロンプト + 「受け入れ可能」を定義するチェック**（テストが通る、lint がクリーン、挙動が変わっていない、ポリシーに従っている）
3. **スイートを CI で非対話実行する**。スケジュール実行に加えて、**`CLAUDE.md` / skill / フックへの変更があったとき**にも実行する
   > **その設定がエージェントを操縦しているのだから、コードと同じリグレッションテストを受けるに値する**
4. **設定変更を結果でゲートする**。合格率を下げる skill 変更は、マージ前にレビューされる
5. **本番インシデントごとに eval を1つ作る**。インシデントを所有していたチームが書き、リグレッションテストとしてスイートに残る

**CI 設定の例（概念）**

```yaml
name: Agent evals
on:
  pull_request:
    paths: ['CLAUDE.md', '.claude/**']   # ← 設定変更で発火
  schedule:
    - cron: '0 2 * * *'                  # ← 毎日定時
jobs:
  evals:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install -g @anthropic-ai/claude-code
      - name: Run eval suite
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          # 各evalのプロンプトを非対話実行し、チェックスクリプトで判定
          ...
```

**ガバナンス**: eval は **QA に、エージェントの出力速度に追いつけるゲートを与える**。合格率のしきい値がマージチェックとして強制され、実行結果はログされ経時比較でき、設定変更を所有するチームが承認する。

**測定**
- 先行指標: eval 合格率の推移、**本番インシデントが恒久的な eval になるまでの時間**
- 遅行指標: CI で捕まえたリグレッション数 vs 本番で見つかったリグレッション数

## 8. Stage 5 — Deploy（リリース）

> レビューは双方向に走り、ガバナンスは**エージェントが行動する瞬間に**強制される。**エージェントは本番ゲートの手前まですべてを行い、その先には一切進めない。**

このステージには**3つのプレイ**があります。

### 8-1. プレイ①: PR レビューループの AI

Claude は**レビューをする側でもあり、される側でもある**:
- 組織のポリシーに照らして流入する PR をレビューする
- 自分の PR に付いたレビューコメントに対応する

これにより、**エンジニアは PR レビューで挙動に集中でき**、それは結局「**意図とリスクの判断**」に帰着します。

**何が変わるか**

| | 内容 |
|---|---|
| **伝統的** | レビュー能力は人間の出力量を前提に計画されていた。PRはレビュアーが全部読むのを待ち、**レビュー品質はレビュアーの負荷でばらつき**、著者は催促し、待ち行列は伸びる |
| **AIネイティブ** | **すべてのPRが同一のレビューパスを受け**、指摘は重大度でランク付けされる。人間の注意は一段上のレイヤーへ: **変更が計画の意図通りか、リスクは受容可能か** |

**実行手順**

1. **マネージド Code Review サービス（リサーチプレビュー）が最速の出発点**。管理者が有効化してリポジトリを選ぶだけ
   - パイプラインを自分で制御したい、または API 呼び出しを自社のクラウド契約経由にしたい場合は、自前 CI で `claude-code-action` を走らせる
2. **テックリードがレビューポリシーを `REVIEW.md` としてリポジトリルートに書く**。組織が重視するパスに分ける:
   - バグと論理エラー
   - セキュリティと脆弱性
   - **`spec.md` / `plan.md` / 設計原則への準拠**
   - `REVIEW.md` は「Important（重要）」と「Nit（些細な指摘）」の境界、および**何をスキップするか**も定義する
3. **テックリードが人間のしきい値を設定する**
   > **指摘それ自体は PR を承認も却下もしない。ブランチ保護は依然としてコードオーナーの承認を要求する。**
   - マージを指摘数でゲートしたいプラットフォームエンジニアは、チェック実行が公開する機械可読な重大度集計を読める
4. **レビュアーまたは著者がレビューコメントで `@claude` をタグ付けすると、Claude がそのコメントに対応して修正をプッシュする**。PRスレッドが依頼と変更の両方を記録する
   - Claude が開いた PR については、さらに進めて **Claude に PR をマージまで面倒を見させる**ことができる
   - チームはこのループをカスタムスラッシュコマンドに包む: 未解決のレビューコメントと失敗チェックを掃き集め、対応し、修正をプッシュする。**PRがグリーンになり、コードオーナー承認だけを待つ状態になるまで**
5. **レビュー指摘を `CLAUDE.md` に還流させる**
   - レビューが同じミスを2回指摘したら、そのレビューの一部として訂正を `CLAUDE.md` に入れる
   - **レビュー自体が `CLAUDE.md` を読むので、次のPRからそのミスは捕捉される**
   - レビューは「変更によって `CLAUDE.md` が古くなった」ことも指摘する
6. **月1回、テックリードがセットアップをチューニングする**。指摘を評価してレビュアーを改善し、`REVIEW.md` で Nit の量に上限をかける。生成されたパスと CI が既に強制しているものは除外する

**REVIEW.md の例**

```markdown
# レビュー指示

## パス
3つのパスを実行し、各指摘にどのパスかタグを付ける:
- バグ: 論理エラー、壊れたエッジケース、微妙なリグレッション
- セキュリティ: インジェクション、認証の抜け、ログ内の個人情報
- 準拠: spec.md / plan.md / 設計原則との一致

## ここでの「Important」の意味
挙動を壊す、データを漏らす、ポリシーに違反する指摘だけを Important とする。
スタイルと命名は nit。

## Nit の上限
1レビューあたり nit は最大5件。残りは件数として要約する。

## 報告しないもの
src/gen/ 配下の生成ファイル、および CI が既に強制しているもの。
```

🔰 「**Nit に上限をかける**」設計が現実的です。AI は無限に指摘を出せるので、**制限しないとレビューがノイズになる**。

**ガバナンス**

> **職務分掌（separation of duties）が保たれる。なぜなら、コードを書いたエージェントには、それを承認する手段が一切ないから。**

- `REVIEW.md` のレビューポリシーが全 PR に適用される
- 指摘、修正、評価、承認はすべて PR 履歴にログされる → **PR そのものが監査記録になる**
- **承認はブランチ保護を通じて人間から来る**。指摘はその判断材料

**測定**
- 先行指標: 初回レビューまでの時間（**分単位まで落ちるはず**）、人間がブランチに触れずに解決されたレビューコメントの割合
- 遅行指標: マージ前に捕捉した欠陥・脆弱性 vs 本番に漏れた数

### 8-2. プレイ②: 承認ゲートとしてのフック

Build フェーズのフックは「**人間なしで許可/ブロック**」でした。フックは「**尋ねる（ask）**」こともできます — **特定の人物が承認するまでアクションを一時停止する**。これがリリースゲートに必要なものです。

🔰 このプレイが Stage 5 に置かれているのは「リリースゲートが最も分かりやすい例だから」であって、**フックは Claude が動くところならどこでも走ります**。例:
- Build 中: 変更チケットなしのマイグレーション/インフラ編集をブロック
- Test 中: 修正タスク中のテストファイル編集を阻止

**実行手順**

1. **エンジニアリングリーダーシップが、変更管理・コンプライアンスとともに、生き残らせるべき人間の承認ゲートを列挙する**（変更管理サインオフ、リリース認可、保護パスの編集など）
2. **プラットフォームエンジニアが各ゲートをフックとして表現する** = Claude が行動する前に走るスクリプトで、**allow / ask / block** を返せる
3. **配置場所を使い分ける**
   - チーム向けフック → git 内の `.claude/settings.json`
   - **交渉不可のフック → プラットフォーム/IT管理者が所有するマネージド設定**（個々のエンジニアが無効化できない場所）
4. **ブロックは自分で説明すること**。フックがアクションを止めたとき、**理由と承認への経路が Claude の出力に現れる**ようにする

**設定の例（概念）**

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/production-gate.sh" }
        ]
      }
    ]
  }
}
```

**ゲート本体（概念）**

```bash
#!/bin/bash
# 本番デプロイには名前付きのリリース認可が必要
# コマンドに deploy と production の両方が含まれ、
# RELEASE_APPROVAL が未設定なら:
#   → メッセージを出して exit 2（exit 2 がアクションをブロックし、
#     メッセージが Claude に渡る）
# それ以外は exit 0（許可）
```

🔰 **exit 2 でブロック、メッセージが Claude に届く**という仕組みが要点です。Claude は「なぜ止められたか」を理解して次の行動を変えられます。

**ガバナンス**: **フックが承認ゲートそのもの**。ゲート条件は毎回、全員に対して強制される。allow / block の判断はタイムスタンプ付きでログされる。ゲートは「何をもって承認とするか」（承認済み変更チケットか、リリースマネージャのサインオフか）も定義する。

### 8-3. 実例: 規制業種向けのマネージド設定

🔰 **これは原文の中でも特に濃い部分です。** プラットフォームチームが MDM または管理コンソール経由で配布し、**エンジニアは編集も上書きもできません**。

各設定が「コントロールとして何を買っているか」:

| 設定キー | 買っているもの |
|---|---|
| `permissions.deny` | **秘密情報をエージェントのコンテキストから排除**し、ツール経由の任意のネットワーク送信をブロック（例: `Read(.env*)`, `WebFetch`, `Bash(curl *)`） |
| `permissions.allow` | 安全な内側ループを事前承認し、**deny リストが「承認疲れ」に化けるのを防ぐ**（例: `Bash(git *)`, `Bash(make test)`） |
| `disableBypassPermissionsMode` + `allowManagedPermissionRulesOnly` | **エンジニア・プロジェクトファイル・コマンドラインフラグのいずれもルールを緩められない** |
| `sandbox` | **権限設定では塞げない穴を塞ぐ**。ツールレベルで `WebFetch` を拒否しても、シェルコマンドがネットワークに到達するのは止まらない。**OSレベルのドメイン許可リストが送信そのものをブロックする** |
| `failIfUnavailable` + `allowUnsandboxedCommands: false` | **サンドボックスをゲートにする**。サンドボックスが初期化できなければ Claude Code は起動を拒否し、**サンドボックス内で失敗したコマンドを外で再試行することもできない** |
| `credentials` | deny ルールが残す穴を塞ぐ。`permissions.deny` は Claude のファイルツールを統制するが、**サンドボックス化されたシェルコマンドは既定で `~/.ssh` や `~/.aws/credentials` を読めてしまう**。このブロックがそれらの読み取りを拒否し、指定した秘密情報を全サンドボックスコマンドの環境変数から除去する |
| `allowManagedHooksOnly` | **このプレイの承認ゲートだけが実行されるフックになる**。ローカルの何物もそれに追加・置換できない |
| `disableSideloadFlags` + `strictKnownMarketplaces` | エンジニアのマシン上のすべての skill・エージェント・フック・MCPサーバーが、**組織の承認済みプラグインマーケットプレイス経由で到着したものになる**。ホームディレクトリからは来ない |
| `allowManagedMcpServersOnly` | **エージェントのツール表面をプラットフォームチームが所有する許可リストにする** |
| `requiredMinimumVersion` | **承認された下限バージョン未満では起動を拒否する**。つまりコントロールは、組織が実際に評価したビルドによって強制される |

> **上記はコピーする推奨設定ではなく、調整の出発点と考えること。** すべての deny は機能性とのトレードオフであり、**適切なバランスはそのリポジトリのデータ分類による**。

**フック自体の測定**
- 先行指標: **各承認ゲートでの待ち時間**。フックの判断はすべてタイムスタンプと allow/block の判定つきで OpenTelemetry にエクスポートされるので、ゲートごとの待ちが可視化される
- 遅行指標: フック導入前後で、本番に到達したゲート違反の数

### 8-4. プレイ③: CI/CD 統合とデプロイ

**要点**: Claude Code を CI/CD パイプライン内で**非対話実行**し、**実行をサンドボックス化**し、**デプロイを MCP 経由で公開**し、**ロールバック経路をエージェントが必要とする前にリハーサルしておく**。

**何が変わるか**

| | 内容 |
|---|---|
| **伝統的** | パイプラインは決定論的なスクリプトを実行し、**判断が必要なものは人間を待つ**。例: 不安定テスト（flaky test）のトリアージ、変更履歴の執筆、ビルドが壊れた原因の究明。デプロイとロールバックは**プレッシャー下で人間が辿るランブック** |
| **AIネイティブ** | Claude が判断ステップのためにパイプライン内で非対話実行される。**スコープを絞った認証情報を持つサンドボックス内で**。デプロイツールが MCP 経由でエージェントに公開されるので、**変更を書いてテストしたワークフローが、そのまま出荷とロールバックまでできる** — 組織が環境ごとに定めたゲートの内側で |

**前提条件**: PRレビューループの Claude、承認ゲートとしてのフック
→ **自動化が加速させる前に、ゲートが存在していなければならないから**

**実行手順**

1. **読み取り専用の判断ステップから始める**。パイプラインジョブで `claude -p` を使い、失敗したビルドをトリアージする、不安定テストを要約する、変更履歴を起草する
2. **既存のゲートの背後に書き込みステップを追加する**。lint 修正、生成ドキュメント更新、`@claude` メンション経由のレビューコメント対応など
   > **エージェントが書いたものはすべてブランチ保護を通る PR として到着し、エージェントには main に push する経路がない**
3. **実行はサンドボックス化する**。エージェントジョブはネットワークポリシー下のコンテナで、**短命でスコープを絞ったトークン**を使って走り、**既定では本番の認証情報を一切保持しない**
4. **デプロイを MCP 経由で公開する**。deploy / status / rollback がツールになり、環境ごとにスコープされる
   > **エージェントのデプロイ権限が「認証情報つきのシェルスクリプト」ではなく「許可リスト」になる**
5. **環境ごとに自律性を段階化する**
   - 開発環境: エージェントが自由にデプロイ
   - 本番: **エージェントはリリースを準備し、リリースマネージャが認可する**。フックが本番ゲートを強制
   - ステージング: その中間
6. **ロールバックはパイプラインで最もリハーサルされた経路であるべき**。エージェントが実行できる単一コマンドで、**ステージングで定期的に練習される**
   - Stage 6 の「ループを閉じる」プレイが管理帯の逸脱時にこのロールバックを呼ぶので、**事前に証明されている必要がある**

**パイプラインステップの例（概念）**

```yaml
- name: 失敗ビルドのトリアージ
  if: failure()
  run: >
    claude -p "out/build.log のビルドログを読み、最も可能性の高い原因を特定し、
    この失敗が flaky か本物かを述べ、PRスレッド用に3行の要約を書いてください。"
    >> triage.md
```

**ガバナンス — 統治原則**

> **エージェントは本番ゲートまでは行動してよく、それを越えることはできない。**

これを強制するコントロール:
- **ブランチ保護**が、エージェントが書いたものすべてを PR に変える。**main への直接経路はない**
- **本番デプロイフック**が、指名されたリリースマネージャが認可するまでリリースをブロックする
- 各非対話実行は**エージェント自身のアイデンティティで動く**ので、**パイプラインログはエージェントの行為と、それを起動したエンジニアの行為を分離できる**
- **環境ごとの権限ティア**が、ゲートに至るまでにエージェントが何をしてよいかを定める

**測定**
- 先行指標: 人を呼び出さずにトリアージされたパイプライン失敗の割合
- 遅行指標: **DORA 指標**（DevOps Research and Assessment）— CI と デプロイツールが既に出しているもの

🔰 **DORA 指標**: デプロイ頻度 / 変更のリードタイム / 変更失敗率 / サービス復旧時間 の4つ。開発組織のパフォーマンス指標としてデファクト。

## 9. Stage 6 — Maintain（運用保守）

> **ループが閉じる。** 起動経路に人間がいない状態でトリガーが Claude を呼び出し、その発見が `intent.md` としてパイプラインに再投入される。

### 9-1. このステージが特別な理由

ここまでのステージは**すべて人間が最初のステップを起動していました**。Stage 6 は、**Claude の自律実行に焦点が移ります**。

例:
```
バグチケット起票
  → 常時稼働の監視エージェントが intent.md を作成
  → 要件 → 計画 → ビルド → テスト → レビュー の各フェーズを流れる
```

Stage 6 は**ヘッドレス（headless / 画面なし・人の対話なし）**で走り、**各ステージの間に独立した信頼度ゲート（confidence gate）**が置かれます。ゲートは決定論的チェック、または**敵対的にレビューするエージェント**で、**前ステージの出力を先に進めるか、人間にエスカレーションするかを判断します**。

**何が変わるか**

| | 内容 |
|---|---|
| **伝統的** | 保守は受動的フェーズ。**すべてのチケットとインシデントが、人が動くのを待つ**。午前3時にアラートが鳴っても見逃されうる。チケットは誰かが拾うまでバックログに座る。**ポストモーテムのアクションは、別の火事が起きればコードベースに届かないまま終わる** |
| **AIネイティブ** | 管理帯の逸脱、チケット、チャンネルのメッセージ、スケジュール等のトリガーが、**経路に人を置かずに** Claude を呼ぶ。Claude は診断し、**ゲートされた経路を通じてのみ行動し**、見つけたことを `intent.md` として書く。人はその作業をトリアージしレビューするが、**もはや起動する必要がない** |

### 9-2. プレイ①: ループを閉じる

**決定論的なスクリプトが本番を監視し、管理帯（control band）が破られたときに Claude を呼び出す。**

🔰 **管理帯（control band）**: 統計的工程管理の考え方。ある指標の「正常な範囲」を平均±標準偏差(σ)で定義し、そこを外れたら異常とみなす帯のこと。

**前提条件**
- `intent.md`（ループが再スタートするための構造化出力を与える）
- Claude によるPRレビュー、行動境界としてのフック、CI/CD のロールバック経路（最高自律ティアが呼ぶ）

**必要なインフラ**
- 検知スクリプトが照会できるメトリクスストア（Prometheus、CI の API など）
- リポジトリへの読み取りアクセス
- Claude Code を CI で非対話実行する手段、または webhook を受けるサービスのための Agent SDK

**実行手順**

1. **サービスオーナーまたはプラットフォームエンジニアが、安定したローリングベースラインを持つメトリクスを1つ選ぶ**
   - 例: CI テスト失敗率、デプロイ後の 5xx 率、PR サイクルタイム
2. **検知スクリプトを書く**
   - 典型的にはローリングウィンドウでの平均と標準偏差 + ルール（Western Electric ルールなど）
   - **スパイクだけでなく緩やかなドリフトも捕まえられるように**
   - **スクリプトはバージョン管理され、単体テストされる**
   - > **検知は完全に決定論的なままにする。モデルは一切関与しない**
3. **対応ティアをバージョン管理された設定で定義する**（`bands.yaml`）
   - **1σ**: スクリプトはログするだけ
   - **2σ**: Claude を**読み取り専用**で呼んで診断させる
   - **3σ**: Claude は**行動してよい** — ただし**レビューゲートに入る PR を開く**か、**事前承認済みのランブックを起動する**ことによってのみ
4. **トリガー層**: GitHub/GitLab のスケジュールワークフロー、既存監視スタックからの webhook、社内ネットワークの Cron ジョブなど
   - Claude は**ステートレス**に走る（CI ランナー上の非対話ステップ、またはサンドボックスコンテナ内の Agent SDK サービス）
   - > **実行がステートレスかつ非対話であるため、誰も起動しなくてもループが始まり終わることができる**
5. **エージェントは診断結果を Stage 1 の形式で `intent.md` として書く** — 異常とその証拠、提案される成果、影響を受けるシステム、未解決の問い
   - そこから先は他の変更と同じようにパイプラインを流れる
6. **サービスオーナーまたはオンコールエンジニアがキューをトリアージする**。プロダクト面の発見はプロダクトオーナーへ。**今直す / スケジュールする / 却下する**
   - **却下が管理帯をチューニングし、ノイズを減らすのに役立つ**
7. **修正が出荷されたら、そのインシデントの eval を追加する**

**bands.yaml の例（CIテスト失敗率を監視）**

```yaml
metric: ci_test_failure_rate
baseline: rolling_30d
rules: western_electric
tiers:
  1sigma: { action: log }
  2sigma: { action: diagnose,
            tools: "Read,Grep,Bash(gh run view *)" }
  3sigma: { action: propose,
            routes: [pull_request, runbook:rollback-deploy] }
```

🔰 `2sigma` のツール指定に注目してください。**Read / Grep / 特定コマンドの参照のみ**で、書き込み系が一切ありません。「診断はさせるが手は出させない」が設定として表現されています。

**具体例**

| 状況 | エージェントの行動 |
|---|---|
| CIテスト失敗率が 3σ 超過 | **不安定テストを隔離するか、revert PR を開く**。判断はレビューゲートが下す |
| デプロイ後 5xx 率が 3σ 超過（ウィンドウ内にデプロイあり） | **既存のロールバックパイプラインを起動する** |
| PR サイクルタイムがドリフトルールに抵触 | **エンジニアリングリーダーシップ向けのレポートを書く**（この仕組みが本番指標だけでなくプロセス指標にも効くことを示す例） |

> **検知は決定論的なままである。管理帯が破られてはじめて Claude が呼ばれ、ティアが「何をしてよいか」を決める。**

**ガバナンス**
- ティア境界はバージョン管理された設定から強制され、**権限とマネージド設定が本番アクセスを拒否する**
- 呼び出し、発見、トリアージ判断はタイムスタンプ付きでログされる
- **サービスオーナーが発見をトリアージ・承認**し、結果の変更は通常の PR レビューゲートを通り、**エージェントが起動できるランブックは事前に承認されている**

**測定**
- 先行指標: **管理帯逸脱からトリアージキューに `intent.md` が並ぶまでの時間** vs 従来の「インシデントからポストモーテムのアクションまで」の時間
- 遅行指標: 発見がマージされた修正になった割合、**同一クラスのインシデント再発率**（修正が eval にケースを追加していくにつれ下がるはず）

### 9-3. プレイ②: 定期的なコードベーススキャン

**問題設定**:

> セキュリティスキャンは「**ある特定のモデルの下で、ある時点のコードベースについて述べた文**」であり、**両方の半分が古くなる**。
> コードは毎週変わる。そして**モデルの世代が変わるたびに、前世代が見逃した脆弱性を見つける**。

**AI ネイティブの答え**: スキャンを**スケジュール実行**し、**起動経路に人間を置かず**、見つけたものを**他の変更と同じゲートに通す**。

**Claude Security** がそのホスト型の形態です。GitHub リポジトリを接続すると、**Anthropic のインフラ上で Claude Mythos 5 でスキャンが走り**、各発見は**報告前に検証され、信頼度レーティングが付きます**。提案されたパッチは Claude Code on the Web でレビュー・適用されます。**組織はモデル自体へのアクセスなしに発見だけを得られます**。

**何が変わるか**

| | 内容 |
|---|---|
| **伝統的** | セキュリティスキャンは**イベント**。リリース前や監査前にスキャンを起動する。レポートはトラッカーへ行き、次のイベントまで手作業でバックログを消化する。**その間に書かれたコードは、PRレビューが拾ったものだけでカバーされる** |
| **AIネイティブ** | 接続された全リポジトリに対しスケジュールでスキャンが走る。**利用可能な最も高性能なモデルで**、発見は誰かが読む前に検証される。各発見は管理帯逸脱と同じ扱い: **1つのPRに収まる修正はレビューゲートを通り、それより大きいものは `intent.md` になる**。**カバレッジは「最初のスキャン」ではなく「最後のスキャン」の日付で語られる** |

**実行手順（要点）**

1. セキュリティリードがリポジトリを接続し、**リポジトリ/サービス/チーム単位でプロジェクトに整理する**（発見の所有権が最初から明確になるように）
2. **最重要リポジトリの初回フルスキャンを実行する** — 他ツールや旧世代モデルで既にスキャン済みのものも含めて
   - **初回スキャンをベースラインとして扱う**
   - > **初回スキャンは、クリーンだと考えられていたコードから発見を出す可能性が高い**
3. **プロジェクトごとにスケジュールを設定する**。活発に開発中のサービスは**週次が妥当な既定値**。大規模・混在リポジトリはディレクトリやブランチにスコープを絞る
4. **信頼度レーティングを手に持ってトリアージする**。**却下は理由付きで**行い、記録として残す（次回同じ発見が「新規」として戻ってこないように）
5. 範囲の限定された発見は、Claude Code on the Web で提案パッチを開き、レビューし、**他の変更と同じPRレビューゲートに通す**
   - > **修正を提案したエージェントに、それを承認する経路はない**
6. **1つのパッチより広いもの**（アーキテクチャ上の弱点、サービス横断で繰り返されるパターン）は、**Stage 1 の形式で `intent.md` に書き、Plan から始める**
7. 修正が本番リリースされたら、**その脆弱性クラスの eval をスイートに追加する**
8. 発見を CSV / Markdown でエクスポート、または webhook を使い、**監査人が既に期待している既存トラッカーを system of record として維持する**

**ガバナンス**
- 接続リポジトリ、スキャンシートの保有者、支出上限はすべて中央で設定される
- **すべての発見に検証結果と信頼度レーティングがあり、すべての却下に理由がある** → **スキャン履歴が「何が見つかり、何が直され、何が意識的に受容されたか」の監査記録になる**
- 修正はスキャン自体からではなく、**PRレビューゲートとブランチ保護を通じて本番に到達する**
- **Claude Security は既存の静的解析・依存関係スキャンを補完する**。決定論的チェックは CI に残り、**モデル駆動のスキャンは、それらのチェックが見つけるようには作られていない文脈依存の脆弱性をカバーする**

**測定**
- 先行指標: スケジュール化されたリポジトリの割合、発見報告からパッチがPRレビューゲートに入るまでの時間
- 遅行指標: スケジュールスキャンが見つけた脆弱性 vs 本番や外部報告で見つかった脆弱性、**複数回スキャンしたリポジトリでのスキャンあたり発見数の推移**（修正と eval が積み上がるにつれ下がるはず）

### 9-4. プレイ③: Claude Tag によるオンコール

インシデントは Slack や Teams のような**職場コミュニケーションアプリ**経由でも到着します。「夜10時のインシデントチャンネルへの緊急修正依頼」も**即座に着手できるようになります**。

**Claude Tag**（Slack でパブリックベータ）は、**Claude をそれらのチャンネルの、独自アイデンティティを持つメンバーにします**。

これにより:
- **新しいインシデントごとに第一対応者がつく**
- **対応そのものがループの一部となり、将来のインシデントのための記憶になる**
- 会話と組織知が**チャンネルに残る**
- **チャンネルにいる誰もが対応を導き、行動できる**
- 誰でもリアルタイムに仮説を検証し、新しい選択肢を探り、調査できる。**チャンネル履歴が監査性を高める**
- MCP 経由で Claude は**メトリクスがベースラインに戻ったことを検証し、スレッドで確認する**
- **ポストモーテムをバージョン管理された「教訓ファイル」に書き**、将来の調査がそれを読める

インシデント以外も同様: MCP 経由でチケットにタグ付けされたり、チャンネルで依頼されたりすれば、Claude は同じようにトリアージする。**小さく境界の明確な修正はPRとしてレビューゲートを通り、それより大きいものは `intent.md` として書き上げられ Stage 1 へ**。

> **チャンネルが監査証跡になる。依頼、診断、人間の認可、修正のすべてが、インシデントが処理された場所に残る。**

## 10. 横断的な仕組みのまとめ

### 10-1. 成果物（Markdown ファイル群）

| ファイル | ステージ | 誰が書く | 誰がレビューする | 役割 |
|---|---|---|---|---|
| `intent.md` | Plan | 発案者 + Claude | プロダクトオーナー | **何が欲しいか・なぜか・制約** |
| `spec.md` | Design | Claude（skill制約下） | プロダクトオーナー | **要件と設計** |
| `plan.md` | Build | Claude（プランモード） | エンジニア | **変更ファイル・順序・テスト・リスク** |
| `CLAUDE.md` | Build（常設） | チーム全員 | コードオーナー | **エージェントの基礎知識** |
| `SKILL.md` | Build（常設） | エンジニア | ポリシー所有者 | **一貫適用すべき組織ポリシー** |
| `REVIEW.md` | Deploy（常設） | テックリード | — | **レビューポリシー** |
| `bands.yaml` | Maintain（常設） | サービスオーナー | — | **異常検知と対応ティア** |

### 10-2. コントロールの3層

これが記事の設計思想の核心です。

| 層 | 手段 | 性質 | 破れるか |
|---|---|---|---|
| **助言層** | `CLAUDE.md`, skill | **確率的**（probabilistic） | **破れる**。従う可能性を高めるだけ |
| **強制層** | hook, permissions, sandbox | **決定論的**（deterministic） | **破れない**。マッチすれば必ず動く |
| **人間層** | ブランチ保護、コードオーナー承認、リリース認可 | **判断** | 人間が責任を負う |

**原則**:
- **必ず守られるべきポリシーには、助言層だけでなく強制層を必ず置く**
- **人間層はゲート（成果物の受け入れ、本番リリース）に集中させ、途中経過には置かない**（並列セッションのクリティカルパスに人を戻さないため）

### 10-3. skill / hook / subagent / CLAUDE.md の使い分け

| | 何か | いつ使う |
|---|---|---|
| **CLAUDE.md** | リポジトリの基礎知識。毎セッション読まれる | 規約、コマンド、アーキテクチャ、頻出ミス。**1ページ以内** |
| **Skill** | 条件付きで発火するポリシー指示 | **一貫して適用すべき組織知**。ブランド、セキュリティ標準、API設計規約 |
| **Hook** | アクション前に走るスクリプト。allow / ask / block | **例外を許さないルール**。保護パス、認証情報、本番ゲート |
| **Subagent** | 独立コンテキストのスコープ限定ヘルパー | **複数タスクで繰り返される仕事**。検証、簡素化、調査 |

### 10-4. 監査証跡はどこにあるか

| 証拠 | 場所 |
|---|---|
| 誰が何を依頼したか | `intent.md` の git 履歴（著者・タイムスタンプ） |
| 何が決められたか | `spec.md` + 適用された skill のバージョン + 生成プロンプト |
| どう作る計画だったか | `plan.md` とその改訂 |
| 何が検証されたか | テスト出力、ビルドログ、スクショ差分（**ツールチェーン由来**） |
| エージェントが何をしたか | セッショントランスクリプト → OpenTelemetry → 可観測性基盤 |
| ゲートの判断 | フックの allow/block ログ（タイムスタンプ付き） |
| 誰が承認したか | PR履歴、ブランチ保護、マージ |
| インシデント対応 | Slack チャンネル履歴、教訓ファイル、eval |

## 12. 導入順序と理解度チェック

### 12-1. 前提条件がない（＝すぐ始められる）プレイ

原文の依存グラフより、**前提条件「なし」のプレイ**:

- `intent.md` として捕捉する（Stage 1）
- `CLAUDE.md`（Stage 3）
- 組織知としての Skill（Stage 3）
- Claude にフィードバックループを与える（Stage 4）
- 承認ゲートとしてのフック（Stage 5）

### 12-2. 依存関係の主な線

```
CLAUDE.md ──┬─→ 並列セッション/サブエージェント
            └─→ 継続的eval ←── フィードバックループ

intent.md ──→ 要件と設計(spec.md) ──→ プランモード(plan.md)
                                            ↓
CLAUDE.md ──────────────────────→ PRレビューループ
                                            ↓
承認ゲートとしてのフック ──────────→ CI/CD統合
                                            ↓
                                     ループを閉じる
                                     （+ intent.md が必要）
```

🔰 **現実的な最初の3つ**（技術的難度が低く、効果が見えやすい順）:
1. **`CLAUDE.md`** — `/init` して削るだけ。前提なし、すぐ効く
2. **フィードバックループ** — `make test` に包んで `CLAUDE.md` に書くだけ
3. **`intent.md`** — 非エンジニア側の変化。組織的な合意が必要な分だけ重い
