## 1. 工程が複雑（総論の具体）

**いま A に6手、B に2手＋4手、C に4手ある。** 説明に資料が23KB要る時点で、研修生には渡せない。

| | いま | 方向 |
|---|---|---|

| **B** | B-1 ＋ B-2 の4手 | 4手は skill / `CLAUDE.md` 側に埋める（指摘6）。**研修生から見える手数を減らす** |

## 2. A は「決める」ではなく「入力を整える」★最大の変更

### 言われたこと

- **A の題名が分かりにくい。「input を整える」に変える**
- **「ドキュメントのブラッシュアップ」という言い方のほうが伝わる**
- **配られたものを「確認」→「更新」の2手にする**
- **欲しい output は、渡したものを精緻化したもの**（input の精緻化版が output）
- **4区分（記載あり／自己判断／要確認／未着手）の仕分けは要らない。「要確認」のリストで足りる**

### 何が変わるか

| | いま（A 決める） | これから（A input を整える） |
|---|---|---|
| **研修生がやること** | AIに未決事項を挙げさせ、**4区分に仕分ける** | **配られたものを確認し、AIに渡す最終形に更新する** |
| **成果物** | `docs/仕様確定.md`（§1確認事項・§2決定事項・§3受入条件） | **精緻化された入力一式**（＋要確認リスト） |
| **やり方** | **手順で指定**（A-1〜A-6） | **任せる。**研修生ごとに違ってよい |
| **評価** | 成果物を出したか／仕分けが妥当か | **アプローチの妥当性を議論して評価**（指摘3） |

**「課題で配られるもの」と「AIに最終的に渡すもの」を分けるのが芯。**
**その2つの差分を作る作業が A** であり、差分の作り方は無数にある。

### ★ output の置き場 — ✅ 配布した設計書に書き戻す（2026-09-01 決着）

> **配布した設計書に書き戻す。最終的に実装と設計がずれたら困るので、設計書を直すのがいい。**

**これで A・B・C が1本に通る。** 全段が同じ動作になる。

| 段 | 何が起きたら | どこに書き戻すか |
|---|---|---|
| **A** | 矛盾・未決を見つけ、仕様管理者に聞いて答えが出た | **設計書** |
| **B** | 実装が設計から逸れた | **設計書**（＋上位者へ上げるか判断） |
| **C** | B で書き漏らした逸脱を拾った | **設計書**（判断できないものは要確認に戻す） |

**「配られた設計書」と「最終的に渡した設計書」の差分 ＝ A の成果物。**
**差分は `git diff` でそのまま見える。**議論の材料が機械的に取り出せる。

### ⚠ この決定で壊れるもの

| | いままでの前提 | どうなるか |
|---|---|---|
| **`todo-app-api-docs/`** | **読むだけ・書き換えさせない**（上流の資産だから） | **書き換える。**「実装と設計をずらさない」が勝つ |
| **別リポジトリにした理由** | 「実務でも設計書リポにPRを出すのは別プロセス」 | **この理由は消える。**分離は残してよいが、根拠を書き直す |
| **`docs/仕様確定.md` §2決定事項** | 決めたことを書く節 | **設計書に溶ける。**節ごと不要になる可能性 |

### 未決 — 残っているもの

- **§3受入条件をどこに持つか。** 設計書に「受入条件」の節は普通ない。**C-2 の作業リストの出所なので、消すと C が立たない**
- **§1確認事項（まだ決まっていないもの）の置き場。** 設計書には書けないので、`仕様確定.md` が要確認リスト専用として残る形か
- **入力を「精緻化」した結果、研修生ごとに B の難度が変わる。** 揃えなくてよいか

## 3. アプローチを議論して評価する

> **やり方を問う必要はない。欲しい output に揃えるためにどうアプローチしたかを、研修生に議論させる。**
> **A は丸ごと、output の評価ではなく、そこに至ったアプローチの妥当性を議論して評価される。**

**「添削はしない／評価はする／議論はする」**（`06_研修の芯` 設計原則2）の議論が、**C だけでなく A にも来る**ということ。

### 芯（06）との衝突 — ✅ 書き換えで決着（2026-09-01）

`06_研修の芯.md` の「軸にしないもの」と衝突していたので、**芯を書き換えた**。

| | 書き換え前 | 書き換え後 |
|---|---|---|
| **コンテキストの与え方** | **経験の中で自得させる。教える項目にしない** | **表から外した。A の主題そのもの** |
| **プロンプトの工夫** | **講師が配る。研修生に考えさせない** | **技法のカタログは教えない。渡すものの組み立てとして A で扱う** |
| **A の名前** | **A 決める** | **A 入力を整える**（構造の図・到達した状態の表も差し替え） |

**「教えない」のではなく「手順では教えず、議論で扱う」に変わった。**

## 4. 模範解答的なアプローチを用意する ★新規タスク

> **アプローチはたくさんあるが、研修としては模範解答的なアプローチを用意しておく必要がある。**
> **参考: <https://claude.com/blog/the-ai-native-sdlc-playbook>（自分で読んで作る）**

### ★これは「答えを配る」ではない（2026-09-01 確認）

> **示すのは、研修生が自分のやり方でやりきったあと。** だから**答えを与えるのとは違う。**

| | |
|---|---|
| **示すもの** | **唯一の正解ではなく、アプローチの一例** |
| **示すタイミング** | **本人が自分のやり方を出しきったあと**。事前に配ればなぞるだけになる |
| **何のために示すか** | **自分のやり方と比べる材料。**比較があって初めて議論になる |

**`06_研修の芯.md` 設計原則2「答えを配らない」は破っていない**（同原則に追記済み）。

### 決めること

| **⚠ 経路** | `03_研修環境とガードレール.md` §8 の「模範解答への経路が構造的に開く」に該当する。**リポジトリに置かない** |

| | いま | これから | 状態 |

## 7. セルフレビューは PR 上でやる

> **AIに対してのレビューは GitHub で PR を作り、そこでセルフレビューする形にしよう。**

- 2か月目で PR とレビューは既習 → **新しく教える技術がゼロ**（設計原則5と整合）
- `検証記録.md` の一部が **PR のコメントに置き換わる**

### ★ AI に GitHub を見せない — リモートは C で足す（2026-09-01）

**⚠ 問題:** `検証記録.md` は「**AIに渡さない**」ために repo 外に置いていた。
**PR コメントに書くと、AI から見える。**

**対処の方針（2026-09-01）:**

> **作る段階（B）で見えなければよい。リモートはあとで足す。**

| 段 | リモート | AI から見えるもの |
|---|---|---|
| **A・B** | **無し（ローカルのみ）** | **GitHub は見えない** |
| **C** | **ここで `git remote add` して push → PR** | PR は見えるが、**もう実装は終わっている** |

**これは `03_研修環境とガードレール.md` §8 の対策E（origin を外す）の改良版。**
**E の難点「PR提出の動線が壊れる」は、「あとで足す」なら起きない。**
**§8 本体（`answer-sample` ブランチへの経路）も同時に塞げる。**

**未決: C-4（別セッションでAIにレビューさせる）と PR セルフレビューの順序。**
**セルフレビューのコメントを AI に見せたくないなら、C-4 を先にやる。**
