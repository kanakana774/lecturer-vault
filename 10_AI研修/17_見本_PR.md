# 見本: PR に何を残すか

**3つに分ける。**

| どこに | 何を | 読み手 | 実務か |
|---|---|---|---|
| **① PR 本文** | 概要・背景／変更点／確認したこと／判断を仰ぎたいこと | **レビュアー** | **実務どおり** |
| **② PR のコメント** | AIレビューの指摘と仕分け | **レビュアー** | **★研修の都合。**実務ではボットが自動で残す |
| **③ `振り返り.md`** | アプローチの記録・気づき・網羅の宣言 | **自分と講師** | **★研修の都合。**実務では書かない |

---

## ① PR 本文

```markdown
## 概要

Todo と Tag の CRUD を実装しました。Tag 5本 → Todo 4本の計9エンドポイントです。
（Tag・Todo の1件取得は `main` に参照実装として既存）

## 背景

設計書どおりの実装です。着手前に未決・矛盾を12件確認し、回答を設計書へ書き戻しました
（`todo-app-api-docs` 側の差分・`確認事項.md`）。

## 変更点

- 45ファイル / +3007行
- **実装**: Tag 一覧取得・登録・更新・削除 ／ Todo 一覧取得・登録・更新・削除
- **テスト**: 10クラス / 89件（Controller層の統合テスト）
- **設計書**: 確認事項12件を反映（別リポジトリ）
- コミットはエンドポイント単位で9本。Tag を先に実装し、削除のトランザクションの型を
  Tag で確立してから Todo に転用しています。

## 確認したこと

- **`mvn test` / `mvn checkstyle:check` が緑。**89件。
- **ケース一覧69件とテストの対応を確認し、欠けていた3件を足しました。**
  - **削除時の紐づき解除が、テストで検出できていませんでした。**
    `TodoService.delete` から `deleteTodoTagsByTodoId` を1行消しても、当時の79件が全て緑のまま通る状態でした。
    正常系が紐づきなしの Todo しか消しておらず、FK に当たらないためです。紐づきありの削除テストを追加しました。
  - **部分一致検索で `%` `_` をエスケープしていませんでした。**`?title=%` で全件返ります。修正とケース追加。
  - **Tag を2件以上持つ Todo での `limit` のケースがありませんでした。**JOIN後の行数に `limit` がかかる
    誤りを検出できないためです。ケース追加。
- **触った範囲は `実装計画.md` の「変更するファイル」と一致しています。**想定外の変更はありません。
- **DoD 9項目を一巡しました**（N+1・層構成・`SELECT *`・トランザクション境界 ほか）。
- **非機能は、性能・セキュリティとも本課題の範囲外として見ていません**（`CLAUDE.md` の前提）。
  並行性のみ、楽観ロックの範囲で確認しています。

## 判断を仰ぎたいこと

- **TOCTOU**: 存在チェックと UPDATE / DELETE が別クエリのため、競合時に本来404を返すべき場面で
  409 が返る余地があります。仕様上の想定を確認したいです。
- **DELETE の `@RequestBody`**: 楽観ロックの version をボディで受けています。プロキシや
  ゲートウェイがボディを落とす構成があるため、設計の確認をお願いします。
- **画面遷移図との不整合**: 「修正するので気にしないで」との回答をいただいたため、未対応です。

## AIの利用

実装は Claude Code で行い、各コミットにトレーラーを付けています。
テストは実装前に書かせ、失敗を確認してから実装しています。
```

**この4欄は実務どおり。**AIで重くなったのは「確認したこと」で、**緑であることが根拠にならない例を1つ出せるかどうか**が中身の差になる。

## ② PR のコメント — AIレビューの指摘と仕分け

**本文ではなくコメントとして自分で貼る。**実務ではボットの指摘がスレッドに残るので、形を合わせる。

```markdown
別セッションの Claude Code に `gh pr diff` を読ませてレビューさせました。4件、いずれも正しい指摘です。

| 指摘 | 判定 | 処置 |
|---|---|---|
| TOCTOU で本来404が409になる余地 | 正しい | **直さない。**仕様の判断が要るため本文に上げた |
| Tag存在チェック(404)が楽観ロック(409)より先。優先順位が未検証 | 正しい | 逸脱ではないが、**順序を固定するテストを追加** |
| DELETE に `@RequestBody` | 正しい | **直さない。**設計の話として本文に上げた |
| `limit=abc` のような型不正が未検証 | 正しい | **ケースを追加** |

自分のレビューで出た3件は本文「確認したこと」に反映済みです。
```

**「直さない」にも処置が書いてある状態で終わり。**「正しい」を全部直した、ではない。

## ③ `振り返り.md` に回したもの

**実務では書かないが、評価には要るもの。**

- **数え**: 自分だけ **3** ／ AIだけ **4** ／ 両方 **0** ／ 的外れ **0**
- **AIが触れなかったもの**: **`%` `_` のエスケープに一言も触れなかった。**差分に4箇所あり、3352行を最後まで読んだうえで。
  さらに「境界値テストの網羅性は問題なし」と締めくくった。**穴がそこにあるのに。**
  → **設計書を渡していないので、仕様として決めたことには届かない。**
- **アプローチの記録**: 未決はAIに列挙させて出した／ケース一覧は別AIにレビューさせた（7件中3件対応、
  残り4件を捨てた理由が残らなかったのが反省）
- **自分で確かめた範囲の網羅宣言**: 上記のどこまでを自分の観測で決着させ、どこから他人の同意が要るか

**`振り返り.md` はAIに渡さない。**渡すと問いへの答えを作られる。
