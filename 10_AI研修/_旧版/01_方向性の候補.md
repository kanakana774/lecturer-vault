## 0. 先に、全案に共通する事実

### 単発1週間は「定着しない」のが定石

最頻の失敗パターンは「試して微妙な結果 → AIってこんなもんか → 離脱」。**研修→実務→振り返りのサイクルが回らないと定着しない**というのが複数の報告の共通見解。ツールを配って構造化された学習がないと、受講者はパワーユーザー10-15% / 実験者30-40% / 懐疑派40-50% に分かれ、大半が定着しない。

→ **どの案を選んでも、1週間で閉じない設計にする必要がある。**配属後のフォロー（振り返りの場、報告会での言語化など）をセットにするか、少なくとも「1週間で完結しない」ことを社長と合意しておく。

### 「速くなるが賢くならない」という実験結果

奈良高専の比較実験（生成AI利用群 vs 教科書利用群）では、**タスク完了時間は短縮したが理解度テストの成績に有意差はなかった**。これは (b) 技術力向上を1週間の研修に期待できない根拠であり、同時に**研修の教材そのものにも使える**（「速くなることと分かることは別」を最初に示す）。

### ジュニア育成モデルの崩壊という論点

「コードを書いてレビューで直されて学ぶ」というジュニア育成の基本モデルが、AIがコード生成とレビューの双方を担うことで消えつつある、という指摘がある。**御社の3か月カリキュラムはまさにこのモデルで成り立っている**ので、AI研修の設計はこの問いと無関係ではいられない。

## 案A: 検証・レビュー型 ―「足りないものが分かった」

> **2026-08-06 改訂**: 「ゼロから作らせて欠陥を探す」から **「既存プロジェクトの枠に実装させ、既存の規約に合っているかを検証する」** に変更。理由は下記。

**一言**: 既存プロジェクト（`develop` の枠）にAIで実装させ、**既存の規約・設計に合っているか**を自分たちのレビュー観点で検証する。

### なぜ「既存プロジェクトへの実装」が正しいのか

1. **研修生は3か月を通してゼロからアプリを作らない**（`MyWork/03_研修カリキュラム.md` §0）。`develop` から clone して枠を埋める形。研修の形が既に実務を模している
2. **SES・受託の実務は圧倒的に既存コードへの追加・修正**。新規プロジェクトの立ち上げは稀で、新人が任されることはまずない
3. **AIが最も苦手なのは「既存の規約と設計に合わせること」。** ゼロから作るのはAIの得意領域。P1 の実験で、ゼロからなら破綻なく書けるのに**既存のエラーハンドリング機構を無視して `@RestControllerAdvice` を自作した**ことが確認できた（§4.1 → `02_実験`）
4. → **実務で必要な能力＝AIが苦手な領域＝人間が価値を出せる領域**が一致する
5. **業界の実際のAI活用も同じ方向**。DeNA の Devin はレガシーコード刷新とコードマイグレーションが主用途、富士通は COBOL 設計書の自動生成。**新規開発ではなく既存コードへの適用が主戦場**
6. **副次効果**: 規約に合っていれば**研修生が読めるコードになる**。「AIの出力が未習の書き方で読めない」という問題が構造的に解決する

### 評価軸が○×で作れる（重要）

「既存の規約に合わせられたか」はチェックリストで判定できる。

- `core/exception` の既存機構を使ったか、自作したか
- 7層構成（controller / entity / form / logic.service / mapper / query / queryCondition）に従ったか
- 未習の機能（record / Lombok / Stream / PATCH）を使っていないか
- Javadoc を書いたか
- Spring Boot のバージョンを合わせたか

→ **「何をもって研修を受けたとするか」という評価設計の悩みが、これで解ける。** 曖昧な「AIを理解した」ではなく、測れる形になる。

### P1（ゼロから作らせる）は捨てず、導入のデモに使う

「ゼロから30分でこれが出る」という衝撃は導入として強力。ただし**研修生にやらせるのではなく講師が実演して見せる**。初日に「AIはゼロからならこれを30分で作る。しかし我々の現場は違う」と繋げれば、その後の既存プロジェクト演習の意味が立つ。

> 将来的に自社サービスや受託に寄るなら「AIで新規開発」の体験も要るが、**1週間では両方入らない。目先SESなら既存優先。**

**5日のスケッチ**（2026-08-06 改訂・既存プロジェクト起点）

| 日 | 内容 |
|---|---|
| 1 | **導入**: 講師が実演 — 何も渡さずAIに Todo API を作らせるとどうなるか（**30分で破綻なく作る／だが既存のエラーハンドリング機構を無視して自作する**）。「速くなることと分かることは別」（奈良高専の実験）を提示。続けて**AIの確率的性質＝なぜ間違えるか**と利用ルール（案Cの1日分）をやってから**解禁** |
| 2 | **`develop` の枠にAIで実装させる**。設計書を渡し、既存コードを読ませる。「既存の規約に合わせられるか」を自分の手で体験する |
| 3 | **出力を規約チェックリストで検証**。`core/exception` を使ったか／7層に従ったか／未習の書き方（record・Lombok・Stream）が混ざっていないか／Javadoc／バージョン。CheckStyle・SonarLint も通す |
| 4 | **自分が2か月目に書いたコードと並べる**。同じレビュー観点を両方に当てて「**どちらも間違える**」を体感。さらに**動かして**「動くけど間違っている」を探す（例: POST のレスポンスと直後の GET で `createdAt` が一致しない） |
| 5 | 成果発表。「**AIに任せてよい範囲／自分が担保する範囲**」＋「**既存コードベースにAIを使うとき、何を渡せば規約が伝わるか**」を各自の言葉で提出 |

**持ち帰るもの**: **自分で書いた「AI向けプロジェクト指示ファイル」**（下記）／任せる・担保するの線引き／既存コードベースへのコンテキストの与え方

### ★成果物は「AI向けプロジェクト指示ファイル」にする（2026-08-06 追加）

実務でAIに渡すコンテキストの本命は、**プロジェクト直下の指示ファイル**（`CLAUDE.md` / `.cursorrules` / `.github/copilot-instructions.md`）。技術スタック・層の責務・使ってよいライブラリ・禁止事項・SQLの方針を書く。**「コンテキストエンジニアリング／ハーネス」の実体がこれ。**

**これを研修生に書かせるのが、案Aの成果物として最も筋が良い。**

| なぜ | |
|---|---|
| **実務でそのまま使える** | 配属先でAIが許可されていれば、最初に書くもの。研修の成果物が現場の成果物と同じ形になる |
| **既存コードベースの理解が前提** | 層の意味・既存機構・規約を分かっていないと書けない。**3か月の学習の上にしか build できない** |
| **陳腐化しにくい** | ファイル名（`CLAUDE.md`/`.cursorrules`/…）は変わってもコンセプトは残る |
| **評価が客観的** | 書いたものを渡して**AIの出力が実際に改善したかで測れる**。「AIを理解した」という曖昧な評価にならない |
| **AIが使えない現場でも無駄にならない** | 中身は「自分たちの設計と規約を言語化したもの」なので、人間の新規参画者向けオンボーディング資料としても機能する |

> **講師側の検証がそのまま教材になる。** P3 の実験で講師が書いた `todo-app-api-develop/CLAUDE.md` が、**模範例としてそのまま使える**（`02_実験` §2）。研修生には「これを自分で書いてみろ」と出せる。

**演習の組み方**: Day 2 で指示ファイル**なし**で実装させ（＝P2b の再現）、Day 3 で欠陥を見つけ、**Day 4 で指示ファイルを自分で書いて再実行し、欠陥が減るかを確認する**。書く→効果を測る→直すのループが1週間に収まる。

> **Day 1 の実演素材は P1 の実験結果がそのまま使える**（`02_実験_プロンプト差の検証.md` §4.1）。Day 3・4 の検証素材は P2・P3 の結果が使える。**実験がそのまま教材になる。**

**効き**: a=◎（面接で語れる具体が残る） b=○（入口として強い） c=◎（他社にない中身）

**講師の習得コスト**: 中（最小セット1〜2日 ＋ 欠陥カタログ作成2〜3日）。**既存のレビュー観点資料が下敷きになるのでゼロからではない**

**作成コスト**: 初回=中。毎期=**小**（課題とレビュー観点は既存資産。AIの出力だけ毎期取り直す）

**陳腐化耐性**: **高**。ツールが変わっても「出力を検証する」型は変わらない

**外部委託**: **不可に近い**。自社の3か月カリキュラムとレビュー観点を知らないと作れない＝**内製の意味が最も大きい**

**客先でAIが使えなくても残るもの**: レビュー眼。むしろAIなしの現場でも効く

**リスク**（2026-08-06 更新）:
- **旧リスク「AIが上手く解きすぎて研修生が無力感で終わる」は、既存プロジェクト起点にしたことで大幅に下がった。** AIは**既存の規約に合わせるのが苦手**なので、必ず粗が出る。P1 で既に確認済み（既存のエラーハンドリング機構を無視して自作した）
- 残るリスクは①**規約違反が自明すぎて演習が退屈になる**（「Lombok 使ってるね、はい終わり」）→ 動かして見つかる欠陥（`createdAt` の不一致など）を Day 4 に置いて深さを担保する ②Day 2 でAIが規約をきれいに守ってしまうと Day 3 の検証が薄くなる → **P2 の実験結果を見てから Day 2 の条件（何を渡すか）を決める**

**参考**: freee（AI禁止フェーズ→AI活用フェーズの対比構成）、演習型「AI生成コードの欠陥探し（4観点）」、LINEヤフーコミュニケーションズ（触らせる前に「なぜ間違えるか」→ Day 1 に採用）

## 現時点の推奨

**A を軸に、C を1日分だけ組み込む**のが、制約に対して最も無理がないと考える。

理由:
1. **講師の未経験という最大の制約に耐える**。既存のレビュー観点資料が下敷きになり、講師の習得コストが中で済む
2. **毎期の作り直しコストが小さい**（陳腐化するのはAIの出力だけで、課題とレビュー観点は既存資産）
3. **内製の意味が最も大きい**。自社の3か月カリキュラムを使うので他社には作れず、それがそのまま (c) プロモの中身になる
4. **AIが使えない配属先でも残る**ものがある。金融系の調査結果を踏まえると、これは軽くない

**B は積極的に外部委託を検討する価値がある**。準備2か月・本業並行で毎期更新を回すのは現実的でなく、かつ配属先で使えない確率が高い。

**D は魅力的だが、今回は見送って将来の拡張候補**にするのが妥当。陳腐化耐性は最高だが、講師の習得コストと「新人に上流は早い」という反論に、2か月では応えきれない。
