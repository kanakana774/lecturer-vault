# 通しの流れ

## 目的

> ### AIに書かせたコードの品質を、自分で担保できるようにする。

対象は**3か月目の新人**。題材は**2か月目と同じ Todo API**（Java 21 / Spring Boot 3.4.1 / MyBatis）。
**実装するのはAI。研修生がやるのは、コンテキストを整えて、委任して、検証すること。**

## 全体

```
【前提】 ガバナンス ── 理解度テストに合格 → 本編

【本編】
  入口（自分）        →      中（AI）      →     出口（自分）
  A 入力を整える            B 任せる           C 確かめる
   （半日）                 （半日）           （半日）
```

**テストが79件あって全部緑、はそのままでは根拠にならない。****何をもってそう言えるのか**——そこを見る。

> [!note]- ★模範アプローチ: 敵対的にテストを検査させる（ミューテーションテスト）
> **実装を機械的に変異させて、テストが落ちるかを見る手法。**「テストのテスト」。
> **Java の定番ツールは PIT（pitest）**だが、**`pom.xml` に依存を足すことになる**ので課題の前提と衝突する。
>
> **→ 別セッションのAIに探させる。**道具を増やさずに同じことができる。
>
> > **`src/main/` の実装を1箇所だけ書き換えて、`mvn test` が緑のまま通る変更を探してください。**
> > **実際に書き換えて `mvn test` を実行し、緑のままだったものだけ報告してください。**
> > **1件ごとに、どのファイルの何行目をどう変えたかを示すこと。**
> > **終わったら `git checkout .` で戻し、`git status` がクリーンなことを確認してください。**
>
> **⚠ 最後の1文が要る。**壊したまま放置されると次に進めない。
>
> **★講師は1回実演する。**試走では `TodoService.delete` から `deleteTodoTagsByTodoId` を**1行消して79件すべて緑のまま**だった。
> **「79件全部緑なのに壊れている」を全員が同時に見る**ほうが、各自でやるより効く。

> [!warning]- リモートは講師が足す。AIには触らせない
> **`gh` を全面的に許すと、org のリポジトリが全部見えます。**2か月目の `todo-app-api` には
> **21人分の完成ブランチと `answer-sample`** があるので、**これが一番危ない経路。**
>
> | | |
> |---|---|
> | **deny のまま** | `gh repo` / `gh api` / `gh search` / `gh browse` ／ `git remote` `git fetch` `git clone` |
> | **allow** | `gh pr diff` / `gh pr view` |
> | **ask** | `git push` / `gh pr create` |
>
> **リモートを足すのは人の作業。**研修生の端末に、org 全体に届くトークンを置かない。
>
> **★リポジトリは期ごとに作り直す。** **GitHub は PR を削除できない**ので、
> ブランチを消しても**過去のレビューのやりとりは残る**。研修生ごとには増やさず、**年1本。**
>
> **★講師の評価コメントはPRに書かない。**口頭にする。**残すと模範アプローチが期をまたいで流出する。**
>
> **★レビューはローカルの Claude Code に `gh pr diff` を読ませ、結果を自分でPRに書く。**
> GitHub Actions で動かすと **API の従量課金**が要る（サブスク枠で動くかは公式に記述が無い）。
> **ローカルなら研修生のシートで動き、追加費用ゼロ。**やることは実務と同じで、違うのは実行場所だけ。

> **★模範アプローチの一例:** **一覧を作るところまではAIにやらせ、判断は自分でする。**
> C-1 の対応表は**機械的な突き合わせ**なので、人が目で追う価値が薄い。
> **⚠ ただし別セッションで。**実装したセッションには「自分が何を変えたか」が残っているので、
> **実際に見ずに記憶で答える**ことがある。**生の出力を並べて出させる。**

### C-3 — 指摘を受けて、直して、また見せる

| 判定 | 処置 |
|---|---|
| **正しい** | **直す → コミット → push → 再レビュー。**★直すときも **B の4手**（テストを書く → 赤 → 実装 → 緑）|
| **的外れ** | **理由を書いて閉じる。**直さない |
| **判断できない** | **★消さない。行き先を決める**（下記） |

**「判断できない」の行き先は2つ。**

| | どこへ |
|---|---|
| **仕様が決まっていない** | **`確認事項.md` に1行**（「いつ」＝`確認時`）→ **仕様管理者へ。**答えが出たら設計書に書き戻す |
| **技術的に分からない** | **調べる。**それでも分からなければ**そのままPRに書いて、レビュアーに上げる** |

> ### ★「判断できない」を消す必要はない。そのまま出すのが正しい。
> **分かったふりをして閉じるほうが悪い。**

**★再レビューは1周で切る。** 2周目に出た新しい指摘は**仕分けるだけで、対応は任意。**

> **Claude Code の Code Review が、既知のノイズ源としてこう挙げている** ——
> **「nit が無限に積み上がる／再レビューのたびに新しい nit が増える」。**
> **収束しない。どこで切るかは人が決める。**

**終わりの条件: 3分類すべてに処置が決まったら終わり。**
**「正しい」を全部直した、ではない。**——**直さないと決めて理由を書いた**ものも、処置済み。

**★C-3 は検証ではなく、A の答え合わせ。** **「AIだけが見つけた」ものが、A で渡し漏れた情報**を指す。

**⚠ C-2 が先。** AIの指摘を先に読むと、**AIが指した場所しか見なくなる**（実測されている）。
**自分が見つけたものと、AIだけが見つけたものの差**が、そのまま議論の材料になる。

**⚠ AIレビューは検証手段に数えない。** 同じ資料を読むので同じ誤読をするし、**渡していない情報は原理的に見えない**。
**ただし拾い漏れの受け皿にはなる。**

> [!warning]- 実測: 人とAIで、見つけたものの重なりがゼロだった（2026-09-11・試走）
> | | 件数 |
> |---|---|
> | 自分だけが見つけた | **3** |
> | AIだけが見つけた | **4** |
> | **両方が見つけた** | **★0** |
> | 的外れ | **0** |
>
> **人は「仕様との対応」を見ていた**（裁定した内容・ケース一覧・fixture の中身）。
> **AIは「コードの構造」を見ていた**（並行性・HTTPの作法・入力の型）。**見ているものが違う。**
>
> **⚠ AIは、A で裁定した `%` `_` のエスケープに一言も触れなかった。**
> 差分に4箇所あり、**3352行を最後まで読んだうえで**。**設計書を渡していないので、仕様として決めたことには届かない。**
>
> **⚠ さらに「境界値テストの網羅性は問題なし」と締めくくった。**——**穴がそこにあるのに。**
> **「指摘が無い」ではなく「問題ない」と書く。**誤った安心を与える。

> [!note]- 実務の形に合わせた（2026-09-10・調査）
> **PR上にAIがコメントを残し、人が見ながらレビューする。**これが実務の標準形で、**調べた事例は全部「AIが先、人が後」**だった。
> 履歴がPRに残るので、**仕分けはコメントへの返信になる**。GitHub には `Addressed / Won't fix / Incorrect` を選ぶ機能まである。
>
> **★研修だけ「自分で先に見る」を1手足している。**
> **AI生成レビューを先に渡すと、レビュアーはAIが指した箇所しか見なくなる**（ICSE 2025・プロ29名の統制実験）。
> **低深刻度の指摘は増えるが、高深刻度の発見は増えず、時間も短縮しない。**
> Meta も同じ現象を実測し、**AIの指摘を著者だけに見せる**設計に変えて解消した。
>
> **実務では型が2つある。**「AI一次 → 人が最終判断」と、「**著者がAI指摘を全部潰してから人間レビューを依頼する**」。
> 後者では**人間レビュアーはAIの指摘を見ない。**研修生＝著者、講師＝レビュアー、と読み替えるとこの形になる。
>
> **⚠ 配属先にAIレビューがあるとは限らない。** コードレビュー工程でのAI活用は**23.7%**（Findy調査・回答873名・2026-04）。
> **だから C-2 が要る。**道具は `mvn test` と `git checkout` だけで、どこでも回る。

### なぜ自分の目で読ませるのか

**人の手抜きは荒れて見えるが、AIの取り違えは自然で一貫して見える。**
**「読んで違和感がない」は、正しさの証拠にならない。**

**だから「テストが79件あって全部緑」も、そのままでは根拠にならない。**
**★何をもって「効いている」と言えるかを、自分で示す**——それが C の中身。

**提出物: PR（コードレビュー・AIの指摘・仕分けが書かれている）**

## 評価

| | 測り方 |
|---|---|
| **ガバナンス** | **理解度テスト。合格が必要** |
| **A** | **アプローチを議論する。**成果物の正しさは測らない |
| **B** | 逸れた箇所を全部上げたか（`確認事項.md` の「いつ」が `実装中` の行） |
| **C** | **PR を読んで、議論を返す** |

**添削はしない／評価はする／議論はする。**

### ★ 先に、問いに答えてから来る

**C が全部終わってから、自分で書く。**AIには書かせない。

| | 問い |
|---|---|
| **1** | **AIが仕様に無いことを独自に決めた箇所はどこか。それは正しいか** |
| **2** | **設計書と違う実装になっている箇所はあるか。**違反か、正しい最適化か。**誰が決めてよいことか** |
| **3** | **外に出してはいけない情報が出ていないか** |
| **4** | **動いた。では正しいと言える根拠は何か** |
| **5** | **どこまで自分で確認し、どこから仕様管理者に問い合わせるか。なぜそこか** |

**正解は無い。講師も答えを持っていない。**

**★C の最後ではなく、評価の入口に置く。** **AIの指摘も材料に入る**ので、
**全部出そろってからでないと答えられない**（試走では順番が逆で、書き足す形になった）。

**★拾った逸脱は、設計書と `確認事項.md` に自分で書き足してから来る**（「いつ」列は `確認時`）。

### 議論の材料は数として出る

| A が甘いと | どこに出るか |
|---|---|
| **入力の確定が甘い** | `確認事項.md` の「いつ」が `実装中` の行が増える |
| **ケース一覧が甘い** | 根拠の書けないケースが残る／`確認事項.md` に戻せていない |
| **渡し漏れがある** | **C-3 で「AIだけが見つけた」が増える** |

> [!warning]- 「的外れの数」は指標にならなかった（2026-09-11・試走）
> **以前は「C-4 の『的外れ』の数＝A で渡し漏れた情報の量」と書いていた。**
> **試走では的外れが 0件。**設計書を渡していないのに、**AIが仕様に踏み込む指摘をしなかった**ため。
>
> **代わりに効いたのは「AIが触れなかったもの」。**——A で裁定した `%` `_` のエスケープに一言も触れなかった。
> **「出たもの」より「出なかったもの」のほうが情報だった。**

**議論のあとに、模範アプローチ（一例）を示す。** 事前に配ればなぞるだけになる。
