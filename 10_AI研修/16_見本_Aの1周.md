## ② 突き合わせ — 14件

**⚠「推測で埋めないで」は必ず入れる。** 言わないと、**AIはもっともらしい答えを書いて矛盾を消す。**

**全件に行番号つきの根拠が付いて返る。**だから仕様管理者としてその場で裁定できる。

### 重いもの（判断が要る）

| | 中身 |
|---|---|
| **★設計書が DoD と衝突** | プログラム設計書は「Todo一覧でループしてTagを取得」と指示。**DoD は「for文の中でSQLを呼ばない」。**しかも要件定義書が「登録上限を設けない」と書いているので、**N+1が無制限になる** |
| **DB定義書と DDL が食い違う** | `todo_tag` は DB定義書で複合PK・NOT NULL。**DDL には PRIMARY KEY 句も NOT NULL 句も無い** |
| **FK制約の方針が明文化されていない** | DB定義書の FK 欄は空、DDL にも無し、プログラム設計書はアプリ層でチェック。**「整合性はアプリ層だけで担保する」という判断そのものがどこにも書かれていない** |
| **`version` の初期値** | DB定義書は「初期値0」。**DDL に `DEFAULT` 句が無く `NOT NULL` のみ。**登録APIのスキーマに `version` は無い |
| **「進捗状況」が浮いている** | 要件定義書に**1箇所だけ**登場。DB定義書・OpenAPI・プログラム設計書のどこにも無い |
| **ENUM制約の言及だけある** | エラー設計書が「ENUM制約に沿わない値」に触れるが、**ENUM型のフィールドがどこにも定義されていない** |

### 軽いもの（直せば済む誤記）

| | 中身 |
|---|---|
| ID型の不一致 | OpenAPI のパスパラメータは `string`、レスポンスは `integer`、要件定義書は「Integer型」 |
| 説明のコピペミス | `tag.yaml` の `tagId` の説明が**「操作対象のTodoID」**になっている |
| 用語の不統一 | 同じ項目が「Todo名」「Todoタイトル」「title」 |
| 参照文書名の誤り | 要件定義書が「**エラー定義書**を参照」。実際は「**エラー設計書**」 |
| 画面遷移図が外部URLのみ | リポジトリ内に実体が無い |

**★軽いものは判断を要しない。仕分けると半分は軽い。**
